## Простыми словами

Ты принимаешь квартиру у застройщика. Можно пройтись по комнатам и потыкать во всё, что попадётся на глаза. А можно взять список: окна, двери, розетки, трубы, стяжка пола — и пройти по нему пункт за пунктом. Со списком ты не забудешь проверить напор воды в ванной и не потратишь час на одну дверную ручку.

Тест-дизайн для API — такой же список для одного эндпоинта. Ты не отправляешь запросы наугад, а идёшь по слоям: кто может вызвать запрос, что можно передать, какие правила действуют, что приходит в ответ, что поменялось в системе, что будет при повторе.

В этом уроке разберём:

- чем тест-дизайн API отличается от тест-дизайна интерфейса;
- **анатомию проверок одного эндпоинта** — чек-лист по слоям;
- как знакомые техники — классы, границы, таблица решений, pairwise, переходы состояний — применяются к API;
- для мидла — **пагинацию, фильтры, сортировку и поиск**: где в них прячутся баги;
- как не утонуть в комбинациях и как записать проверки.

Сами техники ты уже знаешь из урока [«Техники тест-дизайна»](/osnovy/08-tehniki-test-dizayna). Здесь не объясняем их заново, а применяем к запросам.

## Чем тест-дизайн API отличается от UI

| | Интерфейс | API |
|---|---|---|
| **Что можно отправить** | То, что разрешает форма: выпадающий список, маска телефона, кнопка неактивна | Что угодно: другой тип, лишние поля, без обязательных полей, `null`, огромную строку |
| **Скорость** | Один сценарий — минуты кликов | Один запрос — секунды. За час можно проверить десятки комбинаций |
| **Что видно** | Сообщение на экране, иногда расплывчатое | Точный код, тело ответа, заголовки |
| **Что проверяем** | Как выглядит и как ведёт себя экран | **Контракт**: что сервер обещал принять и вернуть |

Главное отличие — **нет защиты интерфейса**. Форма не даст ввести букву в поле «Количество». А в запрос — даст:

```json
{ "productId": 15, "quantity": "много" }
```

Сервер обязан сам отклонить такой запрос, а не надеяться на форму. Поэтому в API негативных проверок больше, чем в UI: всё, что форма «не пропускает», здесь нужно проверить отдельно.

Обратная сторона: через API ты не увидишь, как ошибка показана пользователю. Это проверяют в интерфейсе. Одно не заменяет другое.

### 1. Доступ

Права подробно разобраны в уроке [«Аутентификация и права»](/api/07-autentifikaciya-i-prava). Здесь — минимальный набор для любого эндпоинта:

- без токена — `401`;
- с испорченным или просроченным токеном — `401`;
- под каждой ролью из требований — разрешено или `403`;
- с чужим объектом в пути — `404` или `403`, как записано в спецификации.

### 2. Входные данные

У запроса три места для данных: **path-параметры** — `/orders/{id}`, **query-параметры** — `?status=PAID`, **тело**. Для каждого поля пройди по списку:

- **обязательность**: поле передано, не передано, передано как `null`;
- **тип**: число вместо строки, строка вместо числа, массив вместо объекта, `true` вместо числа;
- **формат**: email, дата, телефон, UUID — правильный и сломанный;
- **границы**: минимальная и максимальная длина или значение, и сразу за ними;
- **enum**: каждое значение, неизвестное значение, другой регистр;
- **лишние и неизвестные поля**: `"isAdmin": true`, `"id": 999`, `"ownerId": 1` — сервер должен их проигнорировать или отклонить, но не сохранить;
- **пустая строка и пробелы**: `""`, `"   "`, пробел в начале и конце;
- **спецсимволы и Unicode**: кавычки, `<`, `&`, `%`, кириллица, эмодзи;
- **очень длинные значения**: 10 000 символов там, где ждут 100.

**`null` и «нет поля» — разные вещи.** В `PATCH` это особенно важно. `{"comment": null}` часто значит «очисти комментарий», а запрос без поля `comment` — «не трогай комментарий». Проверяй оба варианта и сверяй со спецификацией.

### 3. Бизнес-правила и состояния

То, что не видно по типам полей:

- **уникальность**: второй товар с тем же артикулом;
- **лимиты**: не больше 10 адресов доставки, не больше 3 активных промокодов;
- **связи**: заказ на несуществующий товар, курьер из другого города;
- **состояния**: можно ли отменить доставленный заказ? Это **переходы состояний** из урока [«Техники тест-дизайна»](/osnovy/08-tehniki-test-dizayna). Пример — ниже, в разделе про техники.

### 4. Ответ

- **Код** — по спецификации. Классы и спорные пары — в уроке [«Коды ответа»](/api/05-kody-otveta).
- **Тело** — по схеме: все поля на месте, типы верные, нет лишнего — например, хэша пароля. Про схему и контракт — в уроке [«API, REST и форматы данных»](/api/06-api-rest-formaty).
- **Значения** — не только «поле есть», но и «в поле то, что отправили»: имя сохранилось без обрезки, дата в нужном формате, сумма посчитана верно.
- **Заголовки** — `Location` после `201`, `Content-Type`, `Retry-After` после `429`, идентификатор запроса.
- **Ошибка** — в едином формате, с понятным кодом и сообщением, без стектрейса.

### 5. Побочные эффекты

Ответ говорит, что сервер **считает**, что сделал. Что он сделал на самом деле, видно только **вторым запросом**.

- После `POST` — `GET` по адресу из `Location`: объект есть и данные совпадают.
- После `PATCH` — `GET`: изменилось то, что меняли, **и не изменилось** остальное.
- После `DELETE` — `GET` отвечает `404`, объект пропал из списка, а связанные объекты обработаны по правилам.
- После **ошибки** — ничего не создалось и не изменилось. Запрос с `422` не должен оставить «полузаказ» в базе.
- Счётчики и списки: `total` в списке вырос на один, остаток на складе уменьшился.

### 6. Повтор и параллельность

- **Повтор того же запроса** — что будет при двойном нажатии или повторе после таймаута? Идемпотентные методы и ключи идемпотентности — в уроке [«Методы HTTP и идемпотентность»](/api/04-metody-http).
- **Гонки**: два запроса одновременно. Два покупателя берут последний товар, два менеджера меняют один заказ. Подробнее про гонки как уязвимость — в уроке [«Безопасность для тестировщика»](/api/08-bezopasnost).

### 7. Нефункциональное — коротко

- **Время ответа**: список из 20 элементов отвечает за 100 мс, а не за 5 секунд. Как его смотреть — в уроке [«HTTP: запрос и ответ»](/api/03-http-zapros-i-otvet).
- **Размер ответа**: список отдаёт страницу, а не всю базу; в каждом элементе нет лишних тяжёлых полей.

Нагрузочное тестирование — отдельная профессия. Ручному тестировщику достаточно заметить, что ответ подозрительно медленный или огромный, и сообщить.

## Техники применительно к API

Примеры — на выдуманном интернет-магазине и службе доставки.

### Классы эквивалентности и границы

**Числовой параметр.** `GET /products?limit=` — по спецификации от 1 до 50, по умолчанию 20.

| Класс | Примеры | Ожидание |
|---|---|---|
| Валидные | `1`, `20`, `50` | `200`, в ответе не больше `limit` элементов |
| Меньше минимума | `0`, `-1` | Ошибка валидации — код по спецификации |
| Больше максимума | `51`, `1000` | Ошибка валидации или `limit` срезан до 50 — **как записано в спецификации** |
| Не число | `abc`, `1.5`, пустое `limit=` | Ошибка валидации, **не `500`** |
| Не передан | — | Значение по умолчанию: `20` |

Границы: `0`, `1`, `50`, `51`. Плюс по одному представителю из каждого класса.

**Длина строки.** `POST /reviews`, поле `text` — от 10 до 2000 символов.

- границы: 9, 10, 2000, 2001;
- особые классы: пустая строка, поле не передано, `null`, число вместо строки;
- что считается «символом»: 2000 символов кириллицы и 2000 эмодзи. Эмодзи могут считаться за два символа, и граница «поедет».

**Как быстро набрать длинную строку.** В консоли браузера: `'а'.repeat(2000)`. Команда `copy('а'.repeat(2000))` сразу скопирует строку в буфер обмена.

### Enum

`GET /orders?status=` — значения `NEW`, `PAID`, `SHIPPED`, `DELIVERED`, `CANCELLED`.

- **каждое значение** — по отдельности. Пять значений — пять проверок, это дёшево;
- **неизвестное** — `LOST`. Что ждать — `400` или `422`, — решает спецификация. Опасный вариант — сервер молча игнорирует неизвестный фильтр и возвращает **все** заказы;
- **регистр** — `paid`, `Paid`. Принимается или ошибка — тоже по спецификации, но поведение должно быть одинаковым для всех значений;
- **пустое** — `status=`;
- **несколько значений** — `status=PAID,NEW` или `status=PAID&status=NEW`, если API это поддерживает.

### Таблица решений для комбинации фильтров

`GET /products?inStock=true&onSale=true` — два фильтра. Главный вопрос: они работают через **И** или через **ИЛИ**? Ответ должен быть в спецификации. Обычно — **И**: «в наличии **и** со скидкой».

Подготовь четыре товара — по одному на каждую комбинацию:

| Товар | В наличии | Со скидкой |
|---|---|---|
| А | да | нет |
| Б | нет | да |
| В | да | да |
| Г | нет | нет |

Таблица решений:

| `inStock` | `onSale` | Ожидаем при «И» |
|---|---|---|
| не передан | не передан | А, Б, В, Г |
| `true` | не передан | А, В |
| не передан | `true` | Б, В |
| `true` | `true` | только В |

Если на последней строке пришли А, Б, В — фильтры работают через «ИЛИ». Это баг или особенность — смотри в спецификацию. Без четырёх заранее подготовленных товаров эту разницу не увидеть.

### Pairwise для набора query-параметров

`GET /products` с параметрами:

- `category` — 5 значений;
- `sort` — 4 значения;
- `inStock` — 3 варианта: `true`, `false`, не передан;
- `limit` — 3 значения: минимум, обычное, максимум;
- `order` — 2 значения: `asc`, `desc`.

Полный перебор — 5 × 4 × 3 × 3 × 2 = **360** запросов. Попарное тестирование покрывает каждую **пару** значений хотя бы один раз — и получается около 20–25 запросов. Генератор вроде PICT составит набор сам: как — в уроке [«Техники тест-дизайна»](/osnovy/08-tehniki-test-dizayna).

Pairwise ловит баги, которые зависят от **пары** параметров: например, `sort=price` ломается только вместе с `inStock=false`. Ошибки, где важны три параметра сразу, он может пропустить — их добирают точечно, по риску.

### Переходы состояний

Заказ в службе доставки проходит статусы:

```text
NEW → PAID → SHIPPED → DELIVERED
 ↓      ↓
CANCELLED
```

Отменить можно новый или оплаченный заказ, но не отправленный.

| Текущий статус | `POST /orders/{id}/cancel` | Ожидание |
|---|---|---|
| `NEW` | отмена | `200`, статус `CANCELLED` |
| `PAID` | отмена | `200`, статус `CANCELLED`, запущен возврат денег |
| `SHIPPED` | отмена | `409` — нельзя, статус не изменился |
| `DELIVERED` | отмена | `409` — нельзя |
| `CANCELLED` | повторная отмена | `409` или `200` без повторного возврата — по спецификации. **Второго возврата денег быть не должно** |

В API каждый переход — отдельный запрос, поэтому недопустимые переходы проверять удобно: не нужно искать кнопку, которой в интерфейсе нет. После каждого отказа — `GET` и проверка, что статус не изменился.

## Пагинация, фильтры, сортировка, поиск

Это мидл-раздел. Почти в каждом продукте есть списки, и почти в каждом списке — эти четыре механизма. Баги в них частые и неочевидные: на трёх записях всё работает, на трёх тысячах — нет.

### Пагинация

Список отдают кусками — **страницами**. Самый частый вариант — **offset-пагинация**: `limit` — сколько записей на странице, `offset` — сколько пропустить с начала.

```json
{
  "items": [ ... ],
  "total": 57,
  "limit": 20,
  "offset": 40,
  "hasNext": false
}
```

Что проверять:

- **`limit` на границах и за ними**: `0`, минимум, максимум, максимум + 1, отрицательное, не число, не передан;
- **`offset`**: `0`, отрицательный, не число, равен `total`, больше `total`. Ожидание для «за пределами списка» — обычно `200` и пустой `items`, а не ошибка;
- **последняя страница**: в ней меньше записей, чем `limit`, и `hasNext: false`. На предпоследней — `hasNext: true`;
- **ровное деление**: `total` = 40, `limit` = 20. На второй странице `hasNext` должен быть `false` — частая ошибка на единицу;
- **`total` при фильтрах**: считает отфильтрованные записи, а не все;
- **склейка страниц**: пройди весь список страницами по 1–2 записи и сравни с одним запросом на всю длину. Ни одной записи не пропало, ни одна не повторилась.

**Стабильность порядка.** Если порядок записей не задан однозначно, база может отдавать их по-разному от запроса к запросу. Тогда запись попадает и на первую, и на вторую страницу, а соседняя — ни на одну. Защита — сортировка с **вторичным ключом**, обычно по `id`.

**Добавление записей во время листания.** Ты на первой странице новинок, сортировка «сначала новые». В это время в каталог добавили 3 товара. Ты открываешь вторую страницу с `offset=20` — и видишь 3 последних товара первой страницы ещё раз: всё сдвинулось на три позиции. С удалением наоборот — товары пропадают. Это свойство offset-пагинации. Насколько оно допустимо — решает команда, но тестировщик должен его показать.

**Cursor-пагинация — коротко.** Вместо «пропусти 40» клиент передаёт **курсор** — метку последней записи: `?cursor=eyJpZCI6MTAwfQ&limit=20`. Сервер отдаёт записи **после** неё и новый курсор `nextCursor`. При добавлении записей дублей не будет. Что проверять: на последней странице `nextCursor` пустой; испорченный курсор — ошибка, а не `500`; курсор от одного фильтра нельзя подставить к другому; перейти сразу на десятую страницу обычно нельзя — это ограничение, а не баг.

### Фильтры

- **каждое значение** фильтра по отдельности;
- **комбинации**: два фильтра — это «И» или «ИЛИ»? Ожидание — из спецификации. Удобно оформить таблицей решений, как выше;
- **несуществующее значение**: неизвестный статус, `categoryId` несуществующей категории. Ошибка или пустой список — по спецификации, но **не все записи**;
- **пустой результат**: `200` и `"items": []`, `total: 0`. Не `404` — это разбиралось в уроке [«Коды ответа»](/api/05-kody-otveta);
- **фильтр по чужим данным**: `GET /orders?userId=17` от имени другого покупателя не должен отдать заказы пользователя 17. Фильтр сужает **твои** данные, а не открывает чужие. Это контроль доступа из урока [«Безопасность для тестировщика»](/api/08-bezopasnost).

- **одинаковые значения**: десять товаров с одной ценой. В каком порядке они идут между собой? Нужна **вторичная сортировка** — иначе порядок «плавает» и ломает пагинацию;
- **`null`**: товары без рейтинга — в начале списка или в конце? Одинаково ли при `asc` и `desc`?
- **регистр и локаль**: «яблоко» и «Яблоко» рядом или на разных концах списка? Где окажется «ёлка» — рядом с «елью» или после «яблока»? Латиница перед кириллицей или после?
- **числа как строки**: если номер заказа хранится строкой, то `"10"` окажется раньше `"9"`, потому что `"1"` < `"9"`;
- **неизвестное поле**: `sort=color`, когда такого поля нет. Код — по спецификации, обычно `400` или `422`. Плохо, если сервер молча сортирует как попало или падает с `500`.

**Сортировку проверяют на данных, а не на двух записях.** На двух записях порядок угадывается с вероятностью 50%. Нужно 5–7 записей, где правильный порядок отличается от порядка создания, от `id` и от алфавита. И хотя бы две записи с одинаковым значением — для вторичного ключа.

### Поиск

- **подстрока**: «ноут» находит «Ноутбук»? Находит слово из середины названия?
- **регистр**: «НОУТБУК», «ноутбук» и «Ноутбук» дают одно и то же?
- **пустая строка**: ошибка, пустой результат или всё? По спецификации;
- **строка из одних пробелов**: сервер может обрезать пробелы, искать их как есть или вернуть ошибку. Это отдельный класс ввода — сравни поведение с пустой строкой и со спецификацией;
- **спецсимволы**: `%`, `_`, кавычки, обратный слэш. Многие базы ищут через `LIKE`, где `%` значит «любые символы», а `_` — «один любой символ». Если сервер не **экранирует** их, поиск по `%` вернёт всё, а поиск по `_` — лишнее. Кавычка, которая ломает ответ, — повод вспомнить про инъекции;
- **очень длинная строка**: 1000 символов — ошибка валидации или пустой результат, но не `500` и не зависание;
- **Unicode и эмодзи**: «café», «ёжик», «🎧»;
- **что поиск не должен находить** — это мидл-вопрос, о котором часто забывают:
  - **чужие** данные: поиск в «моих заказах» не находит чужие заказы;
  - **удалённые** записи: удалённый товар не всплывает в поиске;
  - **скрытые поля**: поиск в каталоге по email поставщика или по внутреннему комментарию менеджера ничего не находит, если по этим полям искать нельзя. Иначе поиск становится способом «угадывать» скрытые данные.

## Как не утонуть в комбинациях

У эндпоинта списка легко набрать сотни проверок. Все их не сделать — и не нужно.

1. **Сначала смоук эндпоинта.** Один-два позитивных запроса: работает ли вообще? Если нет — дальше проверять нечего.
2. **Приоритет по риску.** Что страшнее всего сломать: деньги, чужие данные, удаление, главный сценарий пользователя? Это проверяется первым. Риск-ориентированный подход — в уроке [«Тестовая документация»](/osnovy/07-testovaya-dokumentaciya).
3. **Негативные — по классам, а не по значениям.** Не нужно проверять `limit` = `-1`, `-2`, `-3`… Достаточно одного представителя класса «отрицательное».
4. **Комбинации — через pairwise.** Не все 360, а 20–25.
5. **Точечные добавки по риску.** Комбинации, где ты подозреваешь баг или где он уже был, — отдельными строками.

## Как записать проверки API

**Чек-лист или тест-кейсы.** Для API обычно хватает **чек-листа**: одна строка — одна проверка, коротко. Тест-кейсы с шагами пишут для сложных сценариев из нескольких запросов: создать заказ, оплатить, отменить, проверить возврат. Подробно о выборе — в уроке [«Тестовая документация»](/osnovy/07-testovaya-dokumentaciya).

**Таблица проверок.** Удобный формат для эндпоинта:

| № | Запрос | Данные | Ожидание | Источник |
|---|---|---|---|---|
| 1 | `GET /products` | `limit=0` | `422 VALIDATION_ERROR` | Спецификация, раздел «Пагинация» |
| 2 | `GET /products` | `limit=50` | `200`, не больше 50 элементов | Там же |
| 3 | `GET /products` | `inStock=true&onSale=true` | Только товар В | Раздел «Фильтры каталога» |

Столбец «Источник» — это трассируемость: видно, откуда взялось ожидание. Если источника нет — ожидание придумано тобой, и его стоит обсудить с аналитиком.

**Data-driven — один запрос, много строк данных.** Строки 1 и 2 — это **один и тот же запрос** с разными данными. В инструментах вроде Postman такие проверки запускают одной коллекцией по таблице значений: запрос описан один раз, а данные подставляются из файла. Об этом — в уроке про Postman и curl.

## На примере TaskFlow

**Ветка:** `training-public`. Источник — `docs/API_SPEC.md`: раздел 2 — правило `401`/`403`/`404`, раздел 4 — общие конвенции, раздел 5 — формат ошибок, раздел 6.3 — Projects.

Разберём два эндпоинта по слоям.

### `POST /api/v1/projects` — создать проект

Из раздела 6.3: доступ — любой авторизованный, успех — `201` и `Location: /api/v1/projects/{id}`, создатель становится `OWNER`. Тело `ProjectCreate`: `name` — от 1 до 100 символов, `description` — необязательное, до 1000.

| Слой | Проверки | Ожидание по спецификации |
|---|---|---|
| Доступ | Без токена | `401 UNAUTHORIZED` — раздел 2 |
| | Обычный `USER` | `201` — создавать может любой авторизованный |
| Вход: `name` | Не передано, `null`, число вместо строки | `422 VALIDATION_ERROR` |
| | Длина 0, 1, 100, 101 | `422`, `201`, `201`, `422` |
| | Кириллица, эмодзи, кавычки, `<b>` | `201`, значение сохранено ровно как отправлено |
| Вход: `description` | Не передано | `201` — поле необязательное |
| | Длина 1000, 1001 | `201`, `422` |
| Вход: лишние поля | `"ownerId": <id другого пользователя>`, `"id": 1` | Поля не применяются: владелец — тот, кто создал |
| Ответ | Тело | `ProjectResponse`: `id`, `name`, `description`, `status`, `ownerId` — `ownerId` равен твоему `id` |
| | Заголовки | `Location: /api/v1/projects/{id}` — раздел 4 и 6.3; `X-Request-ID` |
| | Ошибка | Формат раздела 5: `error.code`, `message` на русском, `correlationId` совпадает с `X-Request-ID` |
| Побочные эффекты | `GET` по адресу из `Location` | `200`, данные совпадают с ответом на `POST` |
| | `GET /api/v1/projects/{id}/members` | Создатель в списке с ролью `OWNER` |
| | После `422` — `GET /api/v1/projects` | `total` не изменился, ничего не создано |
| Повтор | Тот же `POST` дважды | Два проекта с разными `id`: `POST` не идемпотентен. Требования уникальности имени в спецификации нет |

Обрати внимание на строку про лишние поля. Спецификация не говорит, что делать с неизвестными полями: проигнорировать или ответить `422`. Но она точно говорит, кто становится владельцем. Это и есть ожидание.

### `GET /api/v1/projects` — список проектов

Из раздела 6.3: доступ — любой авторизованный, в списке — проекты, где пользователь участник, у `ADMIN` — все. Из раздела 4: обёртка списка `items`, `total`, `limit`, `offset`, `hasNext`; `limit` — от 1 до 100, по умолчанию 20; `offset` — от 0, по умолчанию 0; у сортировки всегда вторичный ключ `id ASC`.

| Слой | Проверки | Ожидание по спецификации |
|---|---|---|
| Доступ | Без токена | `401` |
| | `USER` | Только проекты, где он участник любой роли. Чужих проектов в списке нет |
| | `ADMIN` | Все проекты |
| Вход: `limit` | Не передан | `limit: 20` в ответе |
| | `0`, `1`, `100`, `101` | `422`, `200`, `200`, `422` |
| | `-1`, `abc` | `422 VALIDATION_ERROR` |
| Вход: `offset` | Не передан, `0` | `offset: 0` |
| | `-1`, `abc` | `422` |
| | Равен `total`, больше `total` | `200`, `items: []`, `hasNext: false` |
| Ответ | Обёртка | Все пять полей, `limit` и `offset` совпадают с запросом |
| | `hasNext` | `true`, пока после этой страницы есть записи; на последней — `false` |
| | `total` | Не зависит от `limit` и `offset` |
| Порядок | Склейка страниц с `limit=1` | Та же последовательность, что при `limit=100`, без дублей и пропусков |
| Побочные эффекты | Удалённый проект | Пропадает из списка, `total` уменьшается — раздел 3, Soft delete |

## Инструмент: Swagger

Swagger TaskFlow — `http://localhost:8000/docs` — главный инструмент урока.

- **Schema** у запроса показывает ограничения полей: `minLength`, `maxLength`, `minimum`, `maximum`, список значений enum. Это быстрый способ собрать границы. Но **ожидание** всё равно берём из спецификации: если Swagger и спецификация расходятся — это вопрос к команде, урок [«API, REST и форматы данных»](/api/06-api-rest-formaty).
- **Try it out** — поля для query-параметров и тело. Для enum Swagger показывает выпадающий список, а для чисел может проверить тип ещё до отправки. Это защита **интерфейса Swagger**, а не сервера.
- **Если Swagger не даёт отправить значение** — неизвестный enum, букву вместо числа — выполни запрос с правильным значением, скопируй команду из блока **Curl**, поменяй в ней значение и выполни в терминале. Как запускать `curl` — в уроке [«Клиент-сервер и URL»](/api/01-klient-server-i-url).

## Разборы из жизни

Ниже пять ситуаций, где помогает системный тест-дизайн API. Первый разбор открыт — это образец. Остальные попробуй сначала разобрать сам и только потом открывай.

<details class="details custom-block" open>
<summary>Разбор 1. Товары повторяются и пропадают при листании — маркетплейс</summary>

**Ситуация.** Покупатели жалуются: в разделе «Новинки» на второй странице встречаются товары с первой, а некоторые товары не попадаются вообще. Продавец не может найти свой новый товар, хотя он точно опубликован. Разработчики: «Пагинация — стандартная, `limit` и `offset`, всё по учебнику».

**Что видит мидл.**

- Повторы и пропуски — две стороны одной проблемы. Записи **сдвигаются** между запросами страниц.
- Первая причина — **добавление** товаров во время листания. «Новинки» отсортированы по дате, новые товары встают в начало и сдвигают всё вниз. На маркетплейсе товары добавляют каждую минуту.
- Вторая причина — **нестабильная сортировка**. У многих товаров одинаковое время публикации: их загружают пачкой. Без вторичного ключа база отдаёт их в произвольном порядке, и он может отличаться от запроса к запросу.
- Вторую причину видно даже на неподвижных данных. Первую — только когда данные меняются.

**Что делать.**

1. Проверить стабильность на неподвижных данных: на тестовом стенде загрузить 30 товаров с **одинаковым** временем публикации. Пройти их страницами по 5 и сравнить со списком из одного запроса `limit=50`. Повторить 3–4 раза.
2. Если порядок меняется или есть дубли — баг: «Сортировка по дате без вторичного ключа, порядок нестабилен, при пагинации товары дублируются и пропадают».
3. Проверить сдвиг при добавлении: открыть первую страницу, добавить 3 товара, открыть вторую. Записать, что повторилось.
4. Описать команде оба эффекта отдельно. Нестабильная сортировка — однозначный баг, лечится вторичным ключом. Сдвиг при добавлении — свойство offset-пагинации, решение — cursor-пагинация или договорённость, что так допустимо.
5. Добавить в чек-лист списков: «склейка страниц на данных с одинаковым значением сортировки».

**Чего не делать.**

- Не проверять пагинацию на 5 товарах с разной датой: на них всё работает.
- Не закрывать как «не воспроизводится», если на стенде данные не меняются. Нужно воспроизвести условия: одинаковые значения и добавление во время листания.

</details>

::: details Разбор 2. «Новый» заказ оказался в середине списка — служба доставки
**Ситуация.** В админке службы доставки диспетчер сортирует заказы по статусу, чтобы сверху были новые, требующие внимания. Сверху оказываются «Доставлен», потом «Новый», потом «Отменён», «Оплачен», «Передан курьеру». Диспетчер пропускает новые заказы. Разработчики: «Сортировка работает, проверьте — всё по порядку».

**Что видит мидл.**

- «По порядку» — это **по алфавиту**: Д, Н, О-т, О-п… Статусы хранятся строками, и сервер сортирует их как строки.
- Пользователю нужен **логический** порядок — по этапам жизни заказа: «Новый» → «Оплачен» → «Передан курьеру» → «Доставлен», а «Отменён» отдельно.
- Если в API статусы хранятся английскими кодами, порядок будет другим, но тоже алфавитным — и тоже не тем.

**Что делать.**

1. Найти в требованиях, какой порядок сортировки по статусу ожидается. Если не записан — это пробел в требованиях, вопрос аналитику.
2. Проверить через API: `GET /orders?sort=status&order=asc`, потом `desc`. Записать фактический порядок.
3. Проверить другие поля с «логическими» значениями: срочность, размер посылки, день недели доставки. Скорее всего, там та же проблема.
4. Завести баг: «Сортировка по статусу идёт по алфавиту, ожидается порядок этапов заказа». Приложить ожидаемый порядок списком.

**Чего не делать.**

- Не проверять сортировку на двух статусах: «Новый» и «Доставлен» случайно стоят в правильном порядке и по алфавиту.
- Не считать «отсортировано» достаточным результатом. Важно, **как** отсортировано.
:::

::: details Разбор 3. Поиск по «%» показывает все заказы — кабинет продавца
**Ситуация.** Продавец ищет заказ по комментарию покупателя «скидка 50%». В результатах — все его заказы за год, тысячи строк. Страница грузится 20 секунд. Поддержка: «Поиск работает, он же нашёл».

**Что видит мидл.**

- Символ `%` в поисковой строке сработал как **шаблон** «любые символы». Сервер ищет через `LIKE` и подставляет ввод в шаблон без **экранирования**.
- То же будет с `_` — «один любой символ»: поиск «а_б» найдёт и «а-б», и «а б».
- Пока продавец видит только свои заказы — это неудобство и нагрузка. Но если тот же поиск есть там, где видны чужие данные, `%` превращается в способ выгрузить всё.

**Что делать.**

1. Воспроизвести через API: поиск `%`, `_`, `%%`, `скидка 50%`. Записать `total` и время ответа.
2. Проверить, что поиск **не выходит** за рамки прав: продавец по-прежнему видит только свои заказы.
3. Проверить остальные поля поиска в продукте: товары, покупатели, отзывы.
4. Завести баг: «Спецсимволы `%` и `_` в поиске не экранируются и работают как шаблон». Ожидание: поиск `50%` находит строки, где буквально есть `50%`.
5. Если где-то поиск по `%` показывает чужие данные — отдельный баг с высокой серьёзностью.

**Чего не делать.**

- Не проверять поиск только обычными словами. Спецсимволы — отдельный класс эквивалентности.
- Не путать с SQL-инъекцией: здесь ввод не меняет запрос, а только шаблон поиска. Но рядом стоит проверить и кавычки.
:::

::: details Разбор 4. Пользователь стал администратором через профиль — сервис бронирования
**Ситуация.** В сервисе бронирования переговорных пользователь может менять в профиле имя и телефон. Тестировщик, проверяя `PATCH /users/me`, ради интереса добавляет в тело `"role": "ADMIN"`. Ответ — `200`. Через минуту у него в интерфейсе появляется раздел «Администрирование».

**Что видит мидл.**

- Это **mass assignment** — массовое присвоение. Сервер берёт **все** поля из тела и записывает их в объект пользователя, а не только разрешённые `name` и `phone`.
- Форма профиля не показывает поле «роль» — но защита формы не защищает API.
- Это вертикальное повышение прав, критическая уязвимость.

**Что делать.**

1. Проверить, что изменилось на самом деле: `GET /users/me` — роль в ответе — и запрос к админской функции.
2. Попробовать другие поля, которые не должны меняться: `id`, `email` без подтверждения, `isVerified`, `balance`, `createdAt`.
3. Проверить другие эндпоинты с телом: создание брони — можно ли передать `"price": 0` или `"userId"` другого пользователя?
4. Сразу сообщить команде и завести баг с критической серьёзностью: «`PATCH /users/me` принимает и сохраняет поле `role`». Ожидание: неразрешённые поля игнорируются или запрос отклоняется с ошибкой валидации.
5. Вернуть тестовому пользователю исходную роль.

**Чего не делать.**

- Не ограничиваться проверкой «ответ `200`, имя поменялось». Лишние поля — отдельный класс проверок.
- Не пробовать такое на боевом окружении. Только тестовый стенд и тестовые учётные записи.
:::

::: details Разбор 5. Заказ создан, но его нигде нет — доставка еды
**Ситуация.** Тестировщик проверяет `POST /orders`. Ответ — `201`, в теле `id` заказа, всё по спецификации. Тест отмечен как пройденный. После релиза пользователи пишут: заказ оформлен, деньги списаны, а в «Моих заказах» его нет, и ресторан его не получил.

**Что видит мидл.**

- `201` — это то, что сервер **сказал**. Тест проверил ответ, но не проверил **побочный эффект**: заказ должен появиться в базе, в списке пользователя и в очереди ресторана.
- Возможно, заказ сохраняется в одной транзакции, а уведомление ресторану уходит отдельно — и падает. Или сервер отвечает `201` до того, как заказ записан, а запись не удалась.

**Что делать.**

1. После `POST` проверить `GET /orders/{id}` из `Location` или из тела ответа — заказ есть?
2. Проверить `GET /orders` пользователя — заказ в списке, `total` вырос на один?
3. Проверить сторону ресторана: заказ появился у него в очереди?
4. Проверить при разных условиях: несколько позиций, промокод, оплата картой и наличными. Найти, при каком условии заказ «теряется».
5. Завести баг: «`POST /orders` отвечает `201`, но заказ не появляется в списке и у ресторана». Приложить `id` заказа и идентификатор запроса — по ним разработчики найдут его в логах.
6. Добавить в чек-лист каждого `POST`: проверка вторым запросом.

**Чего не делать.**

- Не считать `201` доказательством, что объект создан.
- Не ограничиваться проверкой в своём списке: у заказа есть и другие получатели — ресторан, курьер.
:::

## Частые ошибки

- **Проверять только код.** `200` пришёл — тест пройден. А в теле не те данные, а в базе ничего не изменилось. Смотри код, тело и побочный эффект.
- **Забывать про лишние поля и `null`.** Форма их не отправляет — а клиент API может. Mass assignment находят именно так.
- **Путать `null` и отсутствие поля.** В `PATCH` это два разных запроса с разным смыслом.
- **Проверять сортировку на 2 записях.** Порядок угадывается случайно. Нужно 5–7 записей, одинаковые значения и логические поля.
- **Проверять только «что нашлось».** Поиск и фильтры проверяют и с другой стороны: не нашлось ли чужое, удалённое, скрытое.
- **Перебирать все комбинации.** 360 запросов — это неделя работы и ни одной лишней найденной ошибки по сравнению с pairwise. Классы, границы, pairwise и риск.
- **Брать ожидание из ответа сервера.** «Сервер вернул `422` — значит, так и надо». Ожидание — из спецификации. Если её нет — вопрос аналитику.
- **Не готовить данные.** Фильтр без заранее подготовленных записей на каждую комбинацию ничего не докажет: пустой список может быть и правильным, и багом.

## Часть 1. Чек-лист для эндпоинта

Интернет-магазин. Покупатель смотрит свои заказы:

```http
GET /orders?status=&from=&to=&sort=&limit=&offset=
```

Что известно из требований:

- доступ — только вошедший покупатель, видит **только свои** заказы;
- `status` — `NEW`, `PAID`, `SHIPPED`, `DELIVERED`, `CANCELLED`, необязательный;
- `from`, `to` — даты в формате `ГГГГ-ММ-ДД`, необязательные. Заказы с датой создания от `from` до `to` **включительно**;
- `sort` — `createdAt` или `total`, по умолчанию `createdAt`; направление — `desc`, новые сверху;
- `limit` — от 1 до 50, по умолчанию 20; `offset` — от 0;
- ответ — `items`, `total`, `hasNext`; ошибки валидации — `422`.

Составь чек-лист из **20–25 проверок** по слоям из теории: доступ, входные данные, бизнес-правила, ответ, побочные эффекты, повтор. Для каждой проверки — запрос с данными и ожидание.

Потом отметь **5 первоочередных** по риску и объясни выбор: что случится с пользователем или бизнесом, если эта проверка провалится.

**Образец** — несколько строк:

| № | Слой | Запрос | Ожидание | Риск |
|---|---|---|---|---|
| 1 | Доступ | `GET /orders` без токена | `401` | Высокий: чужие данные |
| 2 | Вход | `GET /orders?limit=51` | `422` | Низкий |
| 3 | Вход | `GET /orders?from=2026-03-10&to=2026-03-01` — `from` позже `to` | Не описано в требованиях — вопрос аналитику: `422` или пустой список? | Средний |
| 4 | Ответ | `GET /orders?status=PAID` | `200`, у всех `items` `status` = `PAID`, `total` — число оплаченных | Средний |

Обрати внимание на строку 3: если требования молчат, ожидание не придумывают, а записывают вопрос.

Подсказки, о чём не забыть: границы дат `from` и `to`, заказы **ровно** в день `from` и `to`, сортировка заказов с одинаковой суммой, чужие заказы в фильтре, последняя страница.

## Часть 2. TaskFlow: параметры списков и поиска — спецификация против факта

Ты сравниваешь, что обещает спецификация TaskFlow про пагинацию, сортировку, фильтры и границы параметров, с тем, что TaskFlow делает на самом деле.

Заранее неизвестно, найдёшь ли ты расхождение. Умение проверить методично и честно написать «совпадает» — такой же результат, как найденный баг.

Работать будешь в Swagger: `http://localhost:8000/docs`. Как войти — в уроке [«Баг-репорт»](/osnovy/09-bag-report), раздел «Как войти в Swagger». Если Swagger не даёт отправить нужное значение — смотри раздел «Инструмент: Swagger» в теории этого урока.

### Шаг 1. Подготовь данные

Все шаги — под **пользователем А**: готовый пользователь `USER` из `README.md` TaskFlow, раздел «Тестовые учётные записи». Не используй администратора: у глобальной роли `ADMIN` особые права, раздел 3 спецификации.

1. **Проекты.** Посмотри `GET /api/v1/projects`. Если проектов меньше трёх — создай недостающие через `POST /api/v1/projects`. Один из новых назови «Тест-дизайн — проект» и запиши его `id`. Если новых создавать не пришлось — всё равно создай этот проект.
2. **Задачи.** В проекте «Тест-дизайн — проект» создай пять задач через `POST /api/v1/tasks`. Права — `MANAGER` и выше, раздел 6.4. Создатель проекта — `OWNER`, ему можно. Создавай в этом порядке:

| № | `title` | `priority` | `status` |
|---|---|---|---|
| 1 | Деплой на стенд | `HIGH` | `TODO` |
| 2 | Аудит прав | `LOW` | `IN_PROGRESS` |
| 3 | Ввод данных | `MEDIUM` | `DONE` |
| 4 | Багфикс формы | `HIGH` | `IN_PROGRESS` |
| 5 | Галерея проекта | `LOW` | `TODO` |

`status` при создании не передаётся: новая задача получает начальный статус. Где нужен другой — поменяй через `PATCH /api/v1/tasks/{id}` с телом `{"status": "..."}`. Запиши `id` всех пяти задач.

3. **Пользователи.** Для поиска нужны пользователи с разными именами. В TaskFlow уже есть готовые учётные записи из `README.md` и пользователи, которых ты регистрировал в прошлых уроках. Посмотри их имена и email — пригодятся для подбора `q`.

Почему данные такие: порядок создания, алфавит названий, приоритеты и статусы не совпадают друг с другом, а некоторые значения повторяются. На таких данных видно, по какому правилу на самом деле отсортирован и отфильтрован список.

### Шаг 2. Проверь все пять строк

Проверь **все пять** строк — это обязательно.

| Запрос | Что проверить |
|---|---|
| `GET /api/v1/projects` | Пагинация: `limit` и `offset` на границах и за ними, последняя страница, `hasNext` |
| `GET /api/v1/tasks` | Сортировка: каждое поле из списка `sort`, оба направления `order`, порядок результата |
| `GET /api/v1/users/search` | Граничные значения параметра `q`: пустой, из одних пробелов, один символ, максимальная длина |
| `GET /api/v1/tasks` | Фильтры `status` и `priority`: каждое значение, комбинация двух фильтров, несуществующее значение |
| `POST /api/v1/tasks/{taskId}/comments` | Длина `text`: границы по спецификации |

Кто входит и что подставлять:

| Строка | Кто вошёл | Что подставить |
|---|---|---|
| 1 | Пользователь А | Разные `limit` и `offset`. Чтобы дойти до последней страницы, возьми `limit` меньше числа твоих проектов |
| 2 | Пользователь А | `projectId` проекта «Тест-дизайн — проект», чтобы в ответе были только пять подготовленных задач |
| 3 | Пользователь А | Значения `q` по классам из колонки «Что проверить». Для одного символа и длинной строки подбери значения сам |
| 4 | Пользователь А | `projectId` проекта «Тест-дизайн — проект», значения `status` и `priority` по одному и вдвоём |
| 5 | Пользователь А | `taskId` любой из пяти задач. Строку нужной длины набери в консоли браузера: `copy('а'.repeat(N))` |

Расхождение со спецификацией есть не в каждой строке. Где оно есть, а где нет — выяснить твоя задача.

Ожидаемый результат бери из спецификации: раздел 4 — общие конвенции, раздел 5 — формат и реестр ошибок, раздел 6 — таблица и описание нужного ресурса. Не из Swagger и не из ответа сервера. Если ответ не совпал с ожиданием — не подгоняй ожидание под факт. Если спецификация чего-то не говорит — запиши это как вопрос к аналитику, а не как баг.

### Шаг 3. Запиши результат

Для каждой строки:

```text
Строка N: <запрос>
Техники: <классы эквивалентности, граничные значения, таблица решений, …>
Запросы:
  1. <полный запрос с параметрами или телом>
  2. ...
Ожидание: <для каждого запроса — код и что в ответе> — <раздел спецификации или цитата>
Факт: <для каждого запроса — код, error.code, что в ответе>
Вывод: совпадает / расхождение / вопрос к аналитику
```

Для сортировки и фильтров записывай в «Факт» **порядок** или **состав** задач — например, `id` подряд: `3, 1, 4, 2, 5`. Одного кода `200` недостаточно.

### Шаг 4. Если нашёл расхождение

1. Воспроизведи ещё раз — хотя бы дважды.
2. Перечитай нужный раздел `docs/API_SPEC.md`: может, ты понял его иначе.
3. Проверь данные: тот ли пользователь вошёл, тот ли `projectId`, не осталось ли в запросе лишнего параметра от прошлой проверки.

Потом оформи баг-репорт по шаблону из урока [«Баг-репорт»](/osnovy/09-bag-report). В «Ожидаемом результате» укажи ожидание и раздел спецификации, в «Фактическом» — код и тело ответа. Для порядка и состава списка — оба списка `id` рядом.

В отчёте и на скриншотах оставляй от токена первые 10–15 символов и `…`.
:::

## Часть 3 (мидл, письменно). Pairwise для списка задач

## На открытом проекте — альтернатива части 2

Если TaskFlow запустить не получается, сделай вместо части 2 проверку фильтров на **Restful Booker** — [документация](https://restful-booker.herokuapp.com/apidoc/index.html). Ты уже работал с ним в уроках [«Методы HTTP»](/api/04-metody-http) и [«Аутентификация и права»](/api/07-autentifikaciya-i-prava).

```http
GET /booking?firstname=&lastname=&checkin=&checkout=
```

Что важно знать:

- запрос без параметров отвечает `200` и списком вида `[{"bookingid": 1}, {"bookingid": 2}, …]` — только номера бронирований, без данных;
- данные на сервере общие для всех и периодически сбрасываются. Поэтому сначала создай **свои** бронирования через `POST /booking` — токен для этого не нужен. Возьми редкие имена, которые вряд ли есть у других, и запиши `bookingid` из ответа;
- дата в документации описана в формате `CCYY-MM-DD` — то есть `ГГГГ-ММ-ДД`;
- что именно делает каждый фильтр, описано в документации, раздел **Booking — GetBookingIds**. Это и есть твоя спецификация.

Что сделать:

1. Создай 2–3 бронирования с разными именами и датами заезда и выезда.
2. Проверь каждый фильтр по отдельности: `firstname`, `lastname`, `checkin`, `checkout`.
3. Для имён — классы: точное совпадение, другой регистр, часть имени, пустое значение, несуществующее имя.
4. Для дат — граничные значения: день до даты твоего бронирования, ровно эта дата, день после. Отдельно для `checkin` и для `checkout`.
5. Комбинации: `firstname` + `lastname` — это «И» или «ИЛИ»? `checkin` + `checkout` вместе.
6. Неверный формат даты.

Для каждой проверки запиши запрос, ожидание по документации, факт и вывод — как в шаге 3 части 2. При расхождении — баг-репорт по шаблону из урока [«Баг-репорт»](/osnovy/09-bag-report).

## Ситуационные кейсы

Это рабочие ситуации, о которых могут спросить и на собеседовании. Готового ответа, который нужно угадать, здесь нет. Сначала подумай сам, потом открывай разбор.

::: details Кейс 1. «Как протестировать эндпоинт списка с пагинацией?»
**Ситуация.** Интервьюер: «Есть `GET /products?limit=&offset=`. Как будете тестировать пагинацию?»

**Как рассуждать.** Какие у параметров границы и классы? Что должно быть в ответе, кроме самих записей? Что бывает на последней странице? Что может пойти не так на больших данных и при изменении данных?

**Пример ответа.** Сначала найду в спецификации границы и значения по умолчанию. Допустим, `limit` от 1 до 50, по умолчанию 20.

Параметры: `limit` — 0, 1, 50, 51, отрицательное, не число, не передан. `offset` — 0, отрицательный, равен `total`, больше `total`. Невалидные — ошибка валидации, не `500`. За пределами списка — `200` и пустой `items`.

Ответ: `total` не зависит от страницы и учитывает фильтры, `hasNext` верный на предпоследней и последней странице, особенно когда `total` делится на `limit` ровно.

Целостность: пройду весь список маленькими страницами и сравню с одним большим запросом — без дублей и пропусков. Отдельно проверю записи с одинаковым значением сортировки: если нет вторичного ключа, порядок «плавает». И посмотрю, что происходит, если во время листания добавить запись: при offset-пагинации записи сдвигаются, и команде нужно знать, допустимо ли это.
:::

::: details Кейс 2. «Как проверить сортировку, если записей много?»
**Ситуация.** Интервьюер: «В списке 10 000 заказов. Как вы проверите, что сортировка по сумме работает правильно? Не листать же всё».

**Как рассуждать.** Нужны ли все 10 000? Какие данные нужны, чтобы баг проявился? Где сортировка обычно ломается?

**Пример ответа.** Все 10 000 не нужны. Я сужу список фильтром до своих подготовленных данных — например, заказы одного тестового покупателя — и проверяю на 7–10 записях, подобранных специально:

- порядок по сумме отличается от порядка создания и от `id`, чтобы сортировку нельзя было «угадать»;
- есть одинаковые суммы — проверяю вторичный ключ;
- есть суммы с разным числом цифр: 9, 10, 100 — ловлю сортировку чисел как строк;
- есть заказ без суммы, если такое возможно, — где `null`.

Проверяю `asc` и `desc`. Потом — на полном списке: первая и последняя страница, стык двух страниц — последний элемент первой не больше первого элемента второй. Для логических полей вроде статуса сверяю порядок с требованиями — там частая ловушка с алфавитом.
:::

::: details Кейс 3. «Что проверить в поиске, кроме того, что он находит?»
**Ситуация.** Интервьюер: «Поиск находит товары по названию. Что ещё вы бы проверили?»

**Как рассуждать.** Какие классы ввода бывают? Что поиск **не** должен находить? Как поиск связан с правами и производительностью?

**Пример ответа.** Найденное — только половина. Я проверю ввод: регистр, подстроку, пустую строку, строку из пробелов, очень длинную строку, Unicode и эмодзи, спецсимволы. Особенно `%` и `_`: если сервер ищет через `LIKE` без экранирования, `%` вернёт всё.

Вторая половина — что поиск **не должен** находить. Чужие данные: в «моих заказах» нет чужих. Удалённые записи. Поля, по которым искать нельзя: если поиск по каталогу находит товар по email поставщика, через него можно подбирать скрытые данные.

И ответ: пустой результат — `200` и пустой список, `total` совпадает с числом найденного, пагинация работает и в результатах поиска, время ответа разумное даже на коротком запросе вроде одной буквы.
:::

::: details Кейс 4. Хитрый вопрос: «Эндпоинт вернул 201 — тест пройден?»
**Ситуация.** Интервьюер: «Вы отправили `POST /orders`, получили `201`. Тест пройден?»

**Как рассуждать.** Что именно подтверждает код? Что ещё есть в ответе? Как убедиться, что объект действительно создан и создан правильно?

**Пример ответа.** Нет, код — только начало. `201` значит, что сервер **сообщил** о создании.

Дальше проверяю ответ: тело по схеме, значения совпадают с отправленными, сервер сам заполнил то, что должен — `id`, дату, статус. Заголовок `Location` с адресом нового объекта.

Потом побочные эффекты — вторым запросом. `GET` по адресу из `Location` — объект есть, данные те же. Объект появился в списке, `total` вырос. Если у создания есть последствия — списание остатка, уведомление, письмо — проверяю и их. И то, что не должно было измениться: чужие заказы, другие поля.

Бывает, что `201` приходит, а объекта нет — например, запись упала после ответа. Такой баг ловится только вторым запросом.
:::

::: details Кейс 5. «10 параметров по 5 значений — как тестировать?»
**Ситуация.** Интервьюер: «У эндпоинта 10 параметров, у каждого по 5 значений. Сколько проверок вы сделаете?»

**Как рассуждать.** Сколько это при полном переборе? Какие техники сокращают число комбинаций? Как не потерять важное?

**Пример ответа.** Полный перебор — 5 в десятой степени, почти 10 миллионов. Это нереально.

Мой план:

1. Смоук — пара позитивных запросов.
2. Каждый параметр по отдельности: классы и границы, негативные — по одному представителю класса. Это около 50 проверок.
3. Комбинации — попарным тестированием. Генератор вроде PICT даст несколько десятков запросов, где каждая пара значений встречается хотя бы раз.
4. Ограничения между параметрами — в модель генератора, чтобы не было невозможных комбинаций.
5. Точечно по риску: комбинации, которые важны бизнесу или где уже были баги, и тройки параметров, которые зависят друг от друга.

Объясню, что pairwise ловит большинство ошибок взаимодействия, но не все — поэтому пункт 5 обязателен.
:::

::: details Кейс 6. Хитрый вопрос: «Чем тест-дизайн API отличается от UI?»
**Ситуация.** Интервьюер: «Вы уже протестировали форму создания заказа в интерфейсе. Зачем ещё отдельно тестировать API?»

**Как рассуждать.** Что делает форма за пользователя? Кто ещё вызывает API, кроме этой формы? Что видно в API и не видно в интерфейсе?

**Пример ответа.** Форма защищает только саму себя. Она не даст ввести букву в количество, не покажет поле «роль», не отправит пустой обязательный параметр. А API вызывают и мобильное приложение, и партнёры, и любой человек через `curl`. Сервер обязан сам отклонить всё, что форма «не пускает».

Поэтому в API я проверяю то, что через UI не проверить: другие типы, лишние поля, `null`, огромные значения, недопустимые переходы состояний, права без интерфейса.

Ещё в API видны точные коды, тело и заголовки, и проверки идут быстрее — можно перебрать больше классов и комбинаций. И я проверяю контракт: что именно сервер обещал вернуть.

Но API не заменяет UI: как ошибка показана пользователю, проверяют в интерфейсе. Это два уровня, оба нужны.
:::

::: details Кейс 7. Хитрый вопрос: «Что делать, если сервер принимает неизвестные поля?»
**Ситуация.** Интервьюер: «Вы отправили в `POST /users` поле `"foo": "bar"`, которого нет в контракте. Сервер ответил `201`. Это баг?»

**Как рассуждать.** Что говорит контракт? Что сервер сделал с этим полем? А если поле не «foo», а существующее, но запрещённое?

**Пример ответа.** Само по себе — не обязательно. Многие API намеренно **игнорируют** неизвестные поля, чтобы старые и новые клиенты работали вместе. Если в контракте написано «лишние поля отклоняются с `422`» — тогда да, баг.

Важнее другое: **что стало с полем**. Я проверю `GET` созданного объекта — не сохранилось ли оно. И попробую не выдуманное поле, а **реальное, но запрещённое**: `role`, `isAdmin`, `id`, `ownerId`, `balance`. Если сервер его сохранил — это mass assignment, серьёзная уязвимость.

Итог: игнорирование безобидного поля — допустимо, если так задумано. Сохранение запрещённого поля — баг. Молчание контракта на эту тему — вопрос аналитику.
:::
