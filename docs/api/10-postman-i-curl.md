## Простыми словами

Ты в ресторане. **Swagger** — это меню: заказать можно только то, что в нём есть, и только так, как там написано. **curl** — записка на кухню: быстро, коротко, но каждый раз пишешь заново. **Postman** — твой блокнот рецептов: сохранил, разложил по папкам, передал коллеге, запустил всё подряд.

Все три инструмента делают одно и то же — отправляют HTTP-запрос и показывают ответ. Разница в том, что происходит **до** и **после** запроса: как ты его собираешь, где хранишь и как передаёшь данные в следующий запрос.

В этом уроке разберём:

- когда брать Swagger, когда `curl`, когда Postman;
- `curl` — анатомию команды, полезные флаги и **как не сломать её на Windows**;
- Postman — коллекции, переменные, цепочки запросов и простые тесты;
- для мидла — области видимости переменных, **ложно-зелёные тесты**, data-driven прогон, Newman и гигиену коллекций.

Как устроены запрос и ответ, ты уже знаешь из урока [«HTTP: запрос и ответ»](/api/03-http-zapros-i-otvet). Первый запуск `curl` был в уроке [«Клиент-сервер и URL»](/api/01-klient-server-i-url). Здесь — про сами инструменты.

## Три инструмента — одна задача

| | Swagger | curl | Postman |
|---|---|---|---|
| **Где живёт** | В браузере, рядом с API: `/docs` | В терминале, есть почти везде | Отдельное приложение или веб-версия |
| **Что умеет** | Показать контракт и отправить запрос по нему | Отправить **любой** запрос одной командой | Сохранять запросы, переменные, цепочки, тесты, прогон по данным |
| **Сильная сторона** | Документация и запрос в одном месте | Самый воспроизводимый формат: скопировал — выполнил | Многошаговые сценарии без ручного копирования |
| **Слабая сторона** | Только то, что описано в схеме. Не даёт отправить «неправильное» | Каждый раз собирать заново, неудобно для цепочек | Для одного разового запроса — долго |
| **Когда выбрать** | Изучить API, быстро проверить один эндпоинт | Разовый запрос, баг-репорт, сервер без графического интерфейса | Регресс API, цепочки, общая коллекция команды |

Есть и другие клиенты: **Insomnia**, **Bruno**, **HTTPie**, встроенные HTTP-клиенты в VS Code и IntelliJ. Принципы те же: запрос, переменные, окружения, коллекции. Освоишь один — разберёшься с любым.

## curl

### Анатомия команды

```bash
curl -i -X POST "http://localhost:8000/api/v1/projects" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer eyJhbGciOi…" \
  -d '{"name": "Демо"}'
```

| Часть | Что это |
|---|---|
| `curl` | Сама программа |
| `-i` | Показать **заголовки ответа** вместе с телом |
| `-X POST` | Метод. Без `-X` — `GET`, а с `-d` — `POST` |
| `"http://…"` | Адрес. В кавычках — чтобы `&` и `?` в query не сломали команду |
| `-H "…"` | Заголовок запроса. Сколько заголовков — столько `-H` |
| `-d '…'` | Тело запроса |
| `\` в конце строки | Перенос длинной команды на следующую строку. Только macOS и Linux |

### Полезные флаги

| Флаг | Что делает | Зачем тестировщику |
|---|---|---|
| `-i` | Заголовки ответа + тело | Увидеть `Location`, `Content-Type`, `X-Request-ID` |
| `-v` | Весь обмен: DNS, соединение, TLS, заголовки запроса и ответа | Разобраться, **на каком шаге** сломалось. Разбирали в уроках [«Сетевые модели»](/api/02-setevye-modeli) и [«HTTP: запрос и ответ»](/api/03-http-zapros-i-otvet) |
| `-s` | Тихий режим: без полосы загрузки | Чистый вывод, особенно вместе с `-o` и `-w` |
| `-o файл` | Сохранить тело в файл | Большой ответ, файл на скачивание. `-o /dev/null` — выбросить тело |
| `-w "…"` | Вывести после ответа служебные данные | Код и время одной строкой: `-w "\n%{http_code} %{time_total}\n"` |
| `-L` | Идти за редиректом `3xx` | Без него увидишь только `301` и `Location` |
| `--data @файл` | Взять тело из файла | Длинный JSON, Windows, повторяемость |
| `-k` | **Не проверять** сертификат HTTPS | Только для своего тестового стенда — подробнее ниже |

Код и время ответа без тела — частый приём для быстрой проверки:

```bash
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" http://localhost:8000/health
```

Ответ — одна строка вида `200 0.012345`: код и время в секундах.

**Про `-k`.** Сертификат подтверждает, что ты говоришь именно с этим сервером. `-k` отключает проверку: `curl` пойдёт к кому угодно, кто ответит по этому адресу. На своём стенде с самоподписанным сертификатом это иногда допустимо. Но если на **проде** или стейдже `curl` ругается на сертификат — это **находка**, а не помеха. Браузеры пользователей и мобильные приложения увидят ту же ошибку. Не «добавь `-k` и работай», а «сертификат просрочен или цепочка неполная — баг».

### curl на Windows

Здесь ломается больше всего команд. Три правила:

1. **В PowerShell пиши `curl.exe`, а не `curl`.** В Windows PowerShell 5 слово `curl` — это псевдоним команды `Invoke-WebRequest`. У неё другие параметры, и привычная команда падает с ошибкой вроде `Cannot bind parameter 'Headers'`. `curl.exe` — настоящий `curl`, он есть в Windows 10 и 11.
2. **Пиши команду в одну строку.** `\` для переноса работает только в macOS и Linux. В PowerShell перенос — обратная кавычка `` ` ``, в «Командной строке» — `^`. Проще не переносить.
3. **JSON-тело клади в файл.** Кавычки внутри JSON в PowerShell и «Командной строке» обрабатываются по-разному и часто теряются. Сервер получает сломанный JSON и отвечает `422`, а ты ищешь баг там, где его нет. Тело из файла работает везде одинаково.

Одна и та же команда в двух вариантах:

::: code-group

```bash [macOS, Linux]
curl -i -X POST "http://localhost:8000/api/v1/auth/login" \
  -H "Content-Type: application/json" \
  --data "@login.json"
```

```powershell [Windows, PowerShell]
curl.exe -i -X POST "http://localhost:8000/api/v1/auth/login" -H "Content-Type: application/json" --data "@login.json"
```

:::

Файл `login.json` лежит в папке, из которой запускаешь команду. Создай его в Блокноте или VS Code и сохрани в кодировке **UTF-8**. Не создавай его командой `echo … > login.json` в Windows PowerShell 5: файл получится в кодировке UTF-16, и сервер его не поймёт.

`@` в кавычках — `"@login.json"` — потому что в PowerShell символ `@` в начале слова имеет своё значение. В кавычках он безопасен во всех терминалах.

### Откуда брать готовую команду

Набирать `curl` с нуля приходится редко. Готовую команду дают:

- **Swagger** — после выполнения запроса блок **Curl** в ответе;
- **DevTools** — Network → правая кнопка по запросу → **Copy → Copy as cURL**. Подробно — в уроке [«HTTP: запрос и ответ»](/api/03-http-zapros-i-otvet);
- **Postman** — значок **`</>`** (Code) справа у запроса → выбрать `cURL`.

И обратно: в Postman **Import** → вставить команду `curl` как текст. Postman сам разложит её на метод, адрес, заголовки и тело. Так запрос из браузера или из чужого баг-репорта за секунду превращается в запрос в коллекции.

### curl в баг-репорте

Команда `curl` — самый воспроизводимый шаг баг-репорта. Разработчик вставит её в терминал и увидит то же, что ты. Но в скопированной команде **все** заголовки, включая токен и cookie.

Перед отправкой:

- замени токен: `-H "Authorization: Bearer eyJhbGciOi…"` или `Bearer <токен пользователя user1>`;
- удали заголовки `Cookie`, если они не нужны для воспроизведения;
- проверь тело: нет ли там пароля.

Почему это важно — в уроках [«Баг-репорт»](/osnovy/09-bag-report) и [«Безопасность для тестировщика»](/api/08-bezopasnost). Тикет читает много людей, а токен из него — рабочий ключ к чужой учётной записи.

**Красивый вывод JSON.** Ответ `curl` приходит одной длинной строкой. Утилита `jq` делает его читаемым: `curl -s … | jq`. Её нужно установить отдельно, и для этого урока она не обязательна.

## Postman: база

### Запрос и его вкладки

Запрос в Postman — это метод, адрес и вкладки под адресной строкой:

| Вкладка | Что там |
|---|---|
| **Params** | Query-параметры таблицей. Postman сам соберёт `?limit=20&offset=0` |
| **Authorization** | Тип авторизации: Bearer Token, Basic Auth, API Key. Postman сам добавит нужный заголовок |
| **Headers** | Заголовки. Часть Postman добавляет сам — они скрыты, кнопка **hidden** их показывает |
| **Body** | Тело: `raw` + `JSON` для API, `form-data` для файлов |
| **Scripts** | Скрипты **до** запроса (Pre-request) и **после** ответа (Post-response). В старых версиях — вкладки Pre-request Script и Tests |

Под ответом — код, время, размер, тело, заголовки и результаты тестов.

### Коллекция, папки, история

- **Коллекция** — сохранённый набор запросов. Обычно одна коллекция на один API или одну фичу.
- **Папки** внутри — по ресурсам или по сценариям: `Auth`, `Projects`, `Tasks`.
- **История** — все отправленные запросы, даже несохранённые. Удобно найти, «что я отправлял час назад».

Для коллекций и рабочих пространств нужна бесплатная учётная запись Postman. У бесплатного плана бывают ограничения — например, на число запусков Runner. Если упрёшься — есть Newman, о нём ниже.

### Импорт и экспорт

- **Import → файл коллекции** — `.json` из репозитория или от коллеги. Так ты получишь коллекцию TaskFlow.
- **Import → OpenAPI** — ссылка на схему или файл. Для TaskFlow это `http://localhost:8000/openapi.json`. Postman соберёт коллекцию из всех эндпоинтов за минуту: папки по тегам, тела-примеры, параметры. Тестов и цепочек в ней не будет — их добавляешь ты.
- **Export** — коллекция уходит в файл `.json`. Его кладут в репозиторий рядом с кодом.

## Переменные

Переменная — это имя в двойных фигурных скобках: <span v-pre>`{{baseUrl}}`</span>, <span v-pre>`{{accessToken}}`</span>. Postman подставляет значение перед отправкой. Адрес стенда меняется в одном месте, а не в ста запросах.

### Области видимости

Одна и та же переменная может быть задана в нескольких местах. Postman берёт значение из **самой узкой** области — той, что ближе к запросу.

| Область | Где задаётся | Для чего |
|---|---|---|
| **Global** | Во всём Postman | Почти никогда. Глобальные переменные мешают всем коллекциям сразу |
| **Collection** | Вкладка **Variables** коллекции | То, что одинаково на всех стендах: пути, идентификаторы из цепочки |
| **Environment** | Отдельный набор, выбирается справа вверху | То, что **разное на стендах**: `baseUrl`, логины тестовых пользователей, токены |
| **Data** | Строка CSV или JSON-файла при прогоне в Runner | Данные для data-driven прогона |
| **Local** | Из скрипта: `pm.variables.set(…)` | Временное значение на один запуск запроса |

Ловушка для мидла: переменная `baseUrl` есть и в коллекции, и в Environment. Ты меняешь её в коллекции — а запросы упрямо идут на старый адрес. Побеждает Environment. Если «переменная не меняется» — найди, в скольких областях она задана. Наведи курсор на <span v-pre>`{{baseUrl}}`</span> в адресе: Postman покажет значение и область, откуда оно взято.

### Динамические переменные

Postman умеет генерировать значения сам:

- <span v-pre>`{{$timestamp}}`</span> — текущее время в секундах: `1792057545`;
- <span v-pre>`{{$guid}}`</span> — уникальный идентификатор;
- <span v-pre>`{{$randomEmail}}`</span>, <span v-pre>`{{$randomFirstName}}`</span>, <span v-pre>`{{$randomInt}}`</span> — случайные данные.

Важная деталь: динамическая переменная генерируется **заново при каждом использовании**. Если поставить <span v-pre>`{{$randomEmail}}`</span> в регистрацию и в логин, это будут **два разных** email — и логин не пройдёт. Сгенерируй значение один раз скриптом и сохрани в обычную переменную. Как — ниже, в разделе про pre-request script.

### Initial value и current value

У переменных коллекции и Environment два значения:

- **Initial value** — уходит в **экспорт** и синхронизируется в облако Postman. Его видят все, с кем ты поделился коллекцией;
- **Current value** — живёт **только у тебя** на компьютере. Его подставляют в запрос и меняют скрипты.

Правило: **секреты — только в current value**. Токены, пароли, ключи API. В initial value — пустая строка или подсказка вида `<вставь свой токен>`. Ещё надёжнее — хранилище секретов Postman (**Vault**) или тип переменной **secret**: значение скрыто на экране.

В новых версиях Postman эти поля могут называться по-другому. Смысл тот же: одно значение общее, другое — только твоё. Перед экспортом или публикацией коллекции проверь, что лежит в общем.

## Важно не перепутать: Postman Environment ≠ тестовое окружение

Слово одно, понятия разные.

- **Postman Environment** — набор переменных внутри Postman. Например, `baseUrl`, логин тестового пользователя, токен. Переключение Environment меняет только то, **какие значения** подставятся в запросы.
- **Тестовое окружение (стенд)** — живая система: сервер, база, настройки. Dev, test, stage, prod — урок [«Тестовые окружения»](/osnovy/11-testovye-okruzheniya).

Связь простая: переменная `baseUrl` в Environment **указывает** на стенд. Поменял Environment — запросы полетели в другую систему.

Отсюда практические правила:

- **один Environment — один стенд**, имя совпадает с названием стенда: `shop-dev`, `shop-stage`;
- у Environment для prod — **яркое имя**: `PROD — ОСТОРОЖНО`. В Postman можно задать цвет — красный;
- **токенов prod в Postman лучше не держать вовсе**, если по работе они не нужны;
- перед прогоном коллекции — посмотри в правый верхний угол: **какой Environment выбран**.

В разговоре с командой говори точно: «переключил Environment в Postman», а не «переключил окружение». Иначе коллега решит, что ты что-то развернул.

### Скрипт из коллекции TaskFlow — построчно

Вот скрипт, который выполняется **после ответа** на запрос `POST /auth/login` в коллекции TaskFlow. Он записан дословно:

```javascript
if (pm.response.code === 200) {
    pm.collectionVariables.set('accessToken', pm.response.json().accessToken);
}
```

- `pm` — объект Postman, через него скрипт видит запрос, ответ и переменные;
- `pm.response.code === 200` — условие: только если вход успешный;
- `pm.response.json()` — тело ответа как объект, `.accessToken` — поле с токеном;
- `pm.collectionVariables.set('accessToken', …)` — записать значение в переменную коллекции `accessToken`.

Дальше в каждом запросе стоит заголовок <span v-pre>`Authorization: Bearer {{accessToken}}`</span> — и подставится свежий токен.

Обрати внимание: этот скрипт **ничего не проверяет**. Он не говорит «тест пройден» или «тест упал». Если логин ответит `401`, скрипт просто ничего не сделает — и в переменной останется **старый** токен. Это служебная автоматизация рутины, а не тест. Тесты — ниже.

### Pre-request script

Скрипт, который выполняется **до** отправки запроса. Нужен, чтобы подготовить данные.

Пример: уникальный email для регистрации, один и тот же для регистрации и логина.

```javascript
// Pre-request у запроса регистрации
const email = `student_${Date.now()}@example.com`;
pm.collectionVariables.set('studentEmail', email);
```

В теле регистрации и логина — <span v-pre>`"email": "{{studentEmail}}"`</span>. Значение сгенерировано один раз, поэтому совпадёт в обоих запросах. С <span v-pre>`{{$randomEmail}}`</span> так не получится: он разный при каждой подстановке.

Другие частые задачи pre-request: уникальное имя сущности с отметкой времени, дата «завтра» в нужном формате, подпись запроса, получение токена, если его ещё нет.

### Авторизация на уровне коллекции

Мидл-приём. Вместо заголовка `Authorization` в каждом запросе:

1. Открой коллекцию → вкладка **Authorization** → тип **Bearer Token** → значение <span v-pre>`{{accessToken}}`</span>.
2. В запросах на вкладке **Authorization** — **Inherit auth from parent**: взять авторизацию у родителя — папки или коллекции.
3. Для запросов, где нужен другой пользователь — например, админ, — задай авторизацию на папке `Admin` или прямо в запросе. Ближний уровень перекрывает дальний.
4. Для запросов без авторизации — логин, регистрация — **No Auth**.

Плюс: токен меняется в одном месте, а проверить «а что без токена» — переключить один запрос на **No Auth**.

## Тесты в Postman

Тест — это проверка в скрипте после ответа. Каждая проверка — в своём `pm.test`: у неё есть имя, и в результатах видно, что прошло, а что упало.

Пример на выдуманном магазине, `POST /orders`:

```javascript
pm.test('Код 201', () => {
    pm.response.to.have.status(201);
});

pm.test('Есть заголовок Location', () => {
    pm.response.to.have.header('Location');
});

pm.test('В ответе тот товар, который заказали', () => {
    const body = pm.response.json();
    pm.expect(body.productId).to.eql(15);
    pm.expect(body.quantity).to.eql(2);
});

pm.test('Ответ быстрее 500 мс', () => {
    pm.expect(pm.response.responseTime).to.be.below(500);
});
```

- `pm.response.to.have.status(201)` — код ответа;
- `pm.response.to.have.header('Location')` — заголовок есть. Значение — `pm.response.headers.get('Location')`;
- `pm.expect(факт).to.eql(ожидание)` — сравнение значений;
- `pm.response.responseTime` — время ответа в миллисекундах.

### Ложно-зелёные тесты

Зелёный тест, который ничего не доказывает, хуже, чем отсутствие теста: он создаёт уверенность.

| Ловушка | Почему зелёный | Как правильно |
|---|---|---|
| **Проверяется только код** | `200` пришёл, а в теле пустой список или чужие данные | Проверяй ключевые поля тела и побочный эффект вторым запросом — урок [«Тест-дизайн для API»](/api/09-test-dizayn-api) |
| **Проверка вне `pm.test`** | `pm.expect(…)` без `pm.test` не попадает в список тестов. Упавшая проверка — это ошибка скрипта, а в сводке «0 failed». Ошибку скрипта легко не заметить | Каждая проверка — внутри `pm.test` |
| **Сравнение с `undefined`** | Поле называется `owner_id`, а тест читает `body.ownerId`. Ожидание тоже берётся из пустой переменной — `undefined` равно `undefined` | Сначала проверь, что поле есть и не пустое: `pm.expect(body.ownerId).to.be.a('number')` |
| **Сохранение без проверки** | Скрипт сохраняет `id` только при `201`. Запрос упал — переменная осталась вчерашней, следующий шаг идёт на старый объект и проходит | Проверяй код в `pm.test`. При ошибке — очищай переменную: `pm.collectionVariables.unset('projectId')` |
| **Тест никогда не может упасть** | `pm.expect(body.items.length).to.be.at.least(0)` — верно всегда | Спроси себя: «при каком баге этот тест покраснеет?» Нет ответа — тест бесполезен |

Последний вопрос — главный инструмент мидла. Прежде чем доверять зелёной коллекции, сломай ожидание руками: поменяй `201` на `200` — тест должен покраснеть. Не покраснел — он ничего не проверяет.

### Проверка схемы

Вместо проверки каждого поля можно сверить тело с **JSON-схемой**:

```javascript
pm.test('Тело по схеме', () => {
    pm.response.to.have.jsonSchema(schema);
});
```

`schema` — описание полей, типов и обязательности. Её берут из контракта — того же OpenAPI, что лежит за Swagger. Так тест ловит пропавшее поле, лишнее поле или поменявшийся тип: это и есть проверка контракта из урока [«API, REST и форматы данных»](/api/06-api-rest-formaty). Значения при этом всё равно проверяют отдельно: схема скажет «`name` — строка», но не скажет, что строка та, которую ты отправил.

## Runner и data-driven

**Collection Runner** — запуск папки или всей коллекции подряд. Кнопка **Run** у коллекции или папки. В настройках:

- **порядок запросов** — по порядку в коллекции, можно перетащить или снять галочки;
- **Iterations** — сколько раз прогнать;
- **Data** — файл CSV или JSON. Каждая строка — одна итерация.

Это и есть таблица из урока [«Тест-дизайн для API»](/api/09-test-dizayn-api): **запрос → данные → ожидание**. Запрос описан один раз, данные и ожидаемый код — в файле.

Пример для `POST /api/v1/projects` TaskFlow. По разделу 6.3 спецификации `name` — от 1 до 100 символов, `description` — необязательное, до 1000.

```text
case,nameLength,descLength,expectedStatus
name-1,1,,201
name-100,100,,201
name-101,101,,422
name-empty,0,,422
desc-1000,20,1000,201
desc-1001,20,1001,422
```

Строку в 1000 символов в CSV не напишешь руками. Поэтому в файле — **длины**, а саму строку собирает pre-request script:

```javascript
// Pre-request
const nameLength = Number(pm.iterationData.get('nameLength'));
const descLength = pm.iterationData.get('descLength');

const body = { name: ('autotest_' + 'x'.repeat(200)).slice(0, nameLength) };
if (descLength !== '' && descLength !== undefined) {
    body.description = 'd'.repeat(Number(descLength));
}
pm.variables.set('projectBody', JSON.stringify(body));
```

- `pm.iterationData.get(…)` — значение из текущей строки файла;
- `('autotest_' + …).slice(0, n)` — строка ровно нужной длины. С префиксом `autotest_`, если длина позволяет;
- `pm.variables.set` — локальная переменная на этот запуск. Тело запроса — <span v-pre>`{{projectBody}}`</span>.

Тест берёт ожидание тоже из файла:

```javascript
// Post-response
const expected = Number(pm.iterationData.get('expectedStatus'));

pm.test(`${pm.iterationData.get('case')}: код ${expected}`, () => {
    pm.response.to.have.status(expected);
});
```

Шесть строк данных — шесть проверок, а запрос один. Добавить новую границу — дописать строку в файл.

**Порядок и ветвление** — мидл, коротко. По умолчанию Runner идёт по порядку. Скрипт может изменить следующий шаг: `pm.execution.setNextRequest('Имя запроса')` — перейти к другому запросу, `pm.execution.setNextRequest(null)` — остановить прогон. Удобно, например, остановиться, если логин не удался. Злоупотреблять не стоит: коллекция с прыжками читается как запутанный код.

## Newman и CI

**Newman** — Postman без окна: запуск коллекции из командной строки. Нужен Node.js.

```bash
npx newman run TaskFlow.postman_collection.json -e local.postman_environment.json -d projects.csv
```

- `-e` — файл Environment, экспортированный из Postman;
- `-d` — файл данных, как в Runner;
- `--folder Projects` — прогнать одну папку;
- `-r cli,junit` — отчёты: в консоль и в файл для CI. Есть и HTML-отчёты — через дополнительные пакеты.

Зачем это ручному тестировщику:

- Runner в бесплатном Postman ограничен — Newman нет;
- коллекция живёт **в репозитории рядом с кодом**: изменился API — в том же изменении правят коллекцию;
- Newman запускают в **пайплайне**: каждая сборка прогоняет коллекцию, и упавший тест останавливает выкладку. О пайплайнах — дальше в курсе.

Мидл не обязан писать автотесты. Но прочитать такую коллекцию, понять, почему она упала в пайплайне, и поправить тест или данные — обязан.

## Гигиена коллекций и совместная работа

Коллекция, которой пользуется команда, — это **документация**. Плохая коллекция вредит так же, как плохая документация.

- **Описания.** У папки и запроса есть поле Description: что делает запрос, какие права нужны, откуда взять данные.
- **Examples.** У запроса можно сохранить примеры ответов: успешный, `404`, `422`. Новичок увидит, что приходит, не отправляя запрос.
- **Mock-сервер.** Postman умеет поднять сервер-заглушку, который отвечает сохранёнными Examples. Фронтенд и тестировщики могут работать, пока настоящего API ещё нет. Но проверяют на заглушке только клиент, а не сервер.
- **Никаких секретов в общем.** Токены и пароли — только в current value или в Vault. Перед экспортом и коммитом — проверка.
- **Никакого хардкода.** Адрес — <span v-pre>`{{baseUrl}}`</span>, токен — переменная или авторизация коллекции. Ни одного `http://…` прямо в запросе.
- **Чистка за собой.** Прогон Runner создаёт сущности. Имена — с префиксом `autotest_`, чтобы их было видно и легко удалить. В конце папки — запросы на удаление созданного. На общем стенде мусор от твоего прогона мешает коллегам.
- **Порядок и имена.** Папки по ресурсам или сценариям, имя запроса = метод и путь, как в коллекции TaskFlow.

## На примере TaskFlow

**Ветка:** `training-public`. В репозитории — готовая коллекция `postman/TaskFlow.postman_collection.json`, «TaskFlow QA Training API».

**Папки** совпадают с разделами спецификации: Health, Auth, Users, Projects, Tasks, Comments, Labels, Admin.

**Переменные коллекции** — вкладка **Variables** у коллекции:

| Переменная | Откуда значение |
|---|---|
| `baseUrl` | Задано в файле: `http://localhost:8000` |
| `accessToken` | Скрипт после `POST /auth/login` |
| `adminAccessToken` | Скрипт после `POST /auth/login (admin)` |
| `userId` | Скрипт после `POST /auth/register` |
| `projectId` | Скрипт после `POST /projects` |
| `taskId` | Скрипт после `POST /tasks` |
| `commentId` | Скрипт после `POST /tasks/{taskId}/comments` |
| `labelId` | Скрипт после `POST /labels (admin)` |

Все скрипты устроены одинаково: если код успешный — `200` или `201`, — взять `id` или `accessToken` из тела и сохранить в переменную. Найти их можно на вкладке **Scripts → Post-response** у запроса. В старых версиях Postman — вкладка **Tests**.

**Цепочка из пяти запросов:**

1. `Auth → POST /auth/register` — `201`, скрипт сохраняет `userId`.
2. `Auth → POST /auth/login` — `200`, скрипт сохраняет `accessToken`.
3. `Projects → POST /projects` — в заголовке уже <span v-pre>`Bearer {{accessToken}}`</span>. Ответ `201`, скрипт сохраняет `projectId`.
4. `Tasks → POST /tasks` — в теле <span v-pre>`"projectId": {{projectId}}`</span>. Ответ `201`, скрипт сохраняет `taskId`.
5. `Tasks → GET /tasks/{taskId}` — в адресе <span v-pre>`{{taskId}}`</span>. Ответ `200`, `id` в ответе совпадает с сохранённым.

**Про повторный прогон.** В теле регистрации — фиксированный email `student@example.com`. При первом прогоне — `201`. При втором — **`409 EMAIL_ALREADY_EXISTS`**. Это не баг: пользователь уже есть, и спецификация, раздел 6.1, требует именно `409`. Логин после этого всё равно пройдёт — пользователь с этим паролем существует. Если нужен новый пользователь на каждый прогон — сгенерируй email в pre-request script, как в примере выше, и подставь <span v-pre>`{{studentEmail}}`</span> в регистрацию и логин.

**Что можно улучшить в коллекции — мидл-взгляд.** Заголовок `Authorization` прописан в каждом запросе отдельно. Его можно перенести на уровень коллекции — **Inherit auth from parent**, — а для папки `Admin` и запросов `(admin)` задать <span v-pre>`{{adminAccessToken}}`</span>. И скрипты сохраняют значения без проверки: если запрос упал, переменная останется старой. Это не мешает учебной коллекции работать, но в рабочей команде на это стоит обратить внимание.

## На открытом проекте

**Restful Booker** — [документация](https://restful-booker.herokuapp.com/apidoc/index.html). Ты работал с ним в уроках [«Методы HTTP»](/api/04-metody-http) и [«Аутентификация и права»](/api/07-autentifikaciya-i-prava). Цепочка ниже проверена живыми запросами.

1. `POST /auth` с телом `{"username": "admin", "password": "password123"}` → `200`, `{"token": "…"}` — короткая строка.
2. `POST /booking` с заголовками `Content-Type: application/json` и `Accept: application/json` и телом бронирования → `200`, в ответе `bookingid` и само бронирование. Обрати внимание: **`200`, а не `201`** — так и в документации.
3. `GET /booking/{bookingid}` → `200`, данные совпадают с отправленными.
4. `PUT /booking/{bookingid}` с полным телом и заголовком `Cookie: token=<токен из шага 1>` → `200`, в ответе новые данные. Без cookie — `403` и текст `Forbidden`.
5. `DELETE /booking/{bookingid}` с той же cookie → **`201`**, хотя по смыслу подошёл бы `204`. После этого `GET` — `404`.

Это готовая цепочка для Postman: токен из шага 1 и `bookingid` из шага 2 сохраняются скриптами так же, как в коллекции TaskFlow. Данные на сервере общие и периодически сбрасываются. Первый запрос после простоя может идти несколько секунд: сервис «просыпается».

## Разборы из жизни

Ниже шесть ситуаций с Postman и `curl` из рабочих проектов. Первый разбор открыт — это образец. Остальные попробуй сначала разобрать сам и только потом открывай.

<details class="details custom-block" open>
<summary>Разбор 1. Токен прод-админа в общем репозитории — платёжный сервис</summary>

**Ситуация.** Тестировщик платёжного сервиса собрал отличную коллекцию: 120 запросов, цепочки, тесты. Чтобы ей пользовалась вся команда, он экспортировал её и закоммитил в репозиторий. Через неделю служба безопасности пишет: в репозитории лежит рабочий токен администратора **прода**. Репозиторий видят 60 человек, включая подрядчиков.

**Что видит мидл.**

- Токен попал в **initial value** переменной коллекции. Initial value уходит в экспорт — это его назначение.
- Скорее всего, когда-то пришлось проверить что-то на проде, токен вставили «на минутку» и забыли.
- Удаление файла из репозитория не помогает: токен остаётся в **истории коммитов**.
- Рабочий токен админа в чужих руках — это доступ к платежам клиентов. Серьёзность — критическая.

**Что делать.**

1. Сразу сообщить команде и службе безопасности. Не пытаться «тихо удалить».
2. **Отозвать токен** — это первое и главное. Пока он действует, остальное вторично.
3. Убрать токен из файла и попросить разработчиков или DevOps почистить историю — это их инструменты.
4. Перенести все секреты в current value или Vault. В initial value — пустая строка или подсказка `<вставь свой токен>`.
5. Предложить правило: перед коммитом коллекции — поиск по файлу на `Bearer`, `token`, `password`. Многие команды ставят автоматическую проверку на секреты в репозитории.

**Чего не делать.**

- Не ограничиваться удалением файла новым коммитом.
- Не считать «у нас приватный репозиторий» защитой: доступ есть у многих, и у подрядчиков он заканчивается позже, чем стоило бы.

</details>

::: details Разбор 2. 300 тестовых заказов у настоящего магазина — маркетплейс
**Ситуация.** Тестировщик маркетплейса прогоняет в Runner регрессионную коллекцию «Оформление заказа» с файлом данных на 300 строк. Он уверен, что работает на стейдже. Через десять минут звонит менеджер магазина-партнёра: на складе 300 новых заказов от «Тест Тестовича», курьеры уже выехали.

**Что видит мидл.**

- Активным был Environment **prod**. Вчера проверяли инцидент на проде, Environment не переключили обратно.
- Имя Environment ничем не выделялось: `marketplace-prod` рядом с `marketplace-stage`.
- В Environment prod лежал рабочий токен — без него прогон бы упал на первом запросе.
- Postman сделал ровно то, что ему сказали. Проблема в процессе, а не в инструменте.

**Что делать.**

1. Сразу остановить прогон и сообщить команде и поддержке: заказы нужно отменить, пока курьеры не доехали.
2. Передать список созданных заказов — он есть в результатах Runner.
3. Предложить защиту: Environment prod — красный и с именем `PROD — ОСТОРОЖНО`; токенов prod в Postman нет по умолчанию; в pre-request коллекции — проверка, которая останавливает прогон, если `baseUrl` указывает на прод.
4. Для регресса — отдельный тестовый магазин и тестовые товары даже на стейдже.

**Чего не делать.**

- Не прятать инцидент: чем раньше узнают партнёр и поддержка, тем меньше ущерб.
- Не ограничиваться «буду внимательнее». Внимательность подводит, защита в коллекции — нет.
:::

::: details Разбор 3. Все тесты зелёные, а фича сломана — сервис доставки
**Ситуация.** В сервисе доставки коллекция из 80 тестов проходит в пайплайне при каждой сборке. Все зелёные. После релиза пользователи жалуются: в истории заказов пусто. Разработчик удивлён: «Тесты же прошли».

**Что видит мидл.**

- Тест на `GET /orders` проверял **только код** `200`. Сервер отвечал `200` с `"items": []` — тест доволен.
- Похожие тесты рядом: проверяют код, но не тело. Половина коллекции — ложно-зелёная.
- Отдельно стоит посмотреть, нет ли проверок вне `pm.test` и сравнений с несуществующими полями.

**Что делать.**

1. Завести баг на сам дефект: «История заказов пустая для пользователей с заказами».
2. Добавить в тест проверку тела: у тестового пользователя с тремя заказами — `total` равен 3, в `items` — его заказы.
3. Пройтись по коллекции и для каждого теста ответить: «при каком баге он покраснеет?» Где ответа нет — дописать проверки.
4. Проверить, что тест **может** упасть: временно поменять ожидание и убедиться, что он красный.

**Чего не делать.**

- Не считать число зелёных тестов показателем качества. 80 зелёных тестов, проверяющих только код, — это 80 проверок, что сервер не упал.
- Не переписывать всю коллекцию за раз. Начать с самых важных сценариев: заказ, оплата, история.
:::

::: details Разбор 4. «Вчера работало, сегодня 404» — CRM
**Ситуация.** Тестировщик CRM проверяет права менеджеров. В коллекции цепочка: логин → получить сделку → изменить сделку. Вчера он прогонял её под менеджером Анной — всё работало. Сегодня он поменял в теле логина email на менеджера Бориса, чтобы проверить сделку Бориса, и запустил цепочку. «Получить сделку» отвечает `404`. Тестировщик заводит баг «Менеджер не видит собственную сделку».

**Что видит мидл.**

- Логин ответил `401`: ночью при обновлении стенда тестовым пользователям сбросили пароли. Тестировщик смотрел только на последний ответ и этого не заметил.
- Скрипт логина сохраняет токен **только при `200`**. В переменной остался вчерашний токен Анны — он ещё действует.
- Запросы ушли **от имени Анны**. Сделка Бориса для неё чужая, а сервер на чужие объекты отвечает `404`, чтобы не раскрывать, что они существуют. Это правило из урока [«Аутентификация и права»](/api/07-autentifikaciya-i-prava).
- Баг ложный. Настоящая проблема — цепочка без проверок.

**Что делать.**

1. Открыть ответ **каждого** шага, начиная с первого.
2. В скрипте логина — `pm.test` на код `200`. При ошибке — `pm.collectionVariables.unset('accessToken')` и `pm.execution.setNextRequest(null)`: прогон остановится, а не пойдёт со старым токеном.
3. Добавить в начало цепочки `GET /users/me` с тестом на ожидаемого пользователя. Дешёвая страховка: сразу видно, под кем идут запросы.
4. Закрыть ложный баг с объяснением, узнать новый пароль Бориса и повторить проверку.

**Чего не делать.**

- Не заводить баг по последнему шагу, не посмотрев предыдущие.
- Не «лечить» повторным запуском. Пока скрипт сохраняет значения без проверки, ситуация повторится.
:::

::: details Разбор 5. «У меня curl работает, у тебя нет» — банковское приложение
**Ситуация.** Разработчик присылает тестировщику команду `curl`, чтобы воспроизвести ошибку при переводе. У разработчика команда возвращает `500`. Тестировщик на Windows вставляет её в PowerShell и получает красный текст про `Invoke-WebRequest`. Исправив на `curl.exe`, он получает `422`. Разработчик: «Значит, у тебя всё правильно работает, а баг плавающий».

**Что видит мидл.**

- Ошибка про `Invoke-WebRequest` — это псевдоним `curl` в Windows PowerShell 5. Не баг.
- `422` у тестировщика — скорее всего, **сломанное тело**. Команда была с `\` в концах строк и JSON в одинарных кавычках. PowerShell убрал из JSON двойные кавычки, сервер получил невалидный JSON.
- Ещё одно отличие: в команде разработчика — адрес его локального стенда. Тестировщик бил в общий тестовый стенд, где другие данные.
- Сравнивать результаты можно, только когда запросы **одинаковы**: тот же адрес, то же тело, те же заголовки.

**Что делать.**

1. Положить JSON в файл `body.json` и отправить `curl.exe … --data "@body.json"` одной строкой.
2. Проверить адрес и выбрать один общий стенд для воспроизведения.
3. Добавить `-v`, чтобы сравнить, что **действительно** ушло на сервер: заголовки, длина тела.
4. Если на общем стенде тоже `500` — баг воспроизводится. Приложить команду без токена и `X-Request-ID` ответа.

**Чего не делать.**

- Не соглашаться на «плавающий», пока запросы не одинаковы.
- Не переписывать JSON в командной строке экранированием кавычек вручную. Файл надёжнее.
:::

::: details Разбор 6. Сотни мусорных сущностей на общем стенде — система бронирования
**Ситуация.** Тестировщик системы бронирования переговорных написал data-driven прогон: 400 строк в CSV — разные даты, длительности, комнаты. Прогнал на общем тестовом стенде три раза за день. Наутро коллеги жалуются: календарь забит бронями «Test 1», «Test 2», найти свои данные невозможно, а одна из ручных проверок дала ложный баг «нет свободных комнат».

**Что видит мидл.**

- Прогон создаёт сущности, но **не удаляет** их. 1200 броней за день.
- Имена ничем не выделяются — коллеги не могут отличить мусор от своих данных и удалить его.
- Data-driven прогон — мощный, и поэтому опасный на общем стенде: он делает много и быстро.

**Что делать.**

1. Удалить созданное — через API, запросом в цикле или по префиксу. Извиниться перед коллегами.
2. Все создаваемые сущности — с префиксом `autotest_` и меткой прогона: `autotest_20261015_…`.
3. В коллекции — шаг очистки: после создания и проверки брони — `DELETE` её же.
4. Тяжёлые прогоны — на отдельном стенде или в отдельной тестовой организации, если продукт это позволяет. Договориться в команде, где можно «шуметь».
5. Подумать, нужны ли 400 строк. Классы и границы из урока [«Тест-дизайн для API»](/api/09-test-dizayn-api) обычно дают 20–40.

**Чего не делать.**

- Не прогонять большие наборы на общем стенде без очистки.
- Не путать «больше данных» с «лучше проверено».
:::

## Частые ошибки

- **Путать Postman Environment и стенд.** Environment — набор переменных. Стенд — живая система, на которую указывает `baseUrl`.
- **Хардкодить адрес и токен в каждом запросе.** Сменился стенд или истёк токен — правишь сто запросов. Используй <span v-pre>`{{baseUrl}}`</span> и авторизацию коллекции.
- **Писать тест только на код.** `200` с пустым или чужим телом — тоже `200`. Проверяй тело и побочный эффект.
- **Класть секреты в initial value.** Он уходит в экспорт и в облако.
- **Не смотреть, какой Environment выбран.** Перед каждым прогоном — взгляд в правый верхний угол.
- **Копировать `curl` с токеном в тикет или чат.** Замени токен на `…` или на имя тестового пользователя.
- **Писать `curl` в PowerShell без `.exe`** и JSON прямо в команде на Windows. Тело — из файла.
- **Доверять цепочке без проверок.** Скрипт, который сохраняет значение без `pm.test`, при ошибке оставит старое значение — и следующий шаг пойдёт не туда.

## Часть 1. curl

Используй пользователя, которого ты **сам зарегистрировал** в прошлых уроках, — или зарегистрируй нового через Swagger: `POST /api/v1/auth/register`.

На Windows работай в **PowerShell** и пиши `curl.exe`. На macOS и Linux — в Терминале.

### Команда 1. Сервер жив?

::: code-group

```bash [macOS, Linux]
curl -i http://localhost:8000/health
```

```powershell [Windows, PowerShell]
curl.exe -i http://localhost:8000/health
```

:::

Запиши: код ответа, тело, два-три заголовка ответа, которые ты узнаёшь.

### Команда 2. Вход с телом из файла

Создай в папке, где открыт терминал, файл `login.json` со своими email и паролем:

```json
{ "email": "твой-email@example.com", "password": "твой пароль" }
```

На Windows создай файл в Блокноте и сохрани в кодировке UTF-8.

::: code-group

```bash [macOS, Linux]
curl -i -X POST "http://localhost:8000/api/v1/auth/login" -H "Content-Type: application/json" --data "@login.json"
```

```powershell [Windows, PowerShell]
curl.exe -i -X POST "http://localhost:8000/api/v1/auth/login" -H "Content-Type: application/json" --data "@login.json"
```

:::

Ожидаемый ответ — `200` и `accessToken` в теле. Скопируй токен для следующей команды. Если пришёл `429` — ты слишком часто входил: подожди столько секунд, сколько указано в заголовке `Retry-After`.

### Команда 3. Список проектов с токеном, кодом и временем

Сохрани токен в переменную терминала и отправь запрос:

::: code-group

```bash [macOS, Linux]
TOKEN="вставь_сюда_accessToken"
curl -s -H "Authorization: Bearer $TOKEN" -w "\n%{http_code} %{time_total}\n" "http://localhost:8000/api/v1/projects?limit=5"
```

```powershell [Windows, PowerShell]
$TOKEN = "вставь_сюда_accessToken"
curl.exe -s -H "Authorization: Bearer $TOKEN" -w "\n%{http_code} %{time_total}\n" "http://localhost:8000/api/v1/projects?limit=5"
```

:::

Последняя строка вывода — код и время ответа в секундах.

### Что записать

| Команда | Код | Время | Что в ответе — коротко |
|---|---|---|---|
| `GET /health` | | | |
| `POST /auth/login` | | | |
| `GET /projects?limit=5` | | | |

Время для первой и второй команды узнай сам: добавь к ним `-w`. И ответь письменно: зачем в третьей команде адрес в кавычках? Что сломалось бы без них?

::: warning Обрезай токен
В отчёте оставляй от токена первые 10–15 символов и `…`. Это касается и команд, и скриншотов.
:::

## Часть 2. Коллекция TaskFlow и цепочка

### Шаг 1. Импортируй коллекцию

1. Открой Postman → **Import** → выбери файл `postman/TaskFlow.postman_collection.json` из репозитория TaskFlow.
2. Убедись, что слева появилась коллекция «TaskFlow QA Training API» с папками Health, Auth, Users, Projects, Tasks, Comments, Labels, Admin.

### Шаг 2. Проверь `baseUrl`

Открой коллекцию → вкладка **Variables** → найди `baseUrl`. Значение должно быть `http://localhost:8000` — адрес твоего стенда. Проверь своими глазами, а не «наверное, так и есть».

Посмотри и в правый верхний угол: выбран ли какой-то Environment? Для этого задания он не нужен — выбери **No Environment**.

### Шаг 3. Прогони цепочку

Выполни запросы строго в этом порядке. **Ничего не копируй руками** между шагами.

| № | Запрос | Ожидаемый код | Что проверить после |
|---|---|---|---|
| 1 | `Auth → POST /auth/register` | `201` или `409` — см. ниже | Variables: заполнился ли `userId` |
| 2 | `Auth → POST /auth/login` | `200` | Variables: `accessToken` заполнился сам |
| 3 | `Projects → POST /projects` | `201` | Variables: `projectId` заполнился сам |
| 4 | `Tasks → POST /tasks` | `201` | Variables: `taskId` заполнился сам. Посмотри тело запроса: откуда там `projectId` |
| 5 | `Tasks → GET /tasks/{taskId}` | `200` | `id` в ответе совпадает с `taskId` в Variables |

**Если регистрация ответила `409`.** В теле — фиксированный email `student@example.com`. Если его уже регистрировали на твоём стенде, сервер отвечает `409 EMAIL_ALREADY_EXISTS`: такой пользователь уже есть. Это ожидаемое поведение по разделу 6.1 спецификации, а не баг. Логин на шаге 2 всё равно пройдёт. Запиши, что `userId` в этом случае не обновился, и объясни почему — по скрипту запроса.

**Чтобы регистрация каждый раз проходила с `201`** — сделай уникальный email:

1. В запросе регистрации открой **Scripts → Pre-request** и сгенерируй email с отметкой времени в переменную коллекции `studentEmail` — как в теории.
2. В теле регистрации и логина замени email на <span v-pre>`{{studentEmail}}`</span>.
3. Прогони цепочку ещё раз. Ответь: почему нельзя было просто поставить <span v-pre>`{{$randomEmail}}`</span> в оба запроса?

### Шаг 4. Сравни с ручной работой

Запиши:

- на каком шаге ты впервые увидел на вкладке **Variables**, что переменная заполнилась сама;
- сколько **ручных копирований** понадобилось бы на этой же цепочке в `curl` или Swagger — токен в каждый запрос, `id` проекта в тело задачи, `id` задачи в адрес. Посчитай конкретным числом;
- сколько ручных копирований ты сделал в Postman.

### Шаг 5. Объясни скрипт

Открой скрипт после ответа у `POST /auth/login` — или у `POST /projects`, или у `POST /tasks`. Своими словами, без копирования кода:

- какое условие проверяется;
- что и куда сохраняется;
- что произойдёт с переменной, если запрос ответит ошибкой;
- это тест или нет? Почему?

## Часть 3. Свои тесты и data-driven (мидл)

Работай в **своей копии** коллекции: правая кнопка по коллекции → **Duplicate**. Оригинал не трогай.

### Шаг 1. Тесты на `POST /api/v1/projects`

В копии запроса `Projects → POST /projects` напиши тесты на вкладке **Scripts → Post-response**:

- код совпадает с ожидаемым;
- при успехе есть заголовок `Location`, и он указывает на созданный проект;
- `name` в ответе совпадает с тем, что ты отправил.

Ожидания бери из `docs/API_SPEC.md`: раздел 4 — про `201` и `Location`, раздел 6.3 — про проекты. Каждая проверка — в своём `pm.test`. Скрипт сохранения `projectId` из коллекции оставь — он понадобится в шаге 4.

Проверь, что тесты **умеют падать**: временно поменяй ожидаемый код на неправильный и убедись, что тест красный. Верни обратно.

### Шаг 2. Файл данных

Составь CSV на **6–8 строк** по разделу 6.3: границы длины `name` и `description`. Обязательная колонка — `expectedStatus`, ожидаемый код по спецификации. Образец формата — в теории, раздел «Runner и data-driven». Можешь взять его и дополнить: например, `description` не передано совсем.

Строки нужной длины собирай pre-request script, как в теории, — не вписывай 1000 символов в CSV руками.

### Шаг 3. Прогон

1. В своей копии создай папку «Проекты — данные» и перенеси в неё запрос `POST /projects` с тестами и pre-request script. Других запросов в папке пока нет: ни логина, ни чего-то ещё, что меняет `accessToken`.
2. Выполни логин отдельно, руками, — нужен свежий `accessToken`. Логин в папку **не клади**: тогда он выполнялся бы на каждой итерации, а вход ограничен 5 запросами за 60 секунд — раздел 6.1 спецификации. Шестой вход за минуту получит `429`.
3. Запусти Runner на папке «Проекты — данные» с файлом данных.
4. Если Runner в твоём плане Postman ограничен — экспортируй копию коллекции и прогони через Newman. Токен передай ключом `--env-var`:

```bash
npx newman run моя-коллекция.json --folder "Проекты — данные" -d projects.csv --env-var "accessToken=вставь_токен"
```

   Переменная из `--env-var` попадает в область Environment и перекрывает переменную коллекции — это области видимости из теории. Поэтому в папке не должно быть запросов, которые сами пишут `accessToken`.

5. Приложи скриншот результатов Runner или вывод Newman. Токен в выводе и на скриншоте — обрежь.

Для каждой строки, где фактический код **не совпал** с ожидаемым: перечитай раздел 6.3, проверь длину, которую реально собрал скрипт, и только потом делай вывод. Если расхождение подтвердилось — оформи баг-репорт по шаблону из урока [«Баг-репорт»](/osnovy/09-bag-report).

### Шаг 4. Побочный эффект: проект реально читается

`201` — это то, что сервер **сказал**. Проверь, что проект действительно есть — вторым запросом, как в уроке [«Тест-дизайн для API»](/api/09-test-dizayn-api).

1. Добавь в папку «Проекты — данные» после `POST /projects` запрос <span v-pre>`GET /api/v1/projects/{{projectId}}`</span>. Авторизация — тот же <span v-pre>`{{accessToken}}`</span>, запрос его только читает.
2. Тесты: код `200`; `id` и `name` совпадают с тем, что вернул `POST`.
3. Прогони папку ещё раз — Runner или Newman, как в шаге 3.
4. Подумай и запиши: что будет с этим запросом на строках, где `POST` должен ответить `422`? Какой `projectId` он возьмёт? Как сделать, чтобы `GET` не проверял чужой, старый проект? Подсказка — раздел «Ложно-зелёные тесты» в теории.

## На открытом проекте — альтернатива частям 2 и 3

Если TaskFlow запустить не получается, собери цепочку на **Restful Booker** — [документация](https://restful-booker.herokuapp.com/apidoc/index.html). Шаги проверены живыми запросами.

1. Создай в Postman коллекцию «Restful Booker» и переменную коллекции `baseUrl` = `https://restful-booker.herokuapp.com`.
2. <span v-pre>`POST {{baseUrl}}/auth`</span> с телом `{"username": "admin", "password": "password123"}`. Скрипт после ответа: при `200` сохранить `token` в переменную коллекции.
3. <span v-pre>`POST {{baseUrl}}/booking`</span> с заголовками `Content-Type: application/json`, `Accept: application/json` и телом:

```json
{
  "firstname": "Твоё редкое имя",
  "lastname": "Postman",
  "totalprice": 111,
  "depositpaid": true,
  "bookingdates": { "checkin": "2026-11-01", "checkout": "2026-11-05" },
  "additionalneeds": "Breakfast"
}
```

   Ответ — `200`, в теле `bookingid`. Скрипт: сохранить `bookingid` в переменную.

4. <span v-pre>`GET {{baseUrl}}/booking/{{bookingid}}`</span> с `Accept: application/json` — `200`. Тесты: имя и даты совпадают с отправленными.
5. <span v-pre>`PUT {{baseUrl}}/booking/{{bookingid}}`</span> с заголовком <span v-pre>`Cookie: token={{token}}`</span> и **полным** телом — поменяй цену и дату выезда. Ответ — `200`. Тест: в ответе новые значения. Потом убери cookie и отправь ещё раз — запиши код.
6. Прогони всё через Runner. Сделай data-файл на 3–4 строки с разными `firstname` и `totalprice` и прогони шаги 3–4 по нему.
7. В конце удали свои бронирования: <span v-pre>`DELETE {{baseUrl}}/booking/{{bookingid}}`</span> с той же cookie. Запиши код ответа и подумай, какой код ожидал бы по смыслу.

Что записать: скриншот прогона Runner, скрипты сохранения переменных, коды ответов на каждом шаге, ответ на вопрос про `PUT` без cookie и про код `DELETE`.

## Ситуационные кейсы

Это рабочие ситуации, о которых могут спросить и на собеседовании. Готового ответа, который нужно угадать, здесь нет. Сначала подумай сам, потом открывай разбор.

::: details Кейс 1. «Зачем Postman, если есть curl?»
**Ситуация.** Коллега видит, как ты импортируешь коллекцию: «Зачем вообще Postman? `curl` и так всё отправляет».

**Как рассуждать.** Может ли `curl` отправить то, что не может Postman? Что происходит **между** запросами в многошаговом сценарии? Как запросы живут через месяц и передаются коллегам?

**Пример ответа.** Коллега прав: по возможностям отправки разницы почти нет, `curl` отправит любой запрос. Разница — в работе вокруг запроса.

Первое — цепочки. Регистрация → логин → проект → задача: в `curl` после каждого шага я копирую токен или `id` руками. В Postman скрипт сохраняет значение в переменную, следующий запрос его берёт. Ноль копирований, меньше ошибок.

Второе — хранение и командная работа. Коллекция — файл в репозитории: папки, описания, примеры ответов, тесты. Через месяц ей воспользуется новый человек. Историю чужого терминала так не передашь.

Третье — прогон по данным и регресс: Runner или Newman прогоняет сотню запросов с проверками.

Но для одного быстрого запроса и для баг-репорта `curl` лучше: его выполнит любой разработчик без импорта. Это инструменты под разные задачи.
:::

::: details Кейс 2. Хитрый вопрос: «Postman Environment — это тестовое окружение?»
**Ситуация.** Интервьюер: «Вы пишете, что работали с окружениями в Postman. Расскажите, как вы их разворачивали».

**Как рассуждать.** Что такое Environment в Postman на самом деле? Можно ли в нём что-то «развернуть»? Как он связан со стендами?

**Пример ответа.** Это ловушка: в Postman окружения не разворачивают. Postman Environment — набор переменных: адрес стенда, логины тестовых пользователей, токены. Переключение Environment меняет только то, какие значения подставляются в запросы.

Тестовое окружение — живая система: сервер, база, конфигурация. Dev, stage, prod. Его разворачивают DevOps или пайплайн.

Связь в том, что `baseUrl` в Environment **указывает** на стенд. У меня было по одному Environment на стенд, с понятными именами, у prod — красный цвет и без рабочих токенов. Перед прогоном я проверяю, какой Environment выбран.
:::

::: details Кейс 3. Хитрый вопрос: «Все тесты в коллекции зелёные — фича работает?»
**Ситуация.** Интервьюер: «В пайплайне 150 тестов Postman, все зелёные. Можно выпускать?»

**Как рассуждать.** Что именно проверяют эти тесты? Может ли зелёный тест ничего не доказывать? Что не покрыто коллекцией вообще?

**Пример ответа.** Зелёные тесты говорят только то, что **проверенное** ими не сломалось. Я бы спросил, что они проверяют.

Типичные ложно-зелёные тесты: проверка только кода `200` при пустом или неверном теле; проверка вне `pm.test`, которая не попадает в сводку; сравнение `undefined` с `undefined`, когда поле переименовали; цепочка, где упавший шаг оставил старый `id`, и дальше всё проверяется на вчерашнем объекте.

Для важных тестов я задаю вопрос: «при каком баге он покраснеет?» И проверяю, что тест может упасть, — временно ломаю ожидание.

И второе: коллекция покрывает API, но не интерфейс, не интеграции, не новые сценарии фичи, для которых тесты ещё не написали. Зелёный регресс — необходимое условие для выпуска, но не достаточное.
:::

::: details Кейс 4. «Как передать токен между запросами, не копируя руками?»
**Ситуация.** Интервьюер: «У вас 30 запросов, все с авторизацией. Токен живёт час. Как организуете?»

**Как рассуждать.** Где хранить токен? Кто его туда кладёт? Как не прописывать его в каждом запросе? Что будет, когда он истечёт?

**Пример ответа.** Токен — в переменной, например `accessToken`. Его кладёт скрипт после запроса логина: проверяет код в `pm.test` и сохраняет поле из тела ответа через `pm.collectionVariables.set` или `pm.environment.set`.

Чтобы не прописывать заголовок в 30 запросах, ставлю на коллекции авторизацию **Bearer Token** со значением <span v-pre>`{{accessToken}}`</span>, а в запросах — **Inherit auth from parent**. Для запросов от другой роли — своя авторизация на папке.

Для истечения: логин — первым запросом в прогоне Runner. Или pre-request скрипт на коллекции, который получает новый токен через `pm.sendRequest`, если старого нет или он истёк.

И гигиена: токен — только в current value, в экспорт и репозиторий он не уходит.
:::

::: details Кейс 5. «Как прогнать один запрос на 50 наборах данных?»
**Ситуация.** Интервьюер: «Нужно проверить создание пользователя на 50 комбинациях полей. Будете отправлять 50 раз руками?»

**Как рассуждать.** Как отделить запрос от данных? Где хранить ожидание для каждой строки? Как не замусорить стенд?

**Пример ответа.** Нет. Это data-driven прогон: запрос описан один раз, данные — в CSV или JSON-файле.

В файле — колонки с полями и колонка `expectedStatus` — ожидаемый код для строки. В запросе — переменные <span v-pre>`{{email}}`</span>, <span v-pre>`{{age}}`</span> из файла. В тесте ожидание тоже берётся из строки: `pm.iterationData.get('expectedStatus')`. Запускаю в Runner или через Newman с ключом `-d`.

Сами 50 строк — не случайные, а по классам эквивалентности и границам. Возможно, их окажется не 50, а 25.

И чистка: создаваемые пользователи — с префиксом `autotest_`, после прогона — удаление. На общем стенде 50 мусорных пользователей мешают коллегам.
:::

::: details Кейс 6. Хитрый вопрос: «Как отдать разработчику воспроизведение бага с API?»
**Ситуация.** Интервьюер: «Вы нашли баг в API. Что приложите к баг-репорту, чтобы разработчик воспроизвёл его за минуту?»

**Как рассуждать.** Какой формат запроса можно выполнить сразу, без настройки? Что в нём опасного? Что ещё нужно, чтобы найти запрос в логах?

**Пример ответа.** Главное — команду `curl`: метод, адрес, заголовки, тело. Её дают Swagger, DevTools через Copy as cURL и Postman через **Code**. Разработчик вставит её в терминал и увидит то же, что я.

Перед вставкой — вычищаю секреты. Токен заменяю на `…` или пишу, под каким тестовым пользователем воспроизводить. Пароли в теле — тоже. Тикет читает много людей, а токен — рабочий ключ.

К команде — фактический ответ текстом: код, тело, `X-Request-ID` — по нему разработчик найдёт запрос в логах. Время с часовым поясом, стенд, версия сборки. Скриншот Postman — по желанию, для наглядности, но не вместо команды.

Если коллекция команды лежит в репозитории — указываю имя запроса в ней.
:::

::: details Кейс 7. Хитрый вопрос: «В Postman 200, у коллеги тот же запрос — 401. Что проверишь?»
**Ситуация.** Интервьюер: «Вы и коллега отправляете вроде бы один и тот же запрос из одной коллекции. У вас `200`, у него `401`. С чего начнёте?»

**Как рассуждать.** Что в «том же запросе» может отличаться? Где Postman берёт значения переменных? Что должно быть одинаковым, чтобы сравнение было честным?

**Пример ответа.** Начну со сравнения того, что **реально** ушло на сервер, а не того, что видно в окне запроса.

1. **Токен.** У коллеги своё current value. Возможно, он не выполнил логин, токен истёк или скрипт не обновил переменную, потому что логин упал.
2. **Область переменной.** У него `accessToken` может быть задан ещё и в Environment или Global — и побеждает старое значение. Наведу курсор на <span v-pre>`{{accessToken}}`</span> и посмотрю, откуда оно.
3. **Environment.** Выбран другой — запрос идёт на другой стенд, где этого пользователя нет или другой секрет подписи токенов.
4. **Авторизация.** В запросе стоит **Inherit auth**, а у него на папке другая настройка. Или заголовок задан и вручную, и через вкладку Authorization.

Чтобы сравнить точно, мы оба откроем **Postman Console** — там видно фактические заголовки и адрес. Или скопируем запрос как `curl` и сравним команды, без токена в чате.
:::
