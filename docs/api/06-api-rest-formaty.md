## Простыми словами

Ты пришёл в ресторан. На кухню тебя не пустят, и знать, как там устроены плиты, тебе не нужно. У тебя есть **меню**: в нём написано, что можно заказать, из чего это блюдо и сколько оно стоит. Ты заказываешь «пасту карбонара» — и кухня обещает, что принесут именно её, а не «что-то похожее».

**API** — такое же меню, только для программ. Одна программа не лезет внутрь другой, а заказывает по списку: «дай проект 42», «создай комментарий». А вторая обещает, что ответит именно так, как написано в меню: с этими полями, в этом формате, с этими кодами.

Ты работаешь с API с самого начала курса: каждый запрос в Swagger TaskFlow — это заказ по меню. В этом уроке разберём:

- что такое API и почему тестировщику он важнее интерфейса;
- **REST** — самый частый стиль веб-API, и чем от него отличаются SOAP, GraphQL и gRPC;
- **форматы данных** — JSON и XML — и ловушки, на которых ломаются настоящие продукты;
- для мидла — **API как контракт**: OpenAPI и Swagger, версии и изменения, которые ломают старых клиентов.

## Что такое API

**API** — Application Programming Interface, программный интерфейс. Это договорённость о том, как одна программа может обращаться к другой: какие запросы можно отправить, что в них передать и что придёт в ответ.

У человека интерфейс — экран с кнопками. У программы интерфейс — API: кнопок нет, есть запросы и ответы по правилам.

### Не только веб

Слово «API» шире, чем «запросы по сети». API есть у библиотеки — набор функций, которые можно вызвать из своего кода. API есть у операционной системы — так программа просит открыть файл или показать уведомление. API есть у браузера — так сайт просит доступ к камере или геолокации.

В этом курсе и почти всегда в работе тестировщика речь о **веб-API** — API, к которому обращаются по сети, чаще всего по HTTP. Именно его ты видишь во вкладке Network и в Swagger.

### Кому открыт API

| Вид | Кто пользуется | Пример | Что важно |
|---|---|---|---|
| **Публичный** | Кто угодно, часто после регистрации ключа | API погоды, карт, платёжных систем для магазинов | Документация для чужих людей, лимиты запросов, обратная совместимость: клиентов не знаешь в лицо |
| **Партнёрский** | Конкретные компании по договору | Магазин передаёт заказы службе доставки, банк — данные в бюро кредитных историй | Строгий контракт, часто в договоре. Изменения согласуют заранее |
| **Внутренний** | Свои же приложения и сервисы | Фронтенд TaskFlow и его бэкенд, мобильное приложение и сервер | «Свои» — не значит «можно ломать»: старые версии мобильного приложения тоже клиенты |

### Почему тестировщику API важнее интерфейса

Интерфейс — только один из клиентов API. Под ним — сервер, и все важные правила живут там.

- **Быстрее.** Создать проект через API — один запрос. Через интерфейс — открыть страницу, заполнить форму, нажать кнопку. Для проверки сотни комбинаций данных разница огромная.
- **Раньше.** API часто готов раньше экранов. Тестировщик начинает проверять логику, пока фронтенд ещё рисуют.
- **Глубже.** Через API можно отправить то, что интерфейс не даёт: пустое поле, строку вместо числа, 10 000 символов, чужой `id`. Именно так находят самые серьёзные баги.
- **Интерфейс может прятать баги сервера.** Форма не даёт ввести возраст меньше 18 — а сервер принимает 12. Ты видел этот пример в уроке [«Клиент-сервер и URL»](/api/01-klient-server-i-url): проверка только на клиенте — не защита. Обойти интерфейс может старая версия приложения, другой клиент или злоумышленник с Postman.

Это не значит, что интерфейс тестировать не нужно. Но если проверять только его, половина багов сервера останется незамеченной.

## REST

### Архитектурный стиль, а не протокол

**REST** — Representational State Transfer, «передача состояния представления». Это **архитектурный стиль** — набор принципов, как строить API. Его описал Рой Филдинг в своей диссертации в 2000 году.

REST — **не протокол**. Протокол — это точные правила обмена: какие байты в каком порядке. HTTP — протокол. У REST нет своего формата сообщений, нет стандарта, нет версии. REST говорит: «строй API вокруг ресурсов, пользуйся стандартными методами, не храни состояние клиента на сервере». А как именно — решает команда.

Почти всегда REST API работают поверх HTTP. Но «REST» и «HTTP» — не синонимы: HTTP — дорога, REST — правила, как по ней ездить.

Это любимый вопрос собеседований: «REST — это протокол?» Правильный ответ — нет, стиль. Подробно — в кейсе на вкладке «Вопросы».

### Ресурсы: URL — существительные

Главная идея REST — **ресурс**. Ресурс — это «вещь», о которой говорит API: проект, заказ, пользователь, комментарий. У каждого ресурса есть адрес — URL.

В хорошем REST API в адресе — **существительные**, а действие задаёт **метод**:

| Не по REST | По REST | Почему |
|---|---|---|
| `GET /getProject?id=42` | `GET /projects/42` | Действие «получить» уже в методе `GET`. Адрес называет ресурс |
| `POST /createProject` | `POST /projects` | Создание — это `POST` в коллекцию |
| `POST /projects/42/delete` | `DELETE /projects/42` | Для удаления есть свой метод |
| `GET /project_list` | `GET /projects` | Коллекция — существительное во множественном числе |

Принятые договорённости:

- существительные во **множественном числе**: `/projects`, а не `/project`;
- **строчные буквы**, слова через дефис: `/order-items`, а не `/OrderItems`;
- без расширений файлов: `/projects/42`, а не `/projects/42.json` — формат задаёт заголовок `Accept`, урок [«HTTP: запрос и ответ»](/api/03-http-zapros-i-otvet).

### Коллекция и элемент

У ресурса обычно два адреса:

- **коллекция** — все ресурсы этого типа: `/projects`;
- **элемент** — один ресурс по его `id`: `/projects/42`.

| Запрос | Что делает |
|---|---|
| `GET /projects` | Получить список проектов |
| `POST /projects` | Создать новый проект в коллекции |
| `GET /projects/42` | Получить проект 42 |
| `PATCH /projects/42` | Изменить часть полей проекта 42 |
| `DELETE /projects/42` | Удалить проект 42 |

Пять действий — два адреса. Зная это правило, ты угадываешь адреса незнакомого API ещё до того, как открыл документацию.

### Вложенные ресурсы

Если ресурс живёт **внутри** другого, адрес это показывает:

- `/projects/42/members` — участники проекта 42;
- `/projects/42/members/7` — участник с `id` 7 в проекте 42.

Вложенность полезна, когда ресурс без родителя не имеет смысла: участник существует только в рамках проекта. Но глубокая вложенность — `/companies/1/projects/42/tasks/5/comments/9` — неудобна. Обычно останавливаются на одном-двух уровнях.

Что проверяет тестировщик во вложенных ресурсах:

- существующий элемент в **чужом** родителе: участник 7 есть в проекте 42, а ты запрашиваешь `/projects/43/members/7`. Ответ должен быть «не найдено», а не данные участника из другого проекта;
- несуществующий родитель: `/projects/999/members` — `404`, а не пустой список. Помнишь правило из урока [«Коды ответа»](/api/05-kody-otveta)?

### Методы — глаголы, коды — результат

В REST действие над ресурсом выражается **методом HTTP**: `GET` читает, `POST` создаёт, `PUT` и `PATCH` изменяют, `DELETE` удаляет. Подробно, вместе с идемпотентностью, — в уроке [«Методы HTTP и идемпотентность»](/api/04-metody-http).

Результат выражается **кодом ответа**: `201` — создано, `404` — нет такого, `422` — данные не прошли проверку. Об этом — урок [«Коды ответа»](/api/05-kody-otveta).

### Stateless — без состояния

Сервер **не помнит клиента** между запросами. Каждый запрос самодостаточен: всё, что нужно для ответа, — в нём самом, в том числе токен. Ты разбирал это свойство в уроке [«HTTP: запрос и ответ»](/api/03-http-zapros-i-otvet).

Частая путаница: «stateless — значит, сервер ничего не хранит». Нет. Проекты, задачи и пользователи лежат в базе — это данные, они хранятся. Stateless — про то, что сервер не держит в памяти **сессию разговора** с конкретным клиентом. Запрос без токена — запрос незнакомца, даже если секунду назад этот же клиент входил.

Зачем так сделали: любой запрос можно отправить на любой из десяти серверов за балансировщиком, и он будет обработан одинаково. Это и есть масштабирование.

### Шесть ограничений Филдинга

Строго говоря, REST — это шесть ограничений. Знать их наизусть джуну не обязательно, но на собеседовании на мидла их иногда просят перечислить:

1. **Клиент-сервер.** Интерфейс и данные разделены: клиент отвечает за показ, сервер — за хранение и правила.
2. **Stateless.** Сервер не хранит состояние клиента между запросами.
3. **Кэшируемость.** Ответ должен говорить, можно ли его кэшировать и сколько, — заголовки `Cache-Control`, `ETag`.
4. **Единый интерфейс.** Ресурсы с адресами, стандартные методы, понятные представления. Это то, что делает все REST API похожими друг на друга.
5. **Слоистая система.** Клиент не знает, говорит он с самим сервером или с прокси, балансировщиком, кэшем между ними.
6. **Код по требованию** — необязательное. Сервер может прислать клиенту код для выполнения, например JavaScript.

### RESTful и REST-like

Большинство API, которые называют себя REST, соблюдают не все ограничения. Поэтому иногда различают:

- **RESTful** — API, которое строго следует REST;
- **REST-like** — «в духе REST»: ресурсы, методы, JSON, но без части ограничений.

На практике почти все «REST API» — REST-like, и это нормально. Тестировщику не нужно спорить о чистоте стиля. Важно, чтобы API было **последовательным** и совпадало со своей спецификацией.

### Для мидла: HATEOAS и модель зрелости Ричардсона

**HATEOAS** — Hypermedia as the Engine of Application State. Идея: ответ содержит не только данные, но и **ссылки** на то, что можно сделать дальше:

```json
{
  "id": 42,
  "status": "ACTIVE",
  "links": {
    "self": "/projects/42",
    "members": "/projects/42/members",
    "archive": "/projects/42/archive"
  }
}
```

Клиент не собирает адреса сам, а идёт по ссылкам из ответа. Если проект уже в архиве, ссылки `archive` в ответе не будет. Красиво, но в жизни встречается редко.

**Модель зрелости Ричардсона** — способ сказать, «насколько REST» данный API. Четыре уровня:

| Уровень | Что есть | Пример |
|---|---|---|
| 0 | Один адрес, всё через `POST`, действие в теле | SOAP, RPC через `POST /api` |
| 1 | Отдельные адреса для ресурсов | `/projects/42`, но всё равно всё через `POST` |
| 2 | Ресурсы + правильные методы и коды | `GET`, `POST`, `PATCH`, `DELETE`, `201`, `404` — большинство современных API, в том числе TaskFlow |
| 3 | Уровень 2 + HATEOAS | Ссылки на действия в ответах |

На собеседовании достаточно сказать: «большинство API на уровне 2, уровень 3 — редкость».

### SOAP

**SOAP** — Simple Object Access Protocol. В отличие от REST, это **протокол** — со своим стандартом. Каждое сообщение — XML-«конверт» `Envelope`, внутри — необязательный `Header` и обязательный `Body`:

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <GetBalance xmlns="http://bank.example.ru/accounts">
      <accountNumber>40817810000000000001</accountNumber>
    </GetBalance>
  </soap:Body>
</soap:Envelope>
```

- Действие — `GetBalance` — записано **в теле**, а не в адресе и не в методе. Это RPC-стиль, ты встречал его в уроке [«Методы HTTP»](/api/04-metody-http), раздел «Методы не всегда работают классически».
- Контракт описан в **WSDL** — XML-файле со списком операций, параметров и типов. По нему инструменты сами строят запросы. Для ручного тестирования SOAP обычно берут **SoapUI** или Postman.
- Ошибка — элемент `soap:Fault` в теле. По стандарту SOAP 1.1 вместе с ним приходит код `500`, даже если ошибся клиент.

SOAP многословный и тяжёлый, но строгий. Поэтому он живёт там, где строгость важнее удобства и где системы работают десятилетиями.

### GraphQL

**GraphQL** — язык запросов к API. Один адрес, обычно `POST /graphql`, а в теле клиент пишет, **какие именно поля** ему нужны:

```graphql
query {
  project(id: 42) {
    name
    members { firstName role }
  }
}
```

Ответ придёт ровно с этими полями — ни больше ни меньше. В REST для этого понадобились бы два запроса: проект и его участники.

Что тестировать в GraphQL:

- **ошибки внутри `200`** — ответ приходит с кодом `200`, а ошибки лежат в массиве `errors` рядом с `data`. Смотреть только на код бесполезно. Об этом — в уроках [«Методы HTTP»](/api/04-metody-http) и [«Коды ответа»](/api/05-kody-otveta);
- **глубина и сложность запроса** — клиент может попросить проект → участников → их проекты → их участников… Без ограничения такой запрос положит сервер;
- **права на уровне полей** — пользователь может запросить любое поле схемы. Сервер должен проверять права на каждое поле, а не только на весь запрос: например, email участников видят не все.

### gRPC

**gRPC** — способ вызывать функции другого сервиса, как свои. Работает поверх HTTP/2, данные — в формате **protobuf**: компактный бинарный формат, его не прочитать глазами. Контракт — файл `.proto` с описанием функций и сообщений.

Где встречается: общение микросервисов внутри компании, где важна скорость. В браузере почти не встречается. Тестировщику нужен специальный клиент: Postman умеет работать с gRPC, есть и консольные утилиты. Подробнее о микросервисах — в уроке [«Монолит, микросервисы, интеграции»](/api/11-monolit-mikroservisy).

## Форматы данных

Ресурс на сервере — запись в базе. Клиенту отправляется его **представление** — текст в каком-то формате. Какой формат в теле, говорит заголовок `Content-Type`, урок [«HTTP: запрос и ответ»](/api/03-http-zapros-i-otvet).

### JSON

**JSON** — JavaScript Object Notation. Самый распространённый формат веб-API. В нём **шесть типов** значений:

| Тип | Пример | Важно |
|---|---|---|
| **string** — строка | `"Сайт"` | Только в **двойных** кавычках |
| **number** — число | `42`, `-1.5`, `1e3` | Без кавычек. Целых и дробных отдельно нет — просто «число» |
| **boolean** — логическое | `true`, `false` | Без кавычек, строчными буквами |
| **null** — «нет значения» | `null` | Без кавычек. Это не `"null"` и не `""` |
| **object** — объект | `{"id": 42}` | Пары «ключ: значение». Ключ — всегда строка в двойных кавычках |
| **array** — массив | `[1, 2, 3]` | Упорядоченный список любых значений |

Все шесть — в одном ответе TaskFlow на `GET /api/v1/projects?limit=1`:

```json
{
  "items": [
    {
      "id": 42,
      "name": "Сайт",
      "description": null,
      "status": "ACTIVE",
      "ownerId": 7
    }
  ],
  "total": 3,
  "limit": 1,
  "offset": 0,
  "hasNext": true
}
```

- весь ответ — **object**;
- `items` — **array** из объектов-проектов;
- `id`, `total`, `limit`, `offset`, `ownerId` — **number**;
- `name`, `status` — **string**. `status` — строка из фиксированного списка, такой список называют **enum**;
- `description` — **null**: у проекта нет описания;
- `hasNext` — **boolean**: есть ли следующая страница.

Чего в JSON **нет**: комментариев, одинарных кавычек, запятой после последнего элемента, дат, отдельного типа для денег. Последние два пункта — источник целого класса багов.

### Ловушки JSON

Это главный раздел про форматы. Каждая ловушка — реальный класс багов.

**Число против строки.** `"id": 42` и `"id": "42"` — разные типы. Клиент на JavaScript сложит `"42" + 1` и получит `"421"`, а не `43`. Клиент на строго типизированном языке — Kotlin, Swift — просто упадёт, не сумев разобрать ответ. Проверяй **тип** каждого поля, а не только значение.

**`null`, отсутствующее поле и пустая строка — три разные вещи.**

| Что пришло | Что это значит обычно |
|---|---|
| `"description": null` | Поле есть, значения нет |
| поля `description` нет вообще | Сервер его не прислал: не положено, не знает или забыл |
| `"description": ""` | Значение есть, и это пустая строка |

Особенно важно в запросах на изменение. В `PATCH` `{"description": null}` обычно значит «стереть описание», а `{}` — «ничего не менять». Если сервер путает эти случаи, описание пропадёт у того, кто менял только название. Об этом — урок [«Методы HTTP»](/api/04-metody-http), раздел про `PUT` и `PATCH`.

**Большие числа.** В JavaScript все числа — дробные, и целые числа точны только до 2^53 − 1 = `9007199254740991`. Больше — начинается округление:

```js
JSON.parse('{"id": 9007199254740993}').id
// 9007199254740992 — на единицу меньше
```

Сервер на Java или Go спокойно хранит `id` до 2^63. Браузер получает такой `id`, округляет — и следующим запросом просит **другой** ресурс. Поэтому большие `id` часто передают строкой: например, API Twitter отдавал рядом с числовым `id` строковый `id_str` именно по этой причине.

**Даты.** В JSON нет типа «дата» — дату пишут строкой. Договорённость — формат **ISO 8601**:

- `2026-10-14T09:12:05Z` — `Z` значит UTC;
- `2026-10-14T12:12:05+03:00` — тот же момент, по Москве.

А вот `2026-10-14T09:12:05` **без пояса** — это неизвестно какое время: по UTC? по серверу? по пользователю? И совсем плохо — `14.10.2026`: формат зависит от страны, `03.04` в России — 3 апреля, в США — 4 марта. Проверяй, что все даты в API в одном формате и с поясом.

**Деньги — не float.** Дробные числа в компьютере хранятся приблизительно:

```js
0.1 + 0.2
// 0.30000000000000004
```

На одной операции ошибка незаметна. На миллионе операций — копейки, которые не сходятся в отчёте. Деньги передают **целым числом в минимальных единицах** — `1999` копеек вместо `19.99` рублей — или **строкой** `"19.99"`, которую сервер считает точной десятичной арифметикой. Рядом обычно указывают валюту: `"currency": "RUB"`.

**Регистр ключей и стиль имён.** `ownerId`, `OwnerId` и `owner_id` — три **разных** ключа. Клиент, который ждёт `ownerId`, не найдёт `owner_id` и покажет пустое место. Стили:

- **camelCase** — `ownerId`, `hasNext`. Принят в JSON-API, в том числе в TaskFlow;
- **snake_case** — `owner_id`. Частый в Python и базах данных;
- **PascalCase** — `OwnerId`. Встречается в API на C#.

Ошибка — не выбор стиля, а **смесь** стилей в одном API: часть полей `camelCase`, часть `snake_case`. Так бывает, когда поле забыли переименовать между базой и ответом.

**Порядок ключей не важен.** `{"id": 1, "name": "A"}` и `{"name": "A", "id": 1}` — один и тот же объект. Если тест сравнивает ответ как строку и падает из-за порядка — проблема в тесте, а не в API. А вот порядок элементов **в массиве** важен: это порядок сортировки.

**Вложенность.** Поле может быть объектом внутри объекта: `{"owner": {"id": 7, "name": "Анна"}}`. Проверяй вложенные поля так же внимательно, как верхние. Типичный баг: вложенный объект `null`, а клиент обращается к `owner.name` и падает.

**Пустой массив против `null`.** У проекта нет участников: `"members": []` или `"members": null`? Договорённость почти везде — **пустой массив**. Клиент перебирает элементы `[]` и ничего не показывает, а на `null` — падает. Если API отдаёт то `[]`, то `null` — это баг.

**Кодировка и эмодзи.** JSON передают в **UTF-8**. Кириллица и эмодзи должны приходить без искажений — не `Ð¡Ð°Ð¹Ñ‚` вместо «Сайт». Отдельная тонкость — длина. Эмодзи 👍 — один видимый символ, но в UTF-8 это 4 байта, а JavaScript считает его длину как 2. Если фронтенд и бэкенд считают длину по-разному, ограничение «не больше 100 символов» срабатывает в разных местах. Проверяй граничные длины и с кириллицей, и с эмодзи.

### XML

**XML** — eXtensible Markup Language. Данные в тегах, как в HTML:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project id="42">
  <name>Сайт</name>
  <description xsi:nil="true" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"/>
  <status>ACTIVE</status>
  <ownerId>7</ownerId>
</project>
```

- **Элементы** — `<name>Сайт</name>`: открывающий и закрывающий тег, значение между ними.
- **Атрибуты** — `id="42"` внутри тега. Одни и те же данные можно записать и атрибутом, и элементом. Единого правила нет — как решит автор API.
- **Типов нет** — всё текст. Что `<ownerId>7</ownerId>` — число, знает только схема: файл **XSD**.
- **`null` нет.** Его изображают пустым элементом `<description/>`, атрибутом `xsi:nil="true"` или просто не присылают элемент. Пустая строка и «нет значения» легко путаются.
- **Пространства имён** — namespace, `xmlns`. Это способ различать элементы с одинаковыми именами из разных словарей: `<m:name>` — имя из одного словаря, `<p:name>` — из другого.

| | JSON | XML |
|---|---|---|
| Объём | Компактный | Многословный: каждое значение обёрнуто в два тега |
| Читаемость | Легко читать глазами | Читается, но тяжелее |

| Массивы | Есть `[...]` | Повторяющиеся элементы, способ записи выбирает автор |
| Атрибуты | Нет | Есть |
| Пространства имён | Нет | Есть |
| Комментарии | Нет | Есть |
| Описание структуры | JSON Schema, OpenAPI | XSD, WSDL |
| Где встречается | Веб, мобильные приложения, большинство новых API | SOAP, банки, госсистемы, документы, конфиги |

### Другие форматы — одной строкой

- **YAML** — читаемый формат с отступами вместо скобок. Конфигурации и описания API: OpenAPI часто пишут на YAML.
- **CSV** — таблица в тексте, значения через запятую или точку с запятой. Выгрузки в Excel, импорт данных.
- **protobuf** — бинарный формат gRPC. Компактный и быстрый, но глазами не читается.
- **form-data** — `application/x-www-form-urlencoded` и `multipart/form-data`: формы и загрузка файлов, урок [«HTTP: запрос и ответ»](/api/03-http-zapros-i-otvet).

## Swagger и OpenAPI: API как контракт

Это главная часть урока для мидла.

**Контракт** — документ, в котором записано, как API обязан себя вести: какие адреса, какие поля в запросе и ответе, каких типов, какие обязательны, какие коды в каких случаях. Клиенты — фронтенд, мобильное приложение, партнёры — пишут свой код по контракту. Если сервер нарушает контракт, ломаются они.

### OpenAPI и Swagger — не одно и то же

- **OpenAPI** — **спецификация**, то есть стандарт: как в формате YAML или JSON описать REST API. Сейчас актуальны версии 3.0 и 3.1.
- **Swagger** — **инструменты** вокруг этого стандарта: **Swagger UI** — страница, где описание API можно читать и отправлять запросы; **Swagger Editor** — редактор описаний.

Путаница историческая: раньше сам стандарт назывался Swagger Specification. В 2016 году его передали независимому сообществу и переименовали в OpenAPI. Версия 2.0 так и осталась «Swagger 2.0», с версии 3.0 — «OpenAPI 3.0». Поэтому в старых документах `swagger: "2.0"`, в новых — `openapi: 3.0.x` или `3.1.x`.

На собеседовании правильный ответ: «OpenAPI — стандарт описания, Swagger — набор инструментов для него».

### Из чего состоит описание

Вот небольшой фрагмент описания на OpenAPI 3.0 — вымышленный магазин, создание заказа:

```yaml
openapi: 3.0.3
info:
  title: Shop API
  version: 1.4.0
paths:
  /orders:
    post:
      summary: Создать заказ
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/OrderCreate'
      responses:
        '201':
          description: Заказ создан
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Order'
        '422':
          description: Ошибка в данных
  /orders/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
components:
  schemas:
    OrderCreate:
      type: object
      required: [productId, quantity]
      properties:
        productId:
          type: integer
        quantity:
          type: integer
          minimum: 1
          maximum: 99
        comment:
          type: string
          maxLength: 500
          nullable: true
        email:
          type: string
          format: email
    Order:
      type: object
      required: [id, status, createdAt]
      properties:
        id:
          type: string
          format: uuid
        status:
          type: string
          enum: [NEW, PAID, SHIPPED]
        createdAt:
          type: string
          format: date-time
```

Что здесь важно тестировщику:

| Элемент | Что значит | Что проверять |
|---|---|---|
| `paths` | Список адресов и методов | Все ли эндпоинты из требований описаны. Нет ли лишних, о которых никто не знает |
| `parameters` | Параметры в пути, query, заголовках. `in: path` — часть адреса | Обязательность, тип: что будет, если вместо числа передать `abc` |
| `requestBody` | Тело запроса и его схема | Обязательные поля, типы, ограничения |
| `responses` | Какие коды и с каким телом возможны | Совпадает ли факт: код и схема тела |
| `components/schemas` | Общие схемы, на них ссылаются через `$ref` | Один раз описанная схема используется во многих местах — ошибка в ней тоже везде |
| `required` | Список обязательных полей | Запрос без каждого из них. В ответе — что эти поля приходят всегда |
| `type` | `string`, `integer`, `number`, `boolean`, `array`, `object` | Что приходит именно этот тип: `42`, а не `"42"` |
| `enum` | Список допустимых значений | Значение не из списка в запросе, и что в ответе только значения из списка |
| `minLength` / `maxLength` | Длина строки | Границы: 0, 1, max, max+1 |
| `minimum` / `maximum` | Диапазон числа | Границы: min−1, min, max, max+1 |
| `format` | Уточнение формата строки: `date-time`, `email`, `uuid` | Что даты в ISO 8601, email похож на email, `uuid` — настоящий UUID |
| `nullable` | Может ли значение быть `null` | Что клиент готов к `null` в этом поле, и что `null` не приходит там, где запрещён |

**`nullable` в разных версиях.** В OpenAPI 3.0 пишут `nullable: true`. В 3.1 такого ключа нет — `null` указывают как ещё один допустимый тип: `type: [string, "null"]` или вариантом в `anyOf`. Смысл одинаковый: «здесь может быть строка или `null`».

**`required` и `nullable` — разные вещи.** `required` — **есть ли ключ** в объекте. `nullable` — **может ли значение быть `null`**. Поле может быть обязательным и при этом `null`: ключ всегда есть, а значения может не быть. Вспомни ловушку «`null` против отсутствия».

### Как читать схему в Swagger UI

У тела запроса и у каждого ответа в Swagger UI есть две вкладки:

- **Example Value** — **пример** JSON. Удобно, чтобы скопировать и отправить. Но пример показывает только одно возможное значение: из него не видно, какие поля обязательны, какие ограничения по длине и может ли поле быть `null`.
- **Schema** — **сама схема**: поля, типы, обязательность — обязательные поля отмечены звёздочкой, — ограничения, `enum`, допустимость `null`. Раскрывай вложенные объекты стрелками.

Правило: для работы — Example Value, для тест-дизайна — **Schema**. Внизу страницы Swagger UI есть раздел **Schemas** — там все схемы из `components/schemas` в одном месте.

### Code-first и design-first

Описание API появляется одним из двух способов:

- **Code-first** — «сначала код». Разработчики пишут сервер, а описание OpenAPI **генерируется из кода** автоматически. Так работают FastAPI, на котором написан TaskFlow, Spring с библиотекой springdoc и другие фреймворки. Плюс — описание всегда совпадает с кодом. Минус — оно описывает то, что **сделали**, а не то, что **должны были** сделать. Если в коде ошибка — описание её честно повторит.
- **Design-first** — «сначала контракт». Команда сначала пишет и согласует описание OpenAPI, потом по нему пишут сервер и клиентов. Плюс — фронтенд и бэкенд работают параллельно, тестировщик готовит проверки до появления кода. Минус — описание и код могут разойтись, если не проверять соответствие.

### «Документация врёт»

У многих проектов **два** описания API:

- **текстовое** — ТЗ, страница в Confluence, `docs/API_SPEC.md`. Его пишут люди: аналитик, архитектор;
- **автоматическое** — OpenAPI, которое сгенерировал фреймворк.

Они легко расходятся. В ТЗ поле обязательное, а в схеме — нет. В ТЗ лимит 100 символов, в схеме — 255. В ТЗ описан формат ошибок, а в схеме — формат по умолчанию от фреймворка. Сгенерированная схема показывает, как написан **код**, а не как задумано.

Какой документ «правда» — решает не тестировщик, а **договорённость команды**. Чаще всего источником истины считают текстовую спецификацию или согласованный контракт. У TaskFlow так и написано в начале `docs/API_SPEC.md`: при расхождении поведения и документа прав документ. А сгенерированный `/openapi.json` — описание того, что сделано.

Что делает тестировщик, когда видит расхождение:

1. Фиксирует оба места: «в спецификации — так, в Swagger — так, по факту — так».
2. Не решает сам, кто прав, а задаёт вопрос: аналитику, если непонятно, что задумано; разработчику, если задумано ясно, а код другой.
3. После ответа — баг на код или задача на исправление документа. Расхождение двух документов — само по себе находка: кто-то из клиентов уже пишет код по «неправильному».

### Контрактное тестирование — идея

**Контрактное тестирование** — автоматическая проверка, что ответы API совпадают с контрактом: все обязательные поля на месте, типы верные, значения из `enum`. Такие проверки запускают на каждой сборке, и ломающее изменение ловится до релиза. Инструменты, названия которых стоит знать: **Pact** — контракт между конкретным клиентом и сервером, **Schemathesis** — генерирует запросы по OpenAPI и проверяет ответы.

Ручному тестировщику это знание пригодится, чтобы понимать, что уже проверяет автоматизация, а что — нет.

## Версионирование и обратная совместимость

API живёт годами и меняется. Но клиенты обновляются не одновременно с сервером. Отсюда главный вопрос мидла: **сломает ли это изменение тех, кто уже пользуется API?**

### Где живёт версия

| Где | Пример | Что важно |
|---|---|---|
| В адресе | `/api/v1/projects`, `/api/v2/projects` | Самый частый и наглядный способ. Так у TaskFlow |
| В заголовке | `Accept: application/vnd.shop.v2+json` или свой `API-Version: 2` | Адрес не меняется. В Network версию видно только в заголовках |
| В query-параметре | `/projects?version=2` | Встречается реже. Легко забыть параметр — и получить версию по умолчанию |

Версию меняют, когда изменение **ломает** старых клиентов. Неломающие изменения выпускают в той же версии.

**Ломают старых клиентов:**

- **удалить или переименовать поле** — `phone` → `phoneNumber`. Старый клиент ищет `phone`, не находит, показывает пустое место или падает;
- **сменить тип** — `id` был числом, стал строкой. Строго типизированный клиент не разберёт ответ;
- **сделать поле запроса обязательным** — старый клиент его не присылает и получает `422`;
- **сменить формат даты** — был `2026-10-14T09:00:00Z`, стал `14.10.2026`. Клиент не разберёт;
- **сменить код ответа** — был `200`, стал `201` или `204`. Клиент, который проверяет «ровно 200», решит, что произошла ошибка. А `204` ещё и без тела;
- **сузить `enum` или лимит** — убрали значение, которое клиенты уже присылают; уменьшили `maxLength` со 100 до 50. Старые клиенты начнут получать `422`, а уже сохранённые длинные значения — неожиданно не проходить при редактировании.

**Обычно не ломают:**

- **добавить необязательное поле** в запрос или новое поле в ответ — старый клиент его просто не заметит. Если клиент написан правильно и не падает на незнакомых полях;
- **добавить новый эндпоинт** — старые клиенты о нём не знают;
- **расширить лимит** — было до 100 символов, стало до 200. Но проверь, что клиенты, которые **показывают** это поле, не ломают вёрстку на длинных значениях.

**Новое значение `enum` — «зависит».** Статусы заказа были `NEW`, `PAID`, `SHIPPED`, добавили `REFUNDED`. Формально контракт расширился, а не изменился. Но если в мобильном приложении написано «статус может быть только одним из трёх» и нет ветки «неизвестный статус», — экран упадёт. Хорошая практика — клиенты обрабатывают неизвестное значение: показывают как есть или как «другое». Плохая — узнавать об этом из отзывов в магазине приложений.

### Почему в мобайле это критично

Сайт обновляется у всех пользователей сразу: перезагрузил страницу — получил новый фронтенд. Мобильное приложение обновляет **сам пользователь**, и многие этого не делают. Старые версии живут **годами**: кто-то отключил автообновление, у кого-то старый телефон, на который новая версия уже не ставится.

Значит, сервер одновременно обслуживает несколько версий приложения. Любое ломающее изменение API бьёт по всем, кто не обновился. Вспомни разбор из урока [«Методы HTTP»](/api/04-metody-http), где старая версия приложения через `PUT` стирала телефон: она не знала о новом поле и присылала объект без него.

### Что тестирует QA

- **Старый клиент против нового API.** Поставить предыдущую версию приложения — или ту, что ещё массово используется, — и пройти основные сценарии на новом сервере. В мобайле обычно договариваются, какие версии ещё поддерживаются.
- **Сравнение контрактов.** Открыть старое и новое описание API рядом: что удалено, переименовано, стало обязательным, сменило тип.
- **Неизвестные значения.** Что делает клиент, если пришёл новый статус, новое поле, пустой массив вместо `null`.
- **Вывод старой версии из эксплуатации.** Если `v1` закрывают, клиенты должны узнать заранее. Для этого есть заголовки `Deprecation` — «эта версия устарела» — и `Sunset` — дата, после которой версия перестанет работать. Проверь, что они приходят, что дата совпадает с объявленной и что после неё ответ понятный — например, `410 Gone` с сообщением, — а не `500`.

## На примере TaskFlow

**Ветка:** `training-public`. Источники — `docs/API_SPEC.md`, разделы 1, 4 и 6.3, и автоматическое описание `/openapi.json`.

### Базовый адрес и версия

По разделу 1 спецификации:

- базовый адрес — `http://localhost:8000`;
- все запросы к API начинаются с префикса `/api/v1` — версия в адресе;
- Swagger UI — `/docs`, описание OpenAPI — `/openapi.json`;
- формат тела запроса и ответа — JSON, `Content-Type: application/json`.

Вне `/api/v1` живут служебные адреса: `/health` — «сервер жив», `/docs` и `/openapi.json`. У них нет версии: это не часть бизнес-API.

### Ресурсы как REST

| Ресурс | Коллекция | Элемент | Что видно |
|---|---|---|---|
| Проекты | `/api/v1/projects` | `/api/v1/projects/{id}` | Классическая пара «коллекция — элемент». `POST` в коллекцию создаёт, `PATCH`/`DELETE` на элемент изменяют и удаляют |
| Участники проекта | `/api/v1/projects/{id}/members` | `/api/v1/projects/{id}/members/{userId}` | Вложенный ресурс. Элемент адресуется по `userId` пользователя, а не по отдельному `id` участия |
| Комментарии | `/api/v1/tasks/{taskId}/comments` | `/api/v1/tasks/{taskId}/comments/{id}` | Вложенный ресурс: комментарий существует только в рамках задачи |

Существительные во множественном числе, действия — методами, результат — кодами `201`, `204`, `404`, `409`. TaskFlow — REST-like API второго уровня по Ричардсону: ссылок на следующие действия в ответах нет.

### JSON проекта

Ответ на `GET /api/v1/projects/{id}` — схема `ProjectResponse`. Поля по разделу 6.3 спецификации: `id, name, description, status, ownerId`.

```json
{
  "id": 42,
  "name": "Сайт",
  "description": null,
  "status": "ACTIVE",
  "ownerId": 7
}
```

| Поле | Тип | Что значит |
|---|---|---|
| `id` | number | Номер проекта |
| `name` | string | Название |
| `description` | string или `null` | Описание. Его может не быть: при создании оно необязательное |
| `status` | string, enum | `ACTIVE` или `ARCHIVED` |
| `ownerId` | number | `id` владельца |

### Конвенции раздела 4

Раздел 4 спецификации — «Общие конвенции» — правила, общие для всего API. Это тоже контракт, и проверять его можно на любом ответе:

| Правило | Значение по спецификации | Пример |
|---|---|---|
| Имена полей | `camelCase` в запросах и ответах | `ownerId`, `hasNext` |
| Списки | Обёртка `items`, `total`, `limit`, `offset`, `hasNext` | Ответ `GET /api/v1/projects` выше |
| Даты | ISO 8601, UTC, суффикс `Z` | `2026-10-14T09:12:05.412Z` — например, `timestamp` в теле ошибки |
| Enum | Строки в верхнем регистре | `ACTIVE`, `OWNER`, `VIEWER` |
| Пагинация | `limit` от 1 до 100, по умолчанию 20; `offset` от 0, по умолчанию 0 | `?limit=10&offset=20` — третья страница по 10 |

Обрати внимание на пагинацию: `total` — сколько всего, `hasNext` — есть ли следующая страница. Клиент по `hasNext` решает, показывать ли кнопку «Ещё». Если `hasNext` врёт, последняя страница не загрузится или кнопка будет вести в пустоту.

### `/openapi.json` и схема `ProjectCreate`

TaskFlow написан на FastAPI — это **code-first**: описание OpenAPI генерируется из кода автоматически и отдаётся по адресу `http://localhost:8000/openapi.json`. Открой его в браузере — это обычный JSON. В начале — версия стандарта:

```json
{
  "openapi": "3.1.0",
  "info": {
    "title": "TaskFlow QA Training API",
    "version": "2.0.0"
  },
  ...
}
```

`version` здесь — версия самого описания, а не `v1` из адреса. Это разные вещи: адрес говорит, какая версия контракта, а `info.version` — номер сборки документа.

Swagger UI на `/docs` строится по этому же файлу. Посмотреть схему тела для создания проекта:

1. Открой `http://localhost:8000/docs`, группу **Projects**, запрос `POST /api/v1/projects`.
2. В блоке **Request body** переключись с **Example Value** на **Schema**.
3. Ты увидишь схему `ProjectCreate`: поле `name` — строка, обязательное, отмечено звёздочкой, с ограничениями длины `minLength` и `maxLength`; поле `description` — без звёздочки.
4. Сверь с разделом 6.3 спецификации: там записано `name (1–100), description (опционально, ≤1000)`.

Сравнить остальное — схему ответа и реальный ответ — ты сделаешь сам в задании.

### Swagger Petstore: схема `Pet`

[Swagger Petstore](https://petstore.swagger.io) — учебный API зоомагазина от авторов Swagger. Это классический пример OpenAPI, на нём показывают Swagger UI. Есть две версии:

- [petstore.swagger.io](https://petstore.swagger.io) — описание в формате **Swagger 2.0**: [petstore.swagger.io/v2/swagger.json](https://petstore.swagger.io/v2/swagger.json);
- [petstore3.swagger.io](https://petstore3.swagger.io) — то же на **OpenAPI 3.0**: [petstore3.swagger.io/api/v3/openapi.json](https://petstore3.swagger.io/api/v3/openapi.json).

Открой оба файла и найди схему `Pet`. Смысл один, а записано по-разному:

| | Swagger 2.0 | OpenAPI 3.0 |
|---|---|---|
| Первая строка | `"swagger": "2.0"` | `"openapi": "3.0.4"` |
| Где лежат схемы | `definitions` | `components/schemas` |
| Ссылка на схему | `#/definitions/Pet` | `#/components/schemas/Pet` |
| Обязательные поля `Pet` | `name`, `photoUrls` | `name`, `photoUrls` |
| `status` | `enum`: `available`, `pending`, `sold` | То же |

В схеме `Pet` есть всё, о чём шла речь: `required`, типы, `format: int64` у `id`, вложенный объект `category`, массивы `photoUrls` и `tags`, `enum` у `status`. Это хороший материал, чтобы потренироваться читать вкладку **Schema**.

Petstore умеет отвечать и в XML. Попроси один и тот же ресурс в двух форматах — формат выбирается заголовком `Accept`:

```bash
curl -H "Accept: application/json" https://petstore.swagger.io/v2/pet/1
curl -H "Accept: application/xml" https://petstore.swagger.io/v2/pet/1
```

Если питомца `1` уже нет, создай своего — как, разобрано в задании. На Windows в PowerShell пиши `curl.exe`.

Petstore — общий учебный стенд: данные видят все, их периодически чистят. И он сделан для демонстрации Swagger UI, а не как образец строгого API: что он принимает и что возвращает, ты сравнишь со схемой сам.

### SOAP: живой конверт

Публичный SOAP-сервис для примеров — конвертер чисел в слова от DataAccess: [NumberConversion.wso](https://www.dataaccess.com/webservicesserver/NumberConversion.wso). Его WSDL — по адресу с `?WSDL` в конце: [NumberConversion.wso?WSDL](https://www.dataaccess.com/webservicesserver/NumberConversion.wso?WSDL). Открой его в браузере — это и есть контракт SOAP-сервиса: операции, параметры, типы.

Отправить запрос удобнее из файла. Сохрани в `request.xml`:

```xml
<?xml version="1.0" encoding="utf-8"?>
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <NumberToWords xmlns="http://www.dataaccess.com/webservicesserver/">
      <ubiNum>42</ubiNum>
    </NumberToWords>
  </soap:Body>
</soap:Envelope>
```

И отправь:

```bash
curl -X POST https://www.dataaccess.com/webservicesserver/NumberConversion.wso \
  -H "Content-Type: text/xml; charset=utf-8" \
  --data-binary @request.xml
```

На Windows в PowerShell — `curl.exe` и всё в одну строку, без `\`.

Ответ — тоже конверт:

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Body>
    <m:NumberToWordsResponse xmlns:m="http://www.dataaccess.com/webservicesserver/">
      <m:NumberToWordsResult>forty two </m:NumberToWordsResult>
    </m:NumberToWordsResponse>
  </soap:Body>
</soap:Envelope>
```

Что здесь видно:

- метод — `POST`, адрес — один на весь сервис, действие `NumberToWords` — внутри тела;
- у элементов ответа префикс `m:` — это пространство имён `http://www.dataaccess.com/webservicesserver/`;
- попробуй убрать из запроса `xmlns="..."` у `NumberToWords`. Сервис не узнает операцию и ответит `soap:Fault` с кодом `500` — хотя ошибся клиент. Так SOAP 1.1 сообщает об ошибках.

## Инструмент: Swagger UI и `/openapi.json`

Ты уже отправлял запросы в Swagger UI. В этом уроке он нужен как **окно в контракт**. На что смотреть:

- **Schema** у тела запроса и у каждого ответа — поля, типы, обязательность, ограничения;
- **Schemas** внизу страницы — все схемы API в одном месте. Удобно, чтобы сравнить, например, схему создания и схему ответа;
- **Responses** у запроса — какие коды описаны. Описание делали разработчики — сверяй со спецификацией;
- **`/openapi.json`** — сырой файл описания. Его можно открыть в браузере, сохранить и сравнить с версией из прошлого релиза. Так находят ломающие изменения до того, как о них сообщат пользователи.

<summary>Разбор 1. После релиза бэкенда у части пользователей пустые профили — сервис записи к врачу</summary>

**Ситуация.** Во вторник вышел релиз бэкенда. В среду поддержка получает жалобы: «В приложении пропал телефон в профиле, а без него не дают записаться». Жалуются только пользователи Android и iOS, на сайте всё в порядке. Разработчики мобильного приложения: «Мы ничего не выпускали две недели».

**Что видит мидл.**

- Сайт работает, мобильные — нет, а мобильные приложения не менялись. Значит, поменялся **контракт**, а сайт успели обновить вместе с сервером.
- Скорее всего, в ответе профиля что-то переименовали или удалили. Старые версии приложения ищут поле по старому имени.
- Это ломающее изменение без новой версии API.

**Что делать.**

1. Сравнить ответ профиля до и после релиза: старый ответ — из логов, тестового стенда со старой сборкой или прошлого описания `/openapi.json`. Найти разницу: например, `phone` стал `phoneNumber`.
2. Проверить, какие версии приложения затронуты: поставить версию из магазина приложений и пройти по профилю и записи.
3. Завести баг с высоким приоритетом: «В релизе X поле `phone` в ответе `GET /profile` переименовано в `phoneNumber`. Мобильные приложения версий до Y показывают пустой телефон и не дают записаться».
4. Предложить быстрое решение: вернуть `phone` рядом с новым полем — старые клиенты читают своё, новые — своё. Убрать старое поле можно, когда старых версий почти не останется.
5. На будущее: добавить в чек-лист релиза сравнение `/openapi.json` с предыдущей версией и прогон старой версии мобильного приложения.

**Чего не делать.**

- Не заводить баг на мобильную команду: их код не менялся, сломался контракт.
- Не предлагать «пусть пользователи обновятся» как решение. Многие не обновятся никогда.

::: details Разбор 2. В веб-кабинете открывается чужой заказ — маркетплейс
**Ситуация.** Маркетплейс перешёл на новую систему номеров заказов: длинные числа, которые генерирует сервер. Через неделю продавцы пишут: «Нажимаю на заказ в кабинете — открывается другой заказ, иногда вообще "не найден"». В мобильном приложении всё правильно. Бэкенд-разработчик проверяет через `curl`: «Сервер отдаёт правильный `id`».

**Что видит мидл.**

- Новые `id` — длинные числа. Если они больше 2^53, JavaScript в браузере их **округляет** при разборе JSON. Сервер прав, `curl` показывает текст ответа как есть. А веб-кабинет, разобрав JSON, получает другое число.
- Мобильное приложение на Kotlin или Swift хранит 64-битные числа точно — поэтому там всё в порядке.
- Следующий запрос веб уходит с округлённым `id` — на другой заказ или в пустоту.

**Что делать.**

1. Сравнить `id` в сыром ответе — в Network, вкладка **Response**, или `curl` — и в адресе, по которому веб пошёл дальше. Цифры в конце отличаются?
2. Проверить в консоли браузера: `JSON.parse('{"id": <id из ответа>}').id` — получится ли то же число.
3. Завести баг: «`id` заказа больше 2^53 теряет точность в браузере, веб-кабинет открывает не тот заказ». Приложить пару «пришло / ушло».
4. Предложить решение: передавать `id` строкой, например в отдельном поле, а веб переводить на него.
5. Проверить, нет ли других больших чисел: суммы в копейках, номера транзакций, внешние идентификаторы.
6. Оценить, не видел ли кто-то **чужие** заказы. Если да — это уже утечка данных, сообщить по процессу инцидентов.

**Чего не делать.**

- Не закрывать «у меня в `curl` всё правильно»: `curl` не разбирает JSON, браузер — разбирает.
- Не лечить только отображение: если `id` округлился, неправильно уже всё, что дальше делает клиент.
:::

::: details Разбор 3. Итог корзины 269,97299999999996 рубля — интернет-аптека
**Ситуация.** В корзине три товара по 99,99 рубля и скидка 10%. Пользователь пишет: «На экране итог 269,97299999999996 рубля, оплата прошла на 269,97, а в чеке — 269,98». Бухгалтерия жалуется, что за месяц не сходятся несколько тысяч рублей.

**Что видит мидл.**

- Хвост из девяток — признак **дробных чисел с плавающей точкой** — float. Деньги где-то считают во float.
- Три разные суммы — значит, три места считают по-разному: экран, оплата, чек. Где-то округляют вверх, где-то вниз, где-то не округляют.
- Ошибка в копейку на одном заказе — тысячи рублей на миллионе заказов.

**Что делать.**

1. Посмотреть в Network, в каком виде суммы приходят от API: `269.97299999999996`, `"269.97"` или `26997`?
2. Собрать набор проверок для денег: суммы, которые плохо представляются во float, — `0.1`, `0.2`, `99.99`, скидки в процентах, деление на три. Сравнить итог на экране, в оплате и в чеке.
3. Завести баг с примером: товары, скидка, три разные суммы.
4. Уточнить у команды правило: где считается итог — на сервере или на клиенте; в чём хранятся деньги — в копейках целым числом или точной десятичной арифметикой; как округлять.
5. Предложить: итог считает сервер, передаёт его в копейках или строкой, клиенты только показывают.

**Чего не делать.**

- Не считать копейку мелочью. Расхождение между оплатой и чеком — проблема с бухгалтерией и налогами.
- Не проверять деньги только на «круглых» суммах вроде 100 и 500 рублей.
:::

::: details Разбор 4. Запись переезжает на следующий день — сервис записи в барбершопы
**Ситуация.** Сеть барбершопов работает в нескольких городах. Клиенты из Владивостока жалуются: «Записался на 10:00 понедельника, а в подтверждении — 03:00 понедельника». Другие пишут, что вечерняя запись в карточке мастера стоит на следующий день. В Москве жалоб нет. Сервер стоит в Москве.

**Что видит мидл.**

- Разница — 7 часов, ровно разница Владивостока и Москвы. Время где-то потеряло **часовой пояс**.
- Вероятно, клиент отправляет время без пояса — `2026-10-19T10:00:00`, — а сервер считает его московским. Или сервер отдаёт время без пояса, и каждый клиент понимает его по-своему.
- В Москве не видно, потому что там пояс клиента и сервера совпадает.

**Что делать.**

1. Посмотреть в Network формат времени в запросе создания записи и в ответе: есть ли `Z` или `+10:00` в конце.
2. Воспроизвести: сменить часовой пояс на компьютере или телефоне на Владивосток и записаться. Сравнить время на экране, в запросе, в ответе, в подтверждении.
3. Проверить граничные случаи: запись поздно вечером — переезжает ли на другую дату; запись в другом городе, когда пользователь находится в своём.
4. Завести баг: «Время записи передаётся без часового пояса, у пользователей не из Москвы запись смещается». Приложить запрос и ответ.
5. Предложить правило в контракт: все даты в ISO 8601 с поясом, хранение в UTC.

**Чего не делать.**

- Не тестировать время только в своём часовом поясе.
- Не ограничиться «на экране время правильное»: проверить, что ушло на сервер и что пришло в подтверждении и напоминании.
:::

::: details Разбор 5. После релиза падает экран заказов в Android-приложении — магазин электроники
**Ситуация.** Магазин добавил возврат денег. У заказа появился новый статус `REFUNDED`. Сайт и iOS обновили заранее. Через день после релиза у части пользователей Android-приложение падает при открытии «Мои заказы». Бэкенд: «Мы ничего не удаляли, только добавили значение — это неломающее изменение».

**Что видит мидл.**

- Формально бэкенд прав: новое значение `enum` расширяет контракт. Но падают именно пользователи, у которых есть **возвращённый** заказ.
- Android-приложение, видимо, знает только старые статусы и падает на незнакомом, вместо того чтобы показать его как «другой».
- Падают все версии Android, где нет обработки неизвестного статуса. Ждать обновления — неделями.

**Что делать.**

1. Воспроизвести: создать на тесте заказ, оформить возврат, открыть список заказов в текущей и предыдущей версии Android-приложения.
2. Завести два бага. Срочный — на сервер или команду релиза: решить, как защитить старые версии, например отдавать им старый статус, пока не обновятся. Второй — на Android: обрабатывать неизвестные значения `enum` без падения.
3. Проверить другие `enum`, где могут появиться значения: способы оплаты, типы доставки, роли.
4. На будущее: в тест-план любого нового значения `enum` добавить «старые версии клиентов».

**Чего не делать.**

- Не спорить, «ломающее это изменение или нет». Пользователям всё равно, как это назвать: приложение падает.
- Не проверять новый статус только в обновлённых клиентах.
:::

## Частые ошибки

- **Проверять только «есть ли поле».** Поле есть, но `"42"` вместо `42`, дата без пояса, `null` там, где ждали массив. Проверяй тип и формат каждого поля.
- **Не различать `null` и отсутствие поля.** Для клиента и для `PATCH` это разные ситуации. В баг-репорте пиши точно: «поле пришло со значением `null`» или «поля нет в ответе».
- **Верить Swagger без сверки с ТЗ.** Сгенерированная схема описывает код, а не замысел. Если в коде ошибка — схема её повторит.
- **Смотреть только на Example Value.** Пример не показывает ни обязательность, ни ограничения. Для тест-дизайна нужна вкладка Schema.
- **Не думать о старых клиентах.** «Мы только переименовали поле» — для старой версии мобильного приложения это поломка.
- **Считать REST протоколом.** REST — стиль. Протокол — HTTP. На собеседовании это различие проверяют часто.
- **Сравнивать JSON как строку.** Порядок ключей не важен, пробелы не важны. Важны ключи, типы и значения.
- **Тестировать деньги и даты на «удобных» значениях.** `100` рублей и `12:00` по Москве баг не покажут. Покажут `0.1`, `99.99`, `23:30` и другой часовой пояс.

## Часть 1. REST или нет?

Для каждого эндпоинта запиши:

- хорошо ли он сделан по правилам REST;
- если нет — что не так и как переписать.

**Образец** — на эндпоинте, которого нет в списке ниже:

> **`GET /getOrderById?id=7`**
>
> - **По REST?** Нет.
> - **Что не так:** действие «получить» записано в адресе, хотя его уже выражает метод `GET`. `id` передан query-параметром, хотя это адрес конкретного ресурса.
> - **Как переписать:** `GET /orders/7`.

**Эндпоинты:**

1. `GET /getAllProjects`
2. `POST /projects/42/delete`
3. `GET /projects/42/members`
4. `POST /createUser`
5. `PATCH /orders/7`
6. `GET /search?q=телефон`
7. `GET /orders/15/cancel`
8. `POST /orders/7/items`
9. `GET /Products/Get_List`
10. `DELETE /carts/3/items/12`

Для пунктов 6 и 7 подумай отдельно. Поиск — это ресурс или действие, и как ещё его можно оформить? Отмена заказа — это изменение статуса или отдельное действие? Какие варианты встречаются в реальных API и почему вариант 7 опасен независимо от стиля? Подсказка — урок [«Методы HTTP»](/api/04-metody-http), раздел про безопасные методы.

## Часть 2. Найди ошибки в JSON

Ниже четыре ответа API. В каждом есть ошибки: синтаксис, типы, форматы, стиль. Для каждого ответа запиши:

- что не так — каждую ошибку отдельно;
- почему это проблема — что сломается у клиента.

**Ответ А — профиль пользователя**

```text
{
  'id': 15,
  "firstName": "Анна",
  "lastName": "Петрова",
  phone: "+79001234567",
  "isActive": true,
}
```

**Ответ Б — заказ**

```json
{
  "id": "1024",
  "status": "PAID",
  "totalPrice": 1999.99,
  "itemsCount": "3",
  "createdAt": "2026-10-14 15:30:00",
  "deliveryDate": "15.10.2026"
}
```

**Ответ В — товар**

```json
{
  "id": 501,
  "title": "Наушники",
  "inStock": "true",
  "tags": null,
  "category_name": "Электроника",
  "ratingCount": 0,
  "rating": null
}
```

**Ответ Г — список платежей**

```json
{
  "items": [
    {"paymentId": 9223372036854775807, "amount": 0.30000000000000004, "currency": "RUB"},
    {"paymentId": 9223372036854775806, "amount": 150, "Currency": "rub"}
  ],
  "total": 2,
  "hasNext": "false"
}
```

Подсказка: не все странные значения — ошибки. Где-то правильный ответ — «зависит от контракта: нужно уточнить». Объясни, от чего зависит.

**Перевод в XML.** Возьми **исправленный** вариант ответа Б и запиши тот же объект в XML. Реши и объясни:

- что будет элементами, а что — атрибутами, если они есть;
- как ты запишешь поле, если его значение `null`, — добавь в объект поле `"comment": null`;
- что потеряется при переводе — подумай про типы.

## Часть 3. TaskFlow: контракт против факта

Ты сравниваешь три источника: **схему** в Swagger, **спецификацию** `docs/API_SPEC.md` и **факт** — реальный ответ сервера.

Заранее неизвестно, найдёшь ли ты расхождения. Умение проверить методично и честно написать «совпадает» — такой же результат, как найденный баг.

Работать будешь в Swagger: `http://localhost:8000/docs`. Как войти, описано в уроке [«Баг-репорт»](/osnovy/09-bag-report), раздел «Как войти в Swagger». Входи под обычным пользователем `USER` из `README.md` TaskFlow, раздел «Тестовые учётные записи», — не под администратором.

Отправь `GET /api/v1/projects` и проверь ответ по разделу 4 спецификации:

- все ключи в `camelCase`;
- обёртка списка — ровно `items`, `total`, `limit`, `offset`, `hasNext`, с правильными типами;
- значения `status` — в верхнем регистре;
- `limit` и `offset` по умолчанию — те, что в спецификации;
- `hasNext` честный: создай проектов больше, чем `limit`, например отправь `limit=1`, и пройди страницы до конца. На последней странице `hasNext` должен стать `false`.

Дат в ответе проекта нет. Найди в API TaskFlow ответ, где есть дата, — подсказка: вспомни урок [«Коды ответа»](/api/05-kody-otveta), — и проверь её формат по разделу 4.

### Шаг 5. Запиши результат

Для каждого шага — вывод «совпадает» или «расхождение» с подробностями. Если нашёл расхождение кода со спецификацией:

1. Воспроизведи ещё раз.
2. Перечитай нужный раздел спецификации.
3. Оформи баг-репорт по шаблону из урока [«Баг-репорт»](/osnovy/09-bag-report). В «Ожидаемом результате» укажи раздел спецификации.

:::

## Ситуационные кейсы

Это рабочие ситуации, о которых могут спросить и на собеседовании. Готового ответа, который нужно угадать, здесь нет. Сначала подумай сам, потом открывай разбор.

::: details Кейс 1. Хитрый вопрос: «REST — это протокол?»
**Ситуация.** Интервьюер: «Расскажите, что такое REST. Это протокол, как HTTP?»

**Как рассуждать.** Что такое протокол? Есть ли у REST стандарт, формат сообщений, версия? Как связаны REST и HTTP?

**Пример ответа.** Нет, REST — архитектурный стиль, набор принципов построения API. Протокол — это точные правила обмена: формат сообщений, порядок. HTTP — протокол, у него есть стандарт и версии. У REST ничего такого нет.

Принципы REST: API строится вокруг ресурсов с адресами, действия выражаются стандартными методами, сервер не хранит состояние клиента между запросами, ответы можно кэшировать. Почти всегда REST работает поверх HTTP, но это разные уровни: HTTP — дорога, REST — правила движения.

Для тестировщика это важно, потому что «REST API» в каждой компании свой: правила стиля соблюдают в разной степени. Поэтому я проверяю API не по «правилам REST», а по его спецификации, и отдельно смотрю, последовательно ли оно устроено.
:::

::: details Кейс 2. «Чем REST отличается от SOAP? А от GraphQL?»
**Ситуация.** Интервьюер: «Вы работали с REST. Чем от него отличается SOAP? А GraphQL? Что меняется для тестировщика?»

**Как рассуждать.** Сравни по нескольким осям: формат, адреса и методы, контракт, как приходят ошибки. Закончи тем, что это меняет в работе.

**Пример ответа.** REST — стиль: много адресов-ресурсов, разные методы, обычно JSON, смысл результата — в коде ответа.

SOAP — протокол: один адрес, практически всегда `POST`, тело — XML-конверт, действие записано внутри. Строгий контракт в WSDL, по нему инструменты сами строят запросы. Ошибка — элемент `Fault`, обычно с кодом `500`. Встречается в банках и госсистемах.

GraphQL — язык запросов: один адрес, клиент сам перечисляет, какие поля нужны. Ответ — JSON, ошибки часто в массиве `errors` при коде `200`.

Для тестирования: в REST я смотрю на методы и коды. В SOAP — на структуру XML, пространства имён и `Fault`, инструмент — SoapUI или Postman. В GraphQL код ответа почти ничего не говорит, читаю тело. И отдельно проверяю глубину запросов и права на уровне полей: клиент может попросить любое поле схемы.
:::

::: details Кейс 3. «Чем null отличается от отсутствия поля и почему это важно?»
**Ситуация.** Интервьюер: «В ответе API у пользователя `"middleName": null`. А у другого пользователя поля `middleName` нет совсем. Это одно и то же?»

**Как рассуждать.** Что каждый вариант говорит клиенту? Как это выглядит в запросе на изменение? Что записано в схеме: `required`, `nullable`?

**Пример ответа.** Нет. `null` — поле есть, значения нет: отчества нет. Отсутствие поля — сервер его не прислал. Это может быть нормой по контракту, а может быть ошибкой: поле забыли или не хватило прав его видеть. Третий вариант — пустая строка — это значение, просто пустое.

В ответах разница важна для клиентов: строго типизированный клиент может упасть, если обязательного поля нет, хотя спокойно принимает `null`. В запросах на изменение ещё важнее: в `PATCH` `{"middleName": null}` обычно значит «стереть отчество», а `{}` — «ничего не трогать». Если сервер путает эти случаи, данные пропадают.

Как тестировщик я смотрю в схеме и `required`, и `nullable` — это разные свойства. Проверяю, что ответ им соответствует. А для `PATCH` проверяю три запроса: поле со значением, поле с `null` и без поля — и что после каждого стало с данными.
:::

::: details Кейс 4. Хитрый вопрос: «Добавление поля в ответ — ломающее изменение?»
**Ситуация.** Интервьюер: «Бэкенд добавил в ответ новое поле. Это может что-то сломать?»

**Как рассуждать.** Правильный короткий ответ — «обычно нет». Но интервьюер ждёт, что ты назовёшь случаи, когда «обычно» не работает.

**Пример ответа.** По общему правилу добавление необязательного поля — неломающее изменение: старые клиенты его просто не замечают. Но есть исключения, и я бы их проверил:

- клиент со строгим разбором, который падает на незнакомых полях. Это ошибка клиента, но пользователям от этого не легче;
- поле с чувствительными данными — новое поле могут увидеть те, кому не положено. Это уже вопрос безопасности;
- ответ стал заметно больше — например, в каждый элемент списка добавили вложенный объект. Медленнее грузится, особенно в мобильной сети;
- контрактные тесты, которые сравнивают ответ со схемой строго, — они упадут, и это правильно: схему нужно обновить.

И отдельно — похожий случай, который часто считают безопасным: новое значение в `enum`. Формально это расширение, но клиент, который знает только старые значения, может упасть.
:::

::: details Кейс 5. «Swagger и ТЗ расходятся — кому верить?»
**Ситуация.** Ты тестируешь регистрацию. В ТЗ поле `phone` обязательное. В Swagger оно без звёздочки, и сервер принимает запрос без телефона. Разработчик: «Swagger генерируется из кода, значит, он правильный». Аналитик: «В ТЗ написано обязательное, значит, обязательное». Что ты делаешь?

**Как рассуждать.** Что описывает сгенерированная схема — замысел или реализацию? Кто в команде решает, что задумано? Что делать с результатом?

**Пример ответа.** Сгенерированный Swagger показывает, как написан код. Значит, он точно описывает текущее поведение, но не доказывает, что поведение правильное. ТЗ описывает замысел, но может устареть.

Сам я не решаю, кто прав. Я фиксирую расхождение: «ТЗ — раздел такой-то, обязательное; Swagger — необязательное; факт — сервер принимает без телефона». И задаю вопрос тому, кто отвечает за требования, — обычно аналитику или продакт-менеджеру: телефон должен быть обязательным?

Дальше два исхода. Если обязательный — баг на код, Swagger обновится сам. Если необязательный — задача на исправление ТЗ, чтобы следующий человек не споткнулся. В обоих случаях проверяю, что клиенты — веб, мобильные — ведут себя по итоговому решению. И предлагаю договориться в команде, какой документ источник истины, чтобы не решать это каждый раз заново.
:::

::: details Кейс 6. «Зачем тестировщику API, если есть UI?»
**Ситуация.** Интервьюер: «У нас есть веб-интерфейс, и пользователи работают только с ним. Зачем тестировщику проверять API?»

**Как рассуждать.** Кто ещё, кроме веб-интерфейса, обращается к API? Что интерфейс может скрывать? Что быстрее проверить через API?

**Пример ответа.** Во-первых, интерфейс — только один из клиентов. К тому же API обращаются мобильные приложения, в том числе старые версии, интеграции, а ещё — злоумышленники, которым интерфейс не нужен.

Во-вторых, интерфейс прячет баги сервера. Форма не даёт ввести неправильное значение, а сервер его принимает. Кнопка «Удалить» скрыта для обычного пользователя, а запрос на удаление проходит. Через интерфейс такие баги не найти.

В-третьих, это быстрее и раньше. Проверить сто комбинаций данных через API — минуты. А API часто готов раньше экранов.

И наконец, через API точнее локализовать баг: если сервер отвечает правильно, а на экране неправильно, — баг на клиенте, и наоборот. Интерфейс тестировать, конечно, тоже нужно, но только его — мало.
:::

::: details Кейс 7. «Как проверить, что новый API не сломал старое мобильное приложение?»
**Ситуация.** Интервьюер: «Готовится релиз бэкенда. Мобильное приложение у пользователей — разных версий, последние полтора года. Как вы проверите, что релиз ничего не сломает?»

**Как рассуждать.** Какие версии важны? Что сравнить в контракте? Как проверить вживую? Что делать с теми изменениями, которые всё-таки ломают?

**Пример ответа.** Сначала — контракт. Сравниваю описание API до и после релиза: что удалено, переименовано, стало обязательным, сменило тип или формат, какие появились новые значения `enum`, поменялись ли коды ответов. Это быстро и находит большую часть проблем.

Потом — вживую. Уточняю у команды, какие версии приложения ещё поддерживаются и какие самые массовые, — это видно в аналитике. Ставлю эти версии на тестовые устройства, подключаю к новому бэкенду и прохожу основные сценарии: вход, главный экран, ключевая покупка или действие, профиль. Особое внимание — экранам, где задействованы изменённые поля.

Отдельно проверяю данные, которых раньше не было: новый статус, длинное значение после увеличения лимита, пустой список.

Если находится ломающее изменение — предлагаю варианты: сохранить старое поле рядом с новым, вынести изменение в новую версию API или договориться о принудительном обновлении приложения. И чтобы не делать это руками каждый раз — предлагаю автоматическое сравнение контракта и контрактные тесты в сборке.
:::
