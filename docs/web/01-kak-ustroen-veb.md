## Простыми словами

Сайт — это ресторан.

- **Зал** — всё, что видит и трогает гость: столы, меню, кнопка вызова официанта. Это **фронтенд** — то, что работает у тебя в браузере.
- **Кухня** — где готовят и хранят продукты. Гость её не видит. Это **бэкенд**: API и база данных.
- **Официант** носит заказы из зала на кухню и блюда обратно. Это **HTTP-запросы**.

Гостю принесли не то блюдо. Где ошибка? Повар приготовил не то — проблема **на кухне**. Повар приготовил правильно, но официант уронил по дороге или поставил на чужой стол — проблема **в зале**. Официант вообще не дошёл до кухни — заказ даже не передали.

С сайтом так же: баг бывает **на фронте**, **на бэке** или **«запрос не дошёл»**. Главный навык веб-тестировщика — быстро понять, где именно. Этому посвящена большая часть урока.

- немного SEO: что можно проверить за минуту;
- где практиковаться в этом блоке.

## Что делает браузер

Ты вводишь адрес и нажимаешь Enter. Браузер получает три вида файлов:

| Файл | Что это | В ресторане |
|---|---|---|
| **HTML** | Скелет страницы: заголовки, кнопки, поля, таблицы | Расстановка столов и стульев |
| **CSS** | Внешний вид: цвета, шрифты, отступы, расположение | Скатерти, свет, оформление |
| **JS** (JavaScript) | Поведение: что происходит при клике, проверка формы, загрузка данных | Официанты и всё, что движется |

Браузер собирает из них страницу и рисует её. Дальше JS **ходит в API за данными**: список задач, профиль, комментарии. API берёт данные из базы и отвечает — обычно в JSON. JS вставляет их в страницу.

Важно для тестировщика:

- **Фронт работает на твоём компьютере.** Сервер фронта только отдаёт файлы. Код фронта выполняется в твоём браузере — поэтому результат зависит от браузера, размера окна, расширений, медленного интернета.
- **Все правила — на бэке.** Фронт может не пустить пустую форму, но защищать данные должен API. Это ты уже видел в [блоке 2](/api/07-autentifikaciya-i-prava): запрос можно отправить в обход интерфейса.
- **Фронт и бэк общаются через HTTP** — те же запросы и ответы, что в уроке [«HTTP: запрос и ответ»](/api/03-http-zapros-i-otvet). По классификации из урока [«Интеграции»](/api/13-integracii) это **внутренняя · синхронная** интеграция: обе стороны делает одна команда, браузер отправил запрос и ждёт ответа.

## Обычный сайт и SPA

Сайты бывают устроены двумя способами.

**Обычный (многостраничный) сайт.** Каждый клик по ссылке — новая страница с сервера. Экран мигает, страница грузится целиком. Так работают многие новостные сайты, блоги, старые интернет-магазины.

**SPA** (single-page application, «одностраничное приложение»). Браузер один раз загружает приложение — HTML, CSS и большой JS. Дальше страница **не перезагружается**: при переходах JS сам перерисовывает экран и подгружает из API только данные. Так работают Gmail, Trello, Figma, большинство личных кабинетов. **Веб-клиент TaskFlow — тоже SPA** (на React).

| | Обычный сайт | SPA |
|---|---|---|
| Переход по ссылке | Сервер присылает новую страницу | JS перерисовывает экран, подгружает JSON |
| Экран при переходе | Мигает, грузится целиком | Меняется плавно, без перезагрузки |
| Что видно в Network | Запрос новой страницы (HTML) | Запросы к API за данными (Fetch/XHR) |
| Ошибка в JS | Обычно ломает одну кнопку или блок | Может сломать всё — белый экран |

### Что SPA меняет для тестировщика

Адрес в SPA меняет сам JS. Сервер при этом ничего не спрашивают. Отсюда четыре обязательные проверки:

1. **URL.** Открыл задачу — адрес поменялся на что-то вроде `/tasks/42`? Если адрес не меняется, ссылку на задачу нельзя переслать коллеге.
2. **Обновление страницы (F5).** Нажми F5 на любом экране — должен открыться тот же экран, а не главная, не пустая страница и не ошибка.
3. **Кнопка «Назад».** Должна возвращать на предыдущий экран приложения, а не выкидывать с сайта. Открытое модальное окно и выбранные фильтры — отдельный вопрос, его ответ ищи в требованиях.
4. **Ошибки в Console.** Если что-то сломалось «молча» — кнопка не реагирует, экран белый — открой DevTools → вкладка **Console**. Красные ошибки там — первая улика для разработчика.

Навигацию, URL и обновление страницы подробно разберём в отдельном уроке блока.

## Главный навык: где баг — на фронте или на бэке

Самый важный раздел урока.

### Зачем это знать

- **Баг попадёт к нужному человеку.** Во многих командах фронт и бэк делают разные разработчики. Баг «не тому» — день потерян на пересылку.
- **Баг-репорт станет сильнее.** «Кнопка не работает» против «Запрос `PATCH /tasks/42` вернул 200 и новое название, но на экране осталось старое». Второй разработчик чинит сразу.
- **Так спрашивают на собеседовании.** «Как поймёшь, фронтовый баг или бэковый?» — один из самых частых вопросов по вебу.

«Чей баг» — это не про то, кто виноват. Это про то, **где чинить**.

### Как проверить — по шагам

Нужна вкладка **Network** в DevTools — она показывает все запросы страницы, как Postman, только запросы отправляет сам сайт. Подробно DevTools разберём в следующем уроке, сейчас хватит пяти шагов:

1. Открой DevTools: **F12** (на Mac — **Cmd + Option + I**). Перейди на вкладку **Network**.
2. Включи фильтр **Fetch/XHR** — останутся только запросы к API, без картинок и шрифтов.
3. **Повтори действие**, на котором баг: нажми «Сохранить», открой страницу, примени фильтр.
4. Найди запрос, который появился. Посмотри **адрес, метод и код ответа**.
5. Кликни по запросу. Вкладка **Payload** — что фронт отправил. Вкладка **Response** (или **Preview**) — что API ответил.

Дальше — простое правило:

| Что видишь в Network | Чей баг |
|---|---|
| **Запроса нет вовсе** | Фронт: кнопка ничего не отправила |
| Фронт отправил **не то** (пустое поле, не тот id) | Фронт: собрал запрос неправильно |
| API ответил **неверно** (ошибка `500`, не те данные) | Бэк |
| API ответил **верно**, а на экране не то | Фронт: неправильно показал |

### Типичные симптомы

| Симптом на экране | Куда смотреть | Чей баг чаще всего |
|---|---|---|
| Нажимаешь «Сохранить» — ничего не происходит | Network: появился ли запрос? Console: есть ли красные ошибки? | Нет запроса — **фронт**. Есть запрос с ошибкой `500` — **бэк** |
| Дата на экране сдвинута на день | Response: какая дата пришла от API? | Пришла верная — **фронт** (часовой пояс при показе). Пришла неверная — **бэк** |
| В списке нет только что созданной задачи | Response списка: есть ли задача в ответе? | Есть в ответе — **фронт** не перерисовал. Нет — **бэк** (или кэш) |
| «Что-то пошло не так» вместо понятной ошибки | Response: что ответил API? | API вернул понятный текст ошибки, а экран его не показал — **фронт**. API вернул `500` — **бэк** |
| Пользователь видит чужие данные | Response: эти данные пришли от API? | Пришли — **бэк**, и это серьёзный баг безопасности |

Если API ответил верно, но непонятно, что такое «верно» — сверься со спецификацией API. Если ответ **не совпадает со спецификацией** — бэк. Если совпадает, а фронт ждал другое — это расхождение договорённостей: пиши баг и укажи оба факта, команда решит.

### Пример по шагам

Ты переименовал задачу: «Купить молоко» → «Купить хлеб». Нажал «Сохранить». На экране — «Купить молоко».

1. F12 → Network → Fetch/XHR. Сохраняешь ещё раз.
2. Появился запрос `PATCH /api/v1/tasks/42`, код `200`.
3. Payload: `{"title": "Купить хлеб"}` — фронт отправил правильно.
4. Response: `{"id": 42, "title": "Купить хлеб", ...}` — API сохранил и ответил правильно.
5. Нажимаешь F5 — на экране «Купить хлеб».

Вывод: **фронт** не обновил экран после успешного сохранения. В баг-репорте: шаги, ожидаемый и фактический результат, запрос и ответ из Network, «после F5 отображается правильно».

А если бы в Response было старое название — баг **бэка**: API ответил `200`, но не сохранил. Тогда можно проверить в базе, как в [блоке 3](/bd/).

## Немного SEO

**SEO** — всё, что помогает сайту хорошо выглядеть в поиске Google и Яндекса. Этим занимаются отдельные специалисты. Но на многих проектах SEO-ошибки находит именно тестировщик — потому что он видит каждую страницу перед релизом.

Три вещи, которые проверяются за минуту:

| Что | Где видно | Что проверить |
|---|---|---|
| **`<title>`** — заголовок страницы | Текст на вкладке браузера; так же называется ссылка в поиске | Есть на каждой странице, свой у каждой: не «React App» и не одинаковый у всех |
| **meta description** — описание | Текст под ссылкой в поиске. В коде: `<meta name="description" content="...">` | Есть на важных страницах, описывает именно эту страницу |
| **Страница 404** | Открой несуществующий адрес, например `/abracadabra` | Видно понятное «Страница не найдена» и ссылка на главную. **Код ответа — `404`**, а не `200` |

Как посмотреть:

- **Код страницы:** правый клик → «Просмотр кода страницы» (**Ctrl + U**, на Mac — **Cmd + Option + U**). Найди `<title>` и `<meta name="description"` через Ctrl + F.
- **Код ответа:** DevTools → Network → обнови страницу → самый первый запрос (тип `document`) → колонка Status.

::: tip Хитрость с SPA
SPA на любой адрес отдаёт один и тот же HTML, а «Страница не найдена» рисует уже JS. Человек видит 404, а поисковик получает код `200` и считает страницу настоящей. Это называется **soft 404**. Если сайту важен поиск — это баг, если это закрытый личный кабинет — обычно не важно. Уточни у команды.
:::

## Где практиковаться в этом блоке

### Веб-клиент TaskFlow

Тот же TaskFlow, что в блоках 2 и 3, но с браузерным интерфейсом.

1. В репозитории TaskFlow переключись на ветку `web`: `git checkout web`.
2. Пересобери контейнеры: `docker compose down -v`, затем `docker compose up --build -d`. В ветке `web` появляется дополнительный сервис — веб-клиент.
3. Открой `http://localhost:3000`. Тестовые учётные записи — в `README.md`.

Обратно к API без интерфейса — `git checkout main` и та же пересборка.

С чем сверяться:

- **`docs/WEB_SPEC.md`** — спецификация веб-клиента: экраны, роли, права, состояния. Это эталон: расхождение с ним — баг.
- **Макеты** — https://annakrutykh.github.io/taskflow-qa-training-public/ — как экраны должны выглядеть: цвета, шрифты, состояния элементов. Пригодятся в уроке про вёрстку.
- **`docs/API_SPEC.md`** — что должен отвечать API. Нужен, когда решаешь «фронт или бэк».

Интерфейс TaskFlow ходит в API на `http://localhost:8000` — тот же, что ты тестировал в Postman. Значит, каждый запрос из Network можно повторить в Postman.

## Разборы из жизни

Два случая с разных проектов. Первый открыт — это образец.

<details class="details custom-block" open>
<summary>Разбор 1. «Скидка не применяется» — интернет-магазин</summary>

**Ситуация.** Покупатели жалуются: вводят промокод, нажимают «Применить» — сумма не меняется. Бэкенд-разработчик проверил в Postman: промокод работает. Фронтенд-разработчик: «Я ничего не менял». Баг неделю пересылают друг другу.

**Что видит мидл.**

- Вопрос не «кто прав», а «что видно в Network».
- Открыл DevTools, ввёл промокод: запрос `POST /cart/promo` уходит, ответ `200`, в ответе новая сумма со скидкой.
- Значит, бэк отработал. Но на экране старая сумма — фронт не перерисовал корзину.
- Проверил разные промокоды: с промокодом в нижнем регистре всё работает, в верхнем — нет. В Payload видно: фронт отправляет `SALE10`, а в ответе `"code": "sale10"`. Фронт сравнивает отправленный и полученный код, не находит совпадения и игнорирует ответ.

**Что делать.**

1. Завести баг на фронт: шаги, промокод в верхнем регистре, скриншот Payload и Response.
2. В баг-репорте прямо написать: «API отвечает верно — проверено в Network и в Postman».
3. После исправления проверить оба регистра и промокод с пробелом в конце.

**Чего не делать.**

- Не писать «скидка не работает» без запросов — так баг и ходил по кругу неделю.

</details>

::: details Разбор 2. Сайт пропал из поиска после релиза — сайт сети клиник
**Ситуация.** Через две недели после релиза нового сайта маркетинг в панике: заявок с поиска почти нет. Сайт работает, все страницы открываются, тестирование прошло без замечаний.

**Что видит мидл.**

- На тестовом стенде в код страниц добавляют `<meta name="robots" content="noindex">` — «поисковикам не индексировать». Тестовый стенд не должен попасть в поиск, это правильно.
- При выкладке этот тег остался и на боевом сайте. Поисковики послушались и убрали сайт из выдачи.
- Человек тег не видит — страницы выглядят идеально. Найти можно только в коде страницы.

**Что делать.**

1. Открыть код главной на боевом сайте (Ctrl + U), найти `robots` и `noindex`.
2. Завести баг с наивысшим приоритетом: каждый день без поиска — потерянные клиенты.
3. Предложить добавить в чек-лист релиза: «на боевом сайте нет `noindex`, у страниц есть `<title>` и description, несуществующий адрес отдаёт `404`».

**Чего не делать.**

- Не считать SEO «не моей зоной». Проверка занимает минуту, а ошибка стоит дорого.
:::

## Частые ошибки

- **«Кнопка не работает» без Network.** Сначала посмотри, ушёл ли запрос и что вернулось. Это две минуты, а баг-репорт станет вдвое полезнее.
- **«На экране ошибка — значит, бэк».** Если API ответил верно, баг на фронте, даже если на экране написано «Ошибка сервера».
- **Проверка только через интерфейс.** Фронт может не пустить пустую форму, но API надо проверить отдельно — это ты умеешь с блока 2.
- **Забыть про F5 и «Назад» в SPA.** Экран работает, пока не обновишь страницу. Пользователи обновляют постоянно.
- **Не открывать Console.** Белый экран или «мёртвая» кнопка почти всегда оставляют красную ошибку в Console — приложи её к баг-репорту.
