## Простыми словами

**DevTools** (инструменты разработчика) — это рентген страницы. Снаружи ты видишь кнопки и текст. В DevTools видно, что внутри: из чего собрана страница, какие ошибки случились в JS, какие запросы ушли на сервер и что сайт сохранил у тебя в браузере.

DevTools уже встроены в браузер — ничего устанавливать не нужно. Разработчики сидят в них весь день. Тестировщик — тоже: на веб-проекте DevTools открыты почти всегда, когда ты что-то проверяешь.

Зачем это тестировщику на работе:

- **понять, где баг** — на фронте или на бэке (это было в [уроке 1](/web/01-kak-ustroen-veb), здесь научимся делать это уверенно);
- **приложить к баг-репорту доказательства** — ошибку из Console, запрос и ответ из Network;
- **проверить то, чего не видно глазами** — скрытую кнопку, сохранённый токен, лишние запросы;
- **создать нужную ситуацию без разработчика** — подменить ответ, удалить данные из браузера, поменять текст на странице.

В этом уроке:

- как открыть DevTools и как они устроены;
- главные вкладки: **Elements, Console, Network, Application** — что в каждой смотрит тестировщик;
- подмена ответа сервера (Local Overrides);
- полезные мелочи: скриншот всей страницы, Command Menu;
- **порядок действий при любом баге в вебе** — по шагам.

Все примеры — в Chrome. В Edge, Opera и Яндекс Браузере DevTools те же самые (это всё Chromium). В Firefox и Safari устроено похоже, названия вкладок чуть другие. В Safari сначала включи инструменты: «Настройки» → «Дополнения» → «Показывать функции для веб-разработчиков».

## Elements — как выглядит страница

Слева — **дерево HTML**: все элементы страницы, вложенные друг в друга. Справа — **стили** выбранного элемента: какие правила CSS к нему применились.

### Выбрать элемент

Нажми на **стрелку** в левом верхнем углу DevTools (или **Ctrl + Shift + C**) и кликни по элементу на странице. В дереве подсветится его код, на странице — сам элемент с размерами и отступами.

Искать по дереву удобно через **Ctrl + F** (Cmd + F) внутри Elements: можно вводить текст кнопки, например «Сохранить».

### Посмотреть и временно поменять

- **Текст:** двойной клик по тексту в дереве — меняешь, Enter.
- **Стиль:** в панели Styles кликни по значению (например, `color`) и впиши другое. Галочка рядом со свойством выключает его.
- **Удалить элемент:** выбери в дереве и нажми **Delete**. Например, баннер, который закрывает кнопку.

Где это пригодится на работе:

- **Скриншот «как должно быть».** Дизайнер спрашивает: «А если поменять цвет кнопки?» Меняешь в Styles, делаешь скриншот — без разработчика.
- **Проверить длинный текст.** Вставляешь в заголовок карточки 200 символов и смотришь: перенеслось, обрезалось с «…» или вылезло за край?

::: warning Всё пропадёт после F5
Изменения в Elements живут только у тебя в браузере и до перезагрузки страницы. На сервере ничего не меняется, другие пользователи ничего не видят. Поэтому «поменял текст в Elements, и всё сломалось» — не баг: так пользователь сделать не может. А вот «длинное название, сохранённое через форму, ломает карточку» — баг.
:::

### Computed — что на самом деле применилось

Во вкладке Styles правил может быть много, и они перебивают друг друга. Рядом есть вкладка **Computed** — там итог: какой шрифт, размер, цвет, отступы реально у элемента.

На работе: в макете шрифт 16 px, а текст выглядит мельче. Смотришь Computed → `font-size: 14px`. Это уже факт для баг-репорта, а не «кажется, мелковато». Сверку с макетом подробно разберём в уроке про вёрстку.

### Принудительное состояние: hover, focus

Как проверить, какой цвет у кнопки при наведении мыши? Стоит увести мышь в DevTools — и наведение пропадает. Включи состояние принудительно:

1. Выбери кнопку в Elements.
2. В панели Styles нажми **`:hov`**.
3. Поставь галочку **`:hover`** (или `:focus`, `:active`).

Кнопка «застынет» в этом состоянии — можно спокойно смотреть стили и делать скриншот. То же есть в правом клике по элементу в дереве → **Force state**.

### Скрытый элемент: «в коде есть, на экране нет»

Элемент может быть в дереве, но не виден. Чаще всего из-за стиля `display: none` (элемент не рисуется совсем) или `visibility: hidden` / `opacity: 0` (место занято, но пусто). В дереве такие элементы обычно выглядят бледнее.

Где пригодится:

- **Кнопка пропала.** Ищешь её в Elements через Ctrl + F. Нет в дереве вообще — фронт её не нарисовал. Есть, но с `display: none` — её спрятали стилем. Это разные баги, и разработчику полезно знать, какой.
- **Права доступа.** Кнопка «Удалить» у читателя спрятана через `display: none`, но в коде она есть. Это сигнал: проверь, что API тоже запрещает удаление. Спрятать кнопку — не значит защитить данные. Подробно — в уроке 8 «Сессии, права и роли в интерфейсе».

::: tip Лайфхак: редактировать текст прямо на странице
Открой вкладку Console, вставь строку и нажми Enter:

```js
document.designMode = 'on'
```

Теперь любой текст на странице можно править кликом, как в текстовом редакторе. Удобно проверять длинные строки, переводы, перенос слов — сразу в нескольких местах. Выключить — `document.designMode = 'off'` или F5.
:::

## Console — что сломалось в JS

Console — журнал сообщений страницы. Сюда пишет JS сайта и сам браузер.

| Цвет | Что это | Что делать тестировщику |
|---|---|---|
| **Красный** — Error | Ошибка: что-то не выполнилось | Если появилась при твоём действии — почти всегда повод для бага |
| **Жёлтый** — Warning | Предупреждение: работает, но что-то не так | Обычно не баг. Отмечай, если связано с проблемой, которую ищешь |
| Серый / синий — Info, Log | Служебные сообщения разработчиков | Читать не обязательно |

### Ошибка в Console — повод для бага

Нажал кнопку — ничего не произошло, а в Console появилась красная строка. Например:

```
Uncaught TypeError: Cannot read properties of undefined (reading 'name')
    at TaskCard (TaskCard.tsx:42)
```

Понимать текст не обязательно. Обязательно — **скопировать его в баг-репорт целиком** (правый клик по ошибке → Copy или просто выделить). Разработчик по этой строке часто сразу видит файл и место, где сломалось.

Красная ошибка при загрузке страницы, если всё работает, — тоже стоит завести: с низким приоритетом или вопросом разработчику. Сегодня она безобидная, завтра может сломать что-то заметное.

### Не каждая ошибка — баг продукта

- **Расширения браузера.** Блокировщик рекламы, переводчик, менеджер паролей тоже пишут в Console. Признак — в адресе ошибки `chrome-extension://`. Проверка: открой сайт в режиме инкогнито (там расширения обычно выключены). Ошибка пропала — дело в расширении.
- **Заблокированные запросы.** `net::ERR_BLOCKED_BY_CLIENT` — запрос заблокировал твой блокировщик рекламы, а не сайт.
- **Старые ошибки.** Ошибка могла остаться от прошлых действий. Перед воспроизведением очищай Console.

### Полезные кнопки

- **Очистить:** значок 🚫 слева вверху или **Ctrl + L**.
- **Фильтр уровней** (Default levels): оставить только Errors, чтобы не тонуть в сообщениях.
- **Preserve log** (в настройках Console, значок шестерёнки): не очищать журнал при переходе на другую страницу. Нужно, когда ошибка случается прямо перед перезагрузкой или редиректом.

Программировать в Console тестировщику не нужно. Кроме `designMode`, пригодится разве что посмотреть, что сайт сохранил в браузере:

```js
localStorage
```

Но для этого удобнее вкладка Application — о ней ниже.

## Network — что ушло и что пришло

Самая важная вкладка для тестировщика. Network показывает **каждый запрос** страницы: к API, за картинками, шрифтами, скриптами. Это как Postman, только запросы отправляет сам сайт, а ты смотришь.

::: warning Network записывает только при открытых DevTools
Запросы, которые прошли до открытия DevTools, в список не попадут. Открыл Network — повтори действие или обнови страницу.
:::

### Шаг 1. Оставь только нужное

Наверху — фильтры по типу. Чаще всего нужен **Fetch/XHR** — это запросы к API. Остальные:

| Фильтр | Что покажет | Когда нужен |
|---|---|---|
| **Fetch/XHR** | Запросы к API за данными | Почти всегда |
| **Doc** | Саму страницу (HTML) | Код ответа страницы, редиректы |
| **JS, CSS, Font, Img** | Файлы фронта | Не загрузилась картинка или шрифт |
| Поле **Filter** | Поиск по адресу | Найти запрос, например `tasks` |

### Шаг 2. Читай колонки

| Колонка | Что значит |
|---|---|
| **Name** | Адрес запроса (конец адреса) |
| **Status** | Код ответа: `200`, `404`, `500`. `(failed)` или `(canceled)` — ответа нет вовсе |
| **Method** | `GET`, `POST`, `PATCH`, `DELETE`. Если колонки нет — правый клик по заголовку таблицы → **Method** |
| **Size** | Сколько весит ответ |
| **Time** | Сколько шёл ответ |

Красная строка в списке — ошибка: код `4xx`/`5xx` или запрос не дошёл.

### Шаг 3. Кликни по запросу

Справа откроются вкладки:

| Вкладка | Что там | Вопрос тестировщика |
|---|---|---|
| **Headers** | Адрес, метод, код ответа, заголовки запроса и ответа | Туда ли ушло? Есть ли `Authorization`? |
| **Payload** | Что фронт отправил: тело запроса и параметры адреса | Фронт отправил то, что я ввёл? |
| **Preview** | Ответ в удобном виде — раскрывающееся дерево | Быстро найти нужное поле |
| **Response** | Ответ как есть — сырой текст | Скопировать в баг-репорт |
| **Timing** | Из чего сложилось время: ожидание сервера, загрузка | Почему так долго? |

Если у запроса нет тела (например, `GET`), вкладки Payload может не быть или в ней будут только параметры адреса.

### Шаг 4. Галочки, которые спасают

- **Preserve log** — не очищать список при переходе на другую страницу. Без неё после редиректа (например, после входа) запросы с прошлой страницы исчезают — и кажется, что «запрос не отправлялся».
- **Disable cache** — не брать файлы из кэша браузера, пока DevTools открыты. Включай, когда разработчик говорит «я уже исправил, а у тебя старое».

### Как ещё пригодится Network

**Повторить запрос в Postman.** Правый клик по запросу → **Copy** → **Copy as cURL**. В Postman: **Import** → вставить текст. Запрос со всеми заголовками и токеном готов — можно менять поля и проверять API в обход интерфейса. Как работать с cURL, ты знаешь из урока [«Postman и curl»](/api/10-postman-i-curl).

::: tip На Windows
Там два варианта: **Copy as cURL (bash)** и **Copy as cURL (cmd)**. Для Postman подходит bash. Для командной строки Windows — cmd.
:::

**Найти данные во всех запросах.** Нажми **Ctrl + F** (Cmd + F), когда фокус в Network. Откроется поиск по заголовкам и ответам всех запросов. Пример: на экране сумма «1 250 ₽». Ищешь `1250` — и сразу видишь, какой запрос её принёс.

**Медленный интернет.** Выпадающий список **No throttling** → **Slow 4G**, **3G** или **Offline**. Так проверяют, что показывает сайт при медленной сети и без неё. Подробно — в уроке 9 «Сеть, кэш и нестабильность».

**Отдать разработчику всё сразу — HAR.** HAR — файл со всеми запросами и ответами со вкладки Network. Значок «скачать» (стрелка вниз) в панели Network → **Export HAR**. Разработчик откроет его у себя и увидит то же, что ты. Помогает, когда баг воспроизводится только у тебя.

::: danger В HAR — секреты
В HAR попадают тела запросов и ответов: пароль из формы входа, токен в ответе на вход, личные данные пользователя. Новые версии Chrome при обычном экспорте вырезают часть чувствительных заголовков, но тела остаются. Перед отправкой: записывай HAR на тестовом пользователе, не на своём боевом аккаунте; не выкладывай HAR в общий чат; при необходимости открой файл в текстовом редакторе и удали токены и пароли.
:::

### Что увидел в Network → что это значит

| Что видишь | Что это значит | Что делать |
|---|---|---|
| Нужного запроса нет | Фронт не отправил запрос | Проверь фильтры и Preserve log. Если действительно нет — баг фронта, смотри Console |
| `(failed)`, `net::ERR_...` | Запрос не дошёл до сервера: нет сети, сервер недоступен, заблокировал браузер | Повтори. Если стабильно — приложи текст ошибки |
| `(canceled)` | Браузер сам отменил запрос — например, ушёл со страницы или фронт отправил новый | Обычно не баг. Подозрительно, если отменяется нужный запрос |
| `401` | Нет входа или токен не принят | Проверь, что в Headers есть `Authorization` |
| `403` | Вход есть, прав нет | Сверь с ролью по спецификации |
| `4xx` с понятным `message` | API отказал и объяснил | Показал ли фронт этот текст? |
| `500`, `502`, `503` | Ошибка на сервере | Баг бэка (или инфраструктуры). Приложи запрос и ответ |
| `200`, а в ответе не те данные | API ответил неверно | Баг бэка — сверь со спецификацией API |
| `200`, данные верные, а на экране не то | Фронт неправильно показал | Баг фронта |
| Один и тот же запрос уходит 2–5 раз подряд | Лишние запросы | Баг фронта: лишняя нагрузка, иногда двойное создание |
| Time — несколько секунд | Медленный ответ | Посмотри Timing и Size: долго думал сервер или ответ огромный |
| Ответ весит мегабайты | Отдаётся лишнее: все записи без пагинации, лишние поля | Вопрос разработчику, на больших данных станет баг |

## Application — что сохранено в браузере

Сайт может хранить данные прямо у тебя в браузере. Слева в разделе **Storage** — три главных места:

| Хранилище | Что там обычно | Сколько живёт |
|---|---|---|
| **Local Storage** | Токен входа, настройки, тема, черновики, корзина | Пока не удалят: переживает закрытие браузера |
| **Session Storage** | Временные данные одной вкладки: шаг формы, фильтры | До закрытия вкладки. В новой вкладке — пусто |
| **Cookies** | Сессия, токены, согласие с cookie, язык | Пока не истечёт срок или не удалят. Отправляются на сервер с каждым запросом сами |

Внутри каждого хранилища — таблица «ключ → значение». Что с ней можно делать:

- **посмотреть:** кликни по адресу сайта под нужным хранилищем;
- **поменять:** двойной клик по значению;
- **удалить одну запись:** выделить → **Delete**;
- **удалить всё сразу:** раздел **Storage** (самый верх слева) → **Clear site data**. Сайт «забудет» тебя, как будто ты впервые зашёл.

### Где это пригодится на работе

- **Проверить «первый вход».** Онбординг, баннер о cookie, подсказки показываются только новым пользователям. Не нужно заводить новый аккаунт и чистить весь браузер — **Clear site data** для этого сайта.
- **Проверить истёкшую сессию.** Удали или испорти токен → F5. Что увидит пользователь: экран входа с понятным сообщением или белый экран и ошибки?
- **Найти «баг только у меня».** У тебя сломано, у коллеги — нет. Частая причина — старые данные в хранилище. Сравни Local Storage, попробуй Clear site data. Помогло — это тоже баг: у пользователей после релиза будет то же самое.

### Где TaskFlow web хранит вход

У веб-клиента TaskFlow всё просто:

- после входа токен лежит в **Local Storage**, ключ **`taskflow_access_token`**;
- с каждым запросом к API фронт отправляет его в заголовке **`Authorization: Bearer …`** — видно в Network → Headers;
- при открытии страницы фронт отправляет `GET /api/v1/users/me`. Токена нет или API ответил `401` — фронт удаляет ключ и показывает экран входа;
- при выходе («Выйти») — запрос `POST /api/v1/auth/logout`, ключ удаляется из Local Storage;
- cookies для входа веб-клиент не использует.

Сессии, выход, работу в нескольких вкладках подробно разберём в уроке 8 «Сессии, права и роли в интерфейсе».

## Подмена ответа (Local Overrides)

Иногда нужно проверить, как фронт покажет **редкий ответ**: пустой список, очень длинное название, 1000 элементов, странные данные. Создавать всё это через API — долго, а иногда невозможно. В Chrome можно **подменить ответ сервера у себя в браузере**. Бэк при этом не трогаешь, другие пользователи ничего не видят.

Как это сделать (Chrome последних версий, названия пунктов могут слегка отличаться):

1. Network → правый клик по нужному запросу → **Override content**.
2. Первый раз Chrome попросит выбрать папку на компьютере, где хранить подменённые ответы. Создай пустую папку, например `overrides`, и разреши доступ (полоса сверху DevTools → **Allow**).
3. Откроется ответ этого запроса как файл. Поменяй его: например, сделай список пустым или впиши длинное название. Сохрани — **Ctrl + S** (Cmd + S).
4. Обнови страницу. Теперь фронт получает твой ответ. В Network такой запрос помечен значком подмены.
5. **Выключи, когда закончишь:** вкладка Sources → Overrides → снять галочку **Enable Local Overrides**. Иначе потом будешь долго искать, почему данные «не обновляются».

Что так удобно проверять:

- **пустое состояние:** `"items": []` — показал ли фронт «Пока нет данных» или пустую таблицу без объяснений;
- **длинный текст:** название на 300 символов — перенос, обрезка, вылезло ли за край;
- **необычные данные:** `null` вместо имени, будущая дата, отрицательная сумма, эмодзи;
- **много элементов:** в ответе 100 записей вместо 3 — поехала ли вёрстка.

::: warning Подмена — инструмент исследования, а не доказательство
Нашёл проблему с подменённым ответом — сначала подумай, может ли API такое вернуть на самом деле. Пустой список — да. `null` в обязательном по спецификации поле — нет, тогда это не баг фронта. В баг-репорте честно пиши: «ответ подменён через Local Overrides, вот такой».
:::

Код ответа (например, `500` вместо `200`) так подменить не получится — только содержимое и заголовки. Как сымитировать ошибки сервера и обрыв сети — в уроке 9.

## Как этим работать на задаче — по шагам

Чек-лист, который тестировщик делает при каждом баге в вебе.

**До воспроизведения:**

1. Открой DevTools **заранее**: Network и Console записывают только то, что случилось при открытых DevTools.
2. Console: очисти (Ctrl + L).
3. Network: фильтр **Fetch/XHR**, включи **Preserve log**, очисти список (значок 🚫).

**Воспроизведи:**

4. Повтори действие медленно, шаг за шагом.
5. Смотри на Console — появились красные ошибки?
6. Смотри на Network — какой запрос ушёл, какой код, что в Payload и Response?

**Определи и проверь:**

7. По таблице выше реши, где баг: фронт, бэк или «запрос не дошёл».
8. Исключи себя: повтори в инкогнито (расширения) или после Clear site data (старые данные).

**Приложи к баг-репорту:**

- шаги, ожидаемый и фактический результат — как обычно;
- скриншот экрана (или запись экрана);
- **текст ошибки из Console** — целиком, текстом, а не только скриншотом;
- **запрос из Network**: метод, адрес, код ответа, Payload и Response (текст или скриншот);
- если пригодится — cURL запроса или HAR (без секретов!);
- браузер и его версия: ⋮ → «Справка» → «О браузере Google Chrome».

<details class="details custom-block" open>
<summary>Разбор 1. «Кнопка "Оформить заказ" не работает» — но не у всех</summary>

**Ситуация.** Интернет-магазин. В поддержку пишут: нажимаю «Оформить заказ» — ничего не происходит. Тестировщики на стенде повторить не могут: у них всё работает. Жалоб немного, но это деньги.

**Что видит мидл.**

- «Не у всех» — значит, разница в окружении пользователя: браузер, расширения, данные в хранилище.
- Попросил у поддержки скриншот Console от одного из пользователей. Там: `net::ERR_BLOCKED_BY_CLIENT` для скрипта аналитики и сразу за ним красная ошибка `Uncaught TypeError: ... analytics is undefined`.
- Поставил себе популярный блокировщик рекламы — воспроизвелось. Блокировщик не дал загрузиться аналитике, а код кнопки сначала отправляет событие в аналитику и падает, не дойдя до заказа.
- Блокировщик — не вина пользователя. Сайт не должен ломаться из-за того, что не загрузилась аналитика. Это баг продукта.

**Что делать.**

1. Завести баг: шаги с блокировщиком (какой, какая версия), текст ошибки из Console целиком, запрос со статусом «blocked» из Network.
2. Указать масштаб: блокировщиками пользуется заметная доля людей — это не «редкий случай».
3. Предложить добавить в регрессию проверку ключевых сценариев с блокировщиком рекламы.

**Чего не делать.**

- Не закрывать как «не воспроизводится» и не писать «у пользователя проблемы с браузером». Ошибка в Console — прямая улика.

::: details Разбор 2. «Страница заказов грузится 10 секунд»
**Ситуация.** Личный кабинет. Пользователи жалуются, что страница «Мои заказы» открывается очень долго. Бэкенд-разработчик проверил запрос в Postman: отвечает за 300 мс. «У меня всё быстро».

**Что видит мидл.**

- Открыл Network с фильтром Fetch/XHR и обновил страницу. Запрос списка заказов действительно быстрый.
- Но сразу за ним — **по одному запросу на каждый заказ**: `GET /orders/1/status`, `GET /orders/2/status`… У пользователя 300 заказов — 300 запросов. Каждый быстрый, вместе — 10 секунд.
- В Postman это не видно: там проверяли один запрос. Видно только в Network, когда работает настоящий фронт.
- Тестовые пользователи на стенде с 3 заказами этого не замечали.

**Что делать.**

1. Завести баг: скриншот Network с количеством запросов (внизу панели — «300 requests»), время загрузки страницы, сколько заказов у пользователя.
2. Указать, что проблема растёт с количеством данных, и проверить на пользователе с большим числом заказов.
3. Добавить в свои проверки: «сколько запросов уходит при открытии страницы» — это видно за секунду.

**Чего не делать.**

- Не проверять скорость только на тестовом пользователе с тремя записями.
:::

::: details Разбор 3. «После релиза у части пользователей белый экран»
**Ситуация.** После релиза новой версии сайта у части пользователей вместо главной — белый экран. Новые пользователи и тестировщики ничего такого не видят. Откат помогает.

**Что видит мидл.**

- «Новые пользователи не видят» — значит, всё дело в том, что уже сохранено у старых.
- В Console у пострадавшего: `TypeError: Cannot read properties of undefined (reading 'items')`.
- В Application → Local Storage — ключ `cart` в старом формате: просто список, а новая версия ждёт объект с полем `items`. Тестировщики проверяли релиз в чистом браузере — у них старых данных не было.
- Clear site data «чинит» белый экран. Но пользователи так делать не будут — для них сайт просто сломан.

**Что делать.**

1. Завести баг: значение из Local Storage, ошибка из Console, «после Clear site data — работает».
2. Как воспроизвести: открыть старую версию, положить товар в корзину, обновиться до новой версии без очистки данных.
3. Предложить добавить в чек-лист релиза: «обновление поверх старой версии с заполненными данными в браузере».

**Чего не делать.**

- Не советовать пользователям «почистите кэш» как решение. Это обходной путь на время исправления, а не исправление.
:::

## Частые ошибки

- **Открыть DevTools после бага.** Network и Console пишут только при открытых DevTools. Открыл — воспроизведи ещё раз.
- **«Запроса нет», а стоит не тот фильтр** или нет Preserve log. Сначала проверь фильтры.
- **Скриншот ошибки вместо текста.** Ошибку из Console и ответ из Network копируй текстом — разработчик будет их искать.
- **Изменения в Elements принимать за баг.** То, что поменял ты руками, пользователь сделать не может.
- **Отправить HAR в общий чат.** В нём токены и пароли.
- **Забыть выключить Local Overrides или Disable cache.** Потом полдня ищешь, почему «данные не меняются».
- **Каждую ошибку в Console считать багом сайта.** Сначала проверь в инкогнито — может, это расширение.

## Часть 1. Network на TaskFlow

**Задача 1** (джун). Войди как Иван (`ivan@example.com`, пароль — в `README.md` репозитория). Найди запрос входа. Что в Payload? Что в Response? Какой запрос уходит сразу после входа и в каком заголовке он передаёт токен?

::: details Подсказка
Запрос входа — `POST`, в адресе есть `login`. Заголовок с токеном ищи во вкладке Headers следующего запроса, в разделе Request Headers.
:::

::: details Эталон
`POST http://localhost:8000/api/v1/auth/login`, код `200`.

- **Payload:** `email` и `password` — пароль виден открытым текстом. Это нормально: в DevTools ты видишь запрос до отправки, у себя в браузере. В пути его защищает HTTPS (на локальном стенде HTTPS нет). Но именно поэтому HAR с входом нельзя отправлять кому попало.
- **Response:** `accessToken` — токен входа.
- **Следующий запрос:** `GET /api/v1/users/me` — фронт узнаёт, кто вошёл. В Request Headers — `Authorization: Bearer <токен>`, тот же токен, что пришёл при входе.
:::

**Задача 2** (джун). Открой любой проект. В Network найди запрос этого проекта, скопируй его как cURL и импортируй в Postman. Отправь. Ответ тот же? Потом в Postman выключи заголовок `Authorization` и отправь ещё раз.

::: details Эталон
Запрос — `GET /api/v1/projects/<id>`. Правый клик → Copy → **Copy as cURL (bash)**. В Postman: **Import** → вставить текст → Send. Ответ тот же, код `200`: Postman отправил запрос со всеми заголовками и твоим токеном.

Без `Authorization` — код `401`: API не знает, кто ты.

Так на работе быстро переносят запрос из интерфейса в Postman и дальше проверяют API в обход фронта: меняют поля, токен, id.
:::

**Задача 3** (мидл). Нажми **Ctrl + F** (Cmd + F), когда фокус в Network, и найди `ivan@example.com` во всех запросах. В каких запросах он встречается? О чём это говорит, если разработчик попросит у тебя HAR?

::: details Эталон
Как минимум в двух местах: в Payload запроса входа `POST /auth/login` и в ответе `GET /users/me`. Если открывал участников проекта — ещё и там.

Вывод: личные данные и секреты разбросаны по многим запросам — не только по тому, где их вводили. В HAR попадёт всё это сразу: email, пароль из входа, токен. Поэтому HAR записывают на тестовом пользователе и не выкладывают в общие чаты.
:::

## Часть 2. Application и подмена ответа на TaskFlow

**Задача 4** (джун). Найди, где веб-клиент хранит токен. Сравни значение с заголовком `Authorization` из задачи 1. Нажми «Выйти» и посмотри хранилище ещё раз.

::: details Эталон
Application → Storage → **Local Storage** → `http://localhost:3000` → ключ `taskflow_access_token`. Значение совпадает с тем, что после слова `Bearer` в заголовке.

После «Выйти» уходит `POST /api/v1/auth/logout`, и ключ пропадает из Local Storage. В Cookies для входа ничего нет — TaskFlow web их не использует.

**Задача 5** (джун). Войди снова. В Local Storage допиши в конец значения токена пару любых символов (двойной клик по значению). Обнови страницу (F5). Что в Network и что на экране? А что будет, если удалить ключ целиком и обновить страницу?

::: details Эталон
Испорченный токен: при загрузке уходит `GET /api/v1/users/me` с испорченным токеном, ответ `401`. Фронт удаляет ключ из Local Storage и показывает экран входа.

Ключ удалён: запроса `/users/me` нет вовсе — фронт видит, что токена нет, и сразу показывает экран входа.

Так за минуту проверяют «что будет, когда сессия истекла» — не дожидаясь, пока токен устареет сам.

Кнопки создания в пустом блоке нет, она в шапке раздела. Это совпадает со спецификацией. Без подмены пришлось бы искать или создавать пользователя без проектов.
2. Длинное название: смотри, перенеслось ли оно, обрезалось или растянуло таблицу. **Подвох:** в форме создания проекта название ограничено 100 символами, и API тоже не примет длиннее. Значит, 300 символов от API прийти не может. Вёрстку честно проверять на 100 символах — максимуме, который бывает на самом деле. Проблема с 300 символами — не баг, а результат нереальной подмены.
:::

## Часть 3. Учебные сайты

**Задача 7** (джун). Открой [uitestingplayground.com/visibility](http://uitestingplayground.com/visibility) и нажми **Hide**. Кнопки исчезли с экрана. Найди каждую в Elements: какие ещё есть в коде и как они спрятаны?

::: details Подсказка
Выбери кнопку **Hide** в Elements — остальные кнопки рядом в дереве. Смотри панель Styles у каждой.
:::

::: details Эталон
Каждая кнопка спрятана по-своему, и это видно по её названию:

- **Removed** — удалена из дерева совсем;
- **Zero Width** — ширина `0`;
- **Overlapped** — на месте, но перекрыта другим элементом;
- **Opacity 0** — полностью прозрачная, но место занимает;
- **Visibility Hidden** — `visibility: hidden`;
- **Display None** — `display: none`;
- **Offscreen** — сдвинута за пределы экрана.

Вывод: «не видно на экране» — это семь разных ситуаций. В баг-репорте «кнопка пропала» полезно указать, какая из них.
:::

**Задача 8** (джун). Открой [the-internet.herokuapp.com/javascript_error](https://the-internet.herokuapp.com/javascript_error). На экране всё выглядит нормально. Что в Console? Что из этого ты положишь в баг-репорт?

::: details Эталон
В Console красная ошибка, примерно: `Uncaught TypeError: Cannot read properties of undefined (reading 'xyz')`. Справа от неё — файл и строка, где она случилась.

В баг-репорт — текст ошибки целиком (текстом, не только скриншотом), адрес страницы, когда появляется (при загрузке) и браузер. Важно: на экране ничего не сломано, но ошибка при загрузке — тоже повод для бага, просто с низким приоритетом.
:::

**Задача 9** (мидл). Открой [uitestingplayground.com/ajax](http://uitestingplayground.com/ajax) и нажми кнопку. Надпись появляется не сразу. Найди запрос в Network. Сколько он идёт? Из чего складывается время — посмотри вкладку Timing.

::: details Эталон
После клика уходит запрос к серверу, колонка Time — около 15 секунд. На вкладке Timing почти всё время — ожидание ответа сервера (**Waiting for server response**), а сама загрузка ответа — миллисекунды.

Вывод: долго думает сервер, а не долго качается ответ и не тормозит фронт. На реальном проекте с этим — к бэкенду. И второй вопрос для проверки: что видит пользователь эти 15 секунд — есть ли индикатор загрузки и можно ли нажать кнопку второй раз?
:::

## Часть 4. Задачи на внимательность

**Задача 10** (джун). Тестировщик видит в Console красную ошибку, в её адресе `chrome-extension://…`. Заводит баг на сайт. Что не так?

::: details Эталон
Ошибка из расширения браузера — блокировщика, переводчика, менеджера паролей. К сайту она, скорее всего, не относится. Проверь в режиме инкогнито: ошибка пропала — баг сайту не заводить. Если при этом сайт **ломается** из-за расширения — это уже другой разговор, см. разбор 1 в теории.
:::

**Задача 11** (мидл). Тестировщик в Elements поменял цену товара на `0 ₽`, нажал «Купить» — и заказ оформился на 0 ₽. Пишет: «Не баг, я сам поменял страницу». Прав ли он?

::: details О чём подумать
Что фронт отправил на сервер? Посмотри Payload.
:::

::: details Эталон
Зависит от того, что ушло на сервер. Если фронт отправляет только id товара и количество, а сервер сам считает цену — а заказ всё равно на 0 ₽, ищи, откуда взялся ноль. Если фронт отправляет **цену** из страницы, и сервер её принимает — это серьёзный баг бэка: цену можно подменить, даже не трогая Elements, просто запросом из Postman.

Правило: изменения в Elements не баг, пока они остаются на экране. Если они «доехали» до сервера и он их принял — баг.
:::

## Ситуационные кейсы

Это рабочие ситуации, о которых могут спросить и на собеседовании. Готового ответа, который нужно угадать, здесь нет. Сначала подумай сам, потом открывай разбор.

::: details Кейс 1. «Кнопка не работает. Ваши действия?»
**Ситуация.** Интервьюер: «Пользователь пишет, что кнопка "Сохранить" не работает. Что будете делать?»

**Как рассуждать.** Что нужно открыть до того, как нажать кнопку?

**Пример ответа.** Открываю DevTools заранее: Console очищаю, в Network ставлю Fetch/XHR и Preserve log. Нажимаю кнопку. Смотрю Console — есть ли красная ошибка. Смотрю Network — ушёл ли запрос, какой код, что в Payload и Response. Нет запроса и есть ошибка в Console — фронт. Запрос с `500` — бэк. Ответ верный, а экран не обновился — фронт. Повторяю в инкогнито, чтобы исключить расширения. В баг-репорт — текст ошибки, запрос и ответ.
:::

::: details Кейс 2. «Какие вкладки DevTools вы используете?»
**Ситуация.** Интервьюер: «Расскажите, как вы работаете с DevTools».

**Как рассуждать.** Какой вопрос решает каждая вкладка?

**Пример ответа.** Network — главная: запросы, коды, что отправил фронт и что ответил API, время ответа; оттуда же Copy as cURL в Postman и HAR для разработчика. Console — ошибки JS, прикладываю их к багам. Elements — проверить вёрстку и скрытые элементы, принудительно включить hover, временно поменять текст. Application — Local Storage, Session Storage, Cookies: где лежит токен, проверка истёкшей сессии, Clear site data для «первого входа». Ещё Device Mode для быстрого взгляда на мобильную версию и подмена ответов для редких состояний.
:::

::: details Кейс 3. Хитрый вопрос: «В Console ошибка, но всё работает. Заводить баг?»
**Ситуация.** Интервьюер: «При загрузке страницы в Console красная ошибка, но пользователь ничего не замечает. Ваши действия?»

**Как рассуждать.** Чья это ошибка и что она может сломать завтра?

**Пример ответа.** Сначала проверяю, что ошибка от сайта, а не от расширения: смотрю адрес, повторяю в инкогнито. Если от сайта — завожу баг с низким приоритетом, с текстом ошибки и страницей. Ошибка в JS может прервать выполнение кода дальше — сегодня это незаметно, завтра поверх добавят функцию, и она сломается. Плюс сыплющиеся ошибки мешают замечать новые.
:::

::: details Кейс 4. Хитрый вопрос: «Баг воспроизводится только у вас»
**Ситуация.** Интервьюер: «Вы нашли баг, а у разработчика и у коллег всё работает. Что будете делать?»

**Как рассуждать.** Чем твой браузер отличается от браузера коллеги?

**Пример ответа.** Ищу, чем отличается моё окружение. Пробую инкогнито — исключаю расширения. Смотрю Application: что сохранено в Local Storage и Cookies; пробую Clear site data. Включаю Disable cache и делаю жёсткую перезагрузку — исключаю старые файлы. Если после очистки бага нет — это всё равно может быть баг: у пользователей тоже остаются старые данные после релиза. Тогда выясняю, какие именно данные ломают страницу, и отдаю разработчику значение из хранилища или HAR.
:::

::: details Кейс 5. «Как проверить пустой список, если на стенде у всех есть данные?»
**Ситуация.** Интервьюер: «Нужно проверить, как экран выглядит без данных. На тестовом стенде у всех пользователей что-то есть. Удалять нельзя».

**Как рассуждать.** Обязательно ли менять данные на сервере?

**Пример ответа.** Варианты: завести нового пользователя — у него пусто. Или подменить ответ API в браузере через Local Overrides в Chrome: `items: []` — и смотреть, что показал фронт. Бэк при этом не трогаю, другим не мешаю. Важно подменять только на то, что API реально может вернуть, иначе найду «баги», которых не бывает.
:::

::: details Кейс 6. Хитрый вопрос: «Разработчик просит HAR. Отправите в общий чат?»
**Ситуация.** Интервьюер: «Разработчик не может воспроизвести баг и просит HAR. Как подготовите файл?»

**Как рассуждать.** Что лежит внутри HAR?

**Пример ответа.** HAR содержит все запросы и ответы с телами: пароль из формы входа, токены, личные данные. Поэтому записываю его на тестовом пользователе, с открытыми с самого начала DevTools и Preserve log, только нужный сценарий. Отправляю лично разработчику, а не в общий чат. При необходимости открываю файл и вычищаю токены и пароли. Если всё же записал на настоящем аккаунте — меняю пароль и выхожу из системы, чтобы старый токен перестал работать (если система отзывает токены при выходе — это тоже стоит проверить).
:::

::: details Кейс 7. Хитрый вопрос: «Кнопку "Удалить" у читателя спрятали. Проверено?»
**Ситуация.** Интервьюер: «По требованиям читатель не может удалять. В интерфейсе кнопки "Удалить" у него нет. Задача закрыта?»

**Как рассуждать.** Кнопки нет на экране — а в коде? И что будет, если отправить запрос?

**Пример ответа.** Не закрыта. Проверяю в Elements: может, кнопка есть, но спрятана стилем. Главное — отправляю запрос удаления от имени читателя напрямую в API: беру cURL из Network, меняю метод и адрес в Postman. API должен ответить `403`. Если удалил — баг бэка, и серьёзный. Спрятать кнопку — удобство, защита — на сервере.
:::
