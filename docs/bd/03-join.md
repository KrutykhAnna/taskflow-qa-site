## Простыми словами

У тебя два списка. В первом — задачи, и у каждой записан **номер** исполнителя: «Логин — 2», «JWT — 3». Во втором — сотрудники с номерами: «2 — Иван», «3 — Анна». Чтобы получить «Логин — Иван», ты берёшь номер из первого списка и ищешь его во втором.

`JOIN` делает то же самое: склеивает строки двух таблиц по общему номеру. Задача + сотрудник с тем же номером = одна строка результата, где видно и название задачи, и имя исполнителя.

Вся сложность урока — в вопросе «а что делать со строками, для которых пары не нашлось?». Задача без исполнителя, клиент без заказов, сотрудник без руководителя. Разные виды `JOIN` отвечают на него по-разному. И если ответить неправильно, запрос молча потеряет строки.

В этом уроке разберём:

- зачем вообще соединять таблицы;
- **`INNER JOIN`**: синтаксис `JOIN … ON`, псевдонимы таблиц, куда пропадают строки без пары;
- **`LEFT JOIN`** — главный для тестировщика: поиск записей «без пары» и ловушка с условием в `WHERE`;
- `RIGHT`, `FULL` и `CROSS JOIN` — коротко, когда они нужны;
- несколько `JOIN` подряд и соединение таблицы с самой собой;
- связь «многие ко многим» через `project_members`;
- **мидл:** откуда берутся дубли после `JOIN` и почему `DISTINCT` их не лечит;
- `JOIN` и мягкое удаление;
- **как тестировщик использует `JOIN`** в работе.

Примеры в теории — на таблицах TaskFlow и на учебных таблицах магазина: `customers` (клиенты), `orders` (заказы), `order_items` (строки заказа), `products` (товары), `employees` (сотрудники). Скрипт, который их создаёт, — во вкладке «Задание»: выполни его в онлайн-песочнице и повторяй примеры.

## Зачем соединять таблицы

В уроке [«Что такое база данных»](/bd/01-chto-takoe-bd) ты видел: в таблице `tasks` нет имени исполнителя — только `assignee_id`, номер строки в `users`. Нет и названия проекта — только `project_id`.

Это сделано специально. Каждый факт хранится **в одном месте**: имя пользователя — только в `users`. Если Анна сменит фамилию, её поменяют в одной строке, а не в сотне задач, комментариев и списков участников. Такое разложение данных по таблицам называют **нормализацией**.

Цена — чтобы увидеть «задачу с именем исполнителя и названием проекта», таблицы приходится соединять. В уроке 1 ты делал это руками: посмотрел `owner_id`, потом нашёл этот `id` в `users`. `JOIN` делает это одним запросом для всех строк сразу.

## INNER JOIN: только строки с парой

### Синтаксис: JOIN … ON

```sql
SELECT tasks.title, users.first_name, users.last_name
FROM tasks
JOIN users ON users.id = tasks.assignee_id;
```

Как это читать:

- `FROM tasks` — берём задачи, это **левая** таблица;
- `JOIN users` — присоединяем пользователей, это **правая** таблица;
- `ON users.id = tasks.assignee_id` — **условие пары**: строка задачи и строка пользователя склеиваются, если номер исполнителя задачи равен `id` пользователя.

`JOIN` и `INNER JOIN` — одно и то же, слово `INNER` можно не писать.

Условие в `ON` почти всегда связывает **внешний ключ** одной таблицы с **первичным ключом** другой: `tasks.assignee_id → users.id`, `tasks.project_id → projects.id`, `comments.author_id → users.id`. Связи TaskFlow — на ER-схеме из урока 1.

### Где JOIN в порядке выполнения

В уроке [«SELECT: выбрать и отфильтровать»](/bd/02-select) был порядок выполнения: `FROM → WHERE → SELECT → ORDER BY → LIMIT`. `JOIN` — часть шага `FROM`. Сначала база собирает **соединённую таблицу**, и только потом `WHERE` фильтрует её строки. Запомни это: на этом построена главная ловушка урока — она ниже, в разделе про `LEFT JOIN`.

### Псевдонимы таблиц

Писать `tasks.title`, `users.first_name` долго. Таблицам дают короткие **псевдонимы**:

```sql
SELECT t.id, t.title, u.first_name, u.last_name
FROM tasks t
JOIN users u ON u.id = t.assignee_id
WHERE t.deleted_at IS NULL;
```

`tasks t` — то же, что `tasks AS t`. После этого в запросе таблица называется только `t`: написать `tasks.title` уже нельзя.

Обычно берут первую букву или сокращение: `t` — tasks, `u` — users, `p` — projects, `pm` — project_members, `c` — comments.

### Полные имена столбцов

В обеих таблицах есть столбец `id`. И `deleted_at`. И `created_at`. Если написать просто `id`, база не поймёт, какой:

```sql
SELECT id, title, first_name
FROM tasks t
JOIN users u ON u.id = t.assignee_id;
-- ERROR: column reference "id" is ambiguous
```

`ambiguous` — «неоднозначный». Исправление — указать таблицу: `t.id`. Если нужны оба `id`, дай им разные псевдонимы:

```sql
SELECT t.id AS task_id, u.id AS user_id, t.title, u.first_name
FROM tasks t
JOIN users u ON u.id = t.assignee_id;
```

Привычка мидла: **в запросе с `JOIN` писать таблицу перед каждым столбцом**, даже если имя уникально. `first_name` сейчас есть только в `users`, но завтра его могут добавить в другую таблицу — и старый запрос сломается. И читать запрос с `u.first_name` проще: сразу видно, откуда столбец.

### Строки без пары пропадают

`INNER JOIN` оставляет **только пары**. Строка, для которой не нашлось пары, в результат не попадает — ни слева, ни справа.

В TaskFlow у задачи «Настроить CI» исполнителя нет: `assignee_id IS NULL`. Условие `u.id = NULL` для неё — UNKNOWN, пары нет. Запрос выше вернёт все задачи, **кроме** неё. Ошибки не будет. Результат выглядит как «список задач», и в нём просто на одну меньше.

## LEFT JOIN — главный для тестировщика

### Все строки слева

```sql
SELECT t.id, t.title, u.first_name, u.last_name
FROM tasks t
LEFT JOIN users u ON u.id = t.assignee_id
WHERE t.deleted_at IS NULL;
```

`LEFT JOIN` оставляет **все строки левой таблицы**. Есть пара — склеивает. Нет пары — оставляет строку, а столбцы правой таблицы заполняет `NULL`. «Настроить CI» теперь в списке, с `NULL` вместо имени.

Чтобы вместо `NULL` было понятное слово — `COALESCE` из урока 2:

```sql
SELECT t.id, t.title, COALESCE(u.first_name || ' ' || u.last_name, 'не назначен') AS assignee
FROM tasks t
LEFT JOIN users u ON u.id = t.assignee_id
WHERE t.deleted_at IS NULL;
```

`LEFT JOIN` и `LEFT OUTER JOIN` — одно и то же.

**Какая таблица левая.** Та, что в `FROM`. Порядок важен: `tasks LEFT JOIN users` — «все задачи и их исполнители», `users LEFT JOIN tasks` — «все пользователи и их задачи». Это разные вопросы и разные результаты.

**Сколько строк вернёт.** `LEFT JOIN` возвращает **не меньше** строк, чем в левой таблице, — если после него нет `WHERE`. Больше — может: у одного пользователя три задачи — три строки. Про это — раздел о дублях.

### Поиск «без пары»

Самый полезный для тестировщика приём урока. Нужно найти записи, у которых **нет** связанных записей: проекты без задач, пользователи без проектов, заказы без строк.

Рецепт: `LEFT JOIN`, а потом оставить строки, где правая сторона пустая:

```sql
-- клиенты, которые ни разу не заказывали
SELECT c.id, c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
```

Почему работает: у клиента без заказов пары нет, и `LEFT JOIN` заполнил столбцы `orders` `NULL`. У клиентов с заказами `o.id` заполнен — значит, они отсеются. На учебных таблицах — 3 строки.

**Какой столбец проверять на `IS NULL`.** Тот, который у **настоящей** строки правой таблицы пустым быть не может: первичный ключ или столбец `NOT NULL`. Обычно — `id`. Если проверять столбец, который бывает `NULL` сам по себе, — например, `o.employee_id`, — в результат попадут и клиенты, у которых заказ есть, но без менеджера.

В TaskFlow у `project_members` нет столбца `id`: первичный ключ составной — `(project_id, user_id)`. Проверяют любой из них:

```sql
-- пользователи, которые не участвуют ни в одном проекте
SELECT u.id, u.email
FROM users u
LEFT JOIN project_members pm ON pm.user_id = u.id
WHERE pm.user_id IS NULL
  AND u.deleted_at IS NULL;
```

В начальных данных TaskFlow таких двое: Дмитрий Соколов и Ольга Смирнова.

### Ловушка: условие на правую таблицу в WHERE

Нужен список «все клиенты и их доставленные заказы». Клиенты без доставленных заказов тоже должны быть в списке — с пустыми столбцами заказа.

```sql
-- неправильно: клиенты без доставленных заказов исчезли
SELECT c.name, o.id, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'DELIVERED';
```

На учебных таблицах — 4 строки из 10 клиентов. Что произошло:

1. `LEFT JOIN` честно сохранил всех клиентов. У клиента без заказов `o.status` — `NULL`.
2. Потом `WHERE` проверил `o.status = 'DELIVERED'`. Для `NULL` это UNKNOWN — строка выброшена. Для клиента, у которого только отменённый заказ, — FALSE, тоже выброшена.
3. Остались только строки с парой. **`LEFT JOIN` превратился в `INNER JOIN`.**

Правильно — перенести условие в `ON`:

```sql
-- правильно: условие участвует в поиске пары
SELECT c.name, o.id, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'DELIVERED'
ORDER BY c.id;
```

Теперь 10 строк — все клиенты. Условие стало частью вопроса «есть ли пара»: пара — это **доставленный** заказ этого клиента. Нет такого — клиент остаётся с `NULL`.

Правило:

| Условие на … | При `LEFT JOIN` ставь в … | Почему |
|---|---|---|
| **левую** таблицу | `WHERE` | Отбирает, какие строки слева нужны вообще |
| **правую** таблицу | `ON` | Отбирает, какая строка справа считается парой |
| правую таблицу, `IS NULL` | `WHERE` | Это поиск «без пары» — так и задумано |

Для `INNER JOIN` разницы нет: строк без пары там и так не остаётся, условие в `ON` и в `WHERE` даст одно и то же. Обычно в `ON` пишут связь таблиц, а фильтры — в `WHERE`.

## RIGHT, FULL и CROSS JOIN

**`RIGHT JOIN`** — то же, что `LEFT`, только сохраняются все строки **правой** таблицы. `orders o RIGHT JOIN customers c` — то же, что `customers c LEFT JOIN orders o`. На практике почти всегда пишут `LEFT` и ставят главную таблицу в `FROM`: так запрос читается слева направо.

**`FULL JOIN`** (`FULL OUTER JOIN`) сохраняет строки **обеих** таблиц. Есть пара — склеивает, нет пары слева или справа — заполняет `NULL` другую сторону.

```sql
-- сверка: клиенты без заказов и заказы без клиента — в одном списке
SELECT c.name, o.id
FROM customers c
FULL JOIN orders o ON o.customer_id = c.id
WHERE c.id IS NULL OR o.id IS NULL;
```

Когда нужен: **сверка двух списков**. Выгрузка из старой системы и из новой после миграции, заказы в магазине и платежи в платёжной системе. `FULL JOIN … WHERE левая IS NULL OR правая IS NULL` сразу показывает расхождения с обеих сторон. На учебных таблицах — 6 строк: трое клиентов без заказов и три заказа гостей.

**`CROSS JOIN`** — каждая строка слева с **каждой** строкой справа, без условия:

```sql
SELECT c.name, p.name
FROM customers c
CROSS JOIN products p;
-- 10 клиентов × 12 товаров = 120 строк
```

Нужен редко: например, сгенерировать все комбинации «размер × цвет» для тестовых данных. Опасен тем, что его легко получить **случайно**. Старая запись соединения — таблицы через запятую, условие в `WHERE`:

```sql
SELECT o.id, c.name
FROM orders o, customers c
WHERE c.id = o.customer_id;     -- то же, что INNER JOIN
```

Забыл условие в `WHERE` — получил `CROSS JOIN`: 14 заказов × 10 клиентов = 140 строк. На таблицах по 100 000 строк это 10 миллиардов — запрос «повесит» базу. С записью `JOIN … ON` так не ошибёшься: без `ON` PostgreSQL выдаст синтаксическую ошибку.

## Несколько JOIN подряд

`JOIN` можно продолжать: каждый следующий присоединяет таблицу к тому, что уже собрано.

```sql
-- задача → проект → владелец проекта
SELECT t.id, t.title, p.name AS project, owner.first_name AS owner_name
FROM tasks t
JOIN projects p   ON p.id = t.project_id
JOIN users owner  ON owner.id = p.owner_id
WHERE t.deleted_at IS NULL;
```

Условие следующего `JOIN` может ссылаться на **любую** уже присоединённую таблицу. Здесь `owner` цепляется за `p`, а не за `t`.

Одну таблицу можно присоединить **дважды** — под разными псевдонимами. У задачи два разных человека: исполнитель и владелец проекта:

```sql
SELECT t.title,
       p.name                                     AS project,
       owner.first_name || ' ' || owner.last_name AS owner,
       a.first_name || ' ' || a.last_name         AS assignee
FROM tasks t
JOIN projects p     ON p.id = t.project_id
JOIN users owner    ON owner.id = p.owner_id
LEFT JOIN users a   ON a.id = t.assignee_id
WHERE t.deleted_at IS NULL;
```

Для каждой связи решай отдельно — `JOIN` или `LEFT JOIN`. Проект у задачи есть всегда: `project_id NOT NULL`, — значит, `INNER` ничего не потеряет. Исполнителя может не быть — значит, `LEFT`.

**Мидл: один `INNER` после `LEFT` может всё испортить.** Если после `LEFT JOIN users a` написать `JOIN` к таблице, которая цепляется за `a`, — строки, где `a` пустой, снова пропадут. Правило: если таблица присоединена через `LEFT`, всё, что цепляется за неё, тоже присоединяй через `LEFT`.

## Соединение таблицы с самой собой

В учебной таблице `employees` у каждого сотрудника есть `manager_id` — номер его руководителя в **этой же** таблице. Чтобы получить «сотрудник — руководитель», таблицу соединяют саму с собой — **self-join**:

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
JOIN employees m ON m.id = e.manager_id;
```

Одна таблица — два псевдонима и две роли: `e` — «сотрудник», `m` — «руководитель». База работает с ними как с двумя разными таблицами. Без псевдонимов self-join не написать: иначе непонятно, `employees.id` — это чей `id`.

Ловушка та же, что раньше: у генерального директора `manager_id IS NULL`, пары нет, и `INNER JOIN` его теряет — 9 строк из 10. Нужен список всех сотрудников — `LEFT JOIN`:

```sql
SELECT e.name AS employee, e.position, COALESCE(m.name, '—') AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id
ORDER BY e.id;
```

Где ещё встречается: комментарий — ответ на другой комментарий (`parent_id`), категория внутри категории, задача — подзадача. В TaskFlow таких связей нет, но в рабочих проектах их много.

## Многие-ко-многим: project_members

Пользователь участвует в нескольких проектах, в проекте несколько участников. Такую связь «многие ко многим» хранят в **промежуточной таблице** — в TaskFlow это `project_members`. В каждой строке — пара `(project_id, user_id)` и **роль**: `OWNER`, `MANAGER`, `VIEWER` или `ADMIN`.

Чтобы получить «проект — участник — роль» с именами, нужно два `JOIN` — через промежуточную таблицу:

```sql
SELECT p.name AS project, u.first_name, u.last_name, pm.role
FROM project_members pm
JOIN projects p ON p.id = pm.project_id
JOIN users u    ON u.id = pm.user_id
WHERE p.deleted_at IS NULL
ORDER BY p.name, u.last_name;
```

Промежуточная таблица — центр запроса: от неё идут обе связи. Можно начать и с `projects` или с `users` — результат будет тот же, если все `JOIN` внутренние.

Обрати внимание на роль: она хранится **в связи**, а не у пользователя. Иван Иванов — `OWNER` в «Mobile Banking» и `MANAGER` в «TaskFlow Backend». Поэтому вопрос «какая роль у Ивана?» без проекта не имеет ответа.

Это не ошибка `JOIN`, это его смысл: связь «один ко многим» (1:N) размножает строку «одного». Ошибка — когда запрос, который должен был вернуть **проекты**, возвращает **пары проект–задача**, а дальше с ним работают как со списком проектов. «Проектов с задачами — 7», хотя их 4: в начальных данных TaskFlow так и выйдет. «Выручка выросла вдвое», хотя заказов столько же.

Ещё хуже, когда к одной таблице присоединяют **две** таблицы 1:N. Проект с 3 задачами и 3 участниками:

```sql
SELECT p.name, t.title, u.first_name
FROM projects p
JOIN tasks t            ON t.project_id = p.id
JOIN project_members pm ON pm.project_id = p.id
JOIN users u            ON u.id = pm.user_id
WHERE p.id = 1;
```

Задачи и участники друг с другом не связаны — база склеивает **каждую** задачу с **каждым** участником: 3 × 3 = 9 строк. Для «TaskFlow Backend» в начальных данных так и выйдет.

### Почему DISTINCT не лечит

Первая мысль — дописать `DISTINCT`. Посмотри, что получится на учебных таблицах. У Алёны Котовой 3 заказа. Нужен список её заказов, а коллега зачем-то присоединил строки заказов:

```sql
SELECT o.id, o.status
FROM orders o
JOIN customers c    ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
WHERE c.name = 'Алёна Котова';
-- 5 строк: заказ 1 дважды, заказ 3 трижды
```

С `SELECT DISTINCT o.id, o.status` — 2 строки. Дубли пропали, но заказов у Алёны **три**. Заказ 14 пустой — в нём нет ни одной строки, и `INNER JOIN` с `order_items` его потерял. `DISTINCT` спрятал дубли и вместе с ними спрятал, что запрос неправильный.

Правильно — убрать лишний `JOIN`. Он ничего не добавлял в результат, только размножал строки.

`DISTINCT` уместен, когда тебе **по смыслу** нужен список уникальных значений: «какие клиенты покупали товары Sony» — один клиент мог купить два товара, а в ответе он нужен один раз. Неуместен — когда им прикрывают дубли, причину которых ты не понимаешь.

### Проверка числа строк

Привычка, которая ловит и потери, и дубли: **сравнивать число строк до и после `JOIN`**.

1. Сколько строк в главной таблице с твоими условиями — без `JOIN`? DBeaver показывает число строк под результатом.
2. Добавь `JOIN`. Сколько стало?
3. Меньше — `INNER JOIN` потерял строки без пары. Больше — где-то связь 1:N. Ровно столько же — для связи «многие к одному» (задача → проект, задача → исполнитель) так и должно быть.

Задача → проект, комментарий → автор — это «многие к одному»: у каждой задачи **один** проект. Такой `JOIN` строк не размножает. Проект → задачи, пользователь → проекты — «один ко многим»: размножает. Перед каждым `JOIN` полезно спросить себя: «сколько пар может быть у одной строки?».

## JOIN и мягкое удаление

В TaskFlow удалённые записи лежат в базе с заполненным `deleted_at`. В запросе к одной таблице ты уже пишешь `deleted_at IS NULL`. В запросе с `JOIN` фильтр нужен **у каждой** таблицы, которая может быть удалена. Иначе в результат попадут живые задачи удалённого проекта, комментарии удалённых пользователей, удалённые участники.

```sql
-- действующие комментарии действующих задач с именем автора
SELECT c.id, c.text, t.title, u.first_name
FROM comments c
JOIN tasks t ON t.id = c.task_id
JOIN users u ON u.id = c.author_id
WHERE c.deleted_at IS NULL
  AND t.deleted_at IS NULL;
```

А `u.deleted_at`? Зависит от вопроса. Комментарий удалённого пользователя — это всё ещё комментарий к задаче. Если вопрос «какие комментарии видны в задаче» — фильтр по автору не нужен. Если «какие пользователи сейчас комментируют» — нужен. Решай по смыслу, а не «на всякий случай».

**Где ставить фильтр при `LEFT JOIN`.** Это та же ловушка `ON` против `WHERE`. Нужны «все действующие задачи, имя исполнителя — только если он не удалён»:

```sql
-- неправильно: задача удалённого исполнителя пропадает целиком
SELECT t.title, u.first_name
FROM tasks t
LEFT JOIN users u ON u.id = t.assignee_id
WHERE t.deleted_at IS NULL
  AND u.deleted_at IS NULL;

-- правильно: фильтр правой таблицы — в ON
SELECT t.title, u.first_name
FROM tasks t
LEFT JOIN users u ON u.id = t.assignee_id AND u.deleted_at IS NULL
WHERE t.deleted_at IS NULL;
```

Первый вариант коварный. Задачи без исполнителя в нём **остаются**: у них `u.deleted_at` — `NULL`, условие `IS NULL` верно. А вот задача удалённого исполнителя исчезает целиком — хотя задача живая и пользователь её видит. Во втором варианте задача на месте, а имя — `NULL`: пара «удалённый пользователь» не считается парой.

На учебных таблицах та же разница: `orders LEFT JOIN customers` с фильтром `c.deleted_at IS NULL` в `WHERE` — 13 строк из 14, пропал заказ удалённого клиента. В `ON` — все 14.

## Как тестировщик использует JOIN

**1. Сверить ответ API с базой.** `GET /api/v1/tasks?projectId=1` вернул задачи с полями `projectName`, `assigneeFirstName`, `assigneeLastName`. Эти поля API собирает из других таблиц — значит, проверять их нужно тоже соединением:

```sql
SELECT t.id, p.name AS project_name, u.first_name, u.last_name
FROM tasks t
JOIN projects p    ON p.id = t.project_id
LEFT JOIN users u  ON u.id = t.assignee_id
WHERE t.project_id = 1
  AND t.deleted_at IS NULL
ORDER BY t.id;
```

Сравниваешь построчно: то же число задач, те же имена, у задачи без исполнителя в API — `null` в обоих полях имени. Расхождение — повод разбираться, где ошибка: в данных или в коде, который их собирает.

**2. Найти «осиротевшие» записи.** Внешний ключ не даст сохранить задачу с несуществующим `project_id`. Но мягко удалённый проект для внешнего ключа — обычная существующая строка. Поэтому «сирот» ищут так: живая запись, у которой родитель удалён.

```sql
-- живые задачи в удалённых проектах — по спецификации таких быть не должно
SELECT t.id, t.title, p.name, p.deleted_at
FROM tasks t
JOIN projects p ON p.id = t.project_id
WHERE t.deleted_at IS NULL
  AND p.deleted_at IS NOT NULL;
```

Спецификация TaskFlow говорит: удаление проекта каскадом помечает его задачи и их комментарии. Пустой результат — каскад сработал. Не пустой — баг.

Другая «сирота» — живая задача, назначенная на удалённого пользователя. Здесь каскада нет, и это не обязательно баг. Но это готовый тест-кейс: что показывает API в поле исполнителя? Может ли такой пользователь сменить статус задачи?

**3. Проверить права.** Кто в проекте и с какой ролью — `project_members` + `users`. Перед проверкой «`VIEWER` не может создать задачу» найди в базе пользователя, который в этом проекте именно `VIEWER`, а не угадывай.

**4. Найти особые случаи для тестов.** Например, задачи, исполнитель которых **не** участник проекта:

```sql
SELECT t.id, t.title, t.project_id, t.assignee_id
FROM tasks t
LEFT JOIN project_members pm
       ON pm.project_id = t.project_id
      AND pm.user_id    = t.assignee_id
WHERE t.assignee_id IS NOT NULL
  AND pm.user_id IS NULL
  AND t.deleted_at IS NULL;
```

Здесь `ON` из двух условий: пара — это строка участника **этого** проекта с **этим** пользователем. Спецификация TaskFlow такое разрешает — раздел 3, «Доступ исполнителя»: такой пользователь видит задачу, меняет её статус и комментирует, но не правит остальное. Для тестировщика это готовый набор данных: на этих задачах проверяют урезанные права исполнителя.

**Привычки:**

- **сначала — число строк без `JOIN`**, потом с ним. Разница должна быть объяснима;
- **для каждой связи — осознанный выбор `INNER` или `LEFT`**: «может ли тут не быть пары?»;
- **`deleted_at` — у каждой таблицы**, и для `LEFT JOIN` — в `ON`;
- **таблица перед каждым столбцом**: `t.id`, `u.first_name`.

## Разборы из жизни

Пять ситуаций, где `JOIN` обманывает того, кто его пишет. Первый разбор открыт — это образец. Остальные сначала попробуй разобрать сам.

<details class="details custom-block" open>
<summary>Разбор 1. В отчёте «заказы с именами клиентов» нет заказов гостей — магазин цветов</summary>

**Ситуация.** Магазин разрешил заказывать без регистрации. Через месяц бухгалтер сверяет отчёт «Заказы за месяц» с платёжной системой: в отчёте 1 840 заказов, оплат — 2 310. Разработчик: «Отчёт берёт все заказы, фильтров нет».

**Что видит мидл.**

- Фильтров в `WHERE` может и не быть — строки теряет `JOIN`. Отчёт показывает имя клиента, значит, заказы соединены с клиентами.
- У гостевого заказа `customer_id` пустой. `INNER JOIN customers` для него пары не находит — заказ пропадает молча.
- Разница появилась ровно с запуском гостевых заказов — это подтверждает догадку.

**Что делать.**

1. Посчитать в базе заказы за месяц без всяких `JOIN`. Сравнить с отчётом и с оплатами.
2. Найти заказы, которые есть в базе, но нет в отчёте: `orders LEFT JOIN customers … WHERE c.id IS NULL`. Посмотреть, все ли они гостевые.
3. Завести баг: «Отчёт не показывает заказы без аккаунта: 470 заказов за октябрь. Причина — `INNER JOIN` с `customers`. Ожидается: все заказы, у гостевых в столбце клиента — "Гость"». Приложить оба запроса.
4. Проверить другие отчёты и экраны, которые показывают имя клиента. Скорее всего, ошибка не одна.
5. Добавить в регрессию: «в периоде есть гостевой заказ — он в отчёте».

**Чего не делать.**

- Не проверять отчёт на тестовых данных, где у всех заказов есть клиент. На них `INNER` и `LEFT` дают одно и то же.

</details>

::: details Разбор 2. Выручка выросла вдвое за один релиз — служба доставки
**Ситуация.** В отчёт по выручке добавили столбец «служба доставки». После релиза выручка за вчера — 3,1 млн вместо обычных 1,6 млн. Продажи не росли.

**Что видит мидл.**

- Для «службы доставки» к заказам присоединили таблицу доставок. Крупный заказ отправляют несколькими посылками — у заказа несколько доставок, связь 1:N.
- Заказ из двух посылок стал двумя строками, его сумма посчиталась дважды. Из трёх — трижды.
- Выручка почти удвоилась, потому что крупные заказы — те, что дают основные деньги, — чаще делятся на посылки.

**Что делать.**

1. Взять один заказ, который отправили несколькими посылками. Выполнить запрос отчёта только для него — сколько строк?
2. Сравнить число строк отчёта до и после нового `JOIN` за один день.
3. Завести баг: «После добавления столбца "служба доставки" сумма заказа учитывается столько раз, сколько у него доставок. Пример: заказ 5512, 3 доставки, сумма 42 000 — в отчёте 126 000».
4. Подсказать вопрос к требованиям: что показывать в столбце, если у заказа две службы доставки? От ответа зависит исправление.

**Чего не делать.**

- Не предлагать `DISTINCT` как исправление. Два разных заказа на одинаковую сумму тоже «схлопнутся» — выручка станет меньше настоящей.
:::

::: details Разбор 3. «Все менеджеры работали» — а половины нет в отчёте — CRM колл-центра
**Ситуация.** Руководитель смотрит отчёт «Менеджеры и их звонки за сегодня». В нём 12 человек, у всех есть звонки. Он хвалит команду. А в отделе 20 менеджеров.

**Что видит мидл.**

- Отчёт задуман как `managers LEFT JOIN calls`, чтобы менеджеры без звонков тоже были видны — с пустыми столбцами.
- Фильтр «за сегодня» стоит в `WHERE`: `WHERE calls.created_at >= current_date`. У менеджера без звонков `calls.created_at` — `NULL`, условие — UNKNOWN, строка выброшена.
- Условие на правую таблицу в `WHERE` превратило `LEFT JOIN` в `INNER JOIN`. Отчёт показывает ровно тех, кого руководителю и не нужно искать.

**Что делать.**

1. Сравнить: сколько менеджеров в таблице и сколько в отчёте.
2. Найти тех, кого нет, и проверить: у них за сегодня действительно ноль звонков?
3. Завести баг с правильным вариантом: условие на дату — в `ON`: `LEFT JOIN calls c ON c.manager_id = m.id AND c.created_at >= current_date`.
4. Добавить в проверку отчёта данные: менеджер, у которого звонки были **только вчера**. Такой менеджер — лучший тест: с ошибкой он пропадёт, без ошибки — будет в отчёте с нулём.

**Чего не делать.**

- Не проверять отчёт только в день, когда звонили все.
:::

::: details Разбор 4. В выгрузке «сотрудник — руководитель» нет генерального — HR-система
**Ситуация.** HR выгружает оргструктуру для аудиторов: «сотрудник, должность, руководитель». Аудитор: «А где генеральный директор? По штатке у вас 214 человек, в выгрузке 213».

**Что видит мидл.**

- Выгрузка — это self-join: `employees e JOIN employees m ON m.id = e.manager_id`.
- У генерального `manager_id` пустой — руководителя у него нет. `INNER JOIN` пары не нашёл и выбросил строку.
- Если завтра появится второй сотрудник без руководителя — например, совет директоров или внешний консультант, — он пропадёт так же.

**Что делать.**

1. Сравнить число строк выгрузки с числом строк в `employees`.
2. Найти, кого нет: `employees e LEFT JOIN employees m … WHERE m.id IS NULL`.
3. Завести баг: «Выгрузка теряет сотрудников без руководителя. Ожидается: `LEFT JOIN`, в столбце руководителя — пусто или "—"».
4. Заодно проверить сотрудника, чей руководитель уволен. Что показывает выгрузка?

**Чего не делать.**

- Не решать «добавим генеральному руководителя — самого себя». Это ломает данные, чтобы спрятать ошибку запроса, — и кто-нибудь построит дерево подчинения с бесконечным циклом.
:::

::: details Разбор 5. В списке участников чата — уволенные сотрудники — корпоративный мессенджер
**Ситуация.** Сотрудник жалуется: в списке участников рабочего чата видны люди, уволившиеся полгода назад. Им даже можно написать — сообщение «уходит», но ответа нет. Поддержка: «Уволенных мы удаляем, проверьте».

**Что видит мидл.**

- Увольнение — мягкое удаление: у пользователя заполнен `deleted_at`. Строки в таблице участников чатов `chat_members` при этом никто не трогает.
- Список строится так: `chat_members JOIN users`. Фильтр `deleted_at IS NULL` стоит у чата, но не у `users`. Удалённый пользователь — существующая строка, `JOIN` находит пару.
- Это не только ошибка списка. Если уведомления о новых сообщениях строятся тем же запросом, их рассылают по удалённым аккаунтам.

**Что делать.**

1. Найти одного уволенного в списке участников. Проверить в базе: `users.deleted_at` заполнен, строка в `chat_members` на месте.
2. Завести баг на список: «Список участников чата показывает удалённых пользователей. Нет фильтра `users.deleted_at IS NULL`».
3. Спросить у аналитика, как должно быть. Скрывать удалённых? Показывать с пометкой «покинул компанию»? Удалять строки участия при увольнении?
4. Проверить соседние места с тем же `JOIN`: упоминания через `@`, рассылку уведомлений, поиск коллег.

**Чего не делать.**

- Не проверять фильтр мягкого удаления только у «главной» таблицы. Удалена может быть любая таблица в соединении.
:::

## Частые ошибки

- **`INNER JOIN` там, где может не быть пары.** Строки пропадают молча: задачи без исполнителя, заказы гостей, генеральный без руководителя.
- **Условие на правую таблицу в `WHERE` при `LEFT JOIN`.** `LEFT` превращается в `INNER`. Условие — в `ON`.
- **Неверное условие в `ON`.** `c.id = o.id` вместо `c.id = o.customer_id` — запрос выполняется и склеивает случайные строки.
- **Столбец без имени таблицы.** `id`, `name`, `deleted_at` есть в нескольких таблицах — ошибка `ambiguous`, или, хуже, запрос берёт не тот столбец.
- **Таблицы через запятую без условия.** Случайный `CROSS JOIN`: m × n строк.
- **Дубли от связи 1:N.** Две таблицы «многие» в одном запросе — произведение строк.
- **`DISTINCT` вместо поиска причины дублей.** Прячет лишний `JOIN` и потерянные строки.
- **`deleted_at IS NULL` только у первой таблицы.** Удалённые проекты, пользователи, задачи «оживают» через соединение.
- **`IS NULL` не по тому столбцу при поиске «без пары».** Проверяй ключ или `NOT NULL`-столбец правой таблицы.
- **`INNER JOIN` после `LEFT JOIN` к той же цепочке.** Строки без пары, сохранённые `LEFT`, снова пропадают.
- **Не сравнить число строк до и после `JOIN`.** Самая простая проверка, которая ловит почти все ошибки урока.

## Часть 1. Задачи на TaskFlow (DBeaver)

Результаты зависят от твоего стенда: в блоке 2 ты создавал и удалял проекты, задачи, комментарии, участников. Поэтому эталон — это **запрос**, а не числа. Где сказано «в начальных данных» — это про данные, с которыми TaskFlow запускается впервые. «Действующие» записи — те, у которых `deleted_at IS NULL`.

### INNER JOIN

**Задача 1** (джун). Действующие задачи с названием проекта: `id` задачи, название задачи, название проекта.

::: details Подсказка
`tasks JOIN projects ON …`. Какой столбец задачи указывает на проект?
:::

::: details Эталон
```sql
SELECT t.id, t.title, p.name AS project
FROM tasks t
JOIN projects p ON p.id = t.project_id
WHERE t.deleted_at IS NULL
ORDER BY t.id;
```
`project_id` — `NOT NULL`, поэтому `INNER JOIN` здесь ни одной задачи не потеряет. Число строк должно совпасть с `SELECT … FROM tasks WHERE deleted_at IS NULL`.
:::

**Задача 2** (джун). Действующие проекты с именем и фамилией владельца в одном столбце `owner`.

::: details Подсказка
Владелец — `projects.owner_id`. Склейка строк — `||`.
:::

::: details Эталон
```sql
SELECT p.id, p.name, u.first_name || ' ' || u.last_name AS owner
FROM projects p
JOIN users u ON u.id = p.owner_id
WHERE p.deleted_at IS NULL
ORDER BY p.id;
```
То, что в уроке 1 ты делал руками в два запроса, — теперь одним.
:::

**Задача 3** (джун). Действующие задачи с именем исполнителя — через `INNER JOIN`. Сравни число строк с числом действующих задач. Каких задач не хватает?

::: details Подсказка
Какое значение `assignee_id` у задачи, которая не попала?
:::

::: details Эталон
```sql
SELECT t.id, t.title, u.first_name, u.last_name
FROM tasks t
JOIN users u ON u.id = t.assignee_id
WHERE t.deleted_at IS NULL
ORDER BY t.id;
```
Пропали задачи без исполнителя — в начальных данных это «Настроить CI». `INNER JOIN` выбросил их молча.
:::

**Задача 4** (джун). Выполни запрос и прочитай ошибку. Исправь так, чтобы в результате были `id` задачи, её название и имя исполнителя.

```sql
SELECT id, title, first_name
FROM tasks
JOIN users ON users.id = tasks.assignee_id;
```

::: details Подсказка
`id` есть в обеих таблицах. Дай таблицам псевдонимы и укажи, чей `id` нужен.
:::

::: details Эталон
```sql
SELECT t.id, t.title, u.first_name
FROM tasks t
JOIN users u ON u.id = t.assignee_id;
```
Ошибка была `column reference "id" is ambiguous`. `title` и `first_name` без таблицы работали, но привычка — указывать таблицу у каждого столбца.

**Задача 5** (джун). Действующие комментарии: текст, имя автора и название задачи.

::: details Подсказка
Три таблицы: `comments`, `users` по `author_id`, `tasks` по `task_id`.
:::

::: details Эталон
```sql
SELECT c.id, c.text, u.first_name AS author, t.title AS task
FROM comments c
JOIN users u ON u.id = c.author_id
JOIN tasks t ON t.id = c.task_id
WHERE c.deleted_at IS NULL
ORDER BY c.id;
```
`author_id` и `task_id` у комментария обязательны — `INNER` ничего не теряет.

### LEFT JOIN и записи без пары

**Задача 6** (джун). Все действующие задачи с исполнителем. Если исполнителя нет — текст `не назначен`. Сравни число строк с задачей 3.

::: details Подсказка
`LEFT JOIN` и `COALESCE`. Склейка с `NULL` даёт `NULL` — это здесь на руку.
:::

::: details Эталон
```sql
SELECT t.id, t.title,
       COALESCE(u.first_name || ' ' || u.last_name, 'не назначен') AS assignee
FROM tasks t
LEFT JOIN users u ON u.id = t.assignee_id
WHERE t.deleted_at IS NULL
ORDER BY t.id;
```
Строк столько же, сколько действующих задач. В задаче 3 было меньше ровно на число задач без исполнителя.
:::

**Задача 7** (джун). Действующие пользователи, которые не участвуют ни в одном проекте.

::: details Подсказка
`users LEFT JOIN project_members`, потом оставь строки без пары. У `project_members` нет столбца `id` — что проверить на `IS NULL`?
:::

::: details Эталон
```sql
SELECT u.id, u.email, u.first_name, u.last_name
FROM users u
LEFT JOIN project_members pm ON pm.user_id = u.id
WHERE pm.user_id IS NULL
  AND u.deleted_at IS NULL
ORDER BY u.id;
```
Проверяем столбец первичного ключа `pm.user_id`: у настоящей строки участия он не бывает пустым. В начальных данных — Дмитрий Соколов и Ольга Смирнова.
:::

**Задача 8** (мидл). Действующие задачи, у которых нет ни одного **действующего** комментария.

::: details Подсказка
Удалённый комментарий не должен считаться парой. Куда поставить `c.deleted_at IS NULL` — в `ON` или в `WHERE`?
:::

::: details Эталон
```sql
SELECT t.id, t.title
FROM tasks t
LEFT JOIN comments c ON c.task_id = t.id AND c.deleted_at IS NULL
WHERE c.id IS NULL
  AND t.deleted_at IS NULL
ORDER BY t.id;
```
Если поставить `c.deleted_at IS NULL` в `WHERE`, задача, у которой **все** комментарии удалены, пропадёт: её строки с удалёнными комментариями отбросит `WHERE`, а строки «без пары» у неё нет.
:::

**Задача 9** (мидл). Действующие проекты, в которых нет ни одной действующей задачи. Если результат пустой — создай проект через Swagger и выполни снова.

::: details Подсказка
Та же схема, что в задаче 8: фильтр удаления правой таблицы — в `ON`.
:::

::: details Эталон
```sql
SELECT p.id, p.name
FROM projects p
LEFT JOIN tasks t ON t.project_id = p.id AND t.deleted_at IS NULL
WHERE t.id IS NULL
  AND p.deleted_at IS NULL
ORDER BY p.id;
```
В начальных данных у каждого проекта есть задачи, поэтому пусто. Новый проект без задач появится в результате.
:::

**Задача 10** (мидл). Действующие **активные** пользователи, на которых не назначено ни одной действующей задачи.

::: details Подсказка
«Активный» — `is_active`. Условия на `users` — в `WHERE`, условие на `tasks` — в `ON`.
:::

::: details Эталон
```sql
SELECT u.id, u.first_name, u.last_name
FROM users u
LEFT JOIN tasks t ON t.assignee_id = u.id AND t.deleted_at IS NULL
WHERE t.id IS NULL
  AND u.is_active
  AND u.deleted_at IS NULL
```

В начальных данных — System Administrator. Ольга Смирнова тоже без задач, но она неактивна.

**Задача 11** (с собеседования). Все действующие проекты и их действующие задачи в статусе `DONE`. Проекты, где таких задач нет, тоже должны быть в списке — с пустыми столбцами задачи. Сначала поставь условие на статус в `WHERE` и сравни.

::: details Подсказка
Условие на правую таблицу в `WHERE` превращает `LEFT JOIN` в `INNER JOIN`.
:::

::: details Эталон
```sql
-- неправильно: проекты без готовых задач пропали
SELECT p.name, t.title, t.status
FROM projects p
LEFT JOIN tasks t ON t.project_id = p.id AND t.deleted_at IS NULL
WHERE p.deleted_at IS NULL
  AND t.status = 'DONE';

-- правильно
SELECT p.name, t.title, t.status
FROM projects p
LEFT JOIN tasks t
       ON t.project_id = p.id
      AND t.deleted_at IS NULL
      AND t.status = 'DONE'
WHERE p.deleted_at IS NULL
ORDER BY p.name, t.title;
```
В начальных данных первый запрос вернёт 2 проекта, второй — все 4, у «TaskFlow Backend» и «CRM System» столбцы задачи пустые.
:::

**Задача 12** (мидл). 20 последних записей журнала `audit_log`: время, действие, тип и номер объекта и email того, кто выполнил действие. Записи без пользователя тоже нужны.

::: details Подсказка
`audit_log.user_id` может быть пустым — по схеме он `nullable`.
:::

::: details Эталон
```sql
SELECT a.created_at, a.action, a.entity_type, a.entity_id, u.email
FROM audit_log a
LEFT JOIN users u ON u.id = a.user_id
ORDER BY a.created_at DESC, a.id DESC
LIMIT 20;
```
`INNER JOIN` выбросил бы записи без пользователя. Для журнала это опасно: пропадут именно необычные записи, которые и нужно расследовать.
:::

### Несколько JOIN

**Задача 13** (джун). Действующие задачи: название, название проекта и email владельца проекта.

::: details Подсказка
Задача → проект → пользователь. Третий `JOIN` цепляется за проект, а не за задачу.
:::

::: details Эталон
```sql
SELECT t.id, t.title, p.name AS project, owner.email AS owner_email
FROM tasks t
JOIN projects p    ON p.id = t.project_id
JOIN users owner   ON owner.id = p.owner_id
WHERE t.deleted_at IS NULL
ORDER BY t.id;
```
:::

**Задача 20** (мидл). Проверь правило из спецификации: владелец проекта (`projects.owner_id`) всегда есть в `project_members` с ролью `OWNER`. Найди действующие проекты, где это нарушено.

### Мягкое удаление в соединениях

**Задача 24** (мидл). Действующие задачи, исполнитель которых удалён или деактивирован.

::: details Подсказка
`INNER JOIN` здесь подходит: задачи без исполнителя нас не интересуют.
:::

::: details Эталон
```sql
SELECT t.id, t.title, u.email, u.is_active, u.deleted_at
FROM tasks t
JOIN users u ON u.id = t.assignee_id
WHERE t.deleted_at IS NULL
  AND (NOT u.is_active OR u.deleted_at IS NOT NULL)
ORDER BY t.id;
```
Внешний ключ такие задачи не запрещает: удалённый пользователь — существующая строка. Что при этом показывает API в поле исполнителя — хороший вопрос для исследования.

**Задача 25** (мидл). Проверь каскад из спецификации: действующие задачи в удалённых проектах.

::: details Подсказка

```sql
WHERE t.deleted_at IS NULL
  AND p.deleted_at IS NOT NULL;
```

Ожидается пусто: удаление проекта помечает удалёнными и его задачи. Если в блоке 2 ты удалял проект, а здесь есть строки — это находка.

**Задача 26** (мидл). То же для комментариев: действующие комментарии у удалённых задач.

::: details Подсказка
Задача удалена — `t.deleted_at IS NOT NULL`.

::: details Эталон

:::

**Задача 27** (с собеседования). Все действующие задачи с именем исполнителя. Имя показывай только у **неудалённого** пользователя: если исполнитель удалён — `NULL`, но задача остаётся в списке. Задачи без исполнителя — тоже в списке. Напиши два варианта — с `u.deleted_at IS NULL` в `WHERE` и в `ON` — и объясни разницу.

::: details Подсказка
Что `WHERE u.deleted_at IS NULL` сделает со строкой, где исполнитель удалён? А со строкой, где исполнителя нет?
:::

::: details Эталон
```sql
-- в WHERE: задача удалённого исполнителя исчезает целиком
SELECT t.id, t.title, u.first_name
FROM tasks t
LEFT JOIN users u ON u.id = t.assignee_id
WHERE t.deleted_at IS NULL
  AND u.deleted_at IS NULL;

-- в ON: задача на месте, имя — NULL
SELECT t.id, t.title, u.first_name
FROM tasks t
LEFT JOIN users u ON u.id = t.assignee_id AND u.deleted_at IS NULL
WHERE t.deleted_at IS NULL
ORDER BY t.id;
```
Задачи без исполнителя есть в обоих вариантах: у них `u.deleted_at` — `NULL`, условие `IS NULL` верно. Разница видна, только если на стенде есть задача с удалённым исполнителем. Нет такой — удали пользователя-исполнителя через API администратором, `DELETE /api/v1/users/{id}`, и сравни снова.
:::

### Дубли и число строк

**Задача 28** (мидл). Действующие проекты, у которых есть хотя бы одна действующая задача, — каждый проект **один раз**. Сначала напиши `JOIN` без `DISTINCT` и посмотри, сколько раз повторяется каждый проект.

::: details Подсказка
Проект → задачи — связь «один ко многим». Здесь `DISTINCT` уместен: тебе нужен список уникальных проектов, и ты понимаешь, откуда повторы.
:::

::: details Эталон
```sql
-- каждый проект — столько раз, сколько у него задач
SELECT p.id, p.name
FROM projects p
JOIN tasks t ON t.project_id = p.id
WHERE p.deleted_at IS NULL AND t.deleted_at IS NULL;

-- список проектов
SELECT DISTINCT p.id, p.name
FROM projects p
JOIN tasks t ON t.project_id = p.id
WHERE p.deleted_at IS NULL AND t.deleted_at IS NULL
ORDER BY p.id;
```
В `DISTINCT` есть `p.id`: два разных проекта с одинаковым названием не должны схлопнуться в одну строку.
:::

**Задача 29** (с собеседования). Одним запросом: проект с `id = 1`, его действующие задачи и его участники. Посчитай строки. Почему их столько? Как получить нормальный результат?

::: details Подсказка
Задачи и участники друг с другом не связаны. С кем база склеит каждую задачу?
:::

::: details Эталон
```sql
SELECT p.name, t.title, u.first_name, pm.role
FROM projects p
JOIN tasks t            ON t.project_id = p.id AND t.deleted_at IS NULL
JOIN project_members pm ON pm.project_id = p.id
JOIN users u            ON u.id = pm.user_id
WHERE p.id = 1
ORDER BY t.id, u.id;
```
Строк = задачи × участники. В начальных данных 3 × 3 = 9. Каждая задача повторена для каждого участника. Нормальный результат — **два** запроса: задачи проекта отдельно, участники отдельно. Две связи 1:N в одном `JOIN` почти всегда дают такое произведение.
:::

**Задача 30** (мидл). Сверка числа строк. Выполни три запроса и запиши число строк каждого: действующие задачи без `JOIN`; они же с `LEFT JOIN users` по исполнителю; они же с `INNER JOIN users`. Объясни каждое расхождение.

::: details Подсказка
Задача → исполнитель — связь «многие к одному». Может ли `LEFT JOIN` по ней дать больше строк?
:::

::: details Эталон
```sql
SELECT t.id FROM tasks t WHERE t.deleted_at IS NULL;

SELECT t.id FROM tasks t
LEFT JOIN users u ON u.id = t.assignee_id
WHERE t.deleted_at IS NULL;

SELECT t.id FROM tasks t
JOIN users u ON u.id = t.assignee_id
WHERE t.deleted_at IS NULL;
```
Первый и второй — одинаково: у задачи не больше одного исполнителя, а `LEFT` никого не теряет. Третий — меньше на число задач без исполнителя. Если бы второй дал **больше** — связь оказалась бы не «многие к одному», и это повод разбираться в схеме.
:::

## Часть 3 (мидл). Сверь API с базой через JOIN

Ответы API в TaskFlow содержат поля, которых нет в основной таблице: имя исполнителя, название проекта, имя автора комментария. API собирает их из других таблиц. Значит, и проверять их нужно соединением.

Для каждой ситуации напиши:

- какой запрос с `JOIN` выполнишь;
- что сравниваешь с ответом API — поле за полем;
- что будет багом.

Выполни хотя бы три ситуации на своём стенде по-настоящему: запрос в API → запрос в базу → скриншоты.

**Ситуация 1.** `GET /api/v1/projects/1/members` вернул список участников: `userId`, `role`, `firstName`, `lastName` и `total`.

::: details Эталон
```sql
SELECT pm.user_id, pm.role, u.first_name, u.last_name, u.deleted_at
FROM project_members pm
JOIN users u ON u.id = pm.user_id
WHERE pm.project_id = 1
ORDER BY pm.user_id;
```
Сравниваю: число строк с `total`, затем каждую строку — `userId`, роль, имя, фамилию. Багом будет: участник есть в базе, но нет в ответе или наоборот, у участника чужое имя или не та роль. Столбец `deleted_at` вывожу специально: если среди участников есть удалённый пользователь — проверяю, есть ли он в ответе API, и сверяю это с разделом 3 спецификации, «Soft delete». Расхождение со спецификацией — вопрос к аналитику или баг.
:::

**Ситуация 2.** `GET /api/v1/tasks/1/comments` вернул комментарии с полями `authorId`, `authorFirstName`, `authorLastName`, `text`.

::: details Эталон
```sql
SELECT c.id, c.author_id, u.first_name, u.last_name, c.text
FROM comments c
JOIN users u ON u.id = c.author_id
WHERE c.task_id = 1
  AND c.deleted_at IS NULL
ORDER BY c.id;
```
Ожидаю: те же комментарии в том же составе, имя и фамилия автора — из `users` по `author_id`. Удалённых комментариев в ответе нет. Багом будет: имя не того пользователя — например, текущего, а не автора; удалённый комментарий в списке; не хватает комментария.
:::

**Ситуация 3.** `GET /api/v1/projects/2` вернул `ownerId`. Проверь, что владелец — тот, кто нужно, и что правило «владелец — участник с ролью `OWNER`» выполняется.

::: details Эталон
```sql
SELECT p.id, p.name, p.owner_id, u.email, u.first_name, u.last_name, pm.role
FROM projects p
JOIN users u                 ON u.id = p.owner_id
LEFT JOIN project_members pm ON pm.project_id = p.id AND pm.user_id = p.owner_id
WHERE p.id = 2;
```
Ожидаю: `owner_id` совпадает с `ownerId`, в `pm.role` — `OWNER`. `LEFT JOIN` к `project_members` здесь нарочно: если строки участия нет, я увижу `NULL` в `role`, а не пустой результат, который ничего не объясняет. Багом будет `role` пустая или не `OWNER`.
:::

**Ситуация 4.** `GET /api/v1/tasks?projectId=1` вернул задачи с полями `projectName`, `assigneeId`, `assigneeFirstName`, `assigneeLastName`.

::: details Эталон
```sql
SELECT t.id, p.name AS project_name, t.assignee_id, u.first_name, u.last_name
FROM tasks t
JOIN projects p   ON p.id = t.project_id
LEFT JOIN users u ON u.id = t.assignee_id

  AND t.deleted_at IS NULL

```
Ожидаю: то же число задач, `projectName` у всех — название проекта 1, имена исполнителей совпадают. У задачи без исполнителя в API все три поля исполнителя — `null`. `LEFT JOIN` к `users` обязателен: с `INNER` такая задача пропала бы из моей проверки, и я бы решил, что API вернул «лишнюю» задачу. Учти пагинацию: если задач больше `limit`, сравнивай с `total`.

**Ситуация 5.** `POST /api/v1/projects/{id}/members` с телом `{"userId": 6, "role": "VIEWER"}` — добавить участника в свой проект. Ответ `201`.

```sql
SELECT user_id, action, entity_type, entity_id, details, created_at
FROM audit_log

ORDER BY id DESC
LIMIT 3;
```
Ожидаю: появилась ровно одна новая строка — пользователь 6 с ролью `VIEWER`, остальные участники не изменились. Тело ответа `201` совпадает с этой строкой: `userId`, `role`, имя и фамилия. Сразу после — `GET /projects/15/members`: новый участник в списке. В журнале — `project_member.add`, в `details` — `userId` и `role`. Багом будет: другая роль, вторая строка того же пользователя, изменилась роль другого участника.

**Ситуация 6.** `PATCH /api/v1/users/me` с телом `{"firstName": "Иннокентий"}` — ты сменил имя. Где ещё должно поменяться имя?

::: details Эталон

Имя хранится в одном месте — `users`. Все три списка собирают его через `JOIN` в момент запроса. Значит, после `PATCH` новое имя должно сразу появиться в `GET /tasks/{taskId}/comments`, `GET /projects/{id}/members` и `GET /tasks`. Если где-то в API осталось старое имя, а в базе новое — где-то хранится копия или кэш. Это баг, и в отчёте важно указать, в каком именно ответе.
:::

## Ситуационные кейсы

Это рабочие ситуации, о которых могут спросить и на собеседовании. Готового ответа, который нужно угадать, здесь нет. Сначала подумай сам, потом открывай разбор.

::: details Кейс 1. «Чем INNER JOIN отличается от LEFT JOIN?»
**Ситуация.** Интервьюер: «Объясните разницу. И приведите пример, когда выбор между ними — это баг».

**Как рассуждать.** Что каждый делает со строками без пары? Какая таблица «главная» в `LEFT`? Где в реальном отчёте бывают строки без пары?

**Пример ответа.** `INNER JOIN` возвращает только строки, для которых нашлась пара по условию `ON`. `LEFT JOIN` возвращает **все** строки левой таблицы: есть пара — склеивает, нет — заполняет столбцы правой таблицы `NULL`.

Пример бага: отчёт «заказы с именами клиентов» через `INNER JOIN`. Магазин разрешил гостевые заказы, у них `customer_id` пустой — и они молча пропали из отчёта. Ошибки нет, просто строк меньше. Поэтому для каждой связи я спрашиваю: «может ли тут не быть пары?» Если может, а строка нужна — `LEFT`.

Как тестировщик я проверяю такие отчёты на данных, где пары нет: заказ гостя, задача без исполнителя, сотрудник без руководителя. На «полных» данных `INNER` и `LEFT` не отличить.
:::

::: details Кейс 2. «Как найти записи, у которых нет связанных?»
**Ситуация.** Интервьюер: «Есть таблицы `users` и `orders`. Найдите пользователей, которые ни разу ничего не заказывали».

**Как рассуждать.** Что `LEFT JOIN` оставляет для пользователя без заказов? По какому столбцу это видно?

**Пример ответа.**

```sql
SELECT u.id, u.email
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
```

`LEFT JOIN` сохраняет всех пользователей. У тех, кто не заказывал, столбцы `orders` — `NULL`. `WHERE o.id IS NULL` оставляет именно их.

Важно, по какому столбцу проверять: по первичному ключу или столбцу `NOT NULL` правой таблицы. Если взять столбец, который сам бывает `NULL`, — например, `o.promo_code`, — попадут и пользователи с заказами без промокода.

Тот же приём находит проекты без задач, товары без продаж, задачи без комментариев. Для тестировщика это способ быстро найти данные для граничных случаев.
:::

::: details Кейс 3. Хитрый вопрос: «Почему после JOIN строк стало больше, чем в таблице?»
**Ситуация.** Интервьюер: «В таблице `orders` 1000 строк. После `LEFT JOIN` с `deliveries` — 1340. Как так? Это `LEFT`, он же сохраняет строки левой таблицы».

**Как рассуждать.** Сколько доставок может быть у одного заказа? Что `JOIN` делает, если пар несколько?

**Пример ответа.** `LEFT JOIN` гарантирует, что строк будет **не меньше** — но не «столько же». Если у заказа две доставки, база склеит его с каждой: две строки. Связь заказ → доставки — «один ко многим», она размножает строки заказа. 340 лишних строк — это заказы, у которых доставок больше одной.

Опасно, если дальше по такому результату что-то считают: выручка заказа учтётся столько раз, сколько у него доставок.

`DISTINCT` — не лечение: он склеит и два разных заказа на одинаковую сумму, если они совпадут по всем выбранным столбцам. Правильно — понять, что нужно в результате. Нужен заказ — не соединять с доставками. Нужна доставка — работать с доставками. Я бы проверил это сравнением числа строк до и после `JOIN` на заказе, отправленном несколькими посылками.
:::

::: details Кейс 4. Хитрый вопрос: «Условие для LEFT JOIN — в ON или в WHERE?»
**Ситуация.** Интервьюер показывает запрос «все клиенты и их заказы за октябрь» с `LEFT JOIN orders` и `WHERE o.created_at >= '2026-10-01'`. «Клиентов без заказов в октябре нет в результате. Почему?»

**Как рассуждать.** В каком порядке выполняются `JOIN` и `WHERE`? Что `WHERE` делает со строкой, где `o.created_at` — `NULL`?

**Пример ответа.** `JOIN` — часть `FROM`, он выполняется первым. `LEFT JOIN` честно сохранил всех клиентов, у клиентов без заказов `o.created_at` — `NULL`. Потом `WHERE` сравнил `NULL >= '2026-10-01'` — UNKNOWN — и выбросил строку. Остались только клиенты с подходящими заказами: `LEFT` фактически стал `INNER`.

Правило: условие на **правую** таблицу при `LEFT JOIN` — в `ON`: `LEFT JOIN orders o ON o.customer_id = c.id AND o.created_at >= '2026-10-01'`. Тогда оно решает, какой заказ считать парой, а не какого клиента оставить. Условие на **левую** таблицу — в `WHERE`. Исключение — `WHERE правая.id IS NULL` при поиске записей без пары: там так и задумано.

То же касается мягкого удаления: `u.deleted_at IS NULL` для правой таблицы в `WHERE` выбросит строку целиком, а в `ON` — только имя.
:::

::: details Кейс 5. «Что такое self-join? Пример»
**Ситуация.** Интервьюер: «Зачем соединять таблицу саму с собой?»

**Как рассуждать.** Где в одной таблице бывает ссылка на эту же таблицу? Как различить две роли одной таблицы в запросе?

**Пример ответа.** Self-join нужен, когда строки таблицы ссылаются на строки той же таблицы. Классика — сотрудники и руководители: у сотрудника `manager_id` — это `id` другого сотрудника.

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;
```

Одна таблица под двумя псевдонимами: `e` — сотрудник, `m` — руководитель. `LEFT`, потому что у генерального руководителя нет, и `INNER` его потеряет.

Ещё примеры: комментарий-ответ с `parent_id`, вложенные категории, подзадачи. Как тестировщик я бы проверил на такой структуре: запись без родителя, родитель удалён, цикл — запись ссылается сама на себя или два элемента ссылаются друг на друга.
:::

::: details Кейс 6. «Как через базу проверить, что API вернул правильное имя?»
**Ситуация.** Интервьюер: «`GET /tasks` возвращает у каждой задачи `assigneeFirstName`. В таблице `tasks` имени нет, только `assignee_id`. Как проверить, что имена правильные?»

**Как рассуждать.** Откуда API берёт имя? Как получить то же самое запросом? Какие задачи особенные?

**Пример ответа.** API собирает имя из `users` по `assignee_id`. Я делаю то же запросом:

```sql
SELECT t.id, u.first_name, u.last_name
FROM tasks t
LEFT JOIN users u ON u.id = t.assignee_id
WHERE t.project_id = 1 AND t.deleted_at IS NULL
ORDER BY t.id;
```

И сравниваю с ответом построчно: то же число задач, те же имена. `LEFT JOIN` — чтобы не потерять задачи без исполнителя: у них в API имя должно быть `null`, и это тоже нужно проверить.

Особые случаи, которые я бы проверил отдельно: исполнитель удалён или деактивирован; исполнитель сменил имя — новое имя должно появиться сразу во всех ответах; исполнитель не участник проекта. Если в API имя одно, а в базе другое — где-то копия или кэш, и это баг.
:::
