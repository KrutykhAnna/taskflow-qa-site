## Простыми словами

Ты отправляешь посылку. Курьерская служба пишет: «Принято». Это ответ API — служба **сказала**, что всё хорошо. А что на самом деле?

- посылка лежит на складе, а не потерялась по дороге;
- она целая, и в накладной — твой адрес, а не соседа;
- в журнале склада есть запись: кто принял, когда;
- соседние посылки никто не трогал.

Чтобы это узнать, мало прочитать «Принято». Нужно зайти на склад.

В практикуме блока 2 ты проверял фичу **снаружи** — по ответам API. Теперь — **снаружи и изнутри**: каждое действие в Postman, а сразу после него — взгляд в базу в DBeaver. Ты уже умеешь и то и другое по отдельности. Здесь их нужно соединить в одну работу на целой фиче.

Фича практикума — **жизненный цикл задачи** в TaskFlow: создать задачу, изменить её, обсудить в комментариях, удалить комментарий, удалить задачу, удалить проект.

Что пригодится из прошлых уроков:

- процесс тестирования фичи, чек-лист, баг-репорт, отчёт — урок [«Практикум: API-фича целиком»](/api/14-praktikum-api-fichi);
- `SELECT` и `WHERE` — урок [«SELECT: выбрать и отфильтровать»](/bd/02-select);
- `JOIN` и `LEFT JOIN` — урок [«JOIN: соединение таблиц»](/bd/03-join);
- `COUNT(*)`, `COUNT(столбец)` и `GROUP BY` — урок [«Агрегаты, GROUP BY, HAVING»](/bd/04-agregaty);
- приём «API → БД», мягкое удаление, журнал `audit_log` — урок [«Как тестировать базу данных»](/bd/05-testirovanie-bd).

В этом уроке разберём:

- процесс «API + БД» — пять вопросов к каждому шагу фичи;
- карту фичи: какой шаг что меняет в базе и что пишет в журнал;

- три разбора из жизни.

## Где это пригодится

На работе ты почти никогда не тестируешь «базу» отдельно. Ты тестируешь **фичу**, а база — один из инструментов. Типичные ситуации:

- **Новая фича.** Разработчик сделал удаление задач. Ответы API правильные. Но помечаются ли комментарии? Пишется ли журнал? Это видно только в базе.
- **Баг «иногда не сходится».** На экране «3 комментария», в списке — 2. Где правда? Запрос к базе за минуту покажет, кто ошибается — счётчик или список.
- **Разбор инцидента.** «Кто удалил проект?» Ответ — в журнале действий. Если журнал пишется не всегда, это баг, и найти его должен тестировщик до инцидента.
- **Доказательство в баг-репорте.** «API ответил `204`, а в базе запись не помечена» — с запросом и результатом. С таким баг-репортом разработчик не скажет «у меня не воспроизводится».

## Процесс «API + БД» по шагам

Общий процесс тестирования фичи — требования, карта, риски, чек-лист, прогон, баги, отчёт — ты прошёл в уроке [«Практикум: API-фича целиком»](/api/14-praktikum-api-fichi). Он не меняется. Меняется **прогон**: к каждому шагу фичи ты задаёшь пять вопросов.

| № | Вопрос | Чем отвечаешь |
|---|---|---|
| 1 | **Что я делаю?** | Запрос в Postman: кто, какой метод и путь, какое тело |
| 2 | **Что должно прийти?** | Спецификация: код, тело, поля. Запомни `id` из ответа |
| 3 | **Что стало в базе?** | `SELECT` по `id` из ответа — каждое поле |
| 4 | **Что изменилось рядом?** | Соседние таблицы и побочные эффекты: журнал `audit_log`, связанные записи, счётчики, каскады |
| 5 | **Что не должно было измениться?** | Соседние строки, другие задачи и проекты. После отказа — `403`, `404`, `422` — не изменилось **ничего** |

Пятый вопрос забывают чаще всего. А именно он ловит самые неприятные баги: `UPDATE` задел соседние строки, отказ `403` всё-таки что-то записал, повторное удаление перезаписало время.

**Как работать на практике.** Держи открытыми два окна: Postman и DBeaver. В DBeaver — подключение **только для чтения** из урока [«Что такое база данных»](/bd/01-chto-takoe-bd): в практикуме ты базу только читаешь, все изменения — через API. Для каждого шага:

1. Перед действием выполни «снимок» — `SELECT` строк, которые могут измениться.
2. Сделай запрос в Postman.
3. Выполни тот же `SELECT` ещё раз и сравни.
4. Посмотри журнал и соседние таблицы.

Сравнение «до и после» — главный способ поймать то, чего не должно было случиться.

Права — по спецификации, раздел 3 и разделы 6.3–6.5. Глобальный `ADMIN` может всё в любом проекте. Исполнитель без членства в проекте видит задачу, меняет только `status` и пишет комментарии.

Что важно знать о базе, чтобы правильно читать результаты:

- **`commentsCount` в базе не хранится.** Его считают в момент запроса: число комментариев задачи, у которых `deleted_at` пустой. Значит, сверять его надо с `COUNT(*)` по `comments` с условием `deleted_at IS NULL`.
- **В журнале у комментария — свой `id`.** Записи `comment.create`, `comment.update`, `comment.delete` пишутся с `entity_type = 'comment'` и `entity_id` — номером **комментария**, а не задачи. Чтобы найти все записи о комментариях задачи, нужен `JOIN` журнала с `comments`.
- **В `details` пишется не всегда.** У `task.update` и `project.update` — переданные поля и их новые значения. У создания, удаления и изменения комментария `details` пустой — но в базе это JSON-значение `null`, а не SQL `NULL`: DBeaver покажет `null`, а `WHERE details IS NULL` такие строки не найдёт.
- **Журнал пишется в той же транзакции, что и действие.** Нет изменения — нет записи. Отказ `403`, `404` или `422` в журнал не попадает. Чтение — `GET` — тоже.
- **Мягкое удаление.** Задача, комментарий и проект при удалении остаются в таблице, им заполняется `deleted_at`. Через API они после этого — `404`.
- **Каскад — одним моментом.** При удалении задачи её действующие комментарии получают **то же** время `deleted_at`, что и задача. Уже удалённые комментарии сохраняют своё, более раннее время. С проектом — так же: его действующие задачи и их комментарии получают время проекта.
- **Участники проекта при удалении проекта остаются** в `project_members` — по коду их никто не трогает. У этой таблицы нет `deleted_at`.
- **`cascadedTasks` в журнале** при удалении проекта — число задач, которые были **действующими** в момент удаления, а не всех задач проекта.

## Что сверять API ↔ БД

Для каждого шага — что сверить и готовый шаблон. Номера — пример: подставь свои из ответов API.

| Шаг | В ответе API | В базе |
|---|---|---|
| Создать задачу | `201`, `Location`, поля `TaskResponse`, `commentsCount: 0` | Строка в `tasks`: значения как в запросе, умолчания (`status`, `priority`), `deleted_at` пустой. Запись `task.create` |
| Изменить задачу | `200`, новые значения | Изменились **только** переданные поля. Запись `task.update` с этими полями в `details` |
| Отказ — `403`, `404`, `422` | Код и `error.code` | Строка как в снимке «до». Новой записи в журнале нет |
| Комментарий | `201`, `authorId` — тот, чей токен | Строка в `comments`, `author_id` — тот же. `commentsCount` = число действующих комментариев. Запись `comment.create` |
| Удалить комментарий | `204`, потом `GET` — `404` | Строка на месте, `deleted_at` заполнен. `commentsCount` меньше на 1. Запись `comment.delete` от того, **кто удалил** |
| Удалить задачу | `204` | `deleted_at` у задачи и её действующих комментариев — один момент. Запись `task.delete` |
| Удалить проект | `204` | Один момент у проекта, его действующих задач и их комментариев. Участники остались. `project.delete` с `cascadedTasks` |

**Задача целиком** — сверка с `TaskResponse`. `LEFT JOIN` нужен, потому что исполнителя может не быть:

```sql
SELECT t.id, t.project_id, p.name AS project_name,
       t.assignee_id, u.first_name, u.last_name,
       t.title, t.description, t.status, t.priority,
       t.created_at, t.deleted_at
FROM tasks t
JOIN projects p ON p.id = t.project_id
LEFT JOIN users u ON u.id = t.assignee_id
WHERE t.id = 8;
```

Поля ответа и столбцы связаны так: `projectId` — `project_id`, `projectName` — `p.name`, `assigneeId` — `assignee_id`, `assigneeFirstName` и `assigneeLastName` — `u.first_name` и `u.last_name`. В ответе — camelCase, в базе — snake_case, раздел 4 спецификации.

**Счётчик комментариев** — сверка с `commentsCount`:

```sql
SELECT COUNT(*) AS active_comments
FROM comments
WHERE task_id = 8 AND deleted_at IS NULL;
```

**Журнал по задаче:**

```sql
SELECT id, user_id, action, details, created_at
FROM audit_log
WHERE entity_type = 'task' AND entity_id = 8
ORDER BY id;
```

**Журнал по комментариям задачи** — через `JOIN`, потому что в журнале `id` комментария:

```sql
SELECT a.id, a.user_id, a.action, a.entity_id AS comment_id, a.created_at
FROM audit_log a
JOIN comments c ON c.id = a.entity_id
WHERE a.entity_type = 'comment' AND c.task_id = 8
ORDER BY a.id;
```

**Каскад** — сравни время удаления у задачи и её комментариев:

```sql
SELECT id, deleted_at FROM tasks WHERE id = 8;

SELECT id, author_id, deleted_at
FROM comments
WHERE task_id = 8
ORDER BY id;
```

**Соседи не задеты** — сколько удалённых задач в каждом проекте. Сделай до и после удаления: разница должна быть только у твоего проекта.

```sql
SELECT project_id, COUNT(*) AS deleted_tasks
FROM tasks
WHERE deleted_at IS NOT NULL
GROUP BY project_id
ORDER BY project_id;
```

## Как оформить находку с данными из БД

Баг-репорт строится как в блоке 2 — шаблон из урока [«Практикум: API-фича целиком»](/api/14-praktikum-api-fichi), часть 5. Добавляется одно: **доказательство из базы** — запрос и его результат. Запрос должен быть таким, чтобы разработчик скопировал его и увидел то же самое.

Пример — выдуманный сервис записи к врачу:

```text
Заголовок:    Отмена записи не освобождает слот — POST /appointments/{id}/cancel — пациент
Окружение:    тестовый стенд, сборка 2.14, Postman, DBeaver (только чтение)
Предусловия:  пациент записан на слот 3051, запись 812
Шаги:
  1. POST /api/appointments/812/cancel от пациента → 200, "status": "CANCELLED"
  2. GET /api/slots?doctorId=17&date=2026-11-03 → слот 3051 не показан как свободный
  3. Запрос в базу:
     SELECT id, is_booked, appointment_id FROM slots WHERE id = 3051;
Фактический:  API: запись отменена. База:
              id = 3051, is_booked = true, appointment_id = 812
Ожидаемый:    is_booked = false, appointment_id = NULL — слот снова доступен
              для записи. Требования, раздел 4.2: «после отмены слот освобождается»
X-Request-ID: 7f3c…e91 — запрос из шага 1
Серьёзность:  Major — отменённые слоты пропадают из расписания, врач теряет приёмы
Приоритет:    Высокий — потери каждый день, пока не исправлено
```

Что делает этот баг-репорт сильным:

- видно, что API **сказал** — отменено, и что **случилось** — слот занят;
- запрос в базу короткий и точный: по `id`, только нужные столбцы;
- результат запроса — как есть, без пересказа;
- ожидание — со ссылкой на требование.

Чего в баг-репорте быть не должно: пароль от базы, токены целиком, скриншот всей таблицы на сто строк.

## Разборы из жизни

<details class="details custom-block" open>
<summary>Разбор 1. Отзывов «12», а в списке 11 — маркетплейс</summary>

**Что случилось.** На карточке товара — «12 отзывов». Открываешь список — 11. Покупатели жаловались, что «отзывы пропадают». Поддержка отвечала: «Модератор удалил отзыв с нарушением, всё правильно».

**Что сделала тестировщица.** Сравнила счётчик с базой. В таблице товаров был столбец `reviews_count` — счётчик **хранился**, а не считался. Запросы:

```sql
SELECT id, reviews_count FROM products WHERE id = 5521;

SELECT COUNT(*) AS active_reviews
FROM reviews
WHERE product_id = 5521 AND deleted_at IS NULL;
```

`reviews_count = 12`, `active_reviews = 11`. Потом она проверила, на каких действиях счётчик меняется: создание — `+1`, удаление автором — `−1`, **удаление модератором — ничего**. У модератора был отдельный эндпоинт, и про счётчик в нём забыли. Таких товаров нашлось несколько сотен.

</details>

::: details Разбор 2. API ответил 204, а адрес вернулся через сутки — доставка продуктов
**Что случилось.** Пользователь удаляет адрес доставки. API отвечает `204`, адрес пропадает из списка. На следующий день адрес снова в списке. Тестировщик на демо проверил: `204`, `GET` — адреса нет. «Работает».

**Что нашли потом.** В базе у адреса `deleted_at` был пустой. Удаление записывалось только в кэш списка адресов, а изменение в базе не сохранялось — в коде потеряли сохранение. Пока жил кэш, адреса «не было». Кэш истёк — список собрался из базы заново, и адрес «воскрес».

```sql

FROM addresses
WHERE id = 90412;
```

Одного запроса сразу после `204` хватило бы: `deleted_at` пустой — баг.

**Вывод.** `204` — обещание, а не факт. После удаления смотри строку в базе: на месте ли она и заполнен ли `deleted_at`. `GET` после удаления может показывать кэш — про это урок [«Redis: кэш и не только»](/bd/07-redis).
:::

::: details Разбор 3. В журнале нет записи — никто не знает, кто удалил — система учёта сотрудников
**Что случилось.** Из системы пропала карточка сотрудника. Служба безопасности открыла журнал действий — записи об удалении нет. Кто и когда удалил — неизвестно.

**Что выяснили.** Удалить карточку можно было двумя способами: кнопкой «Удалить» на карточке и массово — «Удалить выбранные» в списке. Одиночное удаление писало журнал. Массовое — нет: его сделали позже и про журнал забыли. Тестировщик проверял массовое удаление по API и по базе — строки помечены, всё верно. В журнал не посмотрел.

```sql

FROM audit_log
WHERE entity_type = 'employee' AND entity_id IN (311, 312, 313)
ORDER BY id;
```

После массового удаления трёх карточек — пусто.

**Вывод.** Журнал — тоже результат действия, его проверяют как поле в базе. Для **каждого** пути изменения: есть ли запись, верный ли `user_id` — тот, кто сделал, а не автор объекта, — верные ли `entity_type`, `entity_id`, `details`. И наоборот: после отказа записи быть не должно.
:::

## Частые ошибки

- **Смотрит только ответ.** `201` и правильное тело — ещё не результат. Результат — строка в базе.
- **Ищет строку не по `id`.** Поиск по названию находит задачу из прошлого прогона или из чужого проекта. Ищи по `id` из ответа, а по названию — только вместе с `project_id`.
- **Не делает снимок «до».** Без него не видно, что изменилось лишнее.
- **Не смотрит базу после отказа.** `403` — не повод пропустить проверку: отказ не должен ничего записать.
- **Считает удалённым «то, чего нет в таблице».** В TaskFlow удалённое лежит в таблице с `deleted_at`. Чтобы его не было видно, во всех запросах, кроме проверки удаления, нужно условие `deleted_at IS NULL`.
- **Ищет комментарии в журнале по `id` задачи.** У них свой `entity_type` и свой `id`.
- **Меняет данные в базе руками, чтобы «подготовить» шаг.** В практикуме все изменения — только через API. Данные мимо API не проходят проверок и не пишут журнал.

## Часть 1. Прогон по шагам

Для каждого шага:

1. Сделай снимок «до» — запрос из эталона или свой.

3. Сравни с ожиданием по спецификации.
4. Напиши свой `SELECT` и проверь базу: строку, соседей, журнал.

### Шаг 1. Создать задачу — менеджер

`POST /api/v1/tasks` под менеджером:

```json
{
  "projectId": 5,
  "title": "qa-bd9 Отчёт по продажам",
  "description": "Собрать данные за квартал",
  "priority": "HIGH",
  "assigneeId": 10
}
```

**Проверь в базе:** строку задачи — каждое поле; запись в журнале.

::: details Эталон
```sql
SELECT t.id, t.project_id, p.name AS project_name,
       t.assignee_id, u.first_name, u.last_name,
       t.title, t.description, t.status, t.priority,
       t.created_at, t.deleted_at
FROM tasks t
JOIN projects p ON p.id = t.project_id
LEFT JOIN users u ON u.id = t.assignee_id
WHERE t.id = 8;

SELECT id, user_id, action, entity_type, entity_id, details, created_at
FROM audit_log
WHERE entity_type = 'task' AND entity_id = 8
```

Ожидаю: `project_id = 5`, `assignee_id = 10`, имя и фамилия исполнителя — как в ответе, `title` и `description` — как в запросе, без обрезки и лишних пробелов, `status = 'TODO'`, `priority = 'HIGH'`, `created_at` — только что, в UTC, `deleted_at` — `NULL`.

В журнале — одна запись: `task.create`, `user_id` — менеджер, `entity_id = 8`, `details` пустой — в базе это JSON-значение `null`, DBeaver покажет `null`; `WHERE details IS NULL` такую строку не найдёт.

Багом будет: поле в базе отличается от ответа; в `user_id` журнала не тот, кто создал; две записи `task.create`.

```sql
WHERE entity_type = 'comment' AND action = 'comment.delete'
ORDER BY id DESC
LIMIT 3;
```

После первого: у комментария 7 `deleted_at` пустой, записи `comment.delete` нет.

После второго: строка комментария 6 **на месте**, `deleted_at` заполнен. `all_rows = 3`, `deleted = 1`, `active = 2` — совпадает с `commentsCount`. В журнале — `comment.delete`, `entity_id = 6`, `user_id` — **менеджер**: в журнал пишется тот, кто удалил, а не автор.

После третьего: ничего не изменилось. `deleted_at` у комментария 6 — **прежний**, вторая запись `comment.delete` не появилась.

Багом будет: строки нет совсем — удаление физическое; повторный `DELETE` перезаписал время удаления; `commentsCount` всё ещё `3`.
:::

### Шаг 9. Удалить задачу

Подожди минуту после шага 8 — так время удалений будет легко различить. Сделай снимок задач и комментариев проекта. Два запроса `DELETE /api/v1/tasks/8`:

1. под исполнителем;
2. под менеджером.

2. под владельцем.

**Проверь в базе:** проект, его задачи и комментарии, участников, журнал, соседние проекты.

::: details Эталон

## Часть 2. Чек-лист фичи

Прогон из части 1 — это один проход «по счастливому пути» с несколькими отказами. Настоящий чек-лист шире. Составь чек-лист фичи «жизненный цикл задачи» на **15–20 проверок** «API + БД». Каждая проверка — две половины: что ждёшь от API и что — в базе.

Что должно войти:

- **позитив** — каждый шаг жизненного цикла;
- **права** — кто может и кто не может: `MANAGER+`, исполнитель без членства, автор комментария, `OWNER`;
- **валидация** — границы и обязательные поля, после отказа в базе ничего не изменилось;
- **мягкое удаление** — строка на месте, `deleted_at` заполнен, повтор — `404`;
- **каскады** — одно время, ранее удалённое не перезаписано, соседи не задеты;
- **счётчики** — `commentsCount` после каждого изменения комментариев;
- **аудит** — запись есть, верный `user_id`, верные `entity_type`, `entity_id`, `details`; после отказа записи нет.

## Часть 3. Задачи на внимательность

Пять коротких ситуаций. В каждой — вывод, который сделал кто-то другой. Прочитай, подумай, прав ли он. Потом открой «О чём подумать», потом эталон.

**Задача 1.** «Удалил задачу через API, `GET` вернул `404`. Значит, в базе её нет. Проверено».

::: details О чём подумать
- Что значит «удалить» в TaskFlow?
- `404` — про ответ API или про таблицу?
:::

::: details Эталон
Неправ. В TaskFlow удаление мягкое: строка остаётся в `tasks`, у неё заполняется `deleted_at`. `404` значит только «API её не показывает».

```sql
SELECT id, title, deleted_at
FROM tasks
WHERE id = 8;
```

Ожидаю: строка есть, `deleted_at` заполнен. Если строки нет — удаление физическое, это расхождение с разделом 3 спецификации. Проверено — когда посмотрел и задачу, и её комментарии.
:::

**Задача 2.** «В ответе `commentsCount: 2`, а у задачи в таблице `comments` три строки. Счётчик врёт — баг».

::: details О чём подумать
- Все ли три строки — действующие комментарии?
- Как считается `commentsCount` по спецификации?
:::

::: details Эталон
Не торопись. `commentsCount` — число **неудалённых** комментариев, раздел 6.4. Одна из трёх строк может быть удалённой.

```sql
SELECT COUNT(*) AS all_rows,
       COUNT(deleted_at) AS deleted,
       COUNT(*) - COUNT(deleted_at) AS active
FROM comments
WHERE task_id = 8;
```

Если `active = 2` — всё верно. Баг — если `active` не совпадает с `commentsCount`.
:::

**Задача 3.** «Открыл задачу через `GET /tasks/8` и проверил журнал — записи о моём действии нет. Журнал не работает».

::: details О чём подумать
- Какие действия пишутся в журнал?
:::

::: details Эталон
Неправ. В `audit_log` пишутся только действия, которые **меняют** данные: создание, изменение, удаление. Чтение не пишется. Отказ — `403`, `404`, `422` — тоже.

Чтобы проверить журнал, нужно действие, которое что-то меняет. Например, `PATCH` задачи — и тогда искать `task.update`.
:::

**Задача 4.** «Ищу в журнале, кто комментировал задачу 8:

```sql
SELECT action, user_id
FROM audit_log
WHERE entity_type = 'task' AND entity_id = 8;
```

Записей о комментариях нет. Значит, комментарии в журнал не пишутся — баг».

::: details О чём подумать
- Какой `entity_type` и какой `entity_id` у записи о комментарии?
:::

::: details Эталон
Неправ. Запрос ищет не там. Записи о комментариях — с `entity_type = 'comment'` и `entity_id` — номером **комментария**. Связь с задачей — через таблицу `comments`:

```sql
SELECT a.action, a.user_id, a.entity_id AS comment_id
FROM audit_log a
JOIN comments c ON c.id = a.entity_id
WHERE a.entity_type = 'comment' AND c.task_id = 8
ORDER BY a.id;
```

Прежде чем назвать баг, убедись, что запрос правильный. «Пусто» — это и баг системы, и ошибка в своём `WHERE`.
:::

**Задача 5.** «Создал задачу „qa-bd9 Отчёт по продажам“ и проверил в базе:

```sql
SELECT id, title, status
FROM tasks
WHERE title = 'qa-bd9 Отчёт по продажам';
```

Нашлась строка, статус `TODO`. Всё сходится».

::: details О чём подумать
- Сколько строк вернул запрос?
- Точно ли это та задача, которую ты только что создал?
:::

::: details Эталон
Возможно, сверил не ту задачу. Такое же название могло остаться с прошлого прогона — в другом проекте или удалённое. Запрос вернёт её, и ты сверишь чужую строку.

Ищи по `id` из ответа:

```sql
SELECT id, project_id, title, status, deleted_at

```

Если `id` в ответе нет — по названию, но вместе с `project_id` и `deleted_at IS NULL`, и смотри, сколько строк вернулось.
:::

## Часть 4. Баг-репорты и отчёт

**Баг-репорты.** Если в части 1 или по своему чек-листу нашёл расхождения — оформи каждое по шаблону из урока [«Практикум: API-фича целиком»](/api/14-praktikum-api-fichi), часть 5. Добавь доказательство из базы, как в теории, раздел «Как оформить находку с данными из БД»:

- запрос `SELECT` — короткий, по `id`;
- результат запроса — как есть;
- если важно «до и после» — оба результата.

Найдёшь ли ты расхождения и сколько — заранее не известно. Если всё по спецификации — это тоже результат.

**Отчёт о тестировании.** Коротко, по шаблону из урока [«Практикум: API-фича целиком»](/api/14-praktikum-api-fichi), раздел «Отчёт о тестировании». Добавь одну строку — **что проверено в базе**: какие таблицы, журнал, каскады, счётчик.

- «Что проверено» — числом: сколько проверок, passed, failed, blocked.
- «Что не проверено» — честно, с причиной.
- «Вывод» — можно выпускать, нельзя или можно с условиями. С причиной.

## Ситуационные кейсы

Кейсы для подготовки к собеседованию. Сначала ответь сам, потом открой разбор.

::: details Кейс 1. «Как вы проверите фичу через API и базу?»
Ответ джуна: «Отправлю запрос, посмотрю, что пришло `200`, потом найду запись в базе».

Ответ мидла — процесс и пять вопросов к каждому шагу:

1. **Что делаю** — запрос, от чьего имени, с какими данными.
2. **Что должно прийти** — код и тело по спецификации, `id` из ответа.
3. **Что в базе** — `SELECT` по `id`, каждое поле: значение, `NULL` или пустая строка, длина, время в UTC, умолчания.
4. **Что рядом** — журнал действий, связанные таблицы, счётчики, каскады.
5. **Что не должно было измениться** — снимок «до и после» соседних строк. После отказа — не изменилось ничего.

Плюс: базу только читаю, все изменения — через API; ищу по `id`, а не по названию; проверяю под разными ролями, а не под админом. Пример из практики: «запрос с разрешённым и запрещённым полем вернул `403` — и я проверил в базе, что разрешённое поле тоже не изменилось».
:::

::: details Кейс 2. «API ответил 204 на удаление. Что проверите в базе?»
- **Строка.** Мягкое удаление — строка на месте, `deleted_at` заполнен, время в UTC. Физическое — строки нет. Какое должно быть — по требованиям.
- **Связанные записи.** Каскад: дети помечены тем же моментом. Ранее удалённые дети сохранили своё время.
- **Соседи.** Другие строки не задеты: снимок «до и после».
- **Журнал.** Есть запись об удалении, `user_id` — кто удалил, верные `entity_type` и `entity_id`, в `details` — что нужно, например число затронутых записей.
- **Счётчики.** Если где-то считается число детей — уменьшилось.
- **Повтор.** Тот же `DELETE` ещё раз — по требованиям, обычно `404`. В базе время удаления не перезаписано, второй записи в журнале нет.
- **Через API.** `GET` — `404`, в списках не видно. Но помню: `GET` может отдавать кэш, поэтому база — главное доказательство.
:::

::: details Кейс 3. «Счётчик в ответе не совпадает с базой. Ваши действия?»
1. **Проверить свой запрос.** Учёл ли я пометку удаления? Тот ли `id`? Сравниваю ли с тем же, что считает API, — по спецификации?
2. **Узнать, как устроен счётчик.** Хранится в столбце или считается в момент запроса. Это решает, где искать.
3. **Повторить.** Через минуту — то же? Если сошлось — возможно, кэш.
4. **Найти действие, после которого разошлось.** Создание, удаление автором, модератором, каскадом. Пройти каждое с проверкой счётчика.
5. **Оформить.** Шаги, запрос в базу, результат, ожидание по спецификации. Если затронуты и другие записи — запрос, который покажет масштаб: сколько строк расходятся.

Хитрость вопроса: «база — правда, API — врёт» — не всегда. Бывает, что неверно пометили удаление в базе, а счётчик честно это показал.
:::

::: details Кейс 4. «Зачем тестировщику смотреть журнал аудита?»
- **Это требование.** Журнал нужен для разбора инцидентов, споров с клиентами, проверок регуляторов. Если он пишется не всегда — узнают в самый неудобный момент.
- **Это результат действия.** Как поле в базе: должен появиться после изменения и не появиться после отказа или чтения.
- **Что проверять:** запись есть на **каждом** пути — одиночное и массовое удаление, через интерфейс и через API, каскад; `user_id` — кто сделал, а не автор объекта; `entity_type`, `entity_id`, `details` — верные; время — в UTC.
- **Чем помогает самому тестировщику.** По журналу видно историю объекта: когда и кто менял, — даже если в таблице нет `updated_at`.
:::

::: details Кейс 5. Хитрый вопрос: «В базе всё верно, а API отдаёт другое. Где баг?»
Значит, баг — между базой и ответом. Что проверить:

- **Тот ли объект.** Тот ли `id`, тот ли стенд, та ли база. Самая частая причина — смотришь не туда.
- **Кэш.** API отдаёт сохранённую копию. Подожди время жизни кэша или проверь кэш — урок [«Redis: кэш и не только»](/bd/07-redis).
- **Права и фильтры.** API показывает данные с учётом роли: другой пользователь видит другое. Или в запросе API забыли условие `deleted_at IS NULL` — и удалённое «воскресло».
- **Преобразование.** Поле переименовано, время переведено в другой пояс, `NULL` превращён в пустую строку, значение обрезано при выводе.
- **Незакоммиченное.** Если в базе меняли руками и не сделали `COMMIT` — ты видишь своё, API — старое.

В баг-репорте: запрос в API с ответом, запрос в базу с результатом — рядом. Тогда разработчик сразу видит, на каком шаге «теряется» правда.
:::
