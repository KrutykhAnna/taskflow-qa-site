## Простыми словами

Приложение растёт — и вместе с ним меняется база. Нужно новое поле «телефон» — в таблице появляется столбец. Нужен журнал действий — появляется таблица. Поле больше не нужно — столбец удаляют.

Но база не пустая: в ней уже лежат данные. Её нельзя снести и создать заново. Её нужно **отремонтировать на ходу**.

**Миграция** — это инструкция по ремонту базы. В ней по шагам написано, что поменять: «добавь столбец», «сделай поле обязательным», «перенеси данные». Инструкции нумеруются и выполняются строго по порядку — как история правок в общем документе.

Миграции пишут и запускают **разработчики**. Тестировщик их не пишет. Его работа — **понять, что миграция меняет, и знать, что проверить**, когда в задаче написано «добавить поле», «сделать обязательным» или «переезжаем на новый сервер базы».

В этом уроке разберём:

- что такое миграция и как она выглядит — несколько SQL-команд простыми словами;
- как менялась схема TaskFlow;
- что ломается при миграциях;
- **как тестировщик проверяет миграцию** — обычными `SELECT` в DBeaver и через API;
- рабочие ситуации: новый атрибут, обязательное поле, уникальность, смена типа, переименование, миграция данных и **переезд базы**.

## Что такое миграция

У схемы базы — таблиц, столбцов, типов, ограничений — есть **версия**, как у приложения. Каждая миграция переводит схему из одной версии в следующую.

В миграции обычно две части:

- **upgrade** — вперёд: применить изменение, например добавить столбец;
- **downgrade** — назад: отменить его, например удалить столбец.

Откат возвращает **устройство** базы, но не всегда **данные**: удалённый столбец можно создать заново, но прежние значения в нём уже не появятся.

Где-то в самой базе хранится номер последней применённой миграции — по нему видно, какая версия схемы на стенде. На проектах для всего этого есть готовые инструменты, разработчики их настраивают.

### Миграция схемы и миграция данных

| | Миграция схемы | Миграция данных |
|---|---|---|
| **Что меняет** | Устройство: таблицы, столбцы, ограничения | Сами строки: заполняет, переносит, преобразует |
| **Пример** | Добавить в заказы столбец `delivery_status` | Всем старым заказам проставить `delivery_status = 'DELIVERED'` |
| **Как ломается** | Громко: миграция падает с ошибкой | Тихо: миграция проходит, а данные неправильные |

Миграция данных опаснее: ошибка в схеме видна сразу, ошибка в данных — когда клиент позвонит. Часто это одна задача в три шага: добавить столбец → заполнить его у старых строк → сделать обязательным. Проверять нужно все три.

## Как выглядит миграция

Миграция — это обычно несколько команд SQL. Писать их тебе не нужно — нужно **узнать в лицо** и понять, что каждая делает с данными.

| Команда | Простыми словами | Что будет со старыми строками |
|---|---|---|
| `CREATE TABLE addresses (…)` | Создать новую таблицу | Старые таблицы не трогает |
| `ALTER TABLE customers ADD COLUMN phone varchar(20)` | Добавить столбец | У всех старых строк — `NULL` |
| `ALTER TABLE customers ADD COLUMN city varchar(100) NOT NULL DEFAULT 'Не указан'` | Добавить обязательный столбец со значением по умолчанию | У всех старых строк — `'Не указан'` |
| `ALTER TABLE customers ALTER COLUMN phone SET NOT NULL` | Сделать поле обязательным | Если есть хоть один `NULL` — ошибка, миграция не пройдёт |
| `ALTER TABLE products ALTER COLUMN title TYPE varchar(100)` | Поменять тип или длину | Не влезающие значения — ошибка или, хуже, обрезка |
| `ALTER TABLE customers ADD CONSTRAINT customers_phone_key UNIQUE (phone)` | Запретить повторы | Если повторы уже есть — ошибка |
| `ALTER TABLE orders RENAME COLUMN total TO total_amount` | Переименовать столбец | Данные на месте, но всё, что обращается к старому имени, ломается |
| `ALTER TABLE customers DROP COLUMN middle_name` | Удалить столбец | Значения потеряны |
| `UPDATE orders SET delivery_status = 'DELIVERED' WHERE created_at < '2025-01-01'` | Миграция данных: заполнить старые строки | Изменятся строки под `WHERE` — **проверь условие** |

Если в задаче или в описании изменений встретишь такие строки — ты уже знаешь, куда смотреть.

## Что ломается при миграциях

Примеры — выдуманный интернет-магазин, тексты ошибок — настоящие, PostgreSQL.

**1. Обязательный столбец без значения по умолчанию.** На пустой таблице проходит. На таблице с данными старым строкам нечего записать в новый столбец:

```text
ERROR: column "city" of relation "customers" contains null values
```

**2. Уникальность на данных с повторами.** На тестовой базе повторов не было, в живых данных — есть:

```text
ERROR: could not create unique index "customers_phone_key"
DETAIL: Key (phone)=(+79990001122) is duplicated.
```

**3. Сужение типа.** `varchar(200)` → `varchar(100)`, а есть строка длиннее:

```text
ERROR: value too long for type character varying(100)
```

Хуже, если разработчик «починил» это обрезкой: миграция проходит, а хвосты названий молча пропали.

**4. Переименование.** Миграция проходит. Но всё, что обращается к старому имени, — старая версия приложения, отчёты, выгрузки — падает:

```text
ERROR: column "total" does not exist
```

**5. Удаление столбца.** Проходит без ошибок — и данные исчезают. Вернуть можно только из резервной копии.

**6. Старые строки с `NULL`.** Новый необязательный столбец, у старых строк — `NULL`. Миграция «прошла», а старые записи выпали из фильтров: `NULL` не равен ни одному значению.

**7. Миграция данных с ошибкой в условии.** `UPDATE` без `WHERE` или с неверным `WHERE` — изменены не те строки. Ошибки нет.

**8. Большие таблицы.** Миграция данных на миллионах строк идёт долго и держит строки заблокированными: всё это время приложение не может их изменить.

Общий корень почти всех проблем: **на тестовой базе мало данных, и они чистые**. На проде — годы реальных данных: пустые поля, повторы, длинные строки, записи из времён, когда правила были другие.

### 1. Схема

Вкладка **Columns** таблицы в DBeaver — или запрос из урока [«Как тестировать базу данных»](/bd/05-testirovanie-bd):

```sql
SELECT column_name, data_type, character_maximum_length AS max_len,
       is_nullable, column_default
FROM information_schema.columns
WHERE table_name = 'customers'
ORDER BY ordinal_position;
```

Сверяешь с задачей: столбец есть, тип и длина те, обязательность та, значение по умолчанию то. Ограничения — вкладка **Constraints** или запрос к `pg_constraint` из того же урока.

### 2. Данные

**До миграции** запиши число строк и несколько записей-примеров. **После** — сравни:

```sql
SELECT COUNT(*) FROM customers;                    -- до и после — одинаково?

SELECT * FROM customers WHERE id IN (1, 500, 9999); -- те же значения?
```

Что получили **старые строки** в новом столбце:

```sql
SELECT COUNT(*) FROM customers WHERE phone IS NULL;
```

`NULL` у всех старых — это нормально или нет? Решает не тестировщик, а требования: спроси аналитика, что должно быть у старых записей.

### 3. Приложение

Смоук через API или интерфейс по тому, что задето миграцией:

- **старые** записи открываются, видны в списках и фильтрах;
- **новые** записи создаются, новое поле сохраняется и возвращается в ответе;
- фильтр, сортировка, выгрузка по новому полю работают — и на старых записях тоже.

### 4. Откат

Вопрос команде, а не ручной тест: «если выкладка сломается — как откатываем? что будет с данными? резервная копия есть?» Если миграция удаляет данные, откат их не вернёт — это нужно знать **до** выкладки.

### Короткий чек-лист

| Что | Как проверить |
|---|---|
| Схема | Columns и Constraints в DBeaver или `information_schema.columns` |
| Число строк | `COUNT(*)` до и после — совпадает |
| Старые записи | Те же `id` до и после — те же значения |
| Новое поле у старых строк | `WHERE новое_поле IS NULL` — сколько и так ли задумано |
| Новые записи | Создать через API — поле сохранилось, ответ правильный |
| Списки, фильтры, выгрузки | Старые записи не пропали |
| Откат | Есть ли план и что он сделает с данными |
| Данные | Стенд с данными, похожими на прод, а не пустой |

## Ситуации на работе

Как это выглядит в реальных задачах. В каждой — что меняется и что проверишь.

### Ситуация 1. «Добавить новый атрибут»

**В задаче:** «У клиента добавить поле "телефон", необязательное, до 20 символов». Разработчик добавляет столбец `phone varchar(20)` и поле в API.

Что проверишь:

- **схема**: столбец есть, тип и длина — `varchar(20)`, необязательный, значения по умолчанию нет — как в задаче;
- **старые строки**: у всех `phone` пустой — `SELECT COUNT(*) FROM customers WHERE phone IS NULL` равно числу клиентов. Если по задаче старым клиентам телефон должен был перенестись откуда-то — проверь, что перенёсся;
- **новые записи**: клиент с телефоном через API — в базе тот же телефон; клиент без телефона — `NULL`, а не пустая строка `''`, или как договорились;
- **ответ API**: поле `phone` возвращается и у новых, и у старых клиентов — у старых `null`, а не ошибка;
- **границы**: API принимает 20 символов и отказывает на 21 — с той же границей, что в базе. Если API пропустит 21, база ответит ошибкой — и пользователь увидит `500`;
- **что вокруг**: поиск, фильтры, сортировка, выгрузка в Excel, отчёты и соседние сервисы, которые читают таблицу клиентов.

### Ситуация 2. «Сделать поле обязательным»

**В задаче:** «Телефон клиента теперь обязателен».

Главный вопрос — **что делать со старыми клиентами без телефона**. До миграции посчитай их:

```sql
SELECT COUNT(*) FROM customers WHERE phone IS NULL;
```

Если не ноль — `SET NOT NULL` упадёт. Значит, нужно решение: заполнить чем-то, запросить у клиентов, оставить старых как есть. Это решает бизнес; твоя задача — **поднять вопрос** с числом на руках.

После: старые клиенты открываются и редактируются — форма не требует телефон там, где его нет и взять неоткуда? API без телефона отвечает понятной ошибкой `4xx`, а не `500`.

### Ситуация 3. «Добавить уникальность»

**В задаче:** «Телефон не должен повторяться».

До миграции — есть ли уже повторы:

```sql
SELECT phone, COUNT(*) FROM customers
WHERE phone IS NOT NULL
GROUP BY phone
HAVING COUNT(*) > 1;
```

Это `GROUP BY` и `HAVING` из урока [«Агрегаты»](/bd/04-agregaty). Если строки есть — миграция упадёт, нужно решение о повторах. После миграции: повторный телефон через API — `409` или `422` с понятным текстом, а не `500`.

### Ситуация 4. «Поменять тип или длину»

**В задаче:** «Название товара — до 100 символов вместо 200».

До миграции — сколько значений не влезет:

```sql
SELECT COUNT(*) FROM products WHERE length(title) > 100;
```

Не ноль — вопрос команде: что с ними делать. Обрезка — это потеря данных, её должны согласовать. После: длинные названия не обрезались молча; граница API — тоже 100: проверь 100 и 101 символ.

### Ситуация 5. «Переименовать или удалить поле»

**В задаче:** «Убрать отчество» или «переименовать `total` в `total_amount`».

Что проверишь:

- **удаление**: данные точно больше не нужны? Есть резервная копия? Нигде в приложении, отчётах, выгрузках не осталось этого поля;
- **переименование**: всё, что читало старое имя, обновлено — экраны, API, отчёты, соседние сервисы. Отдельный вопрос — **порядок выкладки**: если миграция выкатится раньше кода, старое приложение будет падать на каждом запросе к этой таблице.

### Ситуация 6. «Миграция данных»

**В задаче:** «Всем заказам до 2025 года проставить статус доставки "Доставлен"».

Посчитай по группам **до** и **после**:

```sql
SELECT delivery_status, COUNT(*) FROM orders
GROUP BY delivery_status;

SELECT COUNT(*) FROM orders WHERE created_at < '2025-01-01';
```

Ожидаешь: «Доставлен» — ровно столько, сколько заказов до 2025 года. Заказы с 2025 года — **не тронуты**. Граница: заказ 31 декабря 2024 года в 23:59 — попал? Остались ли `NULL` там, где их быть не должно?

### Ситуация 7. «Переезд базы»

**В задаче:** «Переносим базу на новый сервер», «обновляем PostgreSQL до новой версии», «переезжаем в облако» или даже «переходим на другую СУБД». Схема та же — но **все данные копируются** в новое место. Что-то может не доехать или доехать иначе.

| Что проверить | Как |
|---|---|
| **Все строки доехали** | `SELECT COUNT(*)` по каждой таблице в старой и новой базе — совпадает |
| **Записи совпадают** | Несколько записей по одним и тем же `id` в обеих базах: все поля одинаковые |
| **Кодировка** | Буква «ё», эмодзи, кавычки-ёлочки, длинные тексты — не превратились в `?` или «кракозябры» |
| **Даты и время** | `created_at` одной записи в обеих базах — одинаковое время, часовой пояс не сдвинулся |
| **`NULL` и пустая строка** | `COUNT(*) WHERE поле IS NULL` и `WHERE поле = ''` — до и после одинаково. Некоторые инструменты переноса путают их |
| **Счётчики `id`** | Новая запись через API создаётся и не падает с «такой `id` уже есть». Счётчик продолжает с последнего номера, а не с 1 |
| **Ограничения, индексы, типы** | Вкладки Constraints и Indexes в новой базе — как в старой. Перечисления на месте |
| **Приложение смотрит в новую базу** | Создал запись через API — она появилась в **новой** базе. В старую после переключения ничего не пишется |
| **Скорость** | Ключевые экраны и списки открываются не медленнее, чем до переезда |
| **План отката** | Если что-то пошло не так — как вернуться на старую базу и что будет с данными, записанными за это время |

Проверить счётчик в PostgreSQL можно так — номер счётчика должен быть не меньше наибольшего `id`:

```sql
SELECT MAX(id) FROM tasks;
SELECT last_value FROM tasks_id_seq;
```

## Миграции и окружения

Про окружения — урок [«Тестовые окружения и CI/CD»](/osnovy/11-testovye-okruzheniya). Что добавляют миграции:

- **Миграции применяются на каждом стенде по очереди** — локально, на тестовом, на стейдже, на проде — одни и те же.
- **«На стейдже прошло» ≠ «на проде пройдёт».** На проде больше данных и они «грязнее».
- **Стенд, отставший по миграциям, — частая причина «у меня работает».** Код новый, а схема старая: нового столбца нет — `500`. Спроси разработчика, какая версия схемы на каждом стенде.
- **Перед миграцией прода делают резервную копию.** Делает не тестировщик, но спросить «бэкап есть?» перед рискованной выкладкой — нормально.

<summary>Разбор 1. Обязательное поле: на стейдже прошло, на проде упало — служба доставки</summary>

**Ситуация.** В карточку курьера добавили обязательное поле «тип транспорта» — `NOT NULL`, без значения по умолчанию. На стейдже миграция прошла, тестировщик проверил форму — всё хорошо. Ночью выкладка на прод: приложение не стартует, сервис лежит 40 минут.

**Что видит мидл.**

- На стейдже таблица курьеров была **пустой**: курьеров создают автотесты и удаляют за собой. В пустую таблицу обязательный столбец добавить можно — заполнять нечего.
- На проде 3 000 курьеров, значения для нового поля у них нет — ошибка `contains null values`.

**Что делать.**

1. Завести баг на миграцию: «на таблице с данными падает: обязательное поле без значения по умолчанию». Приложить текст ошибки.
2. Поднять вопрос: какое значение получат существующие курьеры? Это решает бизнес.
3. Проверить исправленную миграцию на стенде **с данными**: заранее создать курьеров, после миграции — посмотреть значение у них.
4. В чек-лист: «миграции проверяем на непустых таблицах».

**Чего не делать.**

- Не считать «прошло на стейдже» проверкой миграции, если на стейдже нет данных в этой таблице.

::: details Разбор 2. «Миграция применилась» — а старые заказы пропали из истории — логистика
**Ситуация.** Добавили статус доставки заказа. Тестировщик проверил: новый заказ получает статус «Создан», фильтр «Доставлен» работает. После выкладки поддержка: «у клиентов пропала история заказов».

**Что видит мидл.**

- Столбец добавили необязательным и не заполнили. У всех старых заказов — `NULL`.
- История показывает заказы с конкретными статусами. `NULL` не равен ни одному — старые заказы не видны.
- Проверили новые записи, а старые — нет.

**Что делать.**

1. Найти масштаб: `SELECT COUNT(*) FROM orders WHERE delivery_status IS NULL`.
2. Завести баг: «после миграции у N старых заказов нет статуса доставки — они не видны в истории».
3. Проверить исправление — миграцию данных: группы по статусам до и после, ни одного `NULL`.

**Чего не делать.**

- Не проверять миграцию только на записях, созданных после неё.
:::

::: details Разбор 3. Переименовали столбец, миграция раньше кода — 500 везде — маркетплейс
**Ситуация.** Столбец `price` переименовали в `price_rub`. Выкладка: сначала миграция, через 15 минут — новый код. Эти 15 минут каталог и корзина отвечали `500`.

**Что видит мидл.**

- Старое приложение работало с новой схемой: оно просит `price`, а столбца нет — `column "price" does not exist`.
- Тестировщик проверял новую сборку с новой схемой. Промежуточное «старый код + новая схема» не проверял никто.

**Что делать.**

1. Спросить про порядок выкладки и предложить безопасный путь: сначала добавить новый столбец, потом переключить код, старый удалить в следующем релизе.
2. Спросить, кто ещё читает таблицу напрямую: отчёты, выгрузки.

**Чего не делать.**

- Не проверять миграцию только вместе с «правильным» кодом. На проде они появляются не одновременно.
:::

::: details Разбор 4. Переезд базы — вместо «ё» знаки вопроса — онлайн-библиотека
**Ситуация.** Базу перенесли на новый сервер. Число строк во всех таблицах совпало, тестировщик отчитался «переезд проверен». Через день читатели пишут: в названиях книг и именах авторов вместо «ё» и кавычек-ёлочек — `?`.

**Что видит мидл.**

- Число строк проверяет, что строки **доехали**, но не что они доехали **правильно**.
- Скорее всего, при переносе была не та кодировка. Сломались только «особые» символы — латиница и обычная кириллица в порядке, поэтому на первый взгляд всё хорошо.

**Что делать.**

1. Сравнить одни и те же записи в старой и новой базе — особенно с «ё», эмодзи, кавычками.
2. Посчитать масштаб: `SELECT COUNT(*) FROM books WHERE title LIKE '%?%'` в новой базе и в старой.
3. Завести баг на переезд, приложить пары «было — стало».
4. В чек-лист переезда: «выборочное сравнение записей со спецсимволами».

**Чего не делать.**

- Не считать переезд проверенным только по числу строк.
:::

::: details Разбор 5. После переезда новые заказы не создаются — интернет-магазин
**Ситуация.** Базу перевезли на новый сервер. Старые заказы видны, всё открывается. Утром первый новый заказ: `500`. В логах — `duplicate key value violates unique constraint "orders_pkey"`.

**Что видит мидл.**

- Данные скопировали, а **счётчик `id`** — нет: он начал с 1. Новый заказ получает `id = 1`, а такой уже есть.
- Тестировщик проверил чтение, но не создание. Самое частое действие пользователя осталось без проверки.

**Что делать.**

1. Сравнить наибольший `id` и текущее значение счётчика: `SELECT MAX(id) FROM orders` и `SELECT last_value FROM orders_id_seq`.
2. Завести баг: «после переезда счётчики `id` не перенесены — создание записей падает».
3. В чек-лист переезда: «создать новую запись в каждой основной таблице».

**Чего не делать.**

- Не проверять переезд только чтением.
:::

## Частые ошибки

- **«Миграция применилась» = «проверено».** Без ошибки — не значит без потерь.
- **Проверка на пустой базе.** Проблемы миграций живут в реальных данных: `NULL`, повторы, длинные строки, объём.
- **Только новые записи.** Старые строки после миграции — главный объект проверки.
- **«Откатим — и всё вернётся».** Откат возвращает устройство базы, но не удалённые данные.
- **Не спросили, что должно быть у старых записей.** `NULL` или значение по умолчанию — решают требования, а не тестировщик.
- **Переезд проверен по числу строк.** Нужны ещё выборочное сравнение записей, кодировка, даты и создание новых записей.
- **Не спросили про порядок выкладки.** Старый код и новая схема какое-то время работают вместе.
- **Граница в API и в базе разная.** После смены длины проверь `n` и `n + 1` и там, и там.

`information_schema.columns`, условие по `column_name`.

**Задача 4** (мидл). Когда шаг 3 добавил `deleted_at` в таблицу `tasks`, задачи в ней уже были. Что получили старые задачи в этом столбце? Почему здесь важно, что столбец **необязательный**?

::: details О чём подумать
- Что получают старые строки, когда добавляют необязательный столбец без значения по умолчанию?
- Что значит пустой `deleted_at` для приложения?

::: details Эталон
Старые строки получили `NULL`. Пустой `deleted_at` в TaskFlow значит «не удалено» — значит, после миграции все старые задачи остались живыми. Ровно то, что нужно.

Проверка на твоём стенде:
```sql
SELECT COUNT(*) AS all_tasks,
       COUNT(deleted_at) AS deleted
FROM tasks;
```
На начальных данных — `7` и `0`. Если бы столбец сделали обязательным со значением по умолчанию `now()`, все старые задачи после миграции стали бы «удалёнными» и исчезли бы из API. Вот почему у новых столбцов смотрят не только тип, но и что получат старые строки.
:::

## Часть 2. Тебе дали задачу: проверь миграцию

Выдуманный интернет-магазин. В нём таблицы `customers` — клиенты, 120 000 строк, `orders` — заказы, 2 млн строк, `products` — товары. Разработчик прислал миграцию к задаче.

Для каждой ответь письменно:

1. Что пойдёт не так?
2. Как проверишь — какие `SELECT` выполнишь **до** и **после**?
3. Что предложишь команде?

**Задача 9** (джун). Задача: «У клиента должен быть город».

```sql
ALTER TABLE customers ADD COLUMN city varchar(100) NOT NULL;
```

::: details Эталон
**Что не так.** Обязательный столбец без значения по умолчанию. У 120 000 существующих клиентов города нет — миграция упадёт:
```text
ERROR: column "city" of relation "customers" contains null values
```
На пустой тестовой базе она пройдёт — и ошибку увидят только на проде.

**Как проверить.** Прогнать миграцию на стенде, где в `customers` есть данные. После — `SELECT COUNT(*) FROM customers WHERE city IS NULL` (должно быть 0) и что получили старые клиенты.

**Что предложить.** Спросить аналитика, какой город у старых клиентов. Варианты: значение по умолчанию (`DEFAULT 'Не указан'`) или три шага — добавить необязательным, заполнить, сделать обязательным.
:::

**Задача 10** (джун). Задача: «Телефон клиента уникален».

```sql
ALTER TABLE customers ADD CONSTRAINT customers_phone_key UNIQUE (phone);
```

::: details Эталон
**Что не так.** Если в данных уже есть повторы телефонов — миграция упадёт:
```text
ERROR: could not create unique index "customers_phone_key"
DETAIL: Key (phone)=(+79990001122) is duplicated.
```

**Как проверить.** До миграции:
```sql
SELECT phone, COUNT(*) FROM customers
WHERE phone IS NOT NULL
GROUP BY phone
HAVING COUNT(*) > 1;
```
После — повторный телефон через API: ответ `409` или `422` с понятным текстом, а не `500`.

**Что предложить.** Сначала решение бизнеса о повторах: какую запись оставить, как объединить заказы. Только потом ограничение.
:::

**Задача 11** (мидл). Задача: «Привести названия к единому стилю».

```sql
ALTER TABLE orders RENAME COLUMN total TO total_amount;
```

::: details Эталон
**Что не так.** Миграция пройдёт. Но всё, что обращается к `total`, сломается: старая версия приложения, если миграция выкатится раньше кода, отчёты, выгрузки в аналитику — `column "total" does not exist`.

**Как проверить.** После миграции — смоук всего, что показывает сумму заказа: карточка, список, корзина, выгрузка. Вопрос команде: в каком порядке выкладка и кто ещё читает таблицу заказов напрямую.

**Что предложить.** Переименование ради стиля — польза маленькая, риск большой. Если всё же нужно — в несколько выкладок: добавить новый столбец, переключить код, старый удалить потом.
:::

**Задача 12** (джун). Задача: «Ограничить название товара 100 символами».

```sql
ALTER TABLE products ALTER COLUMN title TYPE varchar(100);
```

::: details Эталон
**Что не так.** Если есть названия длиннее 100 символов — миграция упадёт с `value too long for type character varying(100)`. Если разработчик добавит обрезку — пройдёт, но хвосты названий пропадут.

**Как проверить.** До: `SELECT COUNT(*) FROM products WHERE length(title) > 100`. После: ни одно название не обрезано без согласования; API принимает 100 символов и отказывает на 101 — граница совпадает с базой.

**Что предложить.** Показать число и примеры длинных названий — пусть бизнес решит, что с ними делать.
:::

**Задача 13** (джун). Задача: «Отчество больше не нужно».

```sql
ALTER TABLE customers DROP COLUMN middle_name;
```

::: details Эталон
**Что не так.** Отчества 120 000 клиентов удаляются навсегда. Откат вернёт пустой столбец.

**Как проверить.** До: сколько отчеств заполнено — `SELECT COUNT(middle_name) FROM customers`. Где отчество используется: документы, письма, договоры, выгрузки в другие системы. После: эти места работают без отчества.

**Что предложить.** Уточнить, что данные точно больше нигде не нужны — например, в договорах или для закона. Попросить резервную копию перед выкладкой.
:::

**Задача 14** (мидл). Задача: «Заказы старше 2023 года перевести в архив».

```sql
UPDATE orders SET status = 'ARCHIVED';
```

::: details Эталон
**Что не так.** Нет `WHERE` — в архив уйдут **все** 2 млн заказов, в том числе сегодняшние. Ошибки не будет. Плюс один `UPDATE` на 2 млн строк — долго, а строки на это время заблокированы.

**Как проверить.** До и после:
```sql
SELECT status, COUNT(*) FROM orders GROUP BY status;
SELECT COUNT(*) FROM orders WHERE created_at < '2023-01-01';
```
Ожидается: `ARCHIVED` ровно столько, сколько заказов до 2023 года. Свежие заказы — в прежних статусах.

**Что предложить.** Добавить условие `WHERE created_at < '2023-01-01'`. Уточнить: «старше 2023» — это до 1 января 2023 или до 1 января 2024? Спросить про время на объёме прода.
:::

**Задача 15** (мидл). Задача: «Добавить статус доставки». Фильтр «Мои заказы» после выкладки показывает заказы со статусом доставки `CREATED`, `SHIPPED` или `DELIVERED`.

```sql
ALTER TABLE orders ADD COLUMN delivery_status varchar(20);
```

::: details Эталон
**Что не так.** Миграция пройдёт. Но у всех 2 млн старых заказов `delivery_status = NULL` — и они не попадут ни в один статус фильтра. У клиентов «пропадёт» история.

**Как проверить.** После: `SELECT COUNT(*) FROM orders WHERE delivery_status IS NULL`. Через API — фильтр «Мои заказы» у клиента со **старыми** заказами.

**Что предложить.** Спросить аналитика, какой статус у старых заказов, и добавить миграцию данных. После неё — ни одного `NULL` и правильное число в каждой группе.
:::

**Задача 19** (мидл). «Базу перевезли на новый сервер. Число строк во всех таблицах совпало — переезд проверен».

::: details Эталон
Не проверен. Число строк ничего не говорит о содержимом: кодировка («ё», эмодзи), даты и часовой пояс, `NULL` и пустые строки. Нужно сравнить несколько одинаковых записей в двух базах. И создать новые записи: если счётчики `id` не перенесли, создание упадёт на повторе ключа.

**Задача 20** (джун). «Добавили необязательное поле "комментарий курьера". Проверь, что у старых заказов оно заполнено».

У старых заказов будет `NULL` — и это правильно: комментария тогда не было. Подвох в самой постановке. Нужно уточнить ожидание у автора задачи. И проверить, что приложение нормально показывает старые заказы с пустым полем: не падает и не пишет `null` на экране.

**Задача 21** (мидл). «Миграция данных: всем клиентам из Москвы проставить регион 77. Проверь: число клиентов с регионом 77 равно числу клиентов, у которых город `'Москва'`».

::: details О чём подумать
- Как ещё может быть записана Москва в живых данных?
- А не задела ли миграция тех, кого не должна была?
:::

::: details Эталон
Два подвоха.

1. В реальных данных Москва бывает `'москва'`, `'г. Москва'`, `'Москва '` с пробелом. Миграция со строгим `= 'Москва'` их пропустит, и проверка тем же условием это не заметит. Посмотри варианты:
   ```sql

   WHERE city ILIKE '%москв%'
   GROUP BY city;
   ```
2. Проверь и обратное: регион 77 не появился у клиентов из других городов — `SELECT COUNT(*) FROM customers WHERE region = 77 AND city NOT ILIKE '%москв%'` должно быть 0.

## Часть 4 (письменно). Два чек-листа

### Чек-лист 1. Новый атрибут «срок задачи»

Выдуманная фича для TaskFlow: у задачи появляется необязательное поле «срок» — `due_date`, дата без времени. Его можно передать при создании и изменении задачи, а в списке задач — отфильтровать просроченные.

Напиши **10–12 проверок**: схема, старые задачи, новые задачи, API, границы и формат даты, фильтр, удалённые задачи, всё вокруг. Для каждой — что делаешь и что будет багом.

::: details Пример нескольких проверок — не подглядывай, пока не напишешь свои
- В `tasks` есть `due_date`, тип `date`, необязательный, без значения по умолчанию.
- Число задач до и после одинаковое. У всех старых задач `due_date IS NULL`.
- `GET` старой задачи — в ответе поле `dueDate: null`, а не ошибка и не отсутствие поля, если спецификация требует его всегда.
- Создание с датой — в базе та же дата, без сдвига на день из-за часового пояса.
- Неверный формат даты, несуществующая дата 31 февраля — `422`, а не `500`.
- Фильтр «просроченные»: задачи без срока в него не попадают, задача со сроком «сегодня» — по требованиям, уточнить у аналитика.
- Изменение срока через `PATCH` меняет только его; запись в `audit_log` есть.
- Мягко удалённые задачи со сроком в фильтр не попадают.
:::

### Чек-лист 2. Переезд базы

Выдуманный интернет-магазин переносит базу на новый сервер и заодно обновляет PostgreSQL до новой версии. Схема не меняется. Переезд — ночью, в выходные.

Напиши **10–12 проверок** и выдели **3 первоочередные** — что проверишь первым, если времени мало, и почему.

::: details Пример нескольких проверок — не подглядывай, пока не напишешь свои
- `COUNT(*)` по каждой таблице в старой и новой базе — совпадает.
- 5–10 записей по одним и тем же `id` в каждой основной таблице — все поля совпадают.
- Записи с «ё», эмодзи, кавычками-ёлочками, длинными текстами — без искажений.
- `created_at` одних и тех же записей — то же время, часовой пояс не сдвинулся.
- `NULL` и пустые строки: число тех и других в нескольких столбцах — до и после одинаково.
- Создание нового заказа, клиента, товара через API — проходит, `id` продолжает старую нумерацию.
- Ограничения и индексы в новой базе — как в старой: вкладки Constraints и Indexes.
- Приложение пишет в новую базу: созданный заказ виден в новой, в старой — нет.
- Ключевые экраны — каталог, корзина, история заказов — открываются не медленнее.
- План отката: как вернуться и что будет с заказами, созданными после переезда.

Первоочередные: создание заказа (самое частое и денежное действие — ломается из-за счётчиков), число строк и выборочное сравнение в таблицах заказов и платежей, приложение действительно пишет в новую базу.
:::

## Ситуационные кейсы

Это рабочие ситуации, о которых могут спросить и на собеседовании. Готового ответа, который нужно угадать, здесь нет. Сначала подумай сам, потом открывай разбор.

::: details Кейс 1. «Что такое миграция базы данных и зачем она нужна?»
**Ситуация.** Интервьюер: «Объясните простыми словами, что такое миграция базы».

**Как рассуждать.** Почему базу нельзя просто пересоздать? Что было бы без миграций на нескольких стендах?

**Пример ответа.** Миграция — это записанное изменение схемы базы: добавить столбец, создать таблицу, сделать поле обязательным, иногда — преобразовать данные. Миграции нумеруются и применяются по порядку, а в базе хранится номер последней применённой — по нему видно версию схемы.

Нужны они потому, что база уже с данными — её меняют на ходу. И меняют одинаково на всех стендах: локально, на тесте, на проде. Без миграций каждый стенд правили бы руками, и через месяц схемы у всех разные — отсюда баги «у меня работает».

Сам я миграции не пишу. Моя задача — понять, что она меняет, и проверить схему, старые данные и работу приложения после неё.
:::

::: details Кейс 2. «В задаче добавили новое поле. Что проверите?»
**Ситуация.** Интервьюер: «Клиенту добавили поле "дата рождения", необязательное. Что будете проверять?»

**Как рассуждать.** Три группы: база, старые записи, новые записи и всё вокруг.

**Пример ответа.** В базе — столбец есть, тип `date`, необязательный, значения по умолчанию нет.

Старые клиенты — число до и после то же, у всех поле пустое, они открываются и в ответе API поле `null`, а не ошибка.

Новые — дата сохраняется без сдвига на день из-за часового пояса, неверная дата и дата в будущем — `422`, а не `500`.

И всё вокруг: поиск, фильтры, выгрузки, отчёты и соседние сервисы, которые читают таблицу клиентов. Отдельно спрошу у аналитика, должны ли старые клиенты получить дату откуда-то — если да, это уже миграция данных, и её проверяю отдельно.
:::

::: details Кейс 3. Хитрый вопрос: «На тесте миграция прошла, на проде упала. Как так?»
**Ситуация.** Интервьюер: «Почему миграция может пройти на тестовом стенде и упасть на проде? Вы же тестировали».

**Как рассуждать.** Чем база теста отличается от базы прода?

**Пример ответа.** Почти всегда дело в данных. Тестовая база маленькая и чистая, прод — годы реальных данных. Типичные случаи:

- обязательный столбец без значения по умолчанию: на пустой тестовой таблице проходит, на заполненной — нет;
- уникальность: на тесте повторов нет, на проде есть;
- сужение длины: на тесте все строки короткие;
- объём: на тесте секунда, на проде час и заблокированная таблица.

Поэтому миграции проверяют на стенде с данными, похожими на прод, — по объёму и по «грязи». А перед миграцией прода смотрят запросами, нет ли в данных того, на чём она упадёт: `NULL`, повторов, длинных строк.
:::

::: details Кейс 4. «Всегда ли можно откатить миграцию?»
**Ситуация.** Интервьюер: «Если после выкладки что-то сломалось, можно ведь просто откатить миграцию?»

**Как рассуждать.** Что возвращает откат — устройство или данные?

**Пример ответа.** Не всегда. Откат возвращает **устройство** базы, но не всегда **данные**. Удалили столбец — откат создаст его пустым. Преобразовали данные — например, склеили имя и фамилию в одно поле — обратно без потерь не разделить. Бывает, что откат вообще не написан или не работает: про него вспоминают только в аварии.

Поэтому перед рискованной миграцией я спрошу: откат проверяли? что он сделает с данными? есть ли резервная копия? Если откат невозможен — это решение принимается заранее, а не ночью во время аварии.
:::

::: details Кейс 5. «Чем миграция данных опаснее миграции схемы?»
**Ситуация.** Интервьюер: «Разработчик говорит: "там просто UPDATE, заполняем новое поле у старых записей". Что проверите?»

**Как рассуждать.** Как ломается схема и как ломаются данные? Что видно сразу, а что — нет?

**Пример ответа.** Ошибка в схеме громкая: миграция падает. Ошибка в данных тихая: миграция проходит, а данные неправильные — и узнают об этом от клиентов.

Проверяю по группам до и после: сколько строк должно было измениться и сколько изменилось. Строки, которые **не** должны были измениться, — не тронуты. Граничные случаи: `NULL`, пустые строки, разное написание одного значения, граница по дате. И спрошу про объём: `UPDATE` на миллионах строк идёт долго и блокирует таблицу.
:::

::: details Кейс 6. Хитрый вопрос: «Как проверить переезд базы на новый сервер?»
**Ситуация.** Интервьюер: «Базу перенесли на новый сервер. Как проверите, что ничего не потерялось?»

**Как рассуждать.** Число строк — достаточно? Что может доехать «не так»?

**Пример ответа.** Число строк по каждой таблице — первая проверка, но не последняя. Она показывает, что строки доехали, а не что доехали правильно.

Дальше: выборочно сравниваю одни и те же записи в двух базах — все поля. Особенно спецсимволы: «ё», эмодзи, кавычки — на них ломается кодировка. Даты и время — не сдвинулся ли часовой пояс. `NULL` и пустые строки — некоторые инструменты их путают.

Обязательно создаю новые записи: если счётчики `id` не перенесли, создание падает на повторе ключа. Проверяю, что приложение пишет в новую базу, а не в старую. Скорость ключевых экранов. И спрашиваю про план отката.
:::
