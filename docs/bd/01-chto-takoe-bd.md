## Простыми словами

Вспомни регистратуру в поликлинике. Там стоит картотека: у каждого пациента карточка с одинаковыми полями — фамилия, дата рождения, адрес. У каждой карточки свой номер. В соседнем шкафу — картотека анализов, и на каждом бланке анализа написан номер карточки пациента. По этому номеру регистратор находит, чьи это анализы.

База данных — такая картотека, только электронная. Таблицы — это шкафы, строки — карточки, столбцы — поля карточки, номер карточки — ключ. А связи между таблицами — это номера, по которым одну карточку находят в другом шкафу.

«А почему не Excel?» — потому что базе одновременно пишут сотни пользователей, в ней миллионы строк, у неё есть правила, которые нельзя нарушить (две карточки с одним номером не появятся), и связи, которые она сама охраняет (анализ без пациента не сохранится).

В этом уроке разберём:

- зачем тестировщику база данных, если есть API;
- основные понятия: таблица, строка, столбец, тип, `NULL`, ключи;
- типы данных PostgreSQL, которые встретишь в TaskFlow;
- связи между таблицами и **ER-схему TaskFlow**;
- мягкое удаление — почему «удалённое» лежит в базе;
- что такое SQL и как выглядит первый запрос;
- какие бывают СУБД, чем SQL отличается от NoSQL;
- **DBeaver** — как подключиться к базе TaskFlow и ничего в ней не сломать.

## Зачем тестировщику база данных

API показывает то, что сервер решил показать. База — то, что на самом деле сохранилось. Между ними бывает большая разница.

**Что даёт база джуну:**

- **Проверить, что API действительно сохранил.** `201 Created` — это обещание сервера. Строка в таблице — факт. Иногда ответ красивый, а в базе поле пустое или записалось не то.
- **Подготовить данные.** Найти пользователя с нужной ролью, проект с нужным статусом, задачу без исполнителя — запросом быстрее, чем листать списки.
- **Не путать «нет в ответе» и «нет в базе».** Поле может быть в базе, но API его не отдаёт — и это может быть правильно.

**Что даёт база мидлу:**

- **Увидеть то, что API не показывает.** Мягко удалённые записи, служебные поля (`created_at`, `updated_at`), журнал действий `audit_log`, хеши паролей вместо паролей.
- **Найти причину бага.** Кривые данные или кривой код? Если в базе всё правильно, а API отдаёт не то — баг в коде чтения. Если в базе уже неправильно — ищем, кто так записал.
- **Проверять побочные эффекты.** Удалили проект — что стало с его задачами, участниками, комментариями? Через API это видно не всегда.
- **Говорить с разработчиками на одном языке.** «В `tasks.assignee_id` у задачи 5 стоит `NULL`» — короче и точнее, чем «у задачи пропал исполнитель».

**Ограничения — сразу:**

- **Не на проде.** Доступ к базе прода у тестировщика бывает редко и только на чтение. Почему окружения разделяют — в уроке [«Тестовые окружения»](/osnovy/11-testovye-okruzheniya).
- **Только чтение по умолчанию.** Изменять данные в базе — отдельное осознанное действие, а не привычка. Об изменении данных и транзакциях — отдельный урок блока.
- **Только тестовые данные.** Если на стенде копия прода с реальными людьми — это персональные данные, с ними особые правила (разбор 5 ниже).

## Основные понятия

### СУБД, база, схема, таблица

| Понятие | Что это | В TaskFlow |
|---|---|---|
| **СУБД** | Программа, которая хранит данные и выполняет запросы | PostgreSQL 16 — контейнер `db` |
| **База данных** | Набор таблиц одного приложения внутри СУБД | `taskflow` |
| **Схема** | «Папка» внутри базы, в которой лежат таблицы | `public` |
| **Таблица** | Набор однотипных записей | `users`, `projects`, `tasks` и ещё 5 |

Одна СУБД может хранить много баз: на одном сервере PostgreSQL живут базы нескольких приложений.

Слово **«схема»** в работе встречается в двух смыслах. В PostgreSQL схема — это папка внутри базы, как `public`. А «схема базы данных» в разговоре — это описание всех таблиц и связей, часто в виде ER-диаграммы. Из контекста обычно понятно, о чём речь.

### Строка, столбец, тип

- **Строка** (запись) — один объект: один пользователь, одна задача.
- **Столбец** (поле) — одно свойство у всех объектов: `email` у всех пользователей, `title` у всех задач.
- **Тип столбца** — какие значения в нём допустимы: число, строка до 100 символов, дата, `true`/`false`. Значение другого типа база не сохранит.

### NULL — «значения нет»

`NULL` — это не ноль, не пустая строка и не слово «NULL». Это отметка «значение неизвестно или отсутствует».

| Значение в `assignee_id` | Что значит |
|---|---|
| `2` | Исполнитель — пользователь с `id = 2` |
| `NULL` | Исполнителя нет |
| `0` | Ссылка на пользователя с `id = 0`. Такого нет — база не даст сохранить |

Со строками так же: `description = ''` — «описание есть, но пустое», `description = NULL` — «описания нет вообще». Для пользователя на экране они часто выглядят одинаково. Для кода — нет: проверка «описание заполнено?» может по-разному сработать на `''` и на `NULL`. Поэтому в тестах полезно пробовать оба варианта.

У `NULL` есть особые правила сравнения, из-за которых запросы с ним пишут по-особому. Подробно — в [уроке про `SELECT`](/bd/02-select).

### Ключи

- **Первичный ключ** (PK, primary key) — столбец, по которому строку находят однозначно. Уникален и не бывает `NULL`. В TaskFlow почти у всех таблиц это `id`.
- **Составной ключ** — первичный ключ из нескольких столбцов. У `project_members` ключ — пара `(project_id, user_id)`: один пользователь в одном проекте записан только один раз. Своего `id` у таблицы нет — он не нужен.
- **Внешний ключ** (FK, foreign key) — столбец, который ссылается на первичный ключ другой таблицы. `tasks.project_id` ссылается на `projects.id`. База не даст сохранить задачу с `project_id = 999`, если проекта 999 нет.
- **Уникальность** — правило «значение не повторяется». Похоже на первичный ключ, но таких ограничений у таблицы может быть много, и в PostgreSQL уникальный столбец допускает `NULL` (подробнее — в уроке про ограничения). В TaskFlow уникально имя метки `labels.name`.

Ещё одно слово, которое ты увидишь в DBeaver, — **индекс**. Это «оглавление» для столбца: по нему база ищет быстрее, не перебирая все строки. Уникальный индекс заодно запрещает повторы. Подробно — в уроке про ограничения и индексы.

## Типы данных PostgreSQL в TaskFlow

| Тип | Где в TaskFlow | Что важно тестировщику |
|---|---|---|
| `integer`, `serial` | `id` всех таблиц, все `..._id` | `serial` — целое число, которое база сама увеличивает на 1 для новой строки. Номера не переиспользуются: удалили строку 5 — следующая получит новый номер, а не 5 |
| `varchar(n)` | `projects.name` — `varchar(100)`, `users.first_name` — `varchar(50)`, `comments.text` — `varchar(500)` | Строка не длиннее `n` символов. Длиннее — база откажет |
| `text` | В TaskFlow нет | Строка без ограничения длины. Ограничение тогда должно быть в коде |
| `boolean` | `users.is_active` | `true` / `false` (и `NULL`, если столбец это разрешает) |
| `timestamp with time zone` | `created_at`, `updated_at`, `deleted_at` | Момент времени с учётом часового пояса. Хранится в UTC, показывается в поясе того, кто смотрит |
| enum-тип | `users.role` — тип `userrole`, `project_members.role` — тип `projectrole` | Список допустимых значений. Чужое значение база отвергнет |
| `json`, `jsonb` | `audit_log.details` — `json` | Произвольная структура внутри одного поля. `jsonb` — та же идея, но хранится в разобранном виде, по нему быстрее искать |

Что из этого следует для тестов.

**Длина в API и длина в базе — одна граница.** В спецификации TaskFlow название проекта — от 1 до 100 символов, в базе — `varchar(100)`. Если API проверяет длину, на 101 символ ты получишь понятный `422`. Если API проверку забыл — запрос дойдёт до базы, база откажет, и клиент, скорее всего, увидит `500`. Поэтому граничные значения 100 и 101 проверяют не только «пропустит ли», но и **какой код вернётся**.

**Часовой пояс.** Время в базе хранится в UTC. DBeaver может показать его в поясе твоего компьютера, а API по спецификации TaskFlow отдаёт даты в UTC с суффиксом `Z`. Разница в 3 часа между Москвой и UTC — не баг, если пояса учтены. Прежде чем сравнивать время из базы и из API, приведи их к одному поясу.

**Enum в базе — последняя линия обороны.** Тип `userrole` допускает только `USER` и `ADMIN`. Попытка записать `MODERATOR` даже не дойдёт до таблицы. Но это не повод не проверять API: если сервер пропустит неизвестную роль, клиент снова получит `500` вместо понятного `422`. А вот статусы задач и проектов в TaskFlow хранятся обычными строками `varchar` — там допустимые значения охраняет только код.

::: tip Как DBeaver называет типы
В DBeaver часть типов показана короткими именами PostgreSQL: `int4` — это `integer`, `serial4` — `serial`, `bool` — `boolean`, `timestamptz` — `timestamp with time zone`. Это одно и то же. Столбец `serial` DBeaver может показать и как `int4` со значением по умолчанию `nextval(...)` — так база выдаёт следующий номер.
:::

## Связи между таблицами

| Связь | Что значит | Пример |
|---|---|---|
| **Один к одному** | Одной строке соответствует не больше одной строки в другой таблице | Пользователь и его паспортные данные в отдельной таблице. В TaskFlow такой связи нет |
| **Один ко многим** | У одной строки много «детей», у каждого ребёнка один «родитель» | У проекта много задач, у задачи один проект: `tasks.project_id → projects.id` |
| **Многие ко многим** | У строки слева много строк справа и наоборот | Задача — метки: у задачи несколько меток, одна метка висит на многих задачах |

**Один ко многим** делают внешним ключом на стороне «многих»: столбец `project_id` лежит в `tasks`, а не наоборот. В проекте нет списка его задач — есть задачи, которые ссылаются на проект.

**Многие ко многим** одним внешним ключом не сделать. Нужна **промежуточная таблица**, в которой каждая строка — одна пара:

- `task_labels (task_id, label_id)` — «на задаче такой-то висит метка такая-то»;
- `project_members (project_id, user_id, role)` — «пользователь такой-то участвует в проекте таком-то с такой-то ролью».

У `project_members` есть ещё и **данные о самой связи** — роль. Роль принадлежит не пользователю и не проекту, а паре: Иван может быть `MANAGER` в одном проекте и `VIEWER` в другом.

## ER-схема TaskFlow

**ER-диаграмма** (entity-relationship, «сущность — связь») — картинка всех таблиц и связей. Прямоугольник — таблица, внутри — столбцы, линии — связи по внешним ключам.

Как читать линии — нотация **«воронья лапка»**:

- **черта** у таблицы — «один»: со стороны `projects` у связи с `tasks` стоит черта;
- **лапка** из трёх зубцов — «много»: со стороны `tasks` — лапка. Читается: «один проект — много задач»;
- в полной нотации есть ещё кружок — «может не быть ни одного». На схемах ниже его нет, чтобы не перегружать картинку.

Восемь таблиц TaskFlow в одну картинку шириной с экран телефона не помещаются, поэтому схем две. Таблица `tasks` есть на обеих — через неё они стыкуются.

На что обратить внимание:

- **Две связи между `users` и `projects`/`tasks`.** Пользователь — владелец проекта (`projects.owner_id`), и пользователь — участник проекта (`project_members`). Это разные вещи. Владелец по правилам TaskFlow тоже есть в `project_members` с ролью `OWNER`, но связь `owner_id` от этого не исчезает.
- **`assignee_id` может быть `NULL`** — у задачи нет исполнителя. А вот `project_id` у задачи обязателен: столбец `NOT NULL`.
- **`audit_log.user_id` тоже может быть `NULL`**, а пара `entity_type` + `entity_id` — **не внешний ключ**. Это просто запись «с объектом типа `task` и номером 7 что-то сделали». База не проверяет, что такой объект есть: журнал должен пережить даже удаление объекта.
- В DBeaver ты увидишь ещё одну таблицу — **`alembic_version`**. Это служебная таблица миграций: в ней записано, до какой версии обновлена схема базы. К данным приложения она не относится, о миграциях — отдельный урок блока.

Схема — это рисунок. Правда — в самой базе. Схемы в документации устаревают: добавили столбец, а картинку не перерисовали. Поэтому перед проверками смотри реальную структуру в DBeaver.

## Мягкое удаление

**Мягкое удаление** (soft delete) — когда запись не стирают из таблицы, а ставят ей отметку «удалено». В TaskFlow отметка — столбец `deleted_at`:

| `deleted_at` | Что значит |
|---|---|
| `NULL` | Запись живая |
| `2026-10-15 09:12:44+00` | Запись удалена в этот момент |

Так удаляются пользователи, проекты, задачи и комментарии. Метки `labels` удаляются по-настоящему, а журнал `audit_log` не удаляется никогда.

Зачем так делают: удалённое можно восстановить, остаётся история, отчёты за прошлое не ломаются, связанные записи не исчезают каскадом.

Что это значит для тестировщика:

- **«Удалённое» есть в базе.** После `DELETE /tasks/5` строка с `id = 5` в таблице `tasks` осталась — с заполненным `deleted_at`. Это не баг, а устройство.
- **Каждое место, где показывают данные, должно эту отметку учитывать.** Списки, поиск, счётчики, проверки прав. Забыли фильтр в одном запросе — удалённое «воскресает» на одном экране. Как это проверять через API, разбирали в уроке [«Практикум: API-фича целиком»](/api/13-praktikum-api-fichi).
- **«Нет в API» ≠ «нет в базе».** Удалённый пользователь не виден через API, но его строка лежит в `users`.

### Мидл: уникальность «только среди живых»

Пользователь удалил аккаунт и хочет зарегистрироваться заново с тем же email. Если на `email` стоит обычная уникальность, база скажет: «такой email уже есть» — ведь удалённая строка никуда не делась.

В TaskFlow для этого сделан **частичный уникальный индекс** — уникальность действует только для строк, где `deleted_at` пустой:

```sql
CREATE UNIQUE INDEX ix_users_email_active_unique
    ON users (email) WHERE deleted_at IS NULL;
```

Два живых пользователя с одним email быть не могут. Живой и удалённый — могут. Так спецификация TaskFlow и обещает: email освобождается после удаления.

Где тут место для багов в любом проекте: уникальность сделали обычной, и повторная регистрация после удаления падает.

### Мидл: каскадное удаление в базе и мягкое удаление в API

У внешних ключей TaskFlow есть правило **`ON DELETE CASCADE`**: если физически удалить строку проекта, база сама удалит его задачи, участников, а у задач — комментарии и привязки меток. Это правило уровня базы.

Но API TaskFlow проекты физически не удаляет. Он ставит `deleted_at` проекту, его задачам и их комментариям — это делает код приложения, а не база. Каскад в базе сработает, только если кто-то выполнит настоящий `DELETE` в обход API. Например, тестировщик в DBeaver «почистить данные» — и вместе с проектом тихо исчезнут все его задачи.

## SQL — язык запросов

**SQL** (Structured Query Language) — язык, на котором разговаривают с реляционными базами. Он **декларативный**: ты говоришь, **что** хочешь получить, а не **как** это найти. «Дай названия задач проекта 1» — а по каким индексам искать и в каком порядке читать диск, СУБД решает сама.

Команды SQL делят на группы:

| Группа | Для чего | Пример |
|---|---|---|
| **DDL** — Data Definition | Создать и изменить структуру | `CREATE TABLE labels (...);`, `ALTER TABLE`, `DROP TABLE` |
| **DML** — Data Manipulation | Изменить данные | `INSERT`, `UPDATE`, `DELETE` |
| **DQL** — Data Query | Прочитать данные | `SELECT title FROM tasks;` |
| **DCL** — Data Control | Выдать и забрать права | `GRANT SELECT ON tasks TO qa_reader;` |
| **TCL** — Transaction Control | Управлять транзакциями | `BEGIN`, `COMMIT`, `ROLLBACK` |

В некоторых книгах `SELECT` относят к DML, а группу DQL не выделяют. На собеседовании годится любой вариант, если объяснишь.

Тестировщик чаще всего пишет **DQL** — `SELECT`. Это безопасно: чтение ничего не меняет.

### Первый запрос

```sql
SELECT * FROM projects LIMIT 5;
```

- `SELECT *` — «дай все столбцы»;
- `FROM projects` — «из таблицы `projects`»;
- `LIMIT 5` — «не больше 5 строк»;
- `;` — конец запроса.

`SELECT *` удобен для **разведки**: открыл незнакомую таблицу и посмотрел, что в ней есть. Но не в баг-репорте и не в отчёте. Там `*` вытащит лишнее — служебные поля, хеши паролей, персональные данные, — а важное утонет среди 10 столбцов. Кроме того, после добавления столбца тот же запрос вернёт другую таблицу. В отчёт — только нужные столбцы, по именам.

### Ещё четыре конструкции на этот урок

```sql
-- только нужные столбцы
SELECT id, name, status FROM projects;

-- только строки, где условие выполняется
SELECT id, title FROM tasks WHERE project_id = 1;

-- по порядку: ASC — по возрастанию (по умолчанию), DESC — по убыванию
SELECT id, title, created_at FROM tasks ORDER BY created_at DESC;

-- всё вместе: условие, порядок, ограничение
SELECT id, email FROM users WHERE is_active = true ORDER BY id LIMIT 3;
```

Правила записи:

- **строки — в одинарных кавычках**: `WHERE role = 'ADMIN'`. Двойные кавычки в PostgreSQL значат совсем другое — имя столбца или таблицы;
- **числа и `true`/`false` — без кавычек**: `WHERE project_id = 1`, `WHERE is_active = false`;
- **значения enum — как строки, с учётом регистра**: `'ADMIN'` подходит, на `'admin'` PostgreSQL ответит ошибкой — такого значения в типе `userrole` нет;
- **ключевые слова** можно писать и большими, и маленькими буквами. Большими — традиция, так запрос легче читать;
- `--` — комментарий до конца строки.

Порядок частей фиксированный: `SELECT … FROM … WHERE … ORDER BY … LIMIT`. Если переставить — будет ошибка. Сложные условия, поиск по части строки и работа с `NULL` — в [следующем уроке](/bd/02-select).

## СУБД, которые встретишь

| СУБД | Где встречается |
|---|---|
| **PostgreSQL** | Веб-сервисы, финтех, стартапы, госсектор. Бесплатная, очень распространена. **TaskFlow — PostgreSQL 16** |
| **MySQL / MariaDB** | Сайты, интернет-магазины, CMS вроде WordPress. MariaDB — ответвление MySQL |
| **MS SQL Server** | Корпоративные системы на технологиях Microsoft, банки, учёт |
| **Oracle** | Крупные банки, телеком, госкомпании — где большие нагрузки и большие бюджеты |
| **SQLite** | База в одном файле внутри приложения: мобильные приложения, браузеры, тесты |

Основа SQL у всех одна: `SELECT … FROM … WHERE` пишется одинаково. Отличаются **диалекты** — детали: как ограничить число строк (`LIMIT` в PostgreSQL и MySQL, `TOP` в MS SQL Server, `FETCH FIRST` в Oracle), какие есть типы и функции. Выучил PostgreSQL — в другой СУБД разберёшься за день.

## SQL и NoSQL

Реляционные базы хранят данные в таблицах со строгой структурой и связями. **NoSQL** — общее название баз, устроенных иначе. Они не «лучше» и не «хуже» — они под другие задачи.

| Вид | Как хранит | Пример | Где используют |
|---|---|---|---|
| **Реляционные** | Таблицы, строки, связи по ключам | PostgreSQL, MySQL | Заказы, деньги, пользователи — где важна точность и связи |
| **Документные** | Документы похожие на JSON, у каждого может быть своя структура | MongoDB | Каталоги товаров с разными характеристиками, контент |
| **Ключ — значение** | Пара «ключ → значение», всё в памяти | Redis | Кэш, сессии, счётчики, очереди |
| **Поисковые** | Индекс для полнотекстового поиска | Elasticsearch | Поиск по текстам, логи |

В TaskFlow, кроме PostgreSQL, уже работают **Redis** — ограничение частоты запросов, отозванные токены, кэш — и **Elasticsearch** — хранилище логов. Ты их видел в уроке [«Монолит, микросервисы, интеграции»](/api/11-monolit-mikroservisy). Redis и MongoDB подробно разберём в отдельных уроках этого блока.

Частое заблуждение: «NoSQL — значит без схемы». Схема есть всегда — вопрос, **где** она. В реляционной базе её охраняет СУБД. В MongoDB структуру документа держит код приложения — значит, проверять её тоже нужно на уровне приложения.

## Инструменты

- **DBeaver** — бесплатная программа с окнами: дерево таблиц, просмотр данных, редактор запросов, ER-диаграммы. Работает с PostgreSQL, MySQL, Oracle и десятками других СУБД. **Основной инструмент блока.**
- **psql** — консольный клиент PostgreSQL. У TaskFlow он есть внутри контейнера базы: `docker compose exec db psql -U taskflow taskflow`. Пригодится, когда нет окон — например, на удалённом сервере.
- **pgAdmin** — официальный графический клиент PostgreSQL, работает в браузере. Похож на DBeaver, но только для PostgreSQL.

### DBeaver: подключение к TaskFlow

TaskFlow должен быть запущен — по `README.md` репозитория, ветка `training-public`. База слушает порт `5432` на твоём компьютере.

1. Открой DBeaver. **File → New → Database Connection** (или кнопка с вилкой и плюсом на панели).
2. Выбери **PostgreSQL** → **Next**.
3. Заполни поля:

   | Поле | Значение |
   |---|---|
   | Host | `localhost` |
   | Port | `5432` |
   | Database | `taskflow` |
   | Username | `taskflow` |
   | Password | `taskflow` |

4. Нажми **Test Connection**. Если DBeaver предложит скачать **драйвер** PostgreSQL — соглашайся. Драйвер — это библиотека, через которую DBeaver разговаривает с конкретной СУБД.
5. Увидел «Connected» — нажми **Finish**.

### Режим только чтения — включи сразу

Пока подключение не в режиме только чтения, одно неосторожное `UPDATE` или правка ячейки в таблице данных меняет базу стенда.

Правой кнопкой по подключению → **Edit Connection** (или `F4`). В настройках подключения найди галочку **Read-only connection** — обычно она в разделе **General**, в блоке **Security**. Поставь её и сохрани. В разных версиях DBeaver раздел может называться чуть иначе — ищи именно эту галочку.

После этого DBeaver откажется выполнять запросы, которые меняют данные. Для этого урока больше и не нужно.

### Что где в DBeaver

- **Дерево слева**: подключение → **Databases** → `taskflow` → **Schemas** → `public` → **Tables**. Там таблицы TaskFlow и служебная `alembic_version`.
- **Открой таблицу** двойным щелчком. Вкладки сверху:
  - **Properties** — структура. Внутри, слева в списке: **Columns** (столбцы, типы, `Not Null`, значения по умолчанию), **Constraints** (первичный ключ и уникальность), **Foreign Keys** (внешние ключи), **Indexes** (индексы), **DDL** — команда `CREATE TABLE`, которой можно создать эту таблицу. В DDL видно всё сразу, включая условия индексов;
  - **Data** — сами строки. Тут же можно отредактировать ячейку — поэтому и нужен режим только чтения;
  - **ER Diagram** — схема связей этой таблицы. Схема всей базы — правой кнопкой по схеме `public` → **View Diagram**.
- **SQL-редактор**: правой кнопкой по подключению → **SQL Editor → Open SQL script** (или `Ctrl+]`). Напиши запрос и нажми **`Ctrl+Enter`** — выполнится запрос, на котором стоит курсор. Результат появится внизу. На macOS в некоторых версиях — `Cmd+Enter`.
- **Автокоммит** — переключатель режима транзакций на верхней панели: **Auto-Commit** или **Manual Commit**. В режиме автокоммита каждое изменение сохраняется сразу, отменить его нельзя. Что такое транзакции и коммит — в уроке про изменение данных.

::: warning Живая база стенда — это твои же проверки
База, к которой ты подключился, — та же, с которой работает API TaskFlow. Изменил строку в DBeaver — изменился ответ API. Удалил пользователя руками — у тебя «сломался» тест, который ни в чём не виноват. Не меняй данные стенда в обход API, если не понимаешь точно зачем.
:::

## Разборы из жизни

Ниже пять ситуаций, где база помогает или мешает тестировщику. Первый разбор открыт — это образец. Остальные попробуй сначала разобрать сам и только потом открывай.

<details class="details custom-block" open>
<summary>Разбор 1. Заказ создан, API ответил 201, а статуса нет — интернет-магазин</summary>

**Ситуация.** В интернет-магазин добавили поле `status` у заказа: «новый», «оплачен», «доставлен». Тестировщик создаёт заказ через API — `201 Created`, в ответе `"status": "NEW"`. Через день менеджеры жалуются: в отчёте по заказам часть заказов без статуса, фильтр «Новые» их не находит.

**Что видит мидл.**

- Ответ API собирается в коде: код мог подставить `"NEW"` в ответ, но не записать его в базу. Ответу на создание нельзя слепо верить.
- Похоже, столбец `status` добавили в таблицу **без значения по умолчанию** и **без запрета `NULL`**. Старый код, который создаёт заказы другим путём — из мобильного приложения, из импорта, — про новое поле ничего не знает и пишет `NULL`.
- `NULL` не равен `'NEW'`, поэтому фильтр «Новые» такие заказы не видит.

**Что делать.**

1. Найти такие заказы в базе: посмотреть `status` у последних созданных заказов из разных источников — сайта, приложения, импорта.
2. Посмотреть структуру столбца в DBeaver: есть ли `Not Null`, есть ли значение по умолчанию.
3. Завести баг: «Заказы, созданные через мобильное приложение, сохраняются со `status = NULL`. Столбец допускает `NULL` и не имеет значения по умолчанию. Фильтр "Новые" их не показывает». Приложить запрос и результат.
4. Предложить в баге два исправления: значение по умолчанию и запрет `NULL` в базе, плюс обновить старые строки — это решает команда.
5. Добавить в свой чек-лист для новых полей: «проверить в базе значение после создания из **каждого** источника».

**Чего не делать.**

- Не закрывать проверку по ответу `201` — смотреть, что легло в базу.
- Не проверять только один путь создания. Баг живёт там, где новое поле не учли.
- Не исправлять `NULL` в базе руками «чтобы отчёт заработал» — это спрячет баг.

</details>

::: details Разбор 2. Пользователь удалён, а регистрация с его email не проходит — онлайн-школа
**Ситуация.** Ученица попросила удалить её аккаунт. Поддержка удалила в админке. Через месяц она решила вернуться — регистрация отвечает «Пользователь с таким email уже существует». Поддержка: «Мы же удалили!»

**Что видит мидл.**

- Удаление, скорее всего, мягкое: строка осталась с отметкой «удалено».
- На `email` стоит **обычная** уникальность. Она не знает про мягкое удаление и считает удалённую строку занятой.

**Что делать.**

1. Найти пользователя в базе по email: строка есть? Отметка удаления стоит?
2. Посмотреть в DBeaver индексы таблицы пользователей: уникальность по `email` — с условием «только неудалённые» или без?
3. Уточнить у аналитика, что должно быть по требованиям: email освобождается после удаления или нет. Бывает, что не освобождается намеренно — например, из-за правил хранения данных.
4. Если должен освобождаться — баг: «email удалённого пользователя не освобождается, уникальность не учитывает мягкое удаление».
5. Добавить в чек-лист мягкого удаления: «повторное создание с тем же уникальным значением».

**Чего не делать.**

- Не удалять строку из базы руками, чтобы «помочь» ученице. Это обход бага, а не исправление, и на проде у тестировщика такого доступа быть не должно.
- Не решать самому, что «должно освобождаться». Это вопрос требований.
:::

::: details Разбор 3. «Починил данные» на общем стенде — команда мобильного банка
**Ситуация.** Тестировщику нужен клиент с заблокированной картой. Искать долго, и он выполняет в базе стенда `UPDATE cards SET status = 'BLOCKED' WHERE client_id = 15`. Через час у коллег падает половина автотестов: клиент 15 был их эталонным клиентом с активной картой. Полдня ищут «баг» в новой сборке.

**Что видит мидл.**

- Стенд общий. Данные на нём — общий ресурс, как общая кухня.
- Правка в обход API не проходит через бизнес-логику: в журнале нет записи, уведомление не ушло, связанные поля не обновились. Получились данные, которых в жизни не бывает.
- Самое дорогое — не правка, а время коллег, которые ищут причину.

**Что делать.**

1. Сразу написать в общий чат команды: что, где и когда изменил. Вернуть как было, если это возможно.
2. На будущее — создавать свои данные: своего клиента через API или через подготовленный скрипт, который команда согласовала.
3. Если без правки в базе не обойтись — договориться с командой, работать со своими записями и подключаться в режиме только чтения всё остальное время.
4. Предложить команде правило: кто какие тестовые записи использует, и что эталонные данные не трогает никто.

**Чего не делать.**

- Не менять «чужие» записи на общем стенде.
- Не молчать, надеясь, что никто не заметит.
- Не держать подключение к общей базе с правом записи «на всякий случай».
:::

::: details Разбор 4. Время заказа в базе на 3 часа меньше, чем на экране — служба доставки
**Ситуация.** Тестировщик сверяет заказ: на экране «Создан 15.10 в 12:30», в DBeaver `created_at = 2026-10-15 09:30:00+00`. Он заводит баг «Время в базе сохраняется неправильно, отстаёт на 3 часа».

**Что видит мидл.**

- `+00` в конце — это UTC. 09:30 по UTC — это 12:30 по Москве. Время одно и то же, просто показано в разных поясах.
- Хранить в UTC — правильная практика: пользователи в разных городах, переход на летнее время в других странах.
- Баг здесь возможен, но другой: если бы столбец был **без** часового пояса (`timestamp`), а сервер писал в него местное время — тогда сравнивать было бы нельзя вообще.

**Что делать.**

1. Посмотреть тип столбца: `timestamp with time zone` или `timestamp` без пояса.
2. Посмотреть, что отдаёт API: время в UTC с `Z` или со смещением.
3. Проверить, что экран переводит время в пояс пользователя. Сменить пояс на компьютере или в профиле — время на экране должно поменяться, в базе — нет.
4. Проверить границу дня: заказ в 01:30 по Москве — это 22:30 предыдущего дня по UTC. В какой день он попадёт в отчёт «за сегодня»? Вот здесь баги находят часто.

**Чего не делать.**

- Не заводить баг, не проверив, в каком поясе показано время.
- Не сравнивать время из базы и с экрана, не приведя их к одному поясу.
:::

::: details Разбор 5. В отчёт попали реальные телефоны клиентов — тестовый стенд с копией прода
**Ситуация.** Для тестирования отчётов на стенд залили копию базы прода. Тестировщик нашёл баг в выгрузке и приложил к баг-репорту файл: 200 строк с именами, телефонами и адресами клиентов. Баг-трекер видят подрядчики.

**Что видит мидл.**

- Имена, телефоны, адреса — **персональные данные**. Их обработку регулирует закон — в России это 152-ФЗ. Утечка через баг-трекер — это утечка.
- Проблема не только в этом отчёте: если копия прода лежит на стенде без обезличивания, к ней имеет доступ слишком много людей.

**Что делать.**

1. Сразу удалить вложение из баг-трекера и сообщить руководителю или ответственному за безопасность — пусть оценят, что делать дальше.
2. Для баг-репорта оставить 2–3 строки, а персональные поля заменить: `Иван И.`, `+7 900 ***-**-12`. Для воспроизведения бага реальные данные обычно не нужны.
3. Поднять вопрос в команде: копии прода на стенде должны быть **обезличены** — имена, телефоны и адреса заменены на выдуманные.
4. В запросах для отчётов выбирать только нужные столбцы — не `SELECT *`.

**Чего не делать.**

- Не выгружать данные целиком «на всякий случай».
- Не пересылать файлы с персональными данными в мессенджеры и почту.
- Не считать, что раз это тестовый стенд — данные тоже тестовые.
:::

## Частые ошибки

- **Путать `NULL` и пустую строку.** `''` — «значение есть, оно пустое». `NULL` — «значения нет». Код и запросы обрабатывают их по-разному, поэтому в тестах нужны оба случая.
- **Считать, что «есть в базе» = «видит пользователь».** Мягко удалённая запись в базе есть, а в API её нет — и это правильно. Сравнивай с учётом правил: удаление, права, фильтры.
- **Работать в живой базе без режима только чтения.** Случайная правка ячейки в DBeaver — и стенд уже не тот. Read-only включается одной галочкой.
- **`SELECT *` в баг-репорте.** Лишние столбцы, хеши паролей, персональные данные. В отчёт — только нужные столбцы.
- **Верить диаграмме, а не реальной схеме.** Картинка в документации могла устареть. Структуру проверяй в DBeaver: столбцы, типы, ключи, индексы.
- **Сравнивать время, не глядя на пояс.** «Отстаёт на 3 часа» — почти всегда разница UTC и местного времени, а не баг.
- **Проверять только ответ API.** `201` — не доказательство, что данные сохранились правильно. Мидл заглядывает в базу хотя бы для ключевых полей.

## Часть 4. Первые запросы

Используй только то, что разобрано в теории: `SELECT` со списком столбцов или `*`, `FROM`, одно условие `WHERE … = …`, `ORDER BY` по одному столбцу, `LIMIT`.

Результаты зависят от твоего стенда: в блоке 2 ты создавал проекты, задачи и пользователей, а кое-что удалял. Поэтому эталон — это **запрос**, а не числа. Мягко удалённые строки в результат тоже попадут — смотри на `deleted_at`. Как их отфильтровать — в [следующем уроке](/bd/02-select).

## Ситуационные кейсы

Это рабочие ситуации, о которых могут спросить и на собеседовании. Готового ответа, который нужно угадать, здесь нет. Сначала подумай сам, потом открывай разбор.

::: details Кейс 1. «Зачем тестировщику SQL, если есть API?»
**Ситуация.** Интервьюер: «У нас всё тестируется через API и интерфейс. Зачем вам SQL?»

**Как рассуждать.** Что API показывает, а что нет? Чем ответ сервера отличается от того, что сохранилось? Где ещё база помогает — до и после проверки?

**Пример ответа.** API показывает то, что сервер решил показать, а база — что сохранилось на самом деле. Я использую SQL для четырёх вещей.

Первое — проверка побочных эффектов: после `201` смотрю, что записалось в базу, особенно поля, которых нет в ответе, и связанные таблицы. Второе — подготовка данных: найти пользователя с нужной ролью или заказ в нужном статусе запросом быстрее. Третье — локализация бага: если в базе данные правильные, а API отдаёт не то — баг в коде чтения; если в базе уже неправильно — в коде записи или в миграции. Четвёртое — то, что API не показывает вообще: мягко удалённые записи, журнал действий, служебные поля.

И отдельно: на проде у меня доступ только на чтение, если он есть вообще. Данные меняю только через API или согласованными скриптами.
:::

::: details Кейс 2. «Чем первичный ключ отличается от уникального?»
**Ситуация.** Интервьюер: «Первичный ключ ведь тоже уникальный. Зачем тогда отдельно уникальность?»

**Как рассуждать.** Сколько первичных ключей бывает у таблицы? А уникальных столбцов? Может ли там быть `NULL`? На что ссылаются внешние ключи?

**Пример ответа.** Первичный ключ — главный идентификатор строки. Он у таблицы один (может состоять из нескольких столбцов), не бывает `NULL`, и на него ссылаются внешние ключи других таблиц.

Уникальных ограничений может быть сколько угодно, и столбец может быть не главным — например, email у пользователя: `id` — первичный ключ, а email просто не должен повторяться. В PostgreSQL уникальный столбец может содержать `NULL`, причём несколько: `NULL` не считается равным другому `NULL`.

Бывает и частичная уникальность — только среди строк по условию. Типичный пример — email уникален только среди неудалённых пользователей при мягком удалении. Это я бы обязательно проверил: удалить пользователя и зарегистрироваться с тем же email.
:::

::: details Кейс 3. «NULL и пустая строка — в чём разница и почему это важно для тестов?»
**Ситуация.** Интервьюер: «В поле "отчество" у одного клиента пустая строка, у другого `NULL`. Есть разница?»

**Как рассуждать.** Что значит каждое из значений? Как их обработают код, фильтр, отчёт? Как их отправить через API?

**Пример ответа.** Есть. Пустая строка — «значение есть, и оно пустое»: например, человек явно указал, что отчества нет. `NULL` — «значения нет вообще»: не заполнили, не знаем.

Для тестов это важно, потому что код и запросы обрабатывают их по-разному. Проверка «отчество заполнено» может пропустить пустую строку. Фильтр «где отчество равно пустому» не найдёт `NULL`. В отчёте одни клиенты попадут в группу «без отчества», другие — нет. А сравнение с `NULL` через `=` в SQL вообще не работает — для него есть отдельная конструкция.

Поэтому в тестах я пробую оба варианта: в API отправить `""`, `null` и не передать поле совсем — и посмотреть, что легло в базу. Если требований на этот счёт нет — это вопрос аналитику: хранить ли пустую строку как `NULL`.
:::

::: details Кейс 4. Хитрый вопрос: «В базе запись есть, а в API её нет — это баг?»
**Ситуация.** Интервьюер: «Вы нашли в таблице заказов заказ, которого нет в ответе `GET /orders`. Заводите баг?»

**Как рассуждать.** Какие законные причины могут быть у того, что запись не видна? Где взять ожидание?

**Пример ответа.** Не сразу. Сначала проверю законные причины.

Запись может быть мягко удалена — смотрю отметку удаления. Может принадлежать другому пользователю — права. Может не подходить под фильтр по умолчанию: например, список показывает только активные заказы. Может быть на следующей странице пагинации. Может быть черновиком, который пользователю не показывают. Может быть кэш, который ещё не обновился.

Если ни одна причина не подходит и по требованиям запись должна быть видна — это баг. В баг-репорте я укажу запрос в базу со строкой, запрос в API с ответом и раздел требований, по которому её ожидаю. Ловушка вопроса — в слове «есть»: в базе есть многое, что пользователь видеть не должен.
:::

::: details Кейс 5. Хитрый вопрос: «Вам дали доступ к базе прода. Что можно делать?»
**Ситуация.** Интервьюер: «Для расследования инцидента вам выдали доступ к базе прода. Что будете делать?»

**Как рассуждать.** Какие права нужны для расследования? Какие риски у запросов на проде, даже у чтения? Что с персональными данными?

**Пример ответа.** Сначала проверю, что доступ только на чтение, — если нет, попрошу именно такой. Изменять данные на проде тестировщик не должен: любая правка — через исправление в коде или согласованный скрипт с ревью.

Даже чтение на проде не бесплатно. Тяжёлый запрос без условий по большой таблице может нагрузить базу и замедлить сервис для пользователей. Поэтому — только нужные столбцы, условие по ключу, `LIMIT`, и по возможности — на реплике для чтения, а не на основной базе.

И персональные данные: выгружаю минимум, не пересылаю в мессенджеры, в баг-репорт — без реальных телефонов и адресов. Когда расследование закончено — доступ лучше сдать.
:::

::: details Кейс 6. «SQL или NoSQL — когда что?»
**Ситуация.** Интервьюер: «Почему у вас в проекте PostgreSQL, а не MongoDB? И где бы вы взяли MongoDB?»

**Как рассуждать.** Какие данные у проекта: строго связанные или разнородные? Где важна целостность? Какие ещё базы бывают, кроме этих двух?

**Пример ответа.** Реляционная база — когда данные связаны и важна точность: заказы, платежи, пользователи, права. Внешние ключи, типы и транзакции не дадут сохранить заказ без клиента или списать деньги наполовину.

Документная база вроде MongoDB — когда у объектов разная структура и их удобно хранить целиком: каталог товаров, где у телефона одни характеристики, а у дивана другие; контент, профили с произвольными полями. Схема там всё равно есть — только держит её код, а не база, и тестировать это нужно на уровне приложения.

Часто в одном проекте живут несколько баз: основная реляционная, Redis для кэша и счётчиков, Elasticsearch для поиска и логов. Для тестировщика это значит: данные могут быть в одной базе правильные, а в кэше или поисковом индексе — устаревшие. Это отдельное место для проверок.
:::
