## Простыми словами

**Реляционная база** — как таблица в Excel со строгими колонками. У каждой строки одни и те же поля. Клиенты — на одном листе, заказы — на другом, а связь между ними — через номер: «заказ 101, клиент № 7».

**Документная база** — как папка с анкетами. Каждая анкета — отдельный документ, и всё про клиента лежит внутри неё: имя, адреса, заказы. Анкеты могут немного отличаться: в новой есть графа «мессенджер», в старой её нет.

**MongoDB** — самая известная документная база. В TaskFlow её нет — поэтому урок без стенда: разбираем документы и запросы на примерах.

Тестировщик MongoDB не администрирует. Его задача — **узнать её на проекте, понимать, чем она отличается от PostgreSQL, и знать, где в ней прячутся баги**.

В этом уроке:

- какие бывают нереляционные базы — коротко;
- как устроена MongoDB: коллекции, документы, вложенность;
- чем она отличается от PostgreSQL;
- как выглядит запрос — чтобы узнать его на работе;
- **что важно тестировщику** — шесть вещей, из-за которых чаще всего бывают баги.

## Нереляционные базы — какие бывают

Обзор SQL и NoSQL был в уроке [«Что такое база данных»](/bd/01-chto-takoe-bd). Здесь — коротко и с тем, где ты их встретишь.

| Вид | Как хранит — одной строкой | Пример | Где встретишь |
|---|---|---|---|
| **Документные** | Документы, похожие на JSON. Всё про объект — в одном документе | MongoDB | Каталоги товаров, профили, контент |
| **Ключ — значение** | По ключу сразу получаешь значение | Redis — урок [«Redis: кэш и не только»](/bd/07-redis) | Кэш, сессии, счётчики |
| **Поисковые** | Индекс для быстрого поиска по тексту | Elasticsearch — в TaskFlow хранит логи | Поиск на сайте, логи |
| **Колоночные** | Хранят данные по столбцам — быстро считают суммы по миллионам строк | ClickHouse | Аналитика, отчёты |
| **Графовые** | Хранят связи «кто с кем связан» | Neo4j | Друзья друзей, рекомендации |

Главная мысль: **NoSQL — не «без структуры», а «другой способ хранить»**. Структура у данных есть всегда. Вопрос только, кто за ней следит: в PostgreSQL — сама база, в MongoDB — чаще всего код приложения.

## MongoDB в двух словах

Слова другие, но устройство узнаваемое:

| MongoDB | PostgreSQL |
|---|---|
| база | база |
| **коллекция** | таблица |
| **документ** | строка |
| поле | столбец |
| `_id` | первичный ключ `id` |

**Документ** записан в формате, похожем на JSON — ты его видел в уроке [«API, REST и форматы данных»](/api/06-api-rest-formaty). Пример — пользователь:

```js
{
  "_id": ObjectId("665f1c2a9b1e4a0012ab34cd"),
  "email": "anna@example.com",
  "name": "Анна Петрова",
  "address": { "city": "Казань", "street": "Баумана, 5" },
  "phones": ["+7 900 111-22-33", "+7 900 444-55-66"],
  "createdAt": ISODate("2026-03-14T09:12:00Z")
}
```

Что здесь важно:

- **`_id`** — у каждого документа свой, уникальный в коллекции. Обычно это **ObjectId** — длинная строка из букв и цифр, а не 1, 2, 3.
- **Вложенный объект** — `address`: внутри поля целый объект со своими полями.
- **Массив** — `phones`: несколько значений в одном поле. В PostgreSQL для этого понадобилась бы отдельная таблица.
- **Гибкая схема** — по умолчанию база не заставляет все документы коллекции быть одинаковыми. Рядом может лежать пользователь без `address` и с полем `phone` вместо `phones`. Разработчики могут включить проверку структуры, но на многих проектах её нет или она мягкая.

## Чем MongoDB отличается от PostgreSQL

| | PostgreSQL | MongoDB |
|---|---|---|
| **Как хранит** | Таблицы, строки, столбцы | Коллекции документов |
| **Связи** | Внешние ключи и JOIN | Чаще всего — данные вложены в документ. Ссылки по `_id` бывают, но база их не охраняет |
| **Структура** | Строгая: столбцы и типы задаёт база | Гибкая: поля у документов могут отличаться |
| **Типы** | Столбец `price` — всегда число | В одном документе `price` число, в другом может оказаться строкой |
| **Язык запросов** | SQL | Свой язык: `find(...)` с условиями в фигурных скобках |
| **Где удобнее** | Деньги, заказы, остатки — где важны точность и связи | Объекты с разной структурой: каталог, профили, контент, события |

Ни одна не «лучше». Часто на проекте живут обе: заказы и оплаты — в PostgreSQL, каталог или логи действий — в MongoDB.

## Как выглядит запрос

Писать запросы к MongoDB на работе тестировщику приходится редко. Но **узнать** запрос в задаче, в логе или у разработчика в чате — нужно. Четыре примера с переводом на SQL:

| Что нужно | MongoDB | SQL |
|---|---|---|
| Оплаченные заказы | `db.orders.find({ status: "paid" })` | `SELECT * FROM orders WHERE status = 'paid'` |
| Заказы из Москвы — по вложенному полю | `db.orders.find({ "customer.city": "Москва" })` | `SELECT o.* FROM orders o JOIN customers c ON c.id = o.customer_id WHERE c.city = 'Москва'` |
| Заказы дороже 1000 | `db.orders.find({ total: { $gt: 1000 } })` | `SELECT * FROM orders WHERE total > 1000` |
| 5 последних заказов | `db.orders.find().sort({ createdAt: -1 }).limit(5)` | `… ORDER BY created_at DESC LIMIT 5` |

Как читать:

- `db.orders` — коллекция `orders`, `find(...)` — «найди».
- В фигурных скобках — условия. Несколько условий через запятую — это «И»: `{ status: "paid", "customer.city": "Москва" }`.
- Вложенное поле пишут через точку и в кавычках: `"customer.city"`.
- `$gt` — «больше» (greater than), `$lt` — «меньше».
- `sort({ createdAt: -1 })` — по убыванию, `1` — по возрастанию. `limit(5)` — как `LIMIT 5`.

Ещё одно условие, которое пригодится тестировщику, — **«поля нет»**: `db.products.find({ material: { $exists: false } })` найдёт товары, у которых поля `material` нет совсем. В SQL прямого аналога нет: там столбец есть у каждой строки, просто бывает `NULL`.

Изменение данных, агрегации, индексы, репликация — темы для разработчиков и админов, в этом уроке их нет.

**Инструменты** — одной строкой: **MongoDB Compass** — программа с окнами, как DBeaver; **mongosh** — консоль, как `psql`.

## Что важно тестировщику

Главный раздел урока. Шесть вещей, из-за которых в проектах с MongoDB чаще всего бывают баги.

### 1. Разные документы — разные поля

Гибкая схема — это удобно разработчикам и опасно для данных. В одной коллекции поле может:

- **отсутствовать** — у старых документов, созданных до появления поля;
- быть **`null`**;
- быть **другого типа** — `"1500"` строкой вместо `1500` числом, `"true"` вместо `true`.

Новый экран или отчёт пишут и проверяют на свежих документах — а на «старых» он падает: «Cannot read properties of undefined», пустая карточка, `NaN` в сумме.

**Что проверять:** не только новые документы, но и старые — созданные до изменения. Спроси разработчика: «Сколько документов без нового поля? Их обновили или код умеет с ними жить?»

### 2. Данные продублированы

В MongoDB часто кладут копию данных прямо в документ: имя клиента и адрес — в каждый заказ, название товара — в каждую позицию. Так быстрее читать, но копии живут своей жизнью.

Клиент поменял имя в профиле — в новых заказах новое, в старых — старое.

**Баг или так задумано?** Зависит от требований. Для заказа часто правильно хранить **как было на момент покупки** — как в чеке. А вот в списке «Мои заказы» старое имя может выглядеть как ошибка. Требования нет — **вопрос аналитику**: «При смене имени в профиле что должно показываться в старых заказах?»

### 3. Нет внешних ключей

Если документы всё-таки ссылаются друг на друга — например, в комментарии хранится `authorId`, — база **не проверяет**, что такой автор существует. Удалили пользователя — его комментарии остались с `authorId`, который ведёт в пустоту. Это **«осиротевшие» ссылки**.

**Что проверять:** удаление. Удалил объект — что стало с документами, которые на него ссылаются? Экран с ними открывается? Что показано вместо автора?

### 4. Большие вложенные массивы

Комментарии внутри поста, история изменений внутри задачи — массив растёт. У документа MongoDB есть **предел размера — 16 МБ**. До него далеко, но страница, которая загружает пост с десятью тысячами комментариев целиком, начнёт тормозить гораздо раньше.

**Что проверять:** объект с очень большим числом вложенных элементов — открывается ли, как быстро, есть ли постраничный вывод.

### 5. Проверка «API ↔ база» — то же самое, только `find`

Идея из урока [«Как тестировать базу данных»](/bd/05-testirovanie-bd) не меняется: сделал запрос в API — посмотрел, что реально сохранилось. Только вместо `SELECT` — `find` в Compass:

```js
db.users.find({ email: "anna@example.com" })
```

Сверь: все ли поля сохранились, правильного ли они **типа** — число осталось числом, дата — датой, а не строкой; нет ли лишних полей.

### 6. `_id` — не номер по порядку

ObjectId не похож на 1, 2, 3. В нём зашито время создания, но с точностью до секунды, а приложение может задать `_id` и само. Поэтому сортировать по `_id`, чтобы найти «последний созданный» документ, в тестах **ненадёжно**. Надёжнее — по полю даты, например `createdAt`.

## Где встретишь MongoDB на работе

- **Каталоги товаров** — у телефона одни характеристики, у дивана другие, и все лежат в одной коллекции.
- **Профили и настройки** — у каждого пользователя свой набор: тема, уведомления, любимые разделы.
- **Логи и события** — «пользователь нажал», «заказ сменил статус»: много, разной формы, пишутся постоянно.
- **Контент** — статьи, посты, комментарии, отзывы.

## Разборы из жизни

Три коротких случая. Первый открыт — это образец.

<details class="details custom-block" open>
<summary>Разбор 1. У старых товаров нет нового поля — интернет-магазин мебели</summary>

**Ситуация.** В карточку товара добавили «Материал». Тестировщик создал несколько товаров, всё показывается. После релиза половина карточек открывается пустой страницей.

**Что видит мидл.**

- Новые товары создавались уже с полем `material`. У тысяч старых документов этого поля нет.
- Экран обращается к `material.name`, а `material` у старых товаров отсутствует — страница падает с ошибкой.
- Проверяли только на новых данных.

**Что делать.**

1. Завести баг: «Карточка товара без поля "материал" не открывается». Пример — любой товар, созданный до релиза.
2. Найти, сколько таких: `db.products.find({ material: { $exists: false } })`.
3. Вопрос команде: заполнить поле у старых товаров или показывать «не указан»?

**Чего не делать.**

- Не проверять новое поле только на свежих документах — старые важнее.

</details>

::: details Разбор 2. Старое имя в заказах — сервис доставки
**Ситуация.** Пользователь сменил фамилию после свадьбы. В профиле — новая, в истории заказов — старая. Тестировщик заводит баг «имя не обновляется».

**Что видит мидл.**

- Имя клиента скопировано в каждый документ заказа в момент покупки. Профиль и заказы — разные документы.
- Это может быть задумано: заказ — как чек, в нём данные на момент покупки.

**Что делать.**

1. Не баг, а вопрос аналитику: «Что показывать в старых заказах после смены имени — как было или как сейчас?»
2. Если «как сейчас» — тогда это баг, и проверить все места, куда скопировано имя: заказы, отзывы, чаты с поддержкой.

**Чего не делать.**

- Не заводить баг на продублированные данные, пока не узнал, как задумано.
:::

::: details Разбор 3. Сортировка по цене «скачет» — маркетплейс
**Ситуация.** Сортировка «сначала дешёвые»: сверху товары по 300, 500, 900 ₽, потом снова 150 ₽, потом 2000 ₽.

**Что видит мидл.**

- Часть товаров загружена импортом из файла, и цена у них сохранилась **строкой**: `"150"`, `"2000"`. У остальных — числом: `300`, `500`, `900`.
- MongoDB при сортировке ставит все числа раньше всех строк. Поэтому сначала идут числа по порядку, потом строки — а строки сравниваются как текст, по первому символу: `"150"` раньше `"2000"`, но и `"1000"` оказался бы раньше `"200"`.
- Фильтр «до 1000 ₽» товары со строковой ценой тоже не находит: `{ price: { $lt: 1000 } }` сравнивает только с числами.

**Что делать.**

1. Завести баг: «Сортировка по цене нарушена: у товаров из импорта цена хранится строкой». Приложить пару документов из Compass.
2. Проверить импорт: какого типа поля он сохраняет.

**Чего не делать.**

- Не проверять сортировку на трёх товарах, созданных вручную через интерфейс.
:::

## Частые ошибки

- **«NoSQL — значит без схемы, проверять нечего».** Схема есть — её держит код. Значит, ошибки в ней ищет тестировщик.
- **Проверил новое поле только на новых документах.** Старые документы без поля ломают экраны чаще всего.
- **Не посмотрел на тип.** `"1500"` и `1500` на экране выглядят одинаково, а сортируются и фильтруются по-разному.
- **Сразу баг на старые данные в копиях.** Дублирование может быть задумано — сначала вопрос аналитику.
- **Сортировка по `_id` как «по дате создания».** Для тестов надёжнее поле даты.

Дальше — практикум блока: фича целиком, через API и базу.

## Что нужно сделать

Цель — научиться читать документы MongoDB, узнавать запросы и составлять проверки. Ничего устанавливать не нужно — всё письменно.

Задание из четырёх частей:

1. Прочитай документ — 4 задачи.
2. Узнай запрос — 4 задачи.
3. Что проверишь — 2 рабочие ситуации.
4. Задачи на внимательность — 3 задачи.

Уровни: **джун** — база, **мидл** — с подвохом.

Хочешь потренироваться на живых данных — есть онлайн-песочница **Mongo Playground** (mongoplayground.net): слева кладёшь документы, справа пишешь `find`. Это необязательно.

## Часть 1. Прочитай документ

Два документа из коллекции `users` одного проекта:

```js
// Документ А
{
  "_id": ObjectId("665f1c2a9b1e4a0012ab34cd"),
  "email": "anna@example.com",
  "name": "Анна Петрова",
  "address": { "city": "Казань", "street": "Баумана, 5" },
  "phones": ["+7 900 111-22-33", "+7 900 444-55-66"],
  "settings": { "theme": "dark", "notifications": true },
  "createdAt": ISODate("2026-03-14T09:12:00Z")
}

// Документ Б
{
  "_id": ObjectId("64a01b7e2c3d4e0011aa22bb"),
  "email": "boris@example.com",
  "name": "Борис",
  "phone": "+7 900 777-88-99"
}
```

**Задача 1** (джун). Что в документе А вложено? Где объекты, где массивы?

::: details Эталон
Объекты — `address` (город, улица) и `settings` (тема, уведомления). Массив — `phones`, в нём два телефона.
:::

**Задача 2** (джун). Сравни документы А и Б. Чем они отличаются по полям?

::: details Эталон
- У Б нет `address`, `settings`, `createdAt`.
- У А телефоны в поле `phones` — массив. У Б — в поле `phone`, одной строкой. Поле **называется по-другому** и другого вида.

Похоже, Б — старый пользователь, созданный до того, как структуру поменяли.
:::

**Задача 3** (мидл). Экран «Профиль» показывает город, список телефонов и дату регистрации. Его проверили на Анне. Что может сломаться на Борисе?

::: details Эталон
- Город: `address` нет — если код берёт `address.city`, экран может упасть или показать «undefined».
- Телефоны: поля `phones` нет — список пустой, хотя телефон у Бориса есть в `phone`.
- Дата регистрации: `createdAt` нет — пусто, «Invalid Date» или ошибка.

Вывод: проверять экран и на старом документе. И спросить, как задумано показывать пользователей без этих полей.
:::

**Задача 4** (джун). Как бы эти данные выглядели в PostgreSQL?

::: details Эталон
Например:

- `users` — `id`, `email`, `name`, `city`, `street`, `theme`, `notifications`, `created_at`. Адрес и настройки можно держать столбцами или вынести в свои таблицы.
- `user_phones` — `user_id`, `phone`: телефонов несколько, поэтому отдельная таблица со ссылкой на пользователя.

У Бориса в столбцах адреса и настроек был бы `NULL` — но сами столбцы были бы у всех одинаковые.
:::

## Часть 2. Узнай запрос

Скажи, что вернёт запрос, и напиши аналог на SQL. Для SQL считай, что у таблицы те же поля, что у документа; вложенное поле — обычный столбец.

**Задача 5** (джун). `db.users.find({ "address.city": "Казань" })`

::: details Эталон
Пользователи, у которых во вложенном адресе город — Казань. Анна попадёт, Борис — нет: адреса у него нет.

SQL: `SELECT * FROM users WHERE city = 'Казань'`.
:::

**Задача 6** (джун). `db.orders.find({ status: "paid" }).sort({ createdAt: -1 }).limit(10)`

::: details Эталон
10 последних оплаченных заказов — сначала самые новые.

SQL: `SELECT * FROM orders WHERE status = 'paid' ORDER BY created_at DESC LIMIT 10`.
:::

**Задача 7** (мидл). `db.users.find({ settings: { $exists: false } })`. Что вернёт? Из документов части 1 кто попадёт?

::: details Эталон
Пользователи, у которых поля `settings` нет совсем. Из части 1 — Борис.

Точного аналога в SQL нет: столбец `settings` был бы у всех. Ближайшее — `WHERE settings IS NULL`. Такой запрос тестировщик пишет, чтобы найти «старые» документы для проверки.
:::

**Задача 8** (мидл). Напиши сам: заказы со статусом `new` от клиентов из Москвы. Город лежит во вложенном объекте `customer`.

::: details Эталон
```js
db.orders.find({ status: "new", "customer.city": "Москва" })
```
Вложенное поле — через точку и в кавычках.
:::

## Часть 3. Что проверишь

Для каждой ситуации составь список проверок — не меньше пяти пунктов, с вопросами аналитику. Потом сравни с эталоном.

**Задача 9** (мидл). Интернет-магазин, каталог в MongoDB. «В карточку товара добавляем поле "материал". Фильтр по материалу в каталоге».

::: details Эталон
- Новый товар с материалом — поле сохранилось, в карточке показано.
- **Старый товар без поля** — карточка открывается, вместо материала «не указан» или ничего — как задумано.
- Фильтр по материалу находит нужные товары; старые без поля не ломают фильтр.
- Тип и значения: материал из списка или свободный текст? «Дуб» и «дуб» — один материал или два?
- Импорт и другие способы создания товаров тоже заполняют поле.
- Вопрос аналитику: заполнят ли поле у старых товаров? Что показывать, пока не заполнено?
:::

**Задача 10** (мидл). «Переносим профили пользователей из PostgreSQL в MongoDB». Каждый профиль станет документом.

::: details Эталон
- **Количество**: сколько было строк — столько стало документов.
- **Выборочная сверка**: несколько профилей — поле за полем, в том числе с пустыми значениями, длинными именами, буквами ё и эмодзи.
- **Типы**: даты остались датами, числа — числами, `true` — не стал строкой `"true"`.
- **`NULL`**: что с ним стало — поле со значением `null` или поля нет? Приложение понимает оба случая?
- **Связанные данные**: телефоны и адреса из других таблиц оказались внутри документа, ничего не потерялось и не задвоилось.
- **Приложение**: вход, профиль, редактирование, поиск работают на перенесённых данных.
- Вопрос команде: что делаем с профилями, созданными во время переезда?
:::

## Часть 4. Задачи на внимательность

Условия короткие, в каждом — подвох.

**Задача 11** (мидл). Новое поле «скидка» проверили на 5 только что созданных товарах — всё работает. Тестировщик пишет: «Проверено».

::: details Эталон
Проверены только новые документы. Старые товары без поля `discount` — главный риск: экран или расчёт цены может на них упасть. Нужно проверить хотя бы один товар, созданный до изменения.
:::

**Задача 12** (джун). Чтобы найти последний созданный заказ, тестировщик сортирует по `_id` по убыванию и берёт первый. Что не так?

::: details Эталон
`_id` — не счётчик. Время в ObjectId — с точностью до секунды, а приложение может задать `_id` само. Надёжнее — сортировать по полю даты: `sort({ createdAt: -1 })`.
:::

**Задача 13** (мидл). Пользователь удалил аккаунт. Его отзывы на товары остались — в каждом `authorId` удалённого пользователя. Страница товара открывается. Всё в порядке?

::: details О чём подумать
Что показано на месте автора? Кто проверяет, что `authorId` ведёт к существующему пользователю?
:::

::: details Эталон
MongoDB не проверяет ссылки: отзывы с «осиротевшим» `authorId` — нормальная ситуация для базы. Проверить нужно приложение: что показано вместо автора — «Пользователь удалён», пусто, ошибка? Можно ли открыть профиль автора? И вопрос аналитику: отзывы удалённых пользователей оставлять, скрывать или обезличивать?
:::

## Ситуационные кейсы

Это рабочие ситуации, о которых могут спросить и на собеседовании. Сначала подумай сам, потом открывай разбор.

::: details Кейс 1. «Чем MongoDB отличается от PostgreSQL?»
**Ситуация.** Интервьюер: «Чем MongoDB отличается от PostgreSQL? Где бы вы взяли каждую?»

**Как рассуждать.** Как хранит, как связывает, кто следит за структурой?

**Пример ответа.** PostgreSQL — реляционная база: таблицы со строгими столбцами и типами, связи через внешние ключи, запросы на SQL с JOIN. MongoDB — документная: коллекции документов, похожих на JSON. Связанные данные обычно вложены прямо в документ, структура гибкая — поля у документов могут отличаться, а следит за ней код приложения.

PostgreSQL — где важны точность и связи: деньги, заказы, остатки. MongoDB — где у объектов разная структура: каталог товаров, профили, контент, события. Часто на проекте живут обе.
:::

::: details Кейс 2. «Что такое документ и коллекция?»
**Ситуация.** Интервьюер: «Объясните, что такое документ и коллекция в MongoDB».

**Как рассуждать.** С чем это сравнить из реляционных баз?

**Пример ответа.** Коллекция — набор документов, примерно как таблица. Документ — одна запись, примерно как строка, только в формате, похожем на JSON: внутри могут быть вложенные объекты и массивы. У каждого документа есть уникальный `_id`, обычно ObjectId.

Главное отличие от строки: документы одной коллекции не обязаны быть одинаковыми — у одного поле есть, у другого нет.
:::

::: details Кейс 3. «В документах появилось новое поле. Что проверите?»
**Ситуация.** Интервьюер: «В коллекцию товаров добавили поле "гарантия". Что будете проверять?»

**Как рассуждать.** Какие документы были в коллекции до изменения?

**Пример ответа.** Первое — **старые документы без поля**: экраны, фильтры, отчёты и выгрузки на них не падают и показывают то, что задумано. Второе — новые: поле сохраняется правильного типа, во всех способах создания — интерфейс, API, импорт. Третье — поиск и сортировка по полю, если они есть, с учётом документов без него.

Спрошу аналитика и разработчика: будут ли заполнять поле у старых товаров и что показывать, пока оно пустое.
:::

::: details Кейс 4. Хитрый вопрос: «NoSQL — значит без схемы?»
**Ситуация.** Интервьюер: «В MongoDB же нет схемы — значит, и проверять структуру данных не нужно?»

**Как рассуждать.** Кто следит за структурой, если не база?

**Пример ответа.** Нет. Схема есть всегда — приложение ждёт определённые поля определённых типов. Разница в том, кто её охраняет. В PostgreSQL база не даст записать строку в числовой столбец. В MongoDB по умолчанию даст — и ошибку поймает только код приложения или тестировщик.

Поэтому в MongoDB структуру проверять нужно даже внимательнее: отсутствующие поля, `null`, разные типы в одном поле, старые документы после изменений.
:::
